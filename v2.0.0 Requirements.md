# Part I — Requirements

## 1. Product goals & guiding principles

### 1.1 What the app is for

Tzafon is a **personal** productivity app whose job is not to maximise time-in-app but to help one person **plan things, actually do them, hold habits, and move in a chosen direction** — and to *feel* that progress as identity, not score. The name (*north*) is deliberate: the app's differentiator is holding a direction at the top and wiring it to today's action. The research base sets the ceiling explicitly: more tasks ticked is not the goal; the user's life improving is, *even when that means needing the app less* ("graceful success").

The three durable motivational needs (Self-Determination Theory) are the lens for every feature:

- **Autonomy** — *I chose this; it's mine.*
- **Competence** — *I'm making progress; I'm getting better.*
- **Relatedness** — *I'm connected to others through this.* (Deliberately under-used in v2.0.0 — see §10.)

### 1.2 The product goals (synthesised from the source goals + research)

| ID | Goal | Primary levers |
|---|---|---|
| **G1** | Plan tasks **and** actually do them | If-then cues (§4.5), low-friction capture, Today/Planning, visible progress |
| **G2** | Keep habits | Cue-based habits, forgiving in-period rate + long arc, fresh starts |
| **G3** | Move in a chosen life direction | Themes + Goals, the **auto-bridge** from direction to today's action |
| **G4** | Be more productive — *up to a point* | Specific goals, beat procrastination, **cap** active commitments; guard against overwork |
| **G5** | Reflect & re-plan | The weekly/monthly **Review** loop and the **Journey** mirror |
| **G6** | Never punish; always forgive | Can't-fail themes, non-punitive states, "one miss is normal" |

### 1.3 The nine design principles (binding on every requirement)

These are the research compressed; they are the v0.2 data-model principles and the App Views C.0 principles, unified. Every requirement below must satisfy them.

`PRIN-1` **Mirror, not carrot.** All feedback is informational/identity ("you wrote on 18 days"). **No points, badges, or leaderboards.**
`PRIN-2` **Can't fail / forgiving.** No punishing states; one miss is normal; after a lapse offer a clean slate, never a wall of red.
`PRIN-3` **Approach-framed.** *More of what I want*, never *stop doing X*.
`PRIN-4` **Autonomy.** The user sets their own themes, targets, cues; the app never imposes a number.
`PRIN-5` **Concrete wiring, done for you.** The abstract (a Theme) is always one tap from a concrete action, and the app *shows* the link ("serves: …"). This is the one thing a paper journal can't do — and the thing the research says is mandatory.
`PRIN-6` **Few active things.** Soft caps + gentle nudges against overwhelm. The one hard cap is ≤3 active themes.
`PRIN-7` **Cue over clock.** Schedule by trigger ("after morning coffee") where possible, not only by time.
`PRIN-8` **Endowed progress.** Progress bars start non-empty where honest.
`PRIN-9` **Graceful success.** Success = real-world completion, never app-opens. Metrics never reward engagement for its own sake.

> **Corollary — the trellis, not a cage.** Every alignment link (task→theme, habit→goal, …) is *optional*. The user can capture a bare task in one tap and never organise it. Structure is something the app makes *easy* to add — mostly during Review — never something it forces up front. This resolves the standing "friction vs. fluffy themes" tension.

## 2. Scope of v2.0.0

v2.0.0 (Tzafon) is the **major release that re-platforms the TaskManager v1.1.0 web app as a native Android app and grows it into the full research-backed system**: the direction layer (Themes/Goals/Habits), the behavioural engine (Cues, Review, Focus), the complete task state machine, the seven-view navigation, and the recurrence fixes — all under the existing Fox Works design language, now rendered natively.

**Platform decision — see `DEC-1`.** v2.0.0 ships as a **native Android app** on a **new, dedicated Firebase project**. The React web app is frozen at v1.1.0 as the predecessor; Tzafon is a fresh Android codebase against a fresh backend.

**Inherited from v1.1.0 (the re-platform reuses the *spec*, not the data or the code):**
- **The behavioural & data spec** — the recurrence rules, per-occurrence operations, due-date modes, grouping/sort, and all object behaviour defined here. The v1.1.0 web source is the **reference implementation**; its logic (esp. `recurrence.js`/`series.js`) is **re-implemented in Kotlin**, not ported line-for-line.
- **The data-model shape** — the Firestore collection layout (`users/{uid}/…`) and the per-`uid` security-rules pattern are reused as a **design**, re-created from scratch in the new project. No v1.1.0 documents are copied in.
- **The design language** — the Fox Works "Den" palette/type and the "DON'T PANIC" voice, **translated into a Jetpack Compose theme** (`FR-DESIGN`).

**Started fresh (a clean slate):** a **new Firebase project + empty Firestore** (`DEC-1a`) — Tzafon's first run has no tasks, and there is **no data migration** from the web app. Also replaced: the React 18 / Vite / inline-style front end and Netlify hosting → the native Android stack below.

### 2.1 Technology (native Android)

`TECH-1` **Language/UI:** Kotlin + Jetpack Compose (Material 3, heavily re-themed to the Den palette).
`TECH-2` **Backend:** Firebase Android SDK — Auth (Google Sign-In) + Cloud Firestore with **offline persistence** (the built-in replacement for the PWA's offline goal).
`TECH-3` **Notifications/scheduling:** `AlarmManager` for exact-time cues, `WorkManager` for periodic top-up/checks; `POST_NOTIFICATIONS` runtime permission (Android 13+).
`TECH-4` **Known-good toolchain (verified headless on this Mac):** Gradle 9.6.1, AGP 9.2.1, Kotlin 2.2.10, Compose BOM 2026.02.01, JDK 21 (Android Studio JBR); `compileSdk 37 / targetSdk 36 / minSdk 26`. Build/verify runs entirely from the CLI (`gradlew assembleDebug` → `adb install` → `adb shell am start` → `adb exec-out screencap`) with no IDE — this is Claude Code's build-and-see loop for every milestone. *Gotcha:* build under a **space-free path** (the repo path contains a space); use a working copy without spaces.

## 4. Data model requirements

The object spine is **Theme → (Goal | Habit) → Task**, with **Cue** embedded on Tasks/Habits and **Review/Focus** as the behavioural loops wrapped around it. Goal and Habit stay **separate** objects (a Goal completes and pulls via the goal-gradient; a Habit never completes and pulls via identity/rhythm).

Data lives per-user in Firestore under `users/{uid}/…`, re-creating the v1.1.0 `tasks` and `series` collection layout in the new database and adding the new collections below.

### 4.1 Theme (`DM-THEME`)

`DM-THEME-1` A Theme has: `name` (approach-framed; the app nudges "more of…" phrasing — `PRIN-3`), **mandatory `why`** (a theme without it "fluffifies"), and a `window` (user-chosen start + review point, **default one quarter**; no hard length floor — `DEC-5`).
`DM-THEME-2` **Three states:** `active`, `upcoming` (future window start; does **not** count toward the cap), `archived` (window ended / retired / evolved / renewed; feeds Journey).
`DM-THEME-3` **Hard cap: ≤3 *active* themes** (the only hard cap in the app), enforced **at activation**, not at creation. Creating a 4th when 3 are active offers to save it as `upcoming` (`FR-DIR` auto-activation rules).
`DM-THEME-4` **Can't fail:** there is no missed/failed state and no percentage. At window end the app runs a **Review & Renew** prompt (renew / evolve / retire).
`DM-THEME-5` A Theme may link to many Goals, many Habits, and (`DEC` from v0.2 **D1**) **many Tasks directly** — the auto-bridge for one-offs. No link is required.

### 4.2 Goal (`DM-GOAL`)

`DM-GOAL-1` A Goal has `title`, optional `description`, a `type` ∈ {**Stepped**, **Accumulative**, **Generic**}, type parameters (steps list, or target quantity + unit + current), `state` ∈ {`ongoing`, `completed`, `frozen`}, optional `deadline`, optional one-line `commitment` (a lightweight commitment-device/bundle field).
`DM-GOAL-2` **Endowed progress** (`PRIN-8`): a Stepped goal auto-creates a first step *"Defined this goal ✓"* already checked; an Accumulative bar reflects honest starting progress. Never an empty bar.
`DM-GOAL-3` Progress advances **two ways** — by marking a linked Task done (Accumulative prompts "how much?"), **or** by direct edit on the goal. Either path counts **once** (`DM-ATTR`).
`DM-GOAL-4` **Completion handles the rebound:** on completion, celebrate as identity/competence and ask the open *"Where would you like to go from here?"* (make a habit / set a follow-on goal / just enjoy it). Completed goals move to Archive → Journey.
`DM-GOAL-5` **Anti-overwhelm:** a *dismissible* soft warning past **5 active goals**; a **stale-goal nudge** to freeze after ~2 weeks of no activity. Never a hard block. (Thresholds are tunable — §11.)
`DM-GOAL-6` A Goal may serve any number of Themes; may have many Tasks; and (v0.2 **D2**) **may be served by many Habits** ("run 3×/wk" serves "run a marathon").

### 4.3 Habit (`DM-HABIT`)

`DM-HABIT-1` A Habit has `name`, `goalType` ∈ {`frequency`, `quantitative`}, a `target` (X per period) + `unit` (quantitative), a **`cue`** (`DM-CUE`; a habit without a cue is just a tracker), and per-date `history` (did/didn't or measured amount).
`DM-HABIT-2` **Forgiving by construction:** success is hitting the *rate*, which has built-in slack — "3× a week" means missing four days is still a win (the "5 of 7" mechanic for free).
`DM-HABIT-3` **No adherence score, no streaks** (`DEC-2`, `DEC-4`). Show the **in-period rate** with endowed head-start, a **calendar-style history** (weekly grid default; monthly available; quantitative shows logged amount per date), and the **long identity arc**. Honest timeline copy: weeks-to-months, not "21 days."
`DM-HABIT-4` **One miss is normal — and the copy says so** ("Missed yesterday? Normal. Just don't miss twice."). A gap surfaces a **fresh start** ("New week, clean slate"), never a backlog of red.
`DM-HABIT-5` **Logged two ways:** via a linked Task marked Done (frequency → one tick; quantitative → prompt for amount, with the §8.2 date rules), **or** edited directly on any date.
`DM-HABIT-6` A Habit may serve any number of Themes and (v0.2 **D2**) **may serve a Goal**; it is linked from many Tasks, but **each Task links to at most one Habit**.
`DM-HABIT-7` **Delete is destructive** (wipes all history) → confirmation prompt required.
`DM-HABIT-8` Linking/unlinking a habit to/from a **recurring** task prompts: apply to **all occurrences (incl. past)** or **new occurrences only**.

### 4.4 Task (`DM-TASK`) — full state machine

Tasks carry everything from v1.1.0 (title, description, To Do/Due dates, full recurrence, the singular/recurring due modes) **plus**:

`DM-TASK-1` **State machine.** A task's `state` ∈ {**Open**, **Done**, **Closed**, **Frozen**, **Backlog**}. Tzafon uses this `state` field from day one — where v1.1.0 (web) had only a boolean `done` (Open/Done). Because Tzafon starts on an empty database (`DEC-1a`), there is **no `done→state` migration**; the enum is the native shape from the first write.
  - **Open** — active/pending.
  - **Done** — completed.
  - **Closed** — not completed, no longer relevant (≈ skip). No habit/goal contribution.
  - **Frozen** — suspended indefinitely, reserved for resumption ("thaw"). For a recurring task, freezing **terminates generation** after a confirmation prompt; the frozen instance is retained.
  - **Backlog** — deliberately parked someday/maybe (`FR-BACKLOG`). Unscheduled by definition.
`DM-TASK-2` **Thaw** (Frozen → …): user chooses target state. → Open preserves the original To Do Date and, if recurring, restores recurrence (next occurrence generated Open). → Done applies all Done actions incl. linked-habit update, and restores recurrence. → Closed just marks Closed.
`DM-TASK-3` **Skip is non-punitive** (v0.2 **D3**): Closing or Freezing a task **stops its contribution** (no habit completion, no goal progress) but **does not sever** its Theme/Goal/Habit links — the relationship and history survive; active views simply filter it out.
`DM-TASK-4` **Cue** (`DM-CUE`) — optional, prompted at creation: *"When will you do this?"*, anchored to a routine where possible (`PRIN-7`).
`DM-TASK-5` **Direct Theme link** (v0.2 **D1**) and links to many Goals (one typical) and exactly one Habit. A task may be a fully unaligned **orphan** — common and fine (`PRIN`-corollary).
`DM-TASK-6` **Friction floor:** default capture is a **one-line quick-add** (title + Enter → saved), with a clear button to expand into the full form. **Neither capture path pre-fills a date** (`FR-CAPTURE`; v0.4 decision, confirmed in *Comments*).
`DM-TASK-7` Optional one-line `commitment` field (commitment device / temptation bundle), as on Goals.
`DM-TASK-8` Dates are **never** changed automatically by the system; only recurrence *generation* sets a new instance's date at creation (rule-driven, not a modification).

### 4.5 Cue (`DM-CUE`) — embedded implementation intention

`DM-CUE-1` A Cue is the structured *"When **X**, I will do **Y**"* (Gollwitzer & Sheeran, d ≈ 0.65 — the highest evidence-to-effort mechanism in the whole research base). It lives **on** a Task or Habit, never as a standalone row.
`DM-CUE-2` Shape: `trigger` ∈ {*after-routine* ("after morning coffee"), *at-time*, *at-place*} + the action (the Task/Habit itself).
`DM-CUE-3` Cues power reminders that fire on the **cue**, not merely a date (`FR-NOTIF`). Always optional, always one line — never a wizard.

### 4.6 Review (`DM-REVIEW`) — the plan-and-review loop

`DM-REVIEW-1` **Weekly review** (light) fires on the user's chosen first day of the week (global setting, **default Sunday**). **Monthly review** (deeper) does *not* fire on the calendar 1st; it **rides the first weekly review on/after the 1st**. **There is never more than one review in a week** — a longer-horizon review *upgrades* the weekly slot.
`DM-REVIEW-2` **Two halves:** (1) **Reflect** — a no-score mirror of the period (tasks done with theme-aligned ones surfaced as identity; each habit's in-period rate + arc; goal progress moved; one optional free-text line). (2) **Plan (a fresh start)** — set the coming period's **Focus**, adjust cues, act on stale-goal nudges. After a lapse this is a clean slate, never a reckoning.
`DM-REVIEW-3` The monthly review adds, on top of the weekly content: a pass over each **Theme** (renew/evolve/retire), the full **active-goal** list (prune/freeze), and the longer **habit arcs**.
`DM-REVIEW-4` **Never blocking.** The Review is an invitation, dismissible in one tap and resumable; it stays openable later that day and through the next day if untouched. A skipped Review is **not** a failure (`PRIN-2`). Partial progress is preserved.
`DM-REVIEW-5` Each period persists a small **Review artifact** (what got done, what matters next). These artifacts are what let Journey reflect a genuine long identity arc.

### 4.7 Focus (`DM-FOCUS`) — the capped "now"

`DM-FOCUS-1` Focus is **not a new store** — it is a **marker** on existing Tasks (optionally a Goal/Habit to push) for a horizon. Two horizons: **Today's Focus** (the Today view) and **This week's priorities** (a strip set at the weekly Review).
`DM-FOCUS-2` The **number of items marked focused** is **soft-capped** (~3/day, ~3/week — tunable, §11). Crossing it shows a gentle, dismissible nudge where you set it. Never a hard block (`PRIN-4`, `PRIN-6`). Nothing limits total task count.

### 4.8 Relationships & cardinality (`DM-REL`)

| From | To | Cardinality | Required? | Note |
|---|---|---|---|---|
| Theme | Goal / Habit / Task | 1 → many | optional | Task link is the auto-bridge (**D1**) |
| Goal | Habit | 1 → many | optional | the habit is the goal's engine (**D2**) |
| Goal | Task | 1 → many | optional | |
| Habit | Task | 1 habit → many tasks; **1 task → 1 habit** | optional | |
| Goal / Habit / Task | Theme | serves **any number** of themes | optional | the ≤3 cap is on *active themes*, not on links |
| Cue | Task / Habit | embedded (1:1) | optional, prompted | not a standalone row |
| Focus | Task (+ opt Goal/Habit) | capped set (~3) | user-set | |

`DM-REL-1` **Primary-alignment rule.** Many-to-many is allowed, but the UI privileges **one primary parent** per item, shown as *"serves: <X>"*, with a **+N multiplicity indicator** that expands the full list. Don't require more than one link; don't forbid it.
`DM-REL-2` **Week start** is a global setting, default **Sunday**; it drives the weekly Review day, habit in-period boundaries, and all fresh-start framing.

### 4.9 Progress attribution — no double-counting (`DM-ATTR`)

`DM-ATTR-1` **One task-completion contributes to any given Goal at most once.** On Done, the app: (1) gathers every goal reachable from the task — directly-linked goals ∪ goals served by the task's linked habit; (2) dedupes to the unique goal set; (3) applies progress to each goal **once** (for an Accumulative goal reachable by two paths, prefer the explicit task→goal amount, else the habit-derived amount — **never both summed**); (4) **records provenance** so the contribution can be reversed *exactly* on un-do / Close / Freeze.
`DM-ATTR-2` The **habit completion is a separate ledger** from goal progress — the habit is always recorded once for itself; the dedup is only about *goal* progress.
`DM-ATTR-3` **Quantitative unit mapping — the app never invents a conversion.** A habit completion auto-advances a numeric (Accumulative) goal **only when units match**. When units differ, or the goal is Stepped/Generic, the habit→goal link is **directional** (shows wiring, feeds identity, does *not* move a numeric bar automatically); the user advances it directly. *(Per the author's note in Comments: this is user-defined and optional — the user links only what's meaningful.)*

### 4.10 What the data model deliberately does **not** add (`DM-NOT`)

Stated explicitly because the research says these are liabilities, not gaps: **no points/badges/leaderboards**; **no streaks of any kind**; **no external reward economy** over intrinsically-motivated work; **no competitive comparison** (only comparison to one's own past self); **no engagement-for-its-own-sake metrics** (opens, time-in-app, "days active").

## 5. Functional requirements — the view system

Three layers, bound by two data-flows (App Views C.1):
- **Action — *do it*:** Today (default), Planning, All Tasks, Backlog.
- **Direction — *why/aim*:** the Directions hub (Themes + Goals) → Habits.
- **Reflection — *look back*:** Journey.
- **Up-flow:** complete a task → ticks its Habit → advances its Goal → mirrors on its Theme → accrues in Journey (counted once, `DM-ATTR`).
- **Down-flow:** the Review turns direction into a capped **Focus**, which *is* Today.

`FR-NAV-1` **Primary bottom nav: `Today · Planning · Habits · Directions · Journey`.** All Tasks and Backlog are reachable via search/menu. *(Rationale: the first five are touched daily-to-weekly or at Review; All Tasks/Backlog are reference.)*
`FR-NAV-2` **Default landing view = Today** (changed from v1.1.0's All Tasks) (`PRIN`: overwhelm reduction).

### 5.1 Today (`FR-TODAY`) — = Today's Focus

`FR-TODAY-1` Shows active tasks where **To Do Date = today OR Due Date = today** (due-today items scheduled for another day surface here, flagged "due today", per the v1.1.0 due indicators). *(Supersedes structure §7.2's "To Do = today only".)*
`FR-TODAY-2` Tasks are **manually reorderable**.
`FR-TODAY-3` **Overdue is kept out** of the main list (`DEC-7`).
`FR-TODAY-4` A calm, **closeable banner** surfaces slippage — *"3 tasks slipped past — review in Planning"* — linking to Planning. Never a guilt wall.
`FR-TODAY-5` **Overload warning** — a supportive, dismissible nudge when the day is overstuffed ("That's a full plate today. Want to move a couple to tomorrow?") with the offered action. **Static first** (~7–10 scheduled active tasks), then **adaptive** to a personal rolling baseline of *completed*/day (floor + ceiling). Never punitive, never a score, never based on app-opens (`PRIN-9`). *(Distinct from the Focus cap — the two must never nag simultaneously.)*
`FR-TODAY-6` Simple search is available; **no filters** (the date is the filter).

### 5.2 Planning (`FR-PLAN`) — triage / what's on the table

`FR-PLAN-1` Shows three groups: **past not-done (overdue)** grouped at top for review; **today + future** up to a user-set range (**default 7 days**); and **undated active tasks ("Inbox")** as a "needs a date" group.
`FR-PLAN-2` **Range control:** presets (7 / 14 / 30 / "this month") + custom; no hard cap, presets stop ~90 days. The range **drives the generation horizon** (`NFR-PERF-2`) so recurring tasks stay visible when looking ahead.
`FR-PLAN-3` Missed tasks are presented as **"decide what to do with these"** (reschedule / do today / drop / send to Backlog) — never a guilt wall (`PRIN-2`).

### 5.3 All Tasks (`FR-ALL`) — complete searchable index

`FR-ALL-1` Shows every task and the **nearest occurrence of every series** (per `FR-REC-1`). Sorted by To Do Date oldest→newest; undated group at the bottom. *(Utilitarian — retrieval/audit, not motivation. No streak/celebration UI here.)*
`FR-ALL-2` **Search** by title/description.
`FR-ALL-3` **Visibility toggles** for **Done · Frozen · Closed · Backlog** — all hidden by default, each independently toggleable (generalises v1.1.0's single Done toggle).
`FR-ALL-4` **Horizon marker:** a quiet full-width divider at the **effective horizon date** (e.g. *"— scheduled through Aug 22 · recurring tasks repeat beyond this —"*), reflecting the *effective* horizon (which extends when looking further ahead). It explains why series "thin out" past that date.
`FR-ALL-5` **In-view navigation:** sticky group headers; a compact "jump to" (Overdue · Today · Undated + month picker); collapsible groups; **and** an edge **date-scrubber** (confirmed in *Comments* — included on top of the others, not instead).

### 5.4 Backlog (`FR-BACKLOG`) — someday/maybe pool (an explicit state)

`FR-BACKLOG-1` A Backlog task has no To Do Date; it is **excluded** from Today and Planning and from the Today overload count, and hidden by default in All Tasks (behind the Backlog toggle). Alignment links are **preserved but dormant** — no habit completion, no goal progress — until activated (same non-punitive rule as Frozen).
`FR-BACKLOG-2` **Into Backlog:** Open → Backlog (To Do Date cleared, links dormant); Done/Closed → Backlog ("resurrect for someday" — clears the mark/date, **reverses any prior contribution** per `DM-ATTR`); **Recurring → Backlog is not allowed** (offer Frozen instead — a live series can't be "someday").
`FR-BACKLOG-3` **Out of Backlog:** → Open (the "pull when inspired" flow; optionally set a date; links reactivate going forward); → Done ("did it without scheduling" — normal Done actions, counted once); → Closed ("decided against it"); → Frozen is a no-op (both are "parked").
`FR-BACKLOG-4` Only **non-recurring** tasks can enter Backlog. To get "someday, then repeat," pull to Open and *then* add recurrence.

### 5.5 Directions hub (`FR-DIR`) — Themes + Goals, hierarchical

`FR-DIR-1` Themes and Goals are **one hierarchical view** (the trellis made visible), top→bottom: **Active themes** (each a section) → **Goals without a theme** (always-visible orphan section) → **Upcoming themes** → **Archive** (collapsed; feeds Journey).
`FR-DIR-2` Each active theme header shows: `name`, the **why** (mandatory), **window position as orientation not pressure** ("Quarter · week 7" — no %, no countdown), and the **identity mirror** ("this quarter: 23 aligned tasks done · 2 habits held · 1 goal advancing"). Plus a **"this week" nudge** — *"What would this look like this week?"* → one tap to add an aligned goal/habit/task (`PRIN-5`, the auto-bridge).
`FR-DIR-3` Nested under each theme: its **Goal cards**, compact **habit chips**, and a **task count**; everything tappable, chips link to Habits / task list.
`FR-DIR-4` **Goal cards** show title, type, an **endowed progress bar**, *"serves: <Theme> (+N)"*, the **linked Habits** that drive it, and recent linked tasks; near completion they emphasise **what's left** (goal-gradient). Create flow nudges SMART, picks type, optional deadline/commitment/theme. **No adherence %, no score.**
`FR-DIR-5` **Shared goals:** a goal serving multiple themes appears **once**, under its **primary theme**, with *"also serves: +N"*. Each theme section also shows a collapsed **"+ shared goals (n)"** (confirmed in *Comments*) listing read-only references to goals primary-owned elsewhere. A theme with no goals still shows; a goal with no theme lives in the orphan section.
`FR-DIR-6` **Theme states & cap (`DM-THEME-2/3`):** creating a 4th theme when 3 are active offers to save as **Upcoming** with a start date. **Auto-activation by date:** when an Upcoming start arrives and <3 active → auto-activate; if 3 active but one's window has ended → **auto-swap** (archive the ended one with its Review & Renew, activate the upcoming); if 3 active and none ended → **prompt at that moment** (retire/park one). The user may always manually promote/retire/park.

### 5.6 Habits view (`FR-HAB`) — rhythm/identity, kept flat

`FR-HAB-1` Shows **active habits**, each a card with: name; **target** (rate or quantity); the **cue front and centre** ("after morning coffee" — *a habit card without its cue is just a tracker*); **in-period progress** with endowed head-start ("3 of 4 this week"); a **calendar-style history**; the **long arc** ("6 weeks running"); and *"serves: <Theme/Goal>"* links.
`FR-HAB-2` Create / edit / **delete** habits here (delete → destructive confirmation, `DM-HABIT-7`).
`FR-HAB-3` Forgiving by construction; **no streaks, no adherence score**; "one miss is normal" copy; fresh-start after a lapse (`DM-HABIT-2/3/4`).
`FR-HAB-4` Logged two ways (`DM-HABIT-5`); goal contribution counted once (`DM-ATTR`).

### 5.7 Journey (`FR-JOURNEY`) — the reflection / identity mirror

`FR-JOURNEY-1` Renamed from "Achievements" and reframed as an **identity mirror, not a trophy case** (a literal achievements view would contradict `DM-NOT`).
`FR-JOURNEY-2` Contents (all mirror, no carrot): **completed Goals** (the legitimate core — a finished finite pursuit is a genuine achievement, listed with the theme it served + when); **habit identity arcs** (long arcs, never streak counters); **theme journey** (directions over time — "Year of Health → renewed → Year of Strength"); **Review timeline** (the per-period artifacts strung into a narrative); **honest aggregate reflections** ("this quarter, 47 of your completed tasks served a theme").
`FR-JOURNEY-3` **Deliberately NOT here:** badges/trophies/points; streak counters/milestones; leaderboards/other-people comparison; app-engagement metrics. Celebrate a goal at the moment of completion (the "where to from here?" prompt) then file it here. **Forgiving by omission** — there is no "you failed/lapsed" surface anywhere.
`FR-JOURNEY-4` Build it **thin and late** — it is meaningful only once history exists. An empty mirror on day one is worse than no view.

### 5.8 Review & Focus loops (`FR-LOOP`)

`FR-LOOP-1` Review and Focus are **loops, not standalone nav items** (`DM-REVIEW`, `DM-FOCUS`). Review *visits* the direction views and sets Focus; Focus = Today + the weekly-priority strip.
`FR-LOOP-2` The weekly Review surfaces at the chosen week-start day; the monthly rides the first weekly slot on/after the 1st (`DM-REVIEW-1`). Non-blocking, resumable (`DM-REVIEW-4`).

## 6. Recurrence (`FR-REC`) — fixes & carry-forward

`FR-REC-1` **Nearest-occurrence guarantee (App Views Part A — a bug fix).** "All Tasks" must mean *all tasks*: every active series must always be represented by **at least its nearest upcoming occurrence**, even when that occurrence is beyond the rolling horizon. Implementation: keep the rolling 60-day bulk window, but when the normal in-window set is empty and the series has a future occurrence, additionally materialise the **single earliest** occurrence on/after today. Idempotent (deterministic doc IDs); runs in `topUp` so it self-heals; preserves the "occurrences are real documents" model.
`FR-REC-2` **Conditional year in date labels (App Views Part B).** Absolute date labels show the year **only when it differs from the current year** ("Sun, Sep 14" vs. "Tue, Jan 5, 2027"). Relative buckets (Overdue/Today/Tomorrow) unaffected. More relevant once `FR-REC-1` ships (far-future occurrences appear).
`FR-REC-3` **Effective horizon (App Views A.5):** generalise the constant 60-day horizon to `effectiveHorizon = max(60 days, furthest date currently being viewed)`, driven by the Planning range (`FR-PLAN-2`).
`FR-REC-4` **Carried forward unchanged from v1.1.0:** the three patterns (interval / weekday / day-of-month); per-occurrence operations (reschedule one, edit forward in-place, delete one, delete all, end date); singular vs. recurring Due-Date modes; the rule that the next occurrence is computed independently of prior ones (an unfinished prior occurrence never blocks the next).
`FR-REC-5` **Freeze terminates a series** after a confirmation prompt (the frozen instance is retained); thaw restores it (`DM-TASK-2/3`).

## 7. Cross-cutting functional requirements

### 7.1 Capture & friction floor (`FR-CAPTURE`)

`FR-CAPTURE-1` One-line quick-add (title + Enter → saved) is the default path; a clear control expands to the full editor (dates, cue, alignment, recurrence, commitment).
`FR-CAPTURE-2` **Neither path pre-fills a date** — new tasks default to **undated** (Inbox). *(v1.1.0's web editor defaulted the To Do Date to today; the native editor must default it to none.)* All alignment is optional and addable later, typically in Review.

### 7.2 Cue-based notifications (`FR-NOTIF`)

`FR-NOTIF-1` The app delivers **reminders driven by the Cue** (`DM-CUE`), not merely by date — fulfilling the original "notifications" must-have via the research's highest-leverage mechanism. At minimum: at-time and after-routine triggers produce a local notification.
`FR-NOTIF-2` Delivery is via **native Android notifications** — `AlarmManager` for exact-time cues, `WorkManager` for periodic checks (`TECH-3`). Opt-in via the `POST_NOTIFICATIONS` runtime permission (Android 13+); never used for engagement-baiting (`PRIN-9`). *(Going native is a large part of the point of `DEC-1`: OS-level notifications are far more reliable than the web-push a PWA offered.)*
`FR-NOTIF-3` **[OUT OF SCOPE, noted — now feasible on native]** richer cue sources from *Features Backlog.md* — calendar events ("after lunch" when lunch is on the calendar, via `CalendarContract`) and phone signals ("after the alarm turns off") — are future enhancements that ride on the same Cue model. Native Android makes these genuinely reachable (unlike the web PWA), but they remain **out of v2.0.0 core scope** to protect the release.

### 7.3 Settings (`FR-SET`)

`FR-SET-1` **Week start** (default Sunday) — drives Review day, habit periods, fresh-start framing (`DM-REL-2`).
`FR-SET-2` Notification permission/preferences (`FR-NOTIF`).
`FR-SET-3` Sign out (carried from v1.1.0).

### 7.4 Design language (`FR-DESIGN`)

`FR-DESIGN-1` Keep the **Fox Works "Den"** theme, **translated into a Jetpack Compose theme**: the same palette/type tokens (from the web `theme.js` — the Den colours, Newsreader / Hanken Grotesk / Spline Sans Mono, bundled as Compose fonts), the fox mascot, and the supportive **"DON'T PANIC"** voice — which is *already* the forgiving, non-punitive tone the research demands. All new copy (overload, lapse, Review, completion) uses this voice.
`FR-DESIGN-2` New views adopt the same card/grouping/progress-bar idioms (re-expressed in Compose) so Tzafon reads as the continuation of TaskManager, not a different app. Material 3 components are re-themed to the Den look, never left default.

## 8. Non-functional requirements

`NFR-SEC-1` **Data protection (must-have, carried from POC):** all client↔server traffic over TLS (the Firestore Android SDK enforces this); task/theme/goal/habit/review data accessible only to the owning authenticated user, enforced **server-side** by Firestore security rules — extended to cover the new collections (`themes`, `goals`, `habits`, `reviews`, and any `focus`/settings docs), mirroring the existing per-`uid` rule. No data exposed to unauthenticated requests. *(The per-`uid` rules pattern is re-created in the new Firebase project, unchanged in kind from v1.1.0.)*
`NFR-SEC-2` Auth stays Google SSO via Firebase Auth (Android SDK); session persists across app restarts until explicit sign-out.
`NFR-PERF-1` Occurrence generation stays **idempotent and bounded** — the rolling horizon caps pre-created future occurrences; `FR-REC-1`'s floor adds at most one extra doc per far-future series.
`NFR-PERF-2` Generation tops up lazily to the **effective horizon** (`FR-REC-3`); looking 90 days ahead in Planning generates to 90 days for that session only.
`NFR-DATA-1` **Schema evolution (no legacy migration):** Tzafon starts on an empty database (`DEC-1a`), so there is **no migration from the v1.1.0 web data** — the `state` enum and every new field are written natively from day one. The only forward-compatibility concern is *within Tzafon's own build history*: later milestones add fields/collections (habits, goals, themes, cues, focus, reviews), so reads must tolerate documents written by an earlier milestone that predate a newer field. Keep additions **additive** and default-tolerant.
`NFR-DATA-2` **Provenance** for goal contributions (`DM-ATTR-1`) must be persisted so reversals are exact.
`NFR-OFFLINE-1` The app is usable offline for reading and capture via **Firestore offline persistence** (enabled by default in the Android SDK), syncing on reconnect. As a native app it is inherently "installable" — no PWA manifest/service-worker layer.
`NFR-A11Y-1` Meet baseline Android accessibility: sufficient contrast in the Den palette, adequate touch-target sizes, and **TalkBack** content descriptions on icon-only controls (FAB, toggles, bottom nav).
`NFR-TEST-1` Each milestone ships with automated coverage for its logic — **JUnit** unit tests (recurrence math, state machine, attribution dedup, review scheduling, habit-rate math) and **Compose UI tests** for key view behaviour. The web app's existing recurrence tests are the reference oracle for the Kotlin re-implementation. Each milestone is also verified through the headless build/install/screenshot loop (`TECH-4`).

## 9. Acceptance criteria for "v2.0.0 is done"

v2.0.0 is complete when all of the following are true and verified:

1. The data model (`DM-*`) exists in the new Firebase project's Firestore with security rules in place; provenance recorded. (No legacy migration — fresh database per `DEC-1a`.)
2. All seven views (`FR-TODAY/PLAN/ALL/BACKLOG/DIR/HAB/JOURNEY`) are reachable via the bottom nav (Today default), each meeting its requirements above.
3. The five task states + thaw + Backlog transitions behave per `DM-TASK` and `FR-BACKLOG`.
4. Cues exist on tasks & habits and drive at least at-time/after-routine notifications (`FR-NOTIF`).
5. The Review (weekly + monthly, non-blocking) and capped Focus loops work per `DM-REVIEW`/`DM-FOCUS`.
6. Themes (≤3 active, 3 states, auto-bridge "serves:") and Goals (endowed progress, completion prompt) function per `FR-DIR`; Habits show forgiving rate + cue + arc with **no streaks/scores**.
7. `FR-REC-1` (nearest-occurrence) and `FR-REC-2` (conditional year) are fixed and tested.
8. **Nowhere** in the app are points, badges, leaderboards, streak counters, adherence %, or app-engagement metrics present (`DM-NOT`, `DEC-2/3/4`).
9. The app installs and runs as a native Android app on a supported device/emulator, works offline (`NFR-OFFLINE-1`), and data protection (`NFR-SEC`) holds for every collection.

# Part II — Roadmap: TaskManager v1.1.0 (web) → Tzafon v2.0.0 (native Android)

## R.1 Sequencing logic

Four forces set the order:

1. **Re-platform first.** Because v2.0.0 is a native rewrite on a **new, empty backend** (`DEC-1`/`DEC-1a`), the roadmap opens with a **foundation milestone (M0)** that stands up the Android app on a fresh Firebase project and reaches **feature parity with v1.1.0** — including the recurrence fixes, which are simply built into the Kotlin port from the start rather than patched into the retired JS engine. Nothing new can be built until the app *is* an app. *(Starting on an empty database removes the legacy-migration work the previous draft had scheduled.)*
2. **Research priority** — after parity, build the highest evidence-to-effort levers: Cues, endowed/visible progress, forgiving habit rate, the Review+Focus loop, themes-with-auto-bridge ("if you build only five things").
3. **Dependency order** — the **task state machine** and the **object model** are foundations the direction views and loops sit on.
4. **Claude Code cadence** — Claude Code is strongest on **well-scoped, vertically-sliced increments with clear acceptance criteria and tests**, and — crucially for a native app — it can run the **fully headless build/verify loop** (`gradlew assembleDebug` → `adb install` → `am start` → `screencap` → read PNG → `logcat`, per `TECH-4`) to *see* each change on an emulator without an IDE. So: front-load the riskiest piece in isolation (the Kotlin recurrence engine in M0), keep each milestone to one coherent slice with its own JUnit/Compose tests, and produce an **installable debug build** at every step.

**Milestone labels.** Because this is a re-platform under a new name, the intermediate builds are **development milestones M0–M9 of Tzafon 2.0.0**, not public minor versions of the web app — calling a native Tzafon build "TaskManager v1.3.0" would be misleading. The first public release is **Tzafon 2.0.0 at M9**. Each milestone is an internally installable, testable build; each delivers standalone value even if the later direction layer slipped.

## R.2 The milestones

### M0 — Native foundation + v1.1.0 parity *(the re-platform beachhead)*
- **Scope:** create a **new Firebase project + empty Firestore** with the per-`uid` security rules (`DEC-1a`); stand up the Kotlin/Compose project (`TECH-1/4`) in a space-free working path; wire **Firebase Auth (Google SSO)** and **Firestore** against the new project (`TECH-2`); **re-implement the recurrence engine in Kotlin** (`recurrence.js`/`series.js` logic) **with `FR-REC-1` nearest-occurrence, `FR-REC-2` conditional year, and `FR-REC-3` effective-horizon built in from the start**; reproduce Task CRUD, the **All Tasks view**, and the **Den design** in Compose (`FR-DESIGN`); `FR-CAPTURE-2` undated default.
- **Why first:** everything else needs a running native app on its own backend. Doing the recurrence port here means the v1.1.0 "far-future series vanishes" bug never re-enters the native codebase, and the engine — the trickiest logic — is validated against the web app's existing tests as the oracle before anything depends on it.
- **Verify:** JUnit parity tests for the Kotlin engine (mirror the web `recurrence.test.js`, plus the floor + year cases); sign in on the emulator, **create a task and a recurring series, confirm they persist and render** (the database starts empty — there are no legacy tasks); headless screenshot of All Tasks.

### M1 — Task state machine *(foundational state model)*
- **Scope:** `DM-TASK-1/2/3` — implement `state` ∈ {Open, Done, Closed, Frozen} as the native task shape from the start; thaw behaviour; freeze terminates a series (`FR-REC-5`); non-punitive skip (links preserved); All Tasks visibility toggles generalised to Done/Closed/Frozen (`FR-ALL-3`). *(No legacy migration — the DB is fresh, `DEC-1a`.)*
- **Why here:** every later layer (Backlog, contribution rules, Today/Planning filtering) needs states. Kept as its own milestone so the transition logic is built and tested cleanly.
- **Verify:** state-transition tests (incl. thaw paths and recurring-freeze); toggle behaviour via headless screenshots.

### M2 — Action layer: Today, Planning & nav
- **Scope:** bottom-nav scaffold (`FR-NAV`); **Today** as default (`FR-TODAY`) incl. overload warning + slippage banner + manual reorder; **Planning** (`FR-PLAN`) incl. overdue group, Inbox, range control driving the horizon. Generalise All Tasks with horizon marker + jump-nav + edge scrubber (`FR-ALL-4/5`).
- **Why here:** delivers the daily plan→do loop (G1, overwhelm reduction) early; depends only on M1. Biggest day-to-day payoff before any direction objects exist.
- **Verify:** Today/Planning membership rules; overload static threshold; reorder persistence; nav navigation via `adb shell input tap` + screenshot.

### M3 — Backlog state
- **Scope:** `FR-BACKLOG` — Backlog state + full transition table; All Tasks Backlog toggle; recurring-task guard (offer Frozen).
- **Why here:** small, slots onto the state machine + All Tasks toggles; gets someday/maybe out of the active lists. Could fold into M2 if convenient.
- **Verify:** transition-matrix tests, incl. contribution-reversal stubs (full reversal lands with goals in M5).

### M4 — Habits + Cues *(first direction object; top research lever)*
- **Scope:** `DM-HABIT`, `DM-CUE` — Habit object + `users/{uid}/habits`; Cue on tasks & habits (`FR-CAPTURE` prompt); **Habits view** (`FR-HAB`) with cue front-and-centre, forgiving in-period rate + arc, calendar history, log-two-ways, task↔habit linking (incl. retroactive choice `DM-HABIT-8`). **No streaks/scores.** Security rules for the new collection.
- **Why here:** Cue (d≈0.65) + forgiving habits are the highest-value levers, and Habits are the most "ready" direction object. Establishes the direction-layer foundation Goals/Themes build on. *(Cue capture lands here; the notifications that fire from cues come in M9.)*
- **Verify:** in-period rate math (frequency & quantitative), date-prompt rules (§8.2), delete confirmation, retroactive link application.

### M5 — Goals + progress attribution
- **Scope:** `DM-GOAL` — Goal object + `users/{uid}/goals`; types (Stepped/Accumulative/Generic); endowed progress; goal-gradient; habit→goal serving; **progress two ways**; **`DM-ATTR` dedup + provenance** (the no-double-count rule, incl. exact reversal — completing M3's stub); completion "where to from here?"; soft cap + stale-goal nudge.
- **Why here:** Goals depend on Habits (habit→goal) and on the state machine (contribution/reversal). Attribution is the trickiest behavioural logic — its own milestone, heavily tested.
- **Verify:** the C.9 case table (diamond, multi-goal, unit-mismatch, retroactive, reversal) as JUnit tests.

### M6 — Themes + Directions hub *(the thesis: the auto-bridge — the app's namesake)*
- **Scope:** `DM-THEME` — Theme object + `users/{uid}/themes`; 3 states + ≤3 active cap + auto-activation/swap (`FR-DIR-6`); mandatory why; direct task→theme link (D1); **Directions hub** (`FR-DIR`) with nesting, the "serves:" auto-bridge, identity mirror, "this week" nudge, shared-goals affordance, orphan-goal section.
- **Why here:** Themes sit on top of Goals/Habits, so they come after both. This is where Tzafon earns its name (*north* — the direction layer) over a paper journal.
- **Verify:** cap enforcement at activation; auto-swap on aligned windows; primary-vs-shared display; multiplicity indicator.

### M7 — Review + Focus loops
- **Scope:** `DM-REVIEW`/`DM-FOCUS` — weekly + monthly Review (rides-the-weekly-slot scheduling), the two halves (reflect mirror + plan fresh-start), non-blocking/resumable, persisted artifacts; capped Focus (Today's Focus + weekly-priority strip) with soft nudge; week-start setting (`FR-SET-1`).
- **Why here:** the Review reflects across themes/goals/habits, so all three must exist first. Closes the down-flow (direction → today's Focus).
- **Verify:** review-firing logic (no two reviews/week; monthly rides first weekly on/after the 1st), dismiss/resume, Focus soft cap.

### M8 — Journey
- **Scope:** **Journey** (`FR-JOURNEY`) — built thin and late on accumulated history: completed goals, habit identity arcs, theme journey, the Review timeline, honest aggregate reflections. No badges/streaks/leaderboards/engagement metrics.
- **Why here:** the mirror is only meaningful once there is history (completed goals, multi-week arcs, Review artifacts). An empty mirror on day one is worse than none.
- **Verify:** renders the accrued artifacts; confirm none of the forbidden surfaces (`FR-JOURNEY-3`) appear.

### M9 — Notifications, offline, polish → **Tzafon 2.0.0 (public release)**
- **Scope:** cue-driven **native notifications** (`FR-NOTIF`, `TECH-3`) incl. the `POST_NOTIFICATIONS` permission flow; **offline** verification (`NFR-OFFLINE-1`); **accessibility** pass (`NFR-A11Y-1`, TalkBack); copy/voice consistency pass (`FR-DESIGN`); final **security-rule audit** across all collections; full acceptance-criteria (§9) sign-off; **release build → tag Tzafon 2.0.0.**
- **Why last:** notifications are a release-grade concern that needs cues (M4) in place; the final pass confirms `DM-NOT` (no points/streaks/engagement metrics anywhere) holds end-to-end.
- **Verify:** the §9 checklist; notification fires from a cue on the emulator; airplane-mode capture then sync; rules deny cross-user reads on every collection.

| **M0** | New Firebase project + native foundation + v1.1.0 parity (incl. Kotlin recurrence engine with the Part A/B fixes) | — | A native app on a fresh backend; the vanishing-series bug never ships |

| **M2** | Action layer: Today, Planning, nav | M1 | The daily plan→do loop |
