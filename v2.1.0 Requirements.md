# Tzafon — v2.1.0 Requirements & Roadmap

**Product:** **Tzafon** (צפון — Hebrew for *north*). The compass that keeps you pointed at a chosen direction.
**Version:** 2.1.0 (target)
**Platform:** **Native Android** (Kotlin + Jetpack Compose) — unchanged from v2.0.0.
**Builds on:** **Tzafon v2.0.0** — the native Android release (tag `v2.0.0`). v2.1.0 is a **minor, additive
feature release** on the same codebase, backend, and design language. No re-platform, no data migration.
**Status:** Requirements — for review
**Date:** 2026-07-08

**Feature in one line:** *Make the manual habit log fully editable — choose **which date** a completion lands on
(default today), and **correct or add to** an already-logged value — without adding any streak, score, or guilt.*

**Source documents reconciled in this PRD**
1. **`v2.0.0 Requirements.md`** — the standing contract. Every requirement below extends, and must stay
   consistent with, its IDs (`DM-*`, `FR-*`, `PRIN-*`, `DEC-*`). Where this document is silent, v2.0.0 governs.
2. The implemented v2.0.0 codebase under `android/` — the real behaviour this release changes:
   `HabitsViewModel.logToday`, `RoomHabitRepository.logDirect`, `HabitsScreen` (the card action, the display-only
   `HistoryGrid`, the `AmountSheet`), and the single-row-per-(habit, date) `HabitLog` ledger.

# Part I — Requirements

## 1. Motivation

### 1.1 What v2.0.0 does today (verified against the code)

In v2.0.0 a habit is **logged two ways** (`DM-HABIT-5`, `FR-HAB-4`):

- **via a linked Task marked Done** — the log lands on **that task's date** (already date-bearing); and
- **directly on the Habit card** — the primary "Mark today done" affordance (frequency) or the **amount sheet**
  (quantitative).

Reviewing the shipped code surfaces three concrete limits on the direct path:

1. **It only ever writes *today*.** The card action calls `HabitsViewModel.logToday(...)`, which passes
   `Dates.todayIso()` straight into `HabitRepository.logDirect(habitId, date = today, …)`. There is no way to log
   a completion for a **different** date — e.g. "I meditated yesterday but forgot to open the app."
2. **Past logs aren't reachable for editing.** The calendar-history grid (`FR-HAB-1`) is rendered **display-only**
   (`HistoryGrid(...)`, no per-cell tap). So although `DM-HABIT-5` promises a habit can be *"edited directly on any
   date,"* the v2.0.0 UI exposes no entry point to reach a past date's log and change it.
3. **A logged value can only be *replaced*, never *added to*.** For *today's* quantitative log, the amount sheet
   pre-fills the current value and **overwrites** it on confirm (`AmountSheet.suggested` → `onConfirm`). That
   handles "I mistyped 20 as 200" for today — but there is **no way to say "I already logged 20 pages, then read 15
   more, make it 35"** without the user doing the arithmetic themselves, and **no way at all to edit a value on any
   day but today**.

### 1.2 What this release adds

- **(A) Date-aware manual logging** — the primary manual-log action defaults to **today** but lets the user pick
  the date (bounded; §3).
- **(B) Editable logged values, with two distinct intents:**
  - **Correct (replace)** — fix a wrong entry (mistyped value, wrong done/undone), for *any* logged date, not
    just today. *(Use case 1.)*
  - **Add (accumulate)** — top up a quantitative value with more of the same on the same day ("read 15 more
    pages" → 20 becomes 35), computed for the user. *(Use case 2.)*
  - **Clear (remove)** — un-log a date logged by mistake.
- A **reachable entry point** to existing logs: the calendar-history grid becomes **tappable** (a cell opens that
  date's log for edit), alongside the date picker on the log button. Both open the **same** edit surface, showing
  the **current** value.

### 1.3 Why this stays inside the research base

- **Autonomy (`PRIN-4`) & forgiveness (`PRIN-2`).** People remember a day late, mistype, and do a bit more after
  logging. Forcing "today only, and you can't fix it" quietly punishes honesty and invites fake data. Letting the
  user name the real date and correct the real number is truth-keeping, not a new obligation. Editing is framed as
  *fixing the mirror to match reality* (`PRIN-1`), never "you were wrong."
- **No new scorekeeping (`DM-NOT`, `DEC-2/3/4`).** Choosing a date and editing a value only decide **which cell of
  the existing calendar/rate holds which number**. They add **no** streak, adherence %, points, or "days active"
  metric. The ledger stays **one record per habit per date** (`DM-ATTR-2`); *Add* is a client-side convenience that
  computes a new total and still stores a **single** value — it never creates a second row or double-counts a
  completion.

## 2. Scope of v2.1.0

**In scope**

- A **date selector** on the manual ("direct") habit-log flow — frequency and quantitative — **defaulting to
  today, editable** within an allowed range.
- **Editing an existing log** for any logged date: **correct/replace**, **add** (quantitative), and **clear**.
- A **tappable calendar-history grid** as the discovery/entry point for editing a past date, sharing one edit
  surface with the date-picker path.
- The small model/repository/ViewModel change to carry a caller-chosen date and an add-vs-replace intent; copy,
  accessibility, and test coverage for all of the above.

**Explicitly *not* in scope** (see §7)

- Changing the **task-driven** log path (`logForTask`) — a task-marked-Done habit already logs on the task's own
  date; that is correct and untouched (`DEC-v21-5`).
- **Future-dated** habit logging beyond today (`DEC-v21-2`).
- **Moving** a log from one date to another as a single gesture (un-log + re-log covers it — §7).
- **Bulk / multi-date** logging or editing (still deferred with multi-select, v2.0.0 §10).
- Any change to habit **math**, recurrence, or the **shape** of goal attribution (`DM-ATTR`); v2.1.0 only keeps
  attribution **exact** when a value it already fed is edited (`DEC-v21-9`).

### 2.1 Technology

`TECH-v21-1` No new dependencies. The date is captured with the Material 3 **`DatePicker` / `DatePickerDialog`**
from the pinned Compose BOM (2026.02.01); the value edit reuses the existing **`AmountSheet`**, extended with an
add/replace control. Dates remain ISO `yyyy-MM-dd` strings. Changes are confined to the habits slice
(`ui/habits/`, `ui/components/` for the sheet, `data/repo/RoomHabitRepository.kt`) and the `HabitRepository`
interface. **No schema migration** — `HabitLog` already stores an arbitrary `date`, an optional `amount`, a
`done` flag, and a `source`; v2.1.0 only changes *how those fields are chosen and edited*.

## 3. Key decisions & conflict resolutions

| ID | Question | Resolution & reason |
|---|---|---|
| **DEC-v21-1** | **Default date.** Force an explicit pick, or default to today? | **Default to today, editable.** The common case is "I did it just now"; requiring a pick would add friction to the daily action. The date is a **pre-filled, one-tap-to-change** control, never a required step. *(The user's stated requirement.)* |
| **DEC-v21-2** | **Allowed date range (upper).** May the user log/edit a **future** date? | **No future dates.** A habit log records what *happened*; a future "done" is meaningless and would corrupt the in-period rate. Selectable range is **habit-start … today, inclusive**; anything after today is not selectable (consistent with `DM-TASK-8` — the system never fabricates future completion). |
| **DEC-v21-3** | **Allowed date range (lower).** How far back? | **Back to the habit's `startedAt` date, inclusive** — a habit can't have been "held" before it existed, and this keeps the grid/arc honest. `startedAt` already exists on `Habit`. Fall back to the earliest grid-displayable date if a start is somehow absent; never block a legitimate recent back-fill. |
| **DEC-v21-4** *(revises the draft)* | **Re-logging / re-opening a date that already has a value.** Replace or add? | **Default is Replace (correct); Add is an explicit, labelled action.** Opening an existing log **pre-fills the current value** and confirming **replaces** it — no silent summing (that would double-count a completion, violating `DM-ATTR`). A separate **"Add"** control lets the user *intentionally* top up: it computes `new = current + delta` and stores the single new total. **Invariant:** the app never *silently* sums; it sums only on an explicit Add. *(This resolves the tension between use case 1 "correct" and use case 2 "add more".)* |
| **DEC-v21-5** | **Which log path gets these edits.** Direct only, or task path too? | **Direct path only.** The task-driven path (`logForTask`) carries the task's own date; a second date/value control there would contradict it and re-open "which date/amount wins". Marking a task Done logs on the task's date, unchanged. Editing a **value that originated from a task** on the habit card is still allowed (it's the same date's single ledger row) — handled by `DEC-v21-9`. |
| **DEC-v21-6** | **Editing frequency (done/not-done) logs.** | There is no numeric value to correct — only **done ↔ not-done**. Editing a frequency date is therefore **toggle + clear**: mark a past date done, or un-log it (`FR-HAB-EDIT-2`). The Add/Replace distinction applies only to **quantitative** habits. |
| **DEC-v21-7** | **Clearing / zero.** What does an amount of 0 (or a cleared field) mean? | **Amount ≤ 0 (or cleared) = un-log that date** (removes the row), equivalent to "tap to undo". A quantitative habit has no meaningful "logged 0" state distinct from "didn't do it"; collapsing them keeps the grid and rate honest and gives one obvious way to remove a mistaken entry (`FR-HAB-EDIT-3`). |
| **DEC-v21-8** | **How does the user *reach* a past log to edit it?** | **Two entry points, one edit surface:** (a) the **date picker** on the manual-log control, and (b) a **tappable calendar-history grid cell** (the grid becomes interactive — today it is display-only). Both open the same sheet, pre-filled with that date's current value, so grid-tap and picker are one behaviour (`FR-HAB-EDIT-4`, `FR-HAB-LOGDATE-6`). |
| **DEC-v21-9** | **Goal attribution when an already-contributing value is edited.** | **Keep it exact via existing provenance, don't invent new attribution.** If an edited log had fed an Accumulative goal by a **unit-matched** link (`DM-ATTR-3`), the prior contribution is **reversed and re-applied at the new value** using the recorded provenance (`NFR-DATA-2`), so the goal bar reflects the correction with **no double count**. For Stepped/Generic or unit-mismatched links the habit→goal relationship stays **directional** (no automatic numeric move, as in v2.0.0); the user adjusts the goal directly. Clearing a log reverses its contribution exactly (as un-done already does). |

## 4. Data-model requirements

The habit object and its ledger are unchanged in **shape** — still **one `HabitLog` row per (habit, date)** with a
`done` flag, an optional `amount`, and a `source`. This release refines the *behaviour* of writing and editing that
row from the direct path.

`DM-HABIT-5-v21` **(refines `DM-HABIT-5`)** — *Logged two ways; the direct path is **date-aware and editable**.* A
Habit is logged either via a linked Task marked Done (logging on **the task's date**, unchanged), **or created and
edited directly on any date in range** from the Habit card. The direct action **defaults to today but lets the user
select the date** (`DEC-v21-1/2/3`), and lets the user **correct, add to, or clear** the value on any logged date
(`DEC-v21-4/6/7`). The chosen date is `HabitLog.date`; the in-period rate, calendar grid, and arc already key off
that field and need no change.

`DM-HABIT-5a-v21` **One value per (habit, date); Add computes, it does not append.** There is still **at most one**
`HabitLog` per habit per date (`DM-ATTR-2`). *Replace* overwrites the row's `amount`/`done`; *Add* computes
`new = current + delta` and overwrites with the single total; *Clear* deletes the row. The app **never** stores two
rows for the same (habit, date) and **never silently sums** (`DEC-v21-4`).

`DM-HABIT-5b-v21` **Provenance preserved on edit.** A directly created or edited log carries `source = DIRECT`. A
value that **originated from a task** (`source = TASK`, `sourceTaskId` set) may be edited from the card as the same
date's single row; on such an edit the goal contribution is kept exact per `DEC-v21-9`, and the task-reversal path
(`reverseForTask`) still reverses **only** its own contribution — a manual edit never desyncs the task ledger.

> **No other `DM-*` change.** No new field, collection, or migration. `HabitLog` already stores `date`, `amount`,
> `done`, `source`; v2.1.0 lets a human choose the date and edit the value on the primary log action.

## 5. Functional requirements

### 5.1 Date-aware manual logging (`FR-HAB-LOGDATE-*`, refining `FR-HAB-4`)

`FR-HAB-4-v21` **(refines `FR-HAB-4`)** — *Log two ways; the manual log is **date-aware and editable**; goal
contribution still counted once (`DM-ATTR`).*

`FR-HAB-LOGDATE-1` **Entry point & default.** The Habit card's primary manual-log control gains a **date field
pre-set to today**. The user may accept it in one tap (the common path — no extra step over v2.0.0) or change it via
a Material 3 date picker before confirming.

`FR-HAB-LOGDATE-2` **Framing.** The control reads as a calm, optional refinement ("Logged for **Today** · change"),
in the "DON'T PANIC" voice (`FR-DESIGN-1`) — never a required wizard step, never implying the user is late.

`FR-HAB-LOGDATE-3` **Allowed range.** The picker permits **habit-start … today, inclusive** (`DEC-v21-2/3`); dates
after today are not selectable.

`FR-HAB-LOGDATE-6` **One behaviour across entry points.** Choosing a past date via the picker and tapping that same
cell in the calendar grid (`FR-HAB-EDIT-4`) open the **same** edit surface and produce **identical** results over
the shared `logDirect` seam.

`FR-HAB-LOGDATE-7` **Correct period accounting.** After a dated log/edit, the card's rate, grid, and arc update to
reflect the value on its **true** date. A log/edit on a date **outside the current in-period window** affects that
earlier period's history/arc, **not** this week's rate — no "phantom today" tick, no double count (`PRIN-1`).

### 5.2 Editing an existing log (`FR-HAB-EDIT-*`) — new

`FR-HAB-EDIT-1` **Reachable & pre-filled.** Any logged date can be opened for edit (via the date picker or a grid
tap, `DEC-v21-8`); the edit surface **shows the current value** for that date (frequency: done/not-done;
quantitative: the logged amount) so the user always sees what they're changing (non-punitive clarity).

`FR-HAB-EDIT-2` **Correct (replace) & frequency toggle.** The user can **replace** a quantitative value (field
pre-filled with the current amount → confirm overwrites, `DEC-v21-4`), or **toggle** a frequency date done/not-done.
This satisfies use case 1 (mistyped correction) for **any** date, not just today.

`FR-HAB-EDIT-3` **Add (accumulate) — quantitative.** When a quantitative date already has a value, the amount sheet
offers an explicit **Add** action alongside Replace: entering an amount in Add mode stores `current + entered` as
the day's single total (`DM-HABIT-5a-v21`). This satisfies use case 2 ("read 15 more pages" → 20 becomes 35) without
the user computing the sum. Add is **only** available when a value already exists; a first log is a plain Replace.

`FR-HAB-EDIT-4` **Tappable calendar-history grid.** The calendar-history grid (`FR-HAB-1`), display-only in v2.0.0,
becomes **interactive**: tapping a cell within the allowed range (`DEC-v21-2/3`) opens that date's edit surface
(pre-filled per `FR-HAB-EDIT-1`). Out-of-range cells (future, or before habit start) are non-interactive. Tapping is
TalkBack-labelled with the date and its current state (`NFR-v21-A11Y-1`).

`FR-HAB-EDIT-5` **Clear / remove.** From the edit surface the user can **un-log** a date — frequency: toggle to
not-done; quantitative: clear the field or enter 0 (`DEC-v21-7`). Clearing removes the single row and reverses any
goal contribution it made (`DEC-v21-9`), consistent with today's "tap to undo".

`FR-HAB-EDIT-6` **Attribution stays exact.** Editing or clearing a value that had advanced a unit-matched
Accumulative goal reverses-and-reapplies (or reverses) the contribution via recorded provenance so the goal bar
matches the corrected value with no double count (`DEC-v21-9`, `DM-ATTR`, `NFR-DATA-2`). Directional (non-numeric)
links are unaffected, as in v2.0.0.

### 5.3 Copy (`FR-DESIGN`)

`FR-DESIGN-v21-1` All new strings use the Den "DON'T PANIC" voice (`FR-DESIGN-1`): supportive, non-punitive, never
"you were wrong / you're behind". Suggested (final wording tunable): date label "**Logged for {Today | Mon, Jul 7}**
· change"; quantitative edit sheet distinguishes **"Set to"** (replace) and **"Add"** with a live preview of the
resulting total ("20 + 15 → **35** pages"); clearing confirms plainly ("Removed — {date} is clear"). Reuse
`FR-REC-2`'s conditional-year date formatting for all date labels.

## 6. Non-functional requirements

`NFR-v21-DATA-1` **No migration; additive & default-tolerant** (`NFR-DATA-1`). No schema change — `HabitLog` already
carries `date`, `amount`, `done`, `source`. v2.0.0 logs remain valid; v2.1.0 changes only *how the date is chosen and
the value is edited*.

`NFR-v21-DATA-2` **Exact reversal preserved** (`NFR-DATA-2`, `DM-ATTR-1`). The provenance that makes goal
contributions reversible must remain sufficient to reverse **and re-apply** an edited value exactly (`DEC-v21-9`).

`NFR-v21-A11Y-1` **Accessibility** (`NFR-A11Y-1`). The date control, the date picker, the **grid cells** (now
interactive), and the Add/Replace/Clear controls are **TalkBack-labelled** (e.g. grid cell: "Jul 7, done, 20 pages,
double-tap to edit"; date field: "Log date, currently Today, double-tap to change"), keyboard/switch-navigable, with
baseline touch-target sizes. No new icon-only control ships without a content description.

`NFR-v21-TEST-1` **Test coverage** (`NFR-TEST-1`). Unit tests assert: (a) a direct log lands on the **selected**
date, defaulting to today when none is chosen; (b) future dates are rejected/clamped and the lower bound is habit
start (`DEC-v21-2/3`); (c) **Replace** overwrites the single row (frequency & quantitative), never appends
(`DM-HABIT-5a-v21`); (d) **Add** stores `current + delta` as one total and is unavailable on a first log
(`FR-HAB-EDIT-3`); (e) **Clear** / amount ≤ 0 removes the row (`DEC-v21-7`); (f) editing a log in a **prior** period
updates that period's rate/arc, not today's (`FR-HAB-LOGDATE-7`); (g) editing/clearing a value that fed a
unit-matched Accumulative goal reverses-and-reapplies exactly, with no double count (`DEC-v21-9`). A Compose UI test
drives **both** entry points (log-button date picker **and** grid-cell tap) through Replace, Add, and Clear, and
verifies the resulting log. Verified through the headless build/install/screenshot loop (`TECH-4`).

## 7. Out of scope for v2.1.0

| Item | Disposition |
|---|---|
| **Future-dated habit logs** | Excluded (`DEC-v21-2`) — a habit records what happened; logging ahead corrupts the rate. |
| **Date/value controls on the task-driven log path** | Excluded (`DEC-v21-5`) — a task-marked-Done habit logs on the task's own date. Editing the resulting value on the card is in scope (`DEC-v21-9`); adding a picker to the task path is not. |
| **Moving a log from one date to another** (as one gesture) | Out of scope — un-log the wrong date and log the right one (two in-scope ops). A move gesture is a later convenience. |
| **Bulk / multi-date logging or editing** | Deferred with multi-select/bulk-edit (v2.0.0 §10). One date per manual log/edit. |
| **New goal-attribution mechanics** | Excluded — v2.1.0 only keeps *existing* unit-matched Accumulative attribution exact under edits (`DEC-v21-9`); it invents no new habit→goal numeric behaviour (`DM-ATTR-3` stands). |
| **Any streak / score / adherence surface** | **Never** (`DM-NOT`, `DEC-2/3/4`). This release must not add one. |

## 8. Acceptance criteria for "v2.1.0 is done"

v2.1.0 is complete when all of the following are true and verified:

1. From a Habit card's **manual** log action, the user can **confirm or change the date**, defaulting to **today**,
   for both frequency and quantitative habits (`FR-HAB-LOGDATE-1/2`).
2. The selectable range is **habit-start … today, inclusive**; **future dates are not selectable**
   (`DEC-v21-2/3`, `FR-HAB-LOGDATE-3`).
3. Any logged date is **reachable and editable** via **both** a tappable calendar-grid cell and the date picker,
   opening one shared surface **pre-filled with the current value** (`FR-HAB-EDIT-1/4`, `DEC-v21-8`).
4. The user can **Correct/Replace** a value or toggle a frequency date (use case 1), **Add** to a quantitative
   value as an explicit action computing `current + delta` (use case 2), and **Clear** a mistaken log — always
   storing **one** row per (habit, date) and **never silently summing** (`FR-HAB-EDIT-2/3/5`, `DM-HABIT-5a-v21`,
   `DEC-v21-4/7`).
5. Grid-tap and picker paths produce **identical** results; rate/grid/arc update on the log's **true** date, with
   prior-period edits affecting the right period (`FR-HAB-LOGDATE-6/7`).
6. Editing or clearing a value that fed a unit-matched Accumulative goal keeps the goal bar **exact** via existing
   provenance — no double count (`DEC-v21-9`, `FR-HAB-EDIT-6`); directional links unchanged.
7. The **task-driven** log path is unchanged — a task marked Done still logs on the task's date (`DEC-v21-5`).
8. **Nowhere** does this feature add a streak, points, adherence %, or engagement metric (`DM-NOT`).
9. New copy uses the "DON'T PANIC" voice; the date control, picker, grid cells, and Add/Replace/Clear controls are
   TalkBack-accessible (`FR-DESIGN-v21-1`, `NFR-v21-A11Y-1`).
10. Unit + Compose tests (§6 `NFR-v21-TEST-1`) are green; the flows are verified on the emulator against the design
    via the headless loop (`TECH-4`).

# Part II — Roadmap

A single, small, vertically-sliced milestone on top of v2.0.0. It touches the habits slice only and ships an
installable build with its own tests, per the Tzafon cadence.

## M10 — Editable manual habit logging (date + value) → **Tzafon 2.1.0**

- **Scope:**
  - **Repository/ViewModel seam** — `HabitRepository.logDirect` already takes a `date`; expose it up through
    `HabitsViewModel` (replace the `today`-hardcoding `logToday(...)` with `logOn(habitId, date, done, amount)`
    defaulting `date` to today). Add an **Add-vs-Replace** intent for quantitative writes (Add computes
    `current + delta` in the ViewModel/repo, storing one total). Enforce the range clamp (`DEC-v21-2/3`) and the
    "amount ≤ 0 ⇒ clear" rule (`DEC-v21-7`) at the seam so no caller can violate them.
  - **UI** — add the pre-filled, editable **date control** to the card's manual-log affordance
    (`FR-HAB-LOGDATE-1..3`); extend **`AmountSheet`** with a **Set-to / Add** toggle and a live total preview
    (`FR-HAB-EDIT-2/3`, `FR-DESIGN-v21-1`); make the **`HistoryGrid`** cells **tappable** to open a date's edit
    surface pre-filled with its current value (`FR-HAB-EDIT-4`); wire the Material 3 date picker with `max = today`,
    `min = habit start`. Ensure grid-tap and picker share the seam (`FR-HAB-LOGDATE-6`).
  - **Attribution** — when an edited/cleared value fed a unit-matched Accumulative goal, reverse-and-reapply via
    recorded provenance so the bar stays exact (`DEC-v21-9`, `FR-HAB-EDIT-6`).
  - **Copy & a11y** — Den-voice labels, conditional-year date formatting, TalkBack descriptions on the date
    control, picker, grid cells, and Add/Replace/Clear (`FR-DESIGN-v21-1`, `NFR-v21-A11Y-1`).
  - **Tests** — the `NFR-v21-TEST-1` unit matrix + a Compose flow test across both entry points and all three
    intents (Replace / Add / Clear).
- **Depends on:** v2.0.0 M4 (Habits + the `HabitLog` ledger) and M5 (goals/attribution, for `FR-HAB-EDIT-6`). No
  dependency on later milestones.
- **Value even alone:** honest logging — record a habit for the day it happened, fix a mistyped number, and top up
  "did a bit more" without arithmetic; the app stops forcing "today, and no take-backs".
- **Verify:** unit suite green; on the emulator — (1) change the log date to yesterday, confirm, see it land on
  yesterday's grid cell; (2) confirm future cells are non-interactive; (3) log 20 pages, use **Add** 15 → card
  shows 35; (4) **Set to** 200→20 corrects a typo; (5) **Clear** removes a day; (6) a goal fed by an edited value
  reflects the corrected total — all via screenshots; `logcat` clean.
