# Tzafon — v2.1.0 Requirements

**Product:** **Tzafon** (צפון — Hebrew for *north*). The compass that keeps you pointed at a chosen direction.
**Version:** 2.1.0 (target)
**Platform:** Native Android (Kotlin + Jetpack Compose) — see `DEC-1` in v2.0.0.
**Builds on:** **Tzafon v2.0.0** (released). This document is an **increment** — it does not restate the v2.0.0 spec, only the requirements added or refined for v2.1.0. v2.0.0's requirements remain in force except where a section below explicitly refines one.
**Status:** Requirements — auto-groomed
**Date:** 2026-07-10

> **How to read this document**
>
> - Requirements below carry the same code scheme as v2.0.0 (`DM-*`, `FR-<AREA>-n`). New codes extend the existing series (e.g. a new Today requirement continues at `FR-TODAY-7`).
> - A section that **refines** an existing v2.0.0 requirement names it in the header and states precisely what changes; the original requirement is otherwise untouched.
> - Callouts follow v2.0.0 conventions:
>   - **[DECISION]** — a missing detail resolved with a stated assumption; overrule if wrong.
>   - **[OUT OF SCOPE]** — deliberately deferred.
> - Cross-references from feature requests to requirements are listed in each section's header.

## 1. Scope of v2.1.0

v2.1.0 is a **small ergonomics increment** on top of a shipped v2.0.0. No new object types, no new views, no schema migrations (see §4 — Data model deltas below, which is intentionally empty). All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %) and the ≤3 active themes cap.

The increment bundles four small changes: one capture-flow default (`FR-TODAY-7`), one Habits-view density change (`FR-HAB-5`), one contrast bug fix on the create-habit confirmation button (`FR-HAB-6`), and content-direction support for user-authored text so Hebrew/Arabic titles render correctly (`FR-DESIGN-3`).

## 2. Functional requirements

### 2.1 Today quick-add defaults To Do Date to today (`FR-TODAY-7`)

*Source: `FR-2026-07-10-a`. Refines `FR-CAPTURE-2`.*

`FR-TODAY-7` **Quick-add invoked from the Today view defaults the new task's `toDoDate` to today.** The one-line quick-add on Today (title + Enter → saved) writes the task with `toDoDate = <today's ISO date>` so the new task immediately appears in Today (which is its `FR-TODAY-1` membership rule: `To Do Date = today OR Due Date = today`). The user can still clear or change the date by expanding the quick-add into the full editor before saving.

`FR-TODAY-7.1` **Scope is exactly the Today view's quick-add.** All other capture paths retain `FR-CAPTURE-2`'s "undated by default" behavior:
  - the expanded full editor (from any view, including Today) still defaults `toDoDate` to none;
  - quick-add invoked from any other view (Planning, All Tasks, the FAB anywhere outside Today, etc.) still defaults `toDoDate` to none;
  - the user's active edit of the date in the expanded editor overrides the Today default (there is no "sticky today" applied after the user has explicitly set or cleared a date in that same capture flow).

`FR-TODAY-7.2` **Not a system-driven date change.** This is the initial-write default only; it does **not** violate `DM-TASK-8` ("dates are never changed automatically by the system"), which forbids the app *modifying* dates on existing tasks. A quick-add is a new-task write, not a modification.

`FR-TODAY-7.3` **Copy / voice.** No new copy is required — the task simply appears in Today. The quick-add input itself needs no "will be dated today" hint because the outcome is visible one row later; adding a hint would be over-explaining in the "DON'T PANIC" voice (`FR-DESIGN-1`).

> **[DECISION] — refining `FR-CAPTURE-2` in the Today context only.**
> `FR-CAPTURE-2` was written to escape v1.1.0's blanket "always today" default that dated tasks the user didn't mean to date. That risk doesn't exist when the user is *already looking at* Today and typing into its own quick-add — the surrounding view is itself the expression of intent. `FR-TODAY-7` therefore treats "which view invoked the quick-add" as a first-class capture context, and only Today infers a date. Planning's own quick-add (once/if added) would similarly infer no date, matching Planning's Inbox emphasis.

**Acceptance criteria**

1. From the Today view, typing a title into quick-add and pressing Enter creates a task with `toDoDate = <today>` and it renders in Today immediately (state = Open, per `DM-TASK`).
2. From the Today view, expanding the quick-add into the full editor and clearing the date, then saving, produces an **undated** task (Inbox) — the Today-context default does not override an explicit user choice.
3. From any non-Today view, the quick-add still creates an **undated** task (verified in Planning, All Tasks, and the Backlog view).
4. `DM-TASK-8` still holds: no existing task's date changes without a user edit.
5. No gamification surfaces are introduced or exposed (`DM-NOT` unchanged).

**Out of scope for v2.1.0**

- **Context-aware defaults on other views.** e.g. quick-add from a Theme detail defaulting `themeId` to that theme, or quick-add from Planning's per-day group defaulting `toDoDate` to that group's date. These are natural follow-ons but are not part of this request — v2.1.0 ships the Today case only and leaves the pattern extendable.
- **A user setting to disable this default.** The v2.0.0 friction-floor philosophy is one path at a time; adding a toggle before there's evidence of friction would just be preference sprawl.

### 2.2 Habits view — collapsed-by-default cards (`FR-HAB-5`)

*Source: `FR-2026-07-10-b`. Refines `FR-HAB-1`.*

`FR-HAB-5` **Habit cards in the Habits view collapse by default.** In collapsed state a card shows only the essentials: the habit **name**, the **log-activity control** (the same log-two-ways affordance from `DM-HABIT-5` — one tap for frequency habits; opens the "how much?" prompt for quantitative), and an **expand affordance**. Expanding a card reveals the full `FR-HAB-1` contents unchanged: target, cue, in-period rate with endowed head-start, calendar-style history, long identity arc, and *"serves: <Theme/Goal>"* links.

`FR-HAB-5.1` **Scan-first list.** The collapsed row is a compact list-item, sized so ~6 active habits are comfortably surveyable at a glance on a Pixel-8-class device without scrolling. The single-tap log affordance must remain reachable from the collapsed state — logging is the primary daily interaction on a habit (`DM-HABIT-5`) and must not regress to two taps.

`FR-HAB-5.2` **Expand state is not persisted.** Re-entering the Habits view resets all cards to collapsed. Persisting per-habit expansion would grow a stealth "sticky detail" surface that only some cards carry, which defeats the density gain that motivates the collapse. If a user wants the full card, one tap is cheap; the value is the default view being calm.

`FR-HAB-5.3` **No new gamification surfaces.** The collapsed card exposes name and log only. No streak counter, no % complete, no "keep going" copy — collapsing must not become a place to slip an aggregate score in (`DM-NOT`, `DEC-2/4`). The forgiving in-period rate stays inside the expanded card, exactly where `DM-HABIT-3` puts it.

`FR-HAB-5.4` **Cue proximity is preserved on expand.** When expanded, the cue stays front-and-centre per `FR-HAB-1` ("a habit card without its cue is just a tracker") — collapsing hides it from the scan view, but it must not be demoted below any other detail once the card is open.

> **[DECISION] — always collapsed on entry, no auto-expand.**
> Alternatives considered were "auto-expand the habit due today" or "auto-expand the last-logged card". Both re-introduce state ("which is the *featured* card?") that the collapsed default is trying to remove, and both quietly re-open the door to prioritising one habit over others — a pattern the user hasn't asked for. Better to give every habit the same starting shape and let the user open the ones they care about. This mirrors the "one path at a time" friction-floor thinking behind `FR-CAPTURE`.

**Acceptance criteria**

1. Entering the Habits view with N habits renders all N cards collapsed — name + log control + expand affordance only.
2. The log control on a collapsed card logs the day (frequency) or opens the quantity prompt (quantitative), identical in behaviour to logging from the expanded card (`DM-HABIT-5`).
3. Tapping the expand affordance reveals the full `FR-HAB-1` content — target, cue, in-period rate, calendar-style history, long arc, "serves:" — with the cue immediately below the header. Tapping it again collapses the card.
4. Leaving Habits and returning collapses every card again (no persisted expand state).
5. Nowhere in the collapsed *or* expanded card does a streak counter, adherence %, or points/badges surface appear (`DM-NOT` unchanged).
6. TalkBack announces both the collapsed and expanded states with distinct content descriptions (`NFR-A11Y-1`).

**Out of scope for v2.1.0**

- **A "collapse all / expand all" bulk toggle.** With one-tap-per-card and no persistence, the affordance isn't earned yet.
- **Persisted per-habit expand state.** See `FR-HAB-5.2`.
- **Reordering habits in the collapsed list.** Habits view stays in its current order; manual reorder can be revisited as a follow-on if scanning past ~6 habits becomes routine.

### 2.3 Habit-create confirmation button contrast (`FR-HAB-6`)

*Source: `FR-2026-07-10-c` (bug fix). Refines `FR-DESIGN-2` and `NFR-A11Y-1`.*

`FR-HAB-6` **The confirmation button in the create-habit flow uses Den colour tokens with legible contrast.** The button currently renders white text on a bright accent, making the label unreadable. It must route through the correct Material 3 `ColorScheme` role from `AppTheme` (e.g. `primary` + `onPrimary`, or the accent-slot equivalent used by the create-habit surface), so the label meets **WCAG AA ≥ 4.5:1** against its container in both light and dark themes.

`FR-HAB-6.1` **Root cause is a token-pairing regression, not a palette gap.** The Den palette (`FR-DESIGN-1`) already carries an `on-<accent>` for every accent slot; the fix is to bind the button to the correct pair rather than invent a new colour. `FR-DESIGN-2` already forbids leaving Material components at their defaults — this fix restores that guarantee where it slipped.

`FR-HAB-6.2` **Targeted audit of the analogue primary-action buttons.** Verify the same token-pairing on the other create-flow confirmation buttons introduced with the direction layer — create-goal (`FR-DIR-4`) and create-theme (`FR-DIR-6`) — and correct any that carry the same reversed-contrast defect. This is a scoped audit of primary-action confirmations, not a full-app re-theme.

**Acceptance criteria**

1. In the create-habit flow, the confirmation button's label is legible in both light and dark themes; measured contrast between label and container ≥ 4.5:1.
2. The button binds to a Material 3 role pairing from `AppTheme`'s `ColorScheme` — no hard-coded `Color(0xFF…)` at the call site.
3. The create-goal and create-theme confirmation buttons pass the same check per `FR-HAB-6.2` (or are already correct); a manual pass on a Pixel-8-class emulator confirms.
4. No regression on other primary-action buttons that were previously legible.
5. TalkBack announces the button's label unchanged (`NFR-A11Y-1`); the label text itself does not change.

**Out of scope for v2.1.0**

- **A full Den-palette contrast audit across every surface.** v2.1.0 ships the targeted fix on the primary-action confirmations; a broader sweep is left for a future `NFR-A11Y-1` revisit if evidence warrants.

### 2.4 Content-direction support for user-authored text (`FR-DESIGN-3`)

*Source: `FR-2026-07-10-d`. Extends `FR-DESIGN`, refines `NFR-A11Y-1`.*

`FR-DESIGN-3` **User-authored text renders and edits with content-driven direction.** Every field where the user types their own content — task **title** and **description**, habit **name**, goal **title** and **description**, theme **name** and **why**, cue **label**, task/goal `commitment`, and the Review free-text line — applies **content-based bidirectional layout** so Hebrew, Arabic, or any right-to-left script the user types displays right-to-left with the caret at the correct edge, and mixed-direction content is laid out per the Unicode Bidirectional Algorithm. Read-only surfaces that display those same strings (Today's task rows, Planning groups, All Tasks, Habits cards, Directions hub cards, Journey artifacts) apply the same content-based direction so the entered text reads the way the user typed it.

`FR-DESIGN-3.1` **App chrome stays LTR.** Tzafon is authored in English; the bottom-nav labels, section headers, date labels, the "DON'T PANIC" voice copy, and all built-in strings remain LTR. `FR-DESIGN-3` is a content-direction requirement, not a locale swap: no mirroring of layout, FAB position, side padding, icons, or nav.

`FR-DESIGN-3.2` **Implementation shape.** In Compose, apply `TextStyle.textDirection = TextDirection.Content` (or the composable-level equivalent) on the input and display composables covered by `FR-DESIGN-3`, so the Unicode Bidi Algorithm resolves direction from the first strong character. Chrome composables keep their default (`TextDirection.Ltr` from the ambient `LocalLayoutDirection`).

`FR-DESIGN-3.3` **Search and sort are unaffected.** All Tasks' title/description search (`FR-ALL-2`) matches on the underlying string regardless of visual direction; sorts continue to key on `toDoDate`, not on text.

`FR-DESIGN-3.4` **Recurrence unaffected.** Series data and generation (`FR-REC`) are direction-blind; a Hebrew-titled recurring task must generate occurrences identically to an English-titled one.

> **[DECISION] — content-direction, not locale mirroring.**
> The request is that text fields be readable when Hebrew is typed into them — not that the app UI itself be localised. A real locale flip (mirroring layout, translating strings, RTL-anchoring the FAB and bottom nav, translating the "DON'T PANIC" voice) is a much larger change that Tzafon v2.0.0 didn't scope. Restricting `FR-DESIGN-3` to user-authored text solves the reported problem without invalidating the design mocks or the design language, and leaves a full locale pass available as a later initiative if it's ever wanted.

**Acceptance criteria**

1. Typing a Hebrew task title in the full editor renders right-to-left with the caret at the right edge; typing an English title in the same field renders left-to-right. Switching direction mid-edit follows the Bidi Algorithm.
2. A saved Hebrew-titled task appears right-to-left everywhere it is displayed: Today, Planning, All Tasks, the task editor, and any card that surfaces the title.
3. The same behaviour holds for habit names, goal titles/descriptions, theme names and "why", cue labels, commitment fields, and the Review free-text line.
4. Bottom nav, section headers, date labels, and other chrome remain LTR regardless of the content around them.
5. TalkBack reads Hebrew content in its logical order (`NFR-A11Y-1`); no crash or garbled read-out on mixed-script strings.
6. A Hebrew-titled recurring task generates occurrences identically to an English one (`FR-DESIGN-3.4`).

**Out of scope for v2.1.0**

- **Full app localisation / RTL layout mirroring** — translated strings, `res/values-he/`, mirrored chrome, RTL-anchored FAB / bottom nav, translated Den voice. A separate initiative if ever wanted.
- **Per-locale date/number formatting.** Dates continue to render per the existing `FR-REC-2` rules.
- **Locale-specific input methods / keyboard hints.** The system IME choice governs input.

## 5. Acceptance criteria for "v2.1.0 is done"

v2.1.0 is complete when:

1. Each of `FR-TODAY-7`, `FR-HAB-5`, `FR-HAB-6`, and `FR-DESIGN-3` passes its own acceptance criteria in §2 on the emulator.
2. All v2.0.0 acceptance criteria (§9 of v2.0.0 Requirements) still pass — nothing regressed, in particular `DM-NOT` (no gamification anywhere), `FR-CAPTURE-2` in every non-Today capture context, `DM-TASK-8` (no automatic date changes on existing tasks), and `FR-HAB-1`'s full-detail contents when a habit card is expanded.
3. Automated tests cover:
   - the four positive/negative capture paths in §2.1 (`FR-TODAY-7`);
   - the collapse-by-default state, log-from-collapsed behaviour, and no-persisted-expand rule in §2.2 (`FR-HAB-5`), via Compose UI tests;
   - a headless / lint-level contrast check or manual verification on the primary-action confirmation buttons named in §2.3 (`FR-HAB-6`);
   - content-direction behaviour on at least one Hebrew and one English string across an input field and its read-only display for §2.4 (`FR-DESIGN-3`).
4. Debug build installs and launches; no logcat `FATAL` / `AndroidRuntime` lines introduced. Contrast on the audited confirmation buttons meets **WCAG AA ≥ 4.5:1** in both light and dark themes.

## 6. Milestones

Ordered plan for the builder. Each milestone ends with a green test suite, a headless install-and-screenshot verification, and a git commit citing the milestone + requirement codes.

### M1 — Today quick-add defaults to today (`FR-TODAY-7`, refines `FR-CAPTURE-2`)

- **Scope:** wire the Today view's quick-add so that on the initial-write path it passes `toDoDate = <today's ISO date>` into the task write. All other capture paths remain undated. Add tests for the four acceptance-criteria cases in §2.1.
- **Why first:** smallest scope and self-contained; establishes the pattern of view-context-aware capture without touching shared surfaces the later milestones will edit.
- **Verify:** JUnit test on the quick-add call site's date-default logic; Compose test (or headless `adb` verification) that a task typed into Today's quick-add renders in Today immediately, and that the same input path in Planning / All Tasks produces an undated task. `adb logcat -d | grep -iE 'AndroidRuntime|FATAL'` after each verify pass.
- **Done when:** M1 tests pass; §5 acceptance criteria for `FR-TODAY-7` all pass; commit references `FR-TODAY-7` and cross-references source request `FR-2026-07-10-a`.

### M2 — Habit-create confirmation button contrast (`FR-HAB-6`)

- **Scope:** rebind the create-habit confirmation button to the correct `ColorScheme` role from `AppTheme` so its label meets WCAG AA. Audit the create-goal and create-theme confirmation buttons and correct the same defect there if present. No new tokens, no palette change.
- **Why here:** an isolated bug fix, no dependency on the other v2.1.0 items; landing it early gets the create flows out of the "unreadable button" state before further UI work on Habits (M3) touches the same screens.
- **Verify:** on-device screenshot of each of the three create-flow confirmations in both light and dark themes; contrast check ≥ 4.5:1. Confirm no hard-coded `Color(0xFF…)` remains at the call site. `adb logcat -d | grep -iE 'AndroidRuntime|FATAL'` clean.
- **Done when:** M2 §2.3 acceptance criteria pass; commit references `FR-HAB-6` (and `FR-DESIGN-2` / `NFR-A11Y-1`) and cross-references `FR-2026-07-10-c`.

### M3 — Habits view collapsed-by-default cards (`FR-HAB-5`, refines `FR-HAB-1`)

- **Scope:** in the Habits view, make each habit card collapse to *name + log control + expand affordance* by default. Expanding reveals the full `FR-HAB-1` contents unchanged, with the cue immediately below the header. Do not persist expand state across view visits. Preserve the single-tap log affordance from the collapsed row (frequency habits) and the "how much?" prompt (quantitative).
- **Why here:** self-contained Habits view change; naturally sits after M2 so the confirmation-button fix has already stabilised the surrounding create-habit flow.
- **Verify:** Compose UI tests for (a) all cards collapsed on entry, (b) log-from-collapsed works for both frequency and quantitative habits, (c) expand/collapse toggles, (d) navigating away and back re-collapses. Headless screenshot at 3–6 habits before/after expansion. Grep the view for any accidental streak/adherence surface.
- **Done when:** M3 §2.2 acceptance criteria pass; `DM-NOT` audit shows no new gamification surface introduced by the collapse; commit references `FR-HAB-5` and cross-references `FR-2026-07-10-b`.

### M4 — Content-direction support for user-authored text (`FR-DESIGN-3`)

- **Scope:** apply `TextDirection.Content` (or the composable-level equivalent) on the input and display composables that render user-authored strings: task title & description, habit name, goal title & description, theme name & why, cue label, task/goal commitment, Review free-text line. Chrome composables unchanged (LTR).
- **Why here:** cross-cutting text-rendering change touching multiple screens; landing it last means M3's Habits UI refactor is already stable, and this milestone can sweep the same screens in a single pass. Keeps unrelated diffs from tangling with the Habits-view rework.
- **Verify:** Compose UI tests writing Hebrew and English into a task-title field and asserting the resolved direction; on-device screenshots of a Hebrew task in Today / Planning / All Tasks / editor, a Hebrew habit name in Habits, a Hebrew theme name & why in Directions. TalkBack pass on one Hebrew and one mixed-script string. Confirm the bottom nav, section headers, and date labels remain LTR. Confirm a Hebrew-titled recurring series generates identically to an English one.
- **Done when:** M4 §2.4 acceptance criteria pass; `NFR-A11Y-1` still holds for TalkBack ordering; commit references `FR-DESIGN-3` and cross-references `FR-2026-07-10-d`.
