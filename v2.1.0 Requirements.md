# Part I — Requirements

## 1. Motivation

### 1.1 The gap in v2.0.0

In v2.0.0 a habit is **logged two ways** (`DM-HABIT-5`, `FR-HAB-4`):

- **via a linked Task marked Done** — the log lands on **that task's date** (already date-bearing, since the
  task carries a To Do / Due date); and
- **directly on the Habit card** — the "Mark today done" affordance (and the quantitative amount sheet).

The direct path **hard-codes today**. In the shipped code, the card's action calls
`HabitsViewModel.logToday(...)`, which passes `Dates.todayIso()` straight into
`HabitRepository.logDirect(habitId, date = today, …)`. There is **no way, from the direct path, to log a habit
as done for a *different* date** — e.g. "I meditated yesterday but forgot to open the app," or back-filling a
day mid-week.

v2.0.0 *does* already allow editing any past date **by tapping the calendar-history grid** (`DM-HABIT-5`'s "edited
directly on any date", `FR-HAB-1`'s calendar-style history). But the **primary, discoverable "I did it" button**
only ever writes *today*. This release closes that gap: the primary log action becomes **date-aware**, defaulting
to today but editable.

### 1.2 Why this is in-bounds for the research base

- **Autonomy (`PRIN-4`) & forgiveness (`PRIN-2`).** Life is messy; people remember a day late. Forcing every
  manual log to be "today only" quietly punishes the honest back-filler and pushes people to either lie (log
  today for yesterday's action) or give up. Letting the user name the real date is *approach-framed* (`PRIN-3`)
  truth-keeping, not a new obligation.
- **No new scorekeeping (`DM-NOT`, `DEC-2/3/4`).** Choosing a date only decides *which cell* of the existing
  forgiving in-period rate / calendar history a completion lands in. It adds **no** streak, adherence %, points,
  or "days active" metric. The habit ledger (`DM-ATTR-2`) is unchanged in kind — still one record per habit per
  date; this feature only lets the user pick the date on the record.

## 2. Scope of v2.1.0

**In scope**

- A **date selector** on the manual ("direct") habit-log flow — frequency (done/not-done) **and** quantitative
  (amount) habits — **defaulting to today, editable** to any allowed date.
- The small model/repository/ViewModel change to carry a caller-chosen date instead of an implicit `today`.
- Copy, accessibility, and test coverage for the above.

**Explicitly *not* in scope** (see §7)

- Changing the **task-driven** log path (`logForTask`) — a task-marked-Done habit already logs on the task's
  own date; that is correct and untouched.
- Any change to habit **math**, the rate/arc/grid, goal attribution (`DM-ATTR`), or recurrence.
- **Future-dated** habit logging beyond today (a habit is a record of what happened, not a plan — `DEC-v21-2`).
- A bulk / multi-date logging UI (still deferred with multi-select, v2.0.0 §10).

### 2.1 Technology

`TECH-v21-1` No new dependencies. The date field is captured with the Material 3 **`DatePicker` / `DatePickerDialog`**
already available via the pinned Compose BOM (2026.02.01). Dates remain ISO `yyyy-MM-dd` strings (v2.0.0 layout
convention). The change is confined to the habits slice (`ui/habits/`, `data/repo/RoomHabitRepository.kt`) and the
`HabitRepository` interface — no schema migration (the `HabitLog` row already stores an arbitrary `date`).

## 3. Key decisions & conflict resolutions

| ID | Question | Resolution & reason |
|---|---|---|
| **DEC-v21-1** | **Default date.** Should the manual log default to today, or force an explicit pick? | **Default to today, editable.** The overwhelmingly common case is "I did it just now." Requiring a pick every time would add friction (`PRIN` friction-floor spirit) to the daily action. The date is a **pre-filled, one-tap-to-change** control, never a required step. *(This is the user's stated requirement.)* |
| **DEC-v21-2** | **Allowed date range.** May the user log a habit as done for a **future** date? | **No future dates.** A habit log is a record of something that *happened*; logging "done" for next Tuesday is meaningless and would corrupt the in-period rate. The selectable range is **the habit's start date … today, inclusive** (lower bound `DEC-v21-3`). The date picker disables/blocks anything after today. *(Consistent with `DM-TASK-8` — the system never fabricates completion in the future.)* |
| **DEC-v21-3** | **Lower bound.** How far back may the user log? | **Back to the habit's `startedAt` date, inclusive** (no earlier — a habit can't have been "held" before it existed; this also keeps the calendar-history grid and arc honest). If a habit has no meaningful start, fall back to a generous floor (e.g. the earliest date the grid can display) — never block a legitimate recent back-fill. *(`startedAt` already exists on the `Habit` model.)* |
| **DEC-v21-4** | **Editing an existing date's log.** What happens if the user picks a date that already has a log? | **Same as today's toggle, applied to the chosen date.** Frequency: picking a date that is already done and confirming is a no-op / offers un-log; quantitative: the amount sheet pre-fills the existing amount for that date and **overwrites** it (never sums — matches `DM-ATTR` "counted once" and the existing quantitative "Logged X — edit" affordance). This makes the new date selector and the existing tap-the-grid edit path **one consistent behaviour**. |
| **DEC-v21-5** | **Which log path gets the selector.** Direct only, or task path too? | **Direct path only.** The task-driven path (`logForTask`) already carries the task's date; adding a second date picker there would contradict the task's own date and re-open the "which date wins" question. Marking a task Done logs the habit on the task's date, unchanged. |

## 4. Data-model requirements

The habit object and its ledger are unchanged in **shape**. This release refines one behavioural requirement.

`DM-HABIT-5-v21` **(refines `DM-HABIT-5`)** — *Logged two ways, and the direct path is **date-aware**.* A Habit is
logged either via a linked Task marked Done (which logs on **the task's date**, unchanged), **or edited directly on
any date**. The **direct manual-log action defaults to today but lets the user select the date** (`DEC-v21-1`),
within the allowed range (`DEC-v21-2/3`). For a quantitative habit the amount prompt applies to the **selected**
date. The chosen date is the `HabitLog.date`; everything downstream (in-period rate, calendar grid, arc) already
keys off that field and needs no change.

`DM-HABIT-5a-v21` **Idempotent per (habit, date).** There is still **at most one** `HabitLog` per habit per date
(`DM-ATTR-2` habit ledger). Logging done for an already-logged date **replaces**, never appends (`DEC-v21-4`).

`DM-HABIT-5b-v21` **Provenance preserved.** A date-selected manual log is recorded with `source = DIRECT` (as
today's direct logs already are), distinct from `source = TASK`. This keeps the existing task-reversal path
(`reverseForTask`) unaffected: reversing a task never touches a manually date-logged entry, and vice-versa.

> **No other `DM-*` change.** No new field, collection, or migration. The `HabitLog` row already stores an
> arbitrary ISO `date`; v2.1.0 simply lets a human choose it on the primary log action instead of always sending
> `today`.

## 5. Functional requirements

### 5.1 Habits view — date-aware manual log (`FR-HAB`)

`FR-HAB-4-v21` **(refines `FR-HAB-4`)** — *Log two ways; the manual log is date-aware; goal contribution still
counted once (`DM-ATTR`).* The manual-log affordance on a Habit card lets the user **confirm the date** before the
log is written.

`FR-HAB-LOGDATE-1` **Entry point.** The Habit card's primary manual-log control (today's "Mark today done" and the
quantitative amount sheet) gains a **date field pre-set to today**. The user may either (a) accept it in one tap
(the common path — no extra step over v2.0.0), or (b) change it via a **Material 3 date picker** before confirming.

`FR-HAB-LOGDATE-2` **Default & framing.** The default is **today** (`DEC-v21-1`). The control reads as a calm,
optional refinement ("Logged for **Today** · change"), consistent with the "DON'T PANIC" voice (`FR-DESIGN-1`) —
never a required wizard step, never implying the user is late.

`FR-HAB-LOGDATE-3` **Allowed range.** The picker permits **the habit's start date … today, inclusive**
(`DEC-v21-2/3`). Dates after today are **not selectable**. Attempting a future date is prevented in the picker (no
error state needed).

`FR-HAB-LOGDATE-4` **Frequency habits.** Selecting a date and confirming writes a done log for **that** date. If the
chosen date is already done, confirming is a no-op and the card offers to **un-log** that date (mirrors today's
"Done — tap to undo"), per `DEC-v21-4`.

`FR-HAB-LOGDATE-5` **Quantitative habits.** The amount sheet applies to the **selected** date. If that date already
has an amount, the sheet **pre-fills and overwrites** it (never sums — `DEC-v21-4`), matching the existing
"Logged X {unit} — edit" behaviour but for the chosen date.

`FR-HAB-LOGDATE-6` **Consistency with the calendar grid.** Choosing a past date via the new picker and tapping that
same cell in the calendar-history grid (`FR-HAB-1`) must produce **identical** results — the two paths are one
behaviour over the shared `logDirect` seam. (No divergence between "picked from the button" and "tapped the grid".)

`FR-HAB-LOGDATE-7` **Immediate reflection.** After a date-selected log, the card's in-period rate, calendar grid,
and arc update to reflect the log on its true date. If the chosen date falls **outside the current in-period
window**, the log correctly affects that earlier period's history/arc, not this week's rate — no double counting,
no "phantom today" tick (`PRIN-1` mirror-not-carrot: the mirror shows what actually happened, where it happened).

### 5.2 Copy (`FR-DESIGN`)

`FR-DESIGN-v21-1` All new strings use the Den "DON'T PANIC" voice (`FR-DESIGN-1`): supportive and non-punitive.
Suggested copy (final wording tunable): the control label "**Logged for {Today | Mon, Jul 7}** · change"; a
back-filled past log confirms plainly ("Logged for Mon, Jul 7") with **no** "you missed / you're behind" framing.
Reuse `FR-REC-2`'s conditional-year date formatting for the date label (show the year only when it differs from the
current year).

## 6. Non-functional requirements

`NFR-v21-DATA-1` **No migration; additive & default-tolerant** (`NFR-DATA-1`). No schema change — the `HabitLog.date`
column already exists and is written today. v2.0.0 logs remain valid; v2.1.0 changes only *how the date is chosen*.

`NFR-v21-A11Y-1` **Accessibility** (`NFR-A11Y-1`). The date control and picker are **TalkBack-labelled** (e.g.
"Log date, currently Today, double-tap to change"); the picker is keyboard/switch-navigable; touch targets meet the
baseline size. The date field must not become an icon-only control without a content description.

`NFR-v21-TEST-1` **Test coverage** (`NFR-TEST-1`). Unit tests assert: (a) the direct log lands on the **selected**
date, not `today`, when a date is passed; (b) the default remains today when none is chosen; (c) future dates are
rejected / clamped (`DEC-v21-2`); (d) the lower bound is the habit start (`DEC-v21-3`); (e) re-logging an existing
date **replaces** (frequency & quantitative), never appends (`DEC-v21-4`, `DM-HABIT-5a-v21`); (f) in-period rate/arc
math is correct when a log lands in a *prior* period (`FR-HAB-LOGDATE-7`). A Compose UI test drives the card →
picker → confirm flow and verifies the log's date. Verified through the headless build/install/screenshot loop
(`TECH-4`).

---

## 7. Out of scope for v2.1.0

| Item | Disposition |
|---|---|
| **Future-dated habit logs** | Excluded (`DEC-v21-2`) — a habit records what happened; logging ahead is meaningless and would corrupt the rate. |
| **Date picker on the task-driven log path** | Excluded (`DEC-v21-5`) — a task-marked-Done habit already logs on the task's own date; a second picker would contradict it. |
| **Bulk / multi-date logging** (log several days at once) | Deferred with multi-select/bulk-edit (v2.0.0 §10). One date per manual log. |
| **Editing the *date* of an already-written log** (move a log from one day to another) | Out of scope — the user un-logs the wrong date and logs the right one (two existing ops). A move gesture is a later convenience. |
| **Any streak / score / adherence surface** | **Never** (`DM-NOT`, `DEC-2/3/4`). This release must not add one. |

---

## 8. Acceptance criteria for "v2.1.0 is done"

v2.1.0 is complete when all of the following are true and verified:

1. From a Habit card's **manual** log action, the user can **confirm or change the date**, defaulting to **today**
   (`FR-HAB-LOGDATE-1/2`), for both frequency and quantitative habits.
2. The selectable range is **habit-start … today, inclusive**; **future dates are not selectable** (`DEC-v21-2/3`,
   `FR-HAB-LOGDATE-3`).
3. Logging done for a date writes/replaces exactly **one** `HabitLog` for that (habit, date), `source = DIRECT`,
   never appending or double-counting (`DM-HABIT-5a-v21`, `DEC-v21-4`).
4. The date-picker path and the tap-the-calendar-grid path produce **identical** results (`FR-HAB-LOGDATE-6`); the
   card's rate/grid/arc update on the log's **true** date (`FR-HAB-LOGDATE-7`).
5. The **task-driven** log path is unchanged — a task marked Done still logs the habit on the task's date
   (`DEC-v21-5`).
6. **Nowhere** does this feature add a streak, points, adherence %, or engagement metric (`DM-NOT`).
7. New copy uses the "DON'T PANIC" voice; the control and picker are TalkBack-accessible (`FR-DESIGN-v21-1`,
   `NFR-v21-A11Y-1`).
8. Unit + Compose tests (§6 `NFR-v21-TEST-1`) are green; the flow is verified on the emulator against the design
   via the headless loop (`TECH-4`).

# Part II — Roadmap

A single, small, vertically-sliced milestone on top of v2.0.0. It touches the habits slice only and ships an
installable build with its own tests, per the Tzafon cadence.

## M10 — Date-aware manual habit logging → **Tzafon 2.1.0**

- **Scope:**
  - **Repository/interface seam** — `HabitRepository.logDirect` already takes a `date`; expose a date argument up
    through `HabitsViewModel` (replace the `today`-hardcoding `logToday(...)` with a `logOn(habitId, date, done,
    amount)` that defaults `date` to today). Enforce the range clamp (`DEC-v21-2/3`) at the ViewModel/repo boundary
    so no future-dated or pre-start log can be written from any caller.
  - **UI** — add the pre-filled, editable **date control** to the Habit card's manual-log affordance and the
    quantitative **amount sheet** (`FR-HAB-LOGDATE-1..5`); wire the Material 3 date picker with `max = today`,
    `min = habit start`. Ensure grid-tap and picker share the seam (`FR-HAB-LOGDATE-6`).
  - **Copy & a11y** — Den-voice labels, conditional-year date formatting, TalkBack descriptions
    (`FR-DESIGN-v21-1`, `NFR-v21-A11Y-1`).
  - **Tests** — the `NFR-v21-TEST-1` unit matrix + a Compose flow test.
- **Depends on:** v2.0.0 M4 (Habits + the `HabitLog` ledger). No dependency on later milestones.
- **Value even alone:** honest back-filling of a missed-to-log day — the app stops forcing "today or nothing" on
  the primary log button.
- **Verify:** unit suite green; on the emulator, open a habit, change the date to yesterday, confirm, and see the
  log land on yesterday's grid cell (screenshot); confirm future dates are unselectable; confirm re-logging a date
  replaces rather than stacks; `logcat` clean.
