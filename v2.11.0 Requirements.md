## 1. Scope of v2.11.0

v2.11.0 is a **consistency / polish increment** on top of a shipped v2.10.0. Six source requests are groomed here — a mix of small UI reveals, one editor reorder, one export-format regression fix rooted in R8, one system-inset omission, one header inconsistency, and one navigation regression with an escalation the v2.5.0 fix did not cover. Two of the six (`FR-DATA-3`, `FR-NAV-11`) are genuine bugs the user hit *after* the prior release; the other four are refinements to reveals and consistency the user did not previously call out.

- **`FR-2026-07-27-a` → `FR-CUE-3`.** After `FR-CUE-2` (v2.10.0) allowed an `AT_TIME` cue to be saved with an empty `label`, the visible surface of a saved cue on the task-list row and on the editor's cue slot became misleading: `ui/components/TaskRow.kt:111` renders `CueChip(it.label)` — just the label — so a label-less `08:30` cue shows *nothing* on the row (empty chip → invisible), and the editor cue slot at `ui/editor/TaskEditorScreen.kt:224-235` renders `draft.cue?.label ?: "Anchor it to a routine — optional"` with no time either. The user's request is straightforward: the *time*, when set, must be visible without opening the cue edit sheet. `FR-CUE-3` extends both surfaces to render `label · time` when both are set, or just `time` when the label is empty (matching `NotifyLogic.cueLine` at `domain/notify/NotifyLogic.kt:38-46`, which already composes this shape for the notification body).
- **`FR-2026-07-27-b` → `FR-EDITOR-1`.** The current task editor field order is `title, description, cue, serves (habit + goal), dates, recurrence` (`ui/editor/TaskEditorScreen.kt:191-553`). The user wants `serves` above `cue`. The reframing behind the request is that a task's *alignment* — which goal or habit it serves — is a more identity-shaping decision than *when* the user will do it, so it should be chosen first; the cue is then set in context of a task the user already knows the purpose of. `FR-EDITOR-1` reorders the four editor sections between `description` and `dates` to `serves (habit + goals) → cue`, leaving all other slots (`title`, `description`, `dates`, `recurrence`, `delete`) in their current positions.
- **`FR-2026-07-27-c` → `FR-DATA-3` + refinement of `DM-EXPORT-1`.** The user reports the exported JSON's keys are `a, b, c, …` instead of the descriptive field names v2.8.0's `DM-EXPORT-1` promised ("Domain-typed by design — readable + lossless"). The root cause is R8: `android/app/build.gradle.kts:43-47` sets `isMinifyEnabled = true` on release, and `android/app/proguard-rules.pro:5-6` only keeps `data.db.*Entity` field names — the *domain* models (`domain.model.Task`, `Habit`, `Goal`, `Theme`, `Series`, `HabitLog`, `Review`, `Contribution` and their nested types like `Cue`, `Recurrence`, `Step`) that `DataExporter` (`data/transfer/DataExporter.kt:88-93`) actually serializes with Gson get minified to `a, b, c`. `FR-DATA-3` requires the ProGuard rules to keep domain-model field names verbatim so Gson serializes descriptive keys; the refinement of `DM-EXPORT-1` bumps `EXPORT_FORMAT_VERSION` from `1` to `2` and states the invariant explicitly. v1 backups (written by pre-fix releases) are handled per **[DECISION]** below.
- **`FR-2026-07-27-d` → `FR-DESIGN-5`.** The Settings view's scroll bottom is occluded by the Android system navigation buttons; the About view has a smaller but related concern. `ui/settings/SettingsScreen.kt:109-114` uses a fixed `.padding(bottom = 40.dp)` on the scrollable column with no `navigationBarsPadding()` — 40 dp is not enough on devices whose bottom system-inset is 48 dp (3-button nav on a 3.5-band phone) or larger (48 dp gesture bar plus 24 dp handle on some OEM ROMs); `ui/today/TodayScreen.kt:121-127` uses a hefty `.padding(bottom = 200.dp)` that swamps the inset by brute force. `FR-DESIGN-5` teaches Settings and About to apply `navigationBarsPadding()` (or equivalent `WindowInsets.systemBars` consumption) so bottom content is always visible and the system nav buttons are never overlaid on Tzafon chrome.
- **`FR-2026-07-27-e` → `FR-NAV-10`.** All Tasks routes its header hamburger differently from every other top-level view: `ui/alltasks/AllTasksScreen.kt:168` passes `right = { HeaderMenuButton(onClick = { menu = true }) }` to `RustHeader`, whereas Today, Habits, Directions, Backlog and Planning all pass `onMenu = { menu = true }`, letting `RustHeader` render the hamburger at its canonical top-end position (`ui/components/Headers.kt:108-112`). The two paths produce *nearly* the same pixel position but differ by ~2-12 dp because the `right` slot is placed by the header Row's horizontal-arrangement logic (`ui/components/Headers.kt:74-81`) while the `onMenu` path is absolute-positioned inside the header Box with fixed `statusBarsPadding().padding(top = 2.dp, end = 12.dp)`. `FR-NAV-10` requires All Tasks to route through the same `onMenu` slot as every other view so the hamburger sits in exactly the same pixel column.
- **`FR-2026-07-27-f` → `FR-NAV-11` (regression + escalation of `FR-NAV-9`).** `FR-NAV-9` (v2.5.0, `174507fce`) fixed the "reference-view leak" symptom where a reference view (`alltasks`, `backlog`) opened on top of a tab was stashed under that tab's `saveState` bucket and restored on the next tab tap. The user reports the same symptom is now visible again — and observes an escalation the original test did not cover: *repeated* lateral hops between `alltasks` and `backlog` (via `goRef`) accumulate an unbounded stack of alternating reference views above the entry tab, so a subsequent tab tap needs `2×` presses per lateral hop to reach the requested tab (per the user's example: Habits → All Tasks → Backlog, repeated `X` times, then tapping Habits `2X` times alternates between All Tasks and Backlog before finally landing on Habits). `FR-NAV-11` requires the invariant: **any tab tap lands on that tab's base destination, with no reference view above it**, regardless of how many lateral `alltasks ↔ backlog` hops occurred first; and reference-view hops must not accumulate on the stack in the first place.

None of the six is gamification-adjacent. A cue-reveal cell, an editor field reorder, a ProGuard keep-rule + format-version bump, a system-inset consumption, a header routing consolidation, and a navigation invariant. `DM-NOT` and `DEC-2/3/4` continue to hold. All other locked decisions from v2.0.0 — the five-tab primary structure (`FR-NAV-1`), the compass / chosen-direction thesis, local-first-with-clean-seam persistence, the Fox Works "Den" identity, the state-machine and recurrence model, and `PRIN-9` "never engagement-bait" — are untouched.

## 3. Functional requirements

### 3.1 Cue time is visible on the list row and the editor cue slot (`FR-CUE-3`)

*Source: `FR-2026-07-27-a`. Reveals the `Cue.time` field the user has already saved so they can glance at "when" without opening the cue edit sheet. Scope: the shared task row (`ui/components/TaskRow.kt`) and the task editor cue slot (`ui/editor/TaskEditorScreen.kt`). The `HabitEditorSheet` cue row is included by symmetry — the same shared display rule applies wherever a saved `Cue` is rendered.*

Today `Cue.time` is written and reminded on (`NotifyLogic.cueLine` at `domain/notify/NotifyLogic.kt:38-46` composes `"$label · $time"`, `label` alone if `time == null`, or `time` alone if `label` is empty), but the user-facing *display* surfaces only ever render `cue.label`:

- `ui/components/TaskRow.kt:111` — `task.cue?.let { CueChip(it.label) }` — the `CueChip` component receives the label string only.
- `ui/editor/TaskEditorScreen.kt:224-235` — the cue slot's primary line is `draft.cue?.label ?: "Anchor it to a routine — optional"`; the secondary line is `"${type.name} · A TRIGGER BEATS A CLOCK"` — nowhere is `time` shown.

With `FR-CUE-2` (v2.10.0) allowing `label = ""` on `AT_TIME`, a label-less `08:30` cue now renders as *nothing* on the list row (an empty `CueChip`) and as the placeholder text on the editor slot ("Anchor it to a routine — optional") — visually indistinguishable from a task with no cue at all. The user has to open the cue edit sheet to confirm the cue exists and what its time is; every glance elsewhere lies.

`FR-CUE-3` **on every surface that renders a saved `Cue`, the visible line reads `label · time` when both are set, `label` alone when the cue has no time (`AFTER_ROUTINE` / `AT_PLACE`), and `time` alone when the label is empty (`AT_TIME` post-`FR-CUE-2`). The rule matches `NotifyLogic.cueLine` verbatim so the on-row / on-slot text and the notification body always agree.**

- **`FR-CUE-3.1` A shared composer.** Extract `NotifyLogic.cueLine(cue: Cue): String` into a location visible from both `domain/notify/` (its current caller) and the UI layer (e.g. move it to `domain/model/Cue.kt` as `Cue.display(): String`, or expose a UI wrapper that delegates to it). The precise home is a small refactor — the requirement is that both notify body and UI row use the *same* function, so the two never drift. **[DECISION]** below prefers `Cue.display()` on the domain type.
- **`FR-CUE-3.2` `TaskRow` CueChip shows `Cue.display()`.** In `ui/components/TaskRow.kt:111`, replace `CueChip(it.label)` with `CueChip(it.display())` (or `CueChip(cueLine(it))` depending on the refactor from `FR-CUE-3.1`). Every list row that uses `TaskRow` (Today, Planning, All Tasks, Backlog) inherits the change in one place. If the resulting string is empty (which cannot happen after `FR-CUE-2` — either a time or a label is required), the chip is omitted; the existing `hasMeta` guard at `TaskRow.kt:102` continues to work correctly (`task.cue != null` is the trigger; the chip renders only if the cue is saved).
- **`FR-CUE-3.3` `TaskEditorScreen` cue slot primary line.** At `ui/editor/TaskEditorScreen.kt:225`, replace `draft.cue?.label ?: "Anchor it to a routine — optional"` with `draft.cue?.display() ?: "Anchor it to a routine — optional"`. The placeholder text ("Anchor it …") is unchanged for a null cue; the primary line now reads e.g. `"morning routine · 08:30"`, `"morning routine"`, or `"08:30"` depending on which fields the saved cue has.
- **`FR-CUE-3.4` `TaskEditorScreen` cue slot secondary line stays as-is.** The secondary line at `ui/editor/TaskEditorScreen.kt:229-235` (the mono-font `"${type.name} · A TRIGGER BEATS A CLOCK"` caption) already communicates the cue's *type*; keeping the primary line as `label · time` and the caption as `type` keeps the two visual axes orthogonal — primary line is user-authored, caption is the shape of the trigger.
- **`FR-CUE-3.5` `HabitEditorSheet` cue row inherits the same composer.** `ui/habits/HabitEditorSheet.kt` (per the M4 impl) uses a similar cue slot for habits (the cue row visible in the habit's Editor). Wherever it renders a saved `Cue.label`, it too moves to `Cue.display()`. The habit surface for cue reminders is the same as the task surface (`FR-NOTIF-1`), so the display rule must be identical.
- **`FR-CUE-3.6` The CueChip typography does not change.** `CueChip` continues to render at its current font / size / muted colour (`ui/components/Chip.kt` or wherever it lives); only the string content changes. The time segment inherits the same style — no separate font-family or weight — since the whole cue is a single conceptual glance.
- **`FR-CUE-3.7` RTL labels behave as they do today.** A cue with a Hebrew label like `"אחרי הקפה · 08:30"` is a single mixed-direction string; the existing `.contentDir()` text-direction resolution on the chip / label text (which resolves per first-strong character) already handles this — no wrapper change required.
- **`FR-CUE-3.8` No `DM-NOT` surface.** A visible cue string is descriptive, not evaluative; no score / streak / adherence / badge (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — `Cue.display()` on the domain type, not a UI helper.**
> Two homes were considered: (a) a `Cue.display(): String` extension / method on the domain type in `domain/model/Task.kt` (where `Cue` lives), or (b) a UI helper in `ui/components/CueDisplay.kt`. Choice (a) — the domain type — because the display rule is a property of the data (a `Cue` has a canonical human-readable form irrespective of whether it's shown in a notification, a list row, an editor slot, or exported JSON), and because `NotifyLogic.cueLine` is already downstream of the domain type. `Cue.display()` lets `NotifyLogic.cueLine` become a one-liner (`fun cueLine(cue: Cue) = cue.display()`) and lets any future caller (say, a widget or Wear surface) get the same string without re-inventing the rule.

> **[DECISION] — Empty label + empty time is not a defensive case.**
> `Cue.display()` on `Cue(type, label = "", time = null)` returns `""`. This shape is unreachable in practice — `FR-CUE-2.1` requires either a valid time (`AT_TIME`) or a non-blank label (`AFTER_ROUTINE`, `AT_PLACE`) to save. The composer returns `""` for this shape, and the `TaskRow`'s `hasMeta` guard already prevents a chip from rendering when there's nothing to show — no additional runtime check is needed.

**Acceptance criteria**

1. Save a task with `Cue(AT_TIME, label = "", time = "08:30")` (label-less time cue per `FR-CUE-2`) planned for today. On the Today row, the cue chip reads `08:30` (`FR-CUE-3.2`, `FR-CUE-3.3`). Open the task in the editor — the cue slot's primary line reads `08:30`.
2. Save a task with `Cue(AT_TIME, label = "morning routine", time = "08:30")`. Row chip and editor primary line read `morning routine · 08:30` (`FR-CUE-3.2`, `FR-CUE-3.3`).
3. Save a task with `Cue(AFTER_ROUTINE, label = "after the first coffee", time = null)`. Row chip and editor primary line read `after the first coffee` (unchanged from today; `FR-CUE-3.2`, `FR-CUE-3.3`).
4. Save a task with `Cue(AT_PLACE, label = "at the studio", time = null)`. Row chip and editor primary line read `at the studio`.
5. Same rule applies to the same task viewed on Planning, All Tasks, and Backlog rows — one shared change to `TaskRow.kt:111` covers all four (`FR-CUE-3.2`).
6. Save a Hebrew-labelled cue: `Cue(AFTER_ROUTINE, label = "אחרי הקפה", time = null)`. The row chip renders the Hebrew glyphs correctly (right-to-left per `.contentDir()`); no layout regression (`FR-CUE-3.7`).
7. Save a Hebrew-labelled AT_TIME cue: `Cue(AT_TIME, label = "אחרי הקפה", time = "08:30")`. The row chip reads `אחרי הקפה · 08:30` — the middle-dot glyph and the ASCII time render alongside the Hebrew label in the same string (`FR-CUE-3.7`).
8. `HabitEditorSheet` cue row shows the same composed string for a saved cue (`FR-CUE-3.5`).
9. The notification body composed by `NotifyLogic.cueLine` continues to match the on-row string exactly — after `FR-CUE-3.1`, both call `Cue.display()`. No regression to any existing notification test (`NFR-TEST-1`).
10. `DM-NOT` audit clean — no score / streak / badge surface added (`FR-CUE-3.8`).

**Out of scope for v2.11.0**

- **Rendering the cue *type* on the row.** The list row remains a single-line glance; the type (`AT_TIME`, `AFTER_ROUTINE`, `AT_PLACE`) is available on the editor slot's caption. Adding a type badge to the row would clutter the meta strip.
- **Time-format localization.** `Cue.time` is stored as `HH:mm` (24-hour) per `FR-CUE-1.4`; `Cue.display()` renders it verbatim. A future locale-aware `HH:mm` vs `h:mm a` toggle is not requested here.
- **A distinct visual for time-only cues.** The chip's colour / border stays the same for all cue variants; the *content* of the chip (`08:30` vs `after the first coffee`) is enough visual cue.

### 3.2 Task editor field order: `serves` before `cue` (`FR-EDITOR-1`)

*Source: `FR-2026-07-27-b`. Reorders four sections in the task editor so alignment (goal / habit) is chosen before the cue trigger. Scope: `ui/editor/TaskEditorScreen.kt` only. The habit editor's structure is untouched (habits already lead with their identity and cue is elsewhere).*

The current field order in the task editor (`ui/editor/TaskEditorScreen.kt:191-553`) is:

1. **Title** (`lines 191-198`)
2. **Description · optional** (`lines 200-208`)
3. **Cue — "When will you do this?"** (`lines 210-238`)
4. **Serves — habit link** (`lines 240-277`) and **Goal links** (`lines 279-318`), both under one `EdSection("Serves · alignment (optional)")` header at line 241
5. **Dates** (`lines 320-386`)
6. **Recurrence** (`lines 388-536`)
7. **Delete** (`lines 538-553`)

The user's requested order — `title, description, serves, cue, dates, recurrence` — moves the entire `Serves` block (habit + goal, one shared section header) above the `Cue` block, leaving all other blocks in place. The reframing behind the request is that "what this task is *for*" (its alignment to a goal or habit) is a more identity-shaping decision than "*when* I'll do it" (the trigger); once the user has chosen the alignment, the cue is set in context. Ordering the editor to reflect that mirrors how the user thinks about a new task.

`FR-EDITOR-1` **in `ui/editor/TaskEditorScreen.kt`, move the `Serves · alignment (optional)` section (its `EdSection` header + habit Row + goal Row, currently `lines 240-318`) to sit directly after `Description · optional` (currently ending at line 208) and directly before the `Cue` section (currently starting at line 210). The `Cue` section moves down accordingly. Every other section — `Title`, `Description`, `Dates`, `Recurrence`, `Delete` — is unchanged.**

- **`FR-EDITOR-1.1` The moved block is a contiguous unit.** The `EdSection("Serves · alignment (optional)")` header (line 241), the habit-link `Row` (lines 242-277), and the goal-link `Row` (lines 280-318) move together as one block. No internal reordering — habit stays above goal.
- **`FR-EDITOR-1.2` The `Cue` section's own contents are unchanged.** The `EdSection("When will you do this? · cue")` header (line 211) and its `Row` (lines 212-238) move as one block to sit after the moved `Serves` block. No change to the cue slot's styling, click target, or the `sheet = "cue"` binding.
- **`FR-EDITOR-1.3` The `Column`'s vertical spacing continues to derive from `EdSection` / block padding.** No hard-coded spacers between the moved blocks are added — the `EdSection` composable already handles inter-section spacing consistently, and the reorder should preserve today's spacing rhythm.
- **`FR-EDITOR-1.4` The scroll position is preserved across the reorder.** Opening an existing task should still scroll to top (or to the section the caller requests, e.g. from a "change status" affordance); no scroll behaviour depends on the previous absolute pixel order.
- **`FR-EDITOR-1.5` `HabitEditorSheet` is out of scope.** The habit editor's structure — name → cue → schedule → link (goal/theme) — is a different flow; the user's request is about the *task* editor.
- **`FR-EDITOR-1.6` The recurrence-scope banner (EditScope) placement is unchanged.** The scope-selector banner at the top of the editor (visible for a series occurrence, `TaskEditorScreen.kt:165-189`) sits above the `Title` field and stays there — the reorder is confined to the `Description → Cue → Serves` region.
- **`FR-EDITOR-1.7` No `DM-NOT` surface.** A layout reorder is orthogonal to gamification (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Move `Serves` above `Cue`; do not re-title either section.**
> A minor alternative was to also relabel `Serves` (e.g. "Direction · goal or habit") to make the semantic weight more explicit now that it's higher in the editor. Rejected because the existing label "Serves · alignment (optional)" is already clear, and re-wording it would be a separate change with no user request behind it. Keep the reorder minimal.

> **[DECISION] — Do not add an inline hint on `Cue` that says "set the alignment first".**
> The order itself is the guidance — the user encounters `Serves` before `Cue` in natural reading order, so a hint would be redundant and would nudge (`PRIN-9`). No added copy.

1. Open the task editor for a new task. The visible section order top-to-bottom is: `Title` → `Description · optional` → `Serves · alignment (optional)` (containing habit-link row then goal-link row) → `When will you do this? · cue` → `Dates` → `Recurrence` → (optional `Delete` for an existing task). (`FR-EDITOR-1.1`, `FR-EDITOR-1.2`)
2. Open the editor for an existing task with a habit link, a goal link, and an `AT_TIME` cue set. All fields render correctly in the new order — no missing rows, no doubled sections, no cropped chrome (`FR-EDITOR-1.3`).

4. For a series occurrence, the `EditScope` selector banner remains above the `Title` field, unmoved (`FR-EDITOR-1.6`).
5. `HabitEditorSheet` is visually unchanged (`FR-EDITOR-1.5`).
6. Scrolling from top to bottom of the editor is smooth; inter-section spacing is unchanged (`FR-EDITOR-1.3`).
7. `DM-NOT` audit clean (`FR-EDITOR-1.7`).

**Out of scope for v2.11.0**

- **Reordering any other section (`Dates`, `Recurrence`, `Delete`).**
- **Reordering the habit-link and goal-link rows within `Serves`.** The user's requested order names `serves` as a single unit; the internal habit/goal order stays as today (habit above goal).
- **Renaming any section header.** See DECISION.
- **A separate visual grouping** (e.g. a card enclosing `Serves`) — layout is refinement-only.

### 3.3 Export JSON keys are the descriptive domain field names — R8 minification cannot strip them (`FR-DATA-3`, refines `DM-EXPORT-1`)

*Source: `FR-2026-07-27-c`. Fixes a release-build regression: `DataExporter` serializes domain models with Gson, and R8 (enabled on release per `android/app/build.gradle.kts:43-47`) minifies the domain-model field names to `a, b, c, …` because `android/app/proguard-rules.pro:5-6` only keeps `data.db.*Entity` fields. The result: the exported JSON — which `DM-EXPORT-1` promised would be "domain-typed by design — readable + lossless" — currently reads as `{"a":"Clean desk","b":"OPEN","c":"2026-07-28",…}` on any release build. Scope: the ProGuard keep rules, the `EXPORT_FORMAT_VERSION` constant, the importer's v1 acceptance policy, and the export-format documentation.*

`DM-EXPORT-1` (v2.8.0) declared: "Domain-typed by design (the DECISION in v2.8.0 §1: readable + lossless via the domain shapes, not the flat Room rows)". `DataExporter` (`data/transfer/DataExporter.kt:88-93`) implements this by handing an `ExportDocument` to `GsonBuilder().setPrettyPrinting().create().toJson(…)`. Gson serializes each object by reflecting over its fields and writing `{ "<fieldName>": <value>, … }`. This works perfectly in debug builds where R8 is not active — the exported file has descriptive keys like `"title"`, `"toDoDate"`, `"state"`. On release builds (`isMinifyEnabled = true`), R8 renames every field on every class in `com.thefoxworks.tzafon.**` unless a keep rule protects it. `proguard-rules.pro:5-6` keeps `com.thefoxworks.tzafon.data.db.*Entity { <fields> }` — this protects the Firestore sync path (`M9b`), which serializes Room entities by field name — but the *export* path uses `domain.model.**`, which is not kept. R8 renames `Task.title → a`, `Task.description → b`, `Task.toDoDate → c`, …, in an order dependent on the current build's minification seed, and Gson dutifully writes those minified names to the exported JSON.

The user's observation ("keys are just `a, b, c, etc.`, possible to infer but not the goal") matches the R8 minification pattern exactly. The fix is one added ProGuard rule so field names survive minification.

`FR-DATA-3` **on release builds, the exported JSON's keys are the domain-model field names verbatim (`title`, `description`, `toDoDate`, `state`, `cue`, `label`, `time`, `type`, …). > **[DECISION] — ProGuard keep rules, not `@SerializedName` per field.**

Reasoning: an auto-attempt-and-count heuristic (option a) can silently drop fields even when it "succeeds" (nulls under the threshold), and gives the user a false sense of a clean restore. The version-gate is explicit — the user makes an informed decision, and if they proceed and see missing tasks, they know why. If v1 acceptance turns out to be a heavier support burden than expected, we can flip to auto-reject in a later minor.

### 3.6 Tab tap always lands on the tab's base — reference-view leak eliminated, lateral hops don't accumulate (`FR-NAV-11`, regression + escalation of `FR-NAV-9`)

*Source: `FR-2026-07-27-f`. The v2.5.0 `FR-NAV-9` fix (commit `174507fce`) addressed the reference-view leak — a reference view (`alltasks`, `backlog`) opened on top of a tab was stashed under that tab's `saveState` bucket and restored on the next tab tap. The user reports the same symptom is visible again *and* observes a new escalation: repeated lateral hops between `alltasks` and `backlog` accumulate on the stack so a subsequent tab tap needs `2×` presses per hop before it actually reaches the requested tab. Scope: `ui/nav/` (or the navigation setup wherever it lives — currently `MainActivity.kt:165-187`), the `goTab` and `goRef` functions, the `REFERENCE_ROUTES` set, and any test that pins the invariant. This is a regression + escalation; it must not resurface again.*

Current state (`MainActivity.kt:165-187`):

```kotlin
fun goTab(tab: Tab) {
    if (isReferenceView(nav.currentBackStackEntry?.destination?.route)) {
        nav.popBackStack()
    }
    nav.navigate(tab.route) {
        popUpTo(Tab.TODAY.route) { saveState = true }
        launchSingleTop = true
        restoreState = true
    }
}

fun goRef(route: String) {
    nav.navigate(route) { launchSingleTop = true }
}
```

Two failure modes are visible in the user's scenario:

- **Regression of the original leak.** `FR-NAV-9`'s fix pops *the current top* if it's a reference view, then does the standard `popUpTo(TODAY){saveState=true}` + `restoreState=true` tab switch. This works for the simple case (Today → Backlog → Today) but not when the reference view is *not* the current top — e.g. if some code path calls `nav.navigate(...)` without going through `goTab`/`goRef`, or if the standard tab switch's `restoreState = true` restores a saved back-stack that itself contains a reference view above the tab base. The `saveState = true` on `popUpTo(TODAY)` is exactly the mechanism that stashes a tab-with-reference-view-on-top under the tab's key; on a later restoreState, that back-stack (including the reference view) is restored, and the reference view is *now the top*. The user's report indicates this is happening again in some sequence — the exact triggering sequence is not in the report, so the fix has to guard against *all* ways a reference view can end up in a tab's saveState bucket, not just the one the v2.5.0 test pinned.
- **Escalation — lateral hops accumulate.** `goRef` uses `nav.navigate(route) { launchSingleTop = true }`. `launchSingleTop` only prevents duplicating *the same route* on top of itself; it does not merge different routes. So the sequence `goRef("alltasks") → goRef("backlog") → goRef("alltasks") → goRef("backlog") → …` pushes each hop as a new stack entry, growing the stack: `[tab, alltasks, backlog, alltasks, backlog, …]`. On a tab tap, `goTab` pops one reference view (`alltasks` or `backlog`, whichever is on top) then does the tab switch. But if the `popUpTo(TODAY){saveState=true}` machinery stashes the intermediate stack under the entry tab's key, then `restoreState = true` on the target tab may restore a stack containing the residue of the lateral hops — the escalation the user observes ("press Habits `2X` times, each time alternating between All Tasks and Backlog"). The `2X` factor matches the `X` alternations exactly.

`FR-NAV-11` **regardless of any prior sequence of tab taps and reference-view hops, a single tap on any tab lands the user on that tab's *base destination* with no reference view on top. Reference-view hops (`alltasks ↔ backlog`) do not accumulate on the back-stack — each `goRef` call leaves *at most one* reference view above the entry tab.**

The requirement pins the invariant; the implementation may choose between three approaches (or a mix), described in the `[DECISION]` below.

- **`FR-NAV-11.1` `goTab` pops *every* reference view above the target tab, not just the current top.** The pre-navigate pop guard becomes a loop: while the current top is a reference view, pop it; then run the standard `popUpTo(TODAY){saveState=true} + restoreState=true` switch. This handles the accumulation case even without changing `goRef`.
  ```kotlin
  fun goTab(tab: Tab) {
      while (isReferenceView(nav.currentBackStackEntry?.destination?.route)) {
          nav.popBackStack()
      }
      nav.navigate(tab.route) {
          popUpTo(Tab.TODAY.route) { saveState = true }
          launchSingleTop = true
          restoreState = true
      }
  }
  ```
- **`FR-NAV-11.2` `goRef` collapses on top of the entry tab, not on top of another reference view.** Change `goRef` so a reference view is opened *on top of the current tab's base*, not on top of another reference view. Concretely: `nav.navigate(route) { popUpTo(<current-tab-route>) { inclusive = false; saveState = false }; launchSingleTop = true }`, where `<current-tab-route>` is the nearest tab in the stack (walk `nav.currentBackStack` up from the top). This means `Habits → goRef(alltasks) → goRef(backlog)` leaves the stack as `[Habits, backlog]` — not `[Habits, alltasks, backlog]`. Repeated lateral hops replace each other; `goTab(Habits)` then only has to pop `backlog` (`FR-NAV-11.1`'s loop still applies as a defence-in-depth, but now there's only ever one reference view to pop).
- **`FR-NAV-11.3` No reference view is ever included in a tab's `saveState` bucket.** The stash-and-restore behaviour of `popUpTo(TODAY){saveState=true} + restoreState=true` on the tab switch is the *source* of the resurfacing leak. If `goRef` collapses to the current tab (`FR-NAV-11.2`), the reference view is always the current top when a tab tap happens, so `goTab`'s pop guard (`FR-NAV-11.1`) removes it *before* the `popUpTo`/`saveState` machinery saves the tab's stack — the saved bucket contains only the tab's base + genuine within-tab state (scroll, expanded rows), never a reference view.
- **`FR-NAV-11.4` The invariant is unit-tested and the test pins the escalation case.** Extend `NavReferenceLeakTest` (added by v2.5.0's `FR-NAV-9`, per commit `174507f`) with a new test case covering the lateral-hop escalation: seed the nav with a `[Today, Habits]` stack, run `goRef("alltasks")`, `goRef("backlog")`, `goRef("alltasks")`, `goRef("backlog")` in sequence, then `goTab(Habits)` — assert that after that single tab tap, the current destination is `Habits` and no reference view is above it. The existing v2.5.0 assertions (single-hop leak) continue to pass.
- **`FR-NAV-11.5` A temporary `Log.d(TAG, ...)` breadcrumb pins the fix on the emulator.** Per the build/verify loop's guidance ("For nav/back-stack questions, a temporary `Log.d` read back via `adb logcat -d -s <TAG>` — over another screenshot"), add a short-lived log line inside `goTab` that dumps `nav.currentBackStack.map { it.destination.route }` before and after the switch; run the emulator through the sequence in `FR-NAV-11.4`; confirm the "after" list is `[Today, Habits]` (or the equivalent tab's own base) with no reference view. Remove the log line before the milestone commit — it exists only for the emulator verify.
- **`FR-NAV-11.6` `REFERENCE_ROUTES` remains authoritative.** The set at `MainActivity.kt:107` (`setOf("alltasks", "backlog")`) is unchanged — it enumerates every route that is a "reference view opened on top of a tab, not a tab in its own right". If a future refinement adds a third such view, extend the set and both `goTab`'s loop (`FR-NAV-11.1`) and `goRef`'s pop target (`FR-NAV-11.2`) auto-adapt.
- **`FR-NAV-11.7` Genuine within-tab state is preserved.** `FR-NAV-9.2` (v2.5.0) required that after the fix, "the normal save/restore switch preserves genuine within-tab state (scroll, expanded rows)". This continues to hold — the `popUpTo(TODAY){saveState=true} + restoreState=true` machinery is unchanged; only what it *sees* on the stack changes (no reference view residue).
- **`FR-NAV-11.8` The lateral-hop UX (All Tasks ↔ Backlog) still works.** From either reference view, tapping the other one in navigation continues to switch to it (`goRef` from within a reference view — the pop-to-current-tab logic in `FR-NAV-11.2` still needs to work when the "current tab" is walked up past the current reference view). Concretely: if the stack is `[Today, Habits, alltasks]` and `goRef("backlog")` is called from All Tasks, the desired end state is `[Today, Habits, backlog]` — walk up until finding a non-reference destination (`Habits`), popUpTo that, then push `backlog`.
- **`FR-NAV-11.9` The Android system back button is unchanged in intent.** From `[Today, Habits, backlog]`, system back pops backlog and leaves the user on `Habits` (as today). This is the standard `NavController` back behaviour; nothing in `FR-NAV-11` changes it.
- **`FR-NAV-11.10` No `DM-NOT` surface.** A navigation invariant fix is orthogonal to gamification (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Apply all three approaches (`FR-NAV-11.1`, `.2`, `.3`) together, defence-in-depth.**
> Each alone is nearly enough; together they form belt-and-braces. `FR-NAV-11.1` (the pop-loop in `goTab`) catches accumulated reference views regardless of how they got there — a safety net for future callers that navigate outside the `goRef` helper. `FR-NAV-11.2` (the collapse-on-tab in `goRef`) prevents accumulation at the source, so lateral hops don't grow the stack in the first place. `FR-NAV-11.3` (no reference view in `saveState` buckets) is a consequence of the first two — with those in place, the `popUpTo(TODAY){saveState=true}` machinery cannot see a reference view when it snapshots. The three are cheap and complementary. The original v2.5.0 fix picked only the single-top variant of `FR-NAV-11.1`; the resurgence shows that was not enough.

> **[DECISION] — Do not change the reference views' *placement* in the nav graph.**
> An alternative structural fix was to move `alltasks` and `backlog` into a *separate* NavHost or a distinct graph layer that never mixes with the tab back-stack. Rejected as overkill — the current single-graph shape with `REFERENCE_ROUTES` semantics is fine; the bug is in the navigation-call flags, not the graph. Changing the graph structure would ripple through every `nav.navigate("alltasks")` and `nav.navigate("backlog")` call site.

> **[DECISION] — Do not test on-device via screenshots; use `adb logcat` for the back-stack assertion.**
> Screenshots would show which view is visible after a tab tap, but the invariant is about the *stack shape*, not the visible frame. `Log.d(TAG, nav.currentBackStack.map { it.destination.route }.toString())` gives a precise, deterministic assertion that a screenshot can only approximate. This aligns with the CLAUDE.md guidance ("For nav/back-stack questions, a temporary `Log.d` read back via `adb logcat -d -s <TAG>` — over another screenshot").
