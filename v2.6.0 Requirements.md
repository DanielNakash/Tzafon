## 1. Scope of v2.6.0

v2.6.0 is a **focused increment** on top of a shipped v2.5.0. Four source requests. Three are pure UI/behaviour refinements on existing surfaces (Planning, Habits, Backlog) with no schema change; the fourth introduces a device-local user preference (`SettingsStore.palette`) and refactors the `Den` colour object into a swappable palette so the reader can choose an alternate accent base. All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), the ≤3 active themes cap (`DM-THEME-3`), the compass / chosen-direction thesis, and — importantly for `FR-DESIGN-4` — the **Fox Works "Den" identity as the default** (`FR-DESIGN-1`).

The four requirements:

- **`FR-PLAN-5`** removes visual noise from Planning's overdue list. Today, `ActionLogic.planningGroups` (`domain/action/ActionLogic.kt:88-103`) puts every Open task with `toDoDate < today` into the `overdue` bucket, without regard to whether the task belongs to a recurring series that has *already generated the next occurrence*. A user who ran a "clean desk" habit every 2 days and left Sunday's instance open sees, on Tuesday, **both** Sunday's slipped `DecideCard` and Tuesday's live task in Planning — the older one is stale noise that adds a decision cost (`FR-PLAN-3`'s calm-decision framing) without informing today's choice. `FR-PLAN-5` **hides a slipped recurring occurrence from Planning's overdue list when the same series has an occurrence dated today**, so the user only sees today's live instance and the older-and-moot one drops out of the visible decision surface. The hidden occurrence is not deleted, not auto-Skipped, and not auto-Done — it remains Open and remains visible in All Tasks and in the editor (`FR-ALL-*`, `FR-TODAY-*` semantics unchanged). Refines `FR-PLAN-3` (overdue as a calm decision panel), `FR-PLAN-4` (the trimmed action-set + tappable checkbox from v2.4.0), and holds `FR-REC-*` (series generation is untouched).
- **`FR-HAB-9`** closes an un-log gap the v2.4.0 "Log a date…" work opened up. `FR-HAB-8.3` established that on the picker route "a second tap on an already-done day un-logs it" and the collapsed / expanded-row "Mark today done" pill already toggles for frequency habits (`HabitsScreen.kt:112` — `vm.logToday(habitId, done = !loggedToday)`). But two gaps remain: (a) **quantitative habits have no un-log path anywhere** — the `AmountSheet` write path in `HabitsViewModel.logToday(...)` and `.logForDate(...)` only writes `done = true` with an amount, so a quantitative habit mistakenly logged for today can be edited (a second amount write overwrites the first) but not cleared; and (b) **the toggle-back paths that do exist are silent** — the "Mark today done" pill re-labels but does not announce "Un-mark today", and the picker's second-tap semantics from `FR-HAB-8.3` are not discoverable unless the user experiments. The reporter's exact phrasing ("Currently, once a day is logged, it cannot be unlogged") is accurate for the quantitative case and effectively true for the discoverability case. `FR-HAB-9` **exposes an explicit "un-log" affordance on every log surface**: today's pill re-labels to "Un-mark today" when today is logged (frequency), a dedicated "Clear this log" row appears in the amount sheet when reopened on an already-logged day (quantitative), and the picker's second-tap toggle-back is announced. Refines `FR-HAB-4`, `FR-HAB-5`, `FR-HAB-7`, `FR-HAB-8`; realises `DM-HABIT-5` (logged two ways — direct edit "on any date" — in the un-log direction too).
- **`FR-DESIGN-4`** (+ `DM-PREF-1`, `FR-SET-4`) adds a **user-choosable colour palette** to the Settings view, defaulting to the current Fox Works Den palette. Alternates are `Blue`, `Green`, `Magenta`, and `Teal`, each a full palette (background, surface, ink, muted, accents, state tokens, and the three theme-accent slots), not just a hue-swap on the rust accent. The core mechanic is a refactor of `ui/theme/Den.kt`'s `Den` `object` into a `Palette` data class + `LocalPalette` `staticCompositionLocalOf` so every colour access resolves through a composition local; the current Den values become the `denPalette` default. The four alternates are curated at design time (not user-authored) so contrast and the "Den" identity translation into each hue are preserved. The picker is a `PaletteSheet` opened from Settings and persisted in `SettingsStore.palette` (default `"den"`). Refines `FR-DESIGN-1` (Fox Works Den identity — the identity translates *across* palettes; the default is Den), `FR-DESIGN-2` (adjacent DesignSystem work), and adds `FR-SET-4` under the Settings area. Introduces one persisted preference `DM-PREF-1` (`palette: String`, default `"den"`).
- **`FR-DESIGN-3.5`** (a numbered refinement of `FR-DESIGN-3`) applies the content-direction rule from v2.1.0 to the Backlog view's task list, closing a v2.1.0 gap. `FR-DESIGN-3` requires that user-authored strings render right-to-left when the first strong character is RTL — task titles, habit names, goal titles, and so on. The Backlog view uses its own `BacklogRow` composable (`ui/backlog/BacklogScreen.kt:213-265`) rather than the shared `TaskRow`, and that composable's `Text(task.title, ...)` does not apply the `contentDir()` extension the rest of the app uses. A Hebrew-titled Backlog task therefore renders left-to-right on the Backlog list only — inconsistent with Today, Planning, All Tasks, and the editor. `FR-DESIGN-3.5` **applies `contentDir()` to the title `Text` in `BacklogRow`** so the Backlog list conforms to `FR-DESIGN-3`'s content-driven direction rule. Two-line change; no schema impact.

None of the four is gamification-adjacent — one is a filter refinement on an existing list, one is a symmetric un-log addition on existing log paths, one is a colour-palette preference (no scoring, no reward, no badge — pure aesthetics), and one is a two-line RTL rendering fix. `DM-NOT` and `DEC-2/3/4` continue to hold across all four.

## 2. Functional requirements

### 2.1 Hide slipped recurring occurrence when the next occurrence is today (`FR-PLAN-5`, refines `FR-PLAN-3` and `FR-PLAN-4`)

*Source: `FR-2026-07-13-a`. Refines `FR-PLAN-3` (overdue-as-calm-decision) and `FR-PLAN-4` (the trimmed action-set + tappable checkbox from v2.4.0). Holds `FR-REC-*` (series generation is untouched). Holds `FR-ALL-*` and `FR-TODAY-*` (the hidden task remains where it lives in those surfaces).*

Planning's overdue bucket is computed in `ActionLogic.planningGroups` (`android/app/src/main/kotlin/com/thefoxworks/tzafon/domain/action/ActionLogic.kt`, roughly `lines 88-103`) as:

```
val overdue = open.filter { (it.toDoDate ?: "") < today && it.toDoDate != null }
    .sortedBy { it.toDoDate }
```

The filter is state- and date-driven: any Open task whose `toDoDate < today` is overdue. That rule is right for one-off tasks — a slipped one-off is a genuine decision the user must make. But for a recurring task where the series has already generated an occurrence dated today (per `services/series.js` / the Kotlin recurrence engine), the older occurrence is a duplicate of the same intention: two "clean desk" cards in the same view, one dated Sunday (slipped) and one dated Tuesday (today's), competes for the user's attention on Tuesday morning when the honest answer is "today's card is what I should look at; Sunday is water under the bridge."

`FR-PLAN-5` **A task with `seriesId != null` and `toDoDate < today` is excluded from Planning's overdue list when the same series (`seriesId`) has any occurrence with `toDoDate == today` — regardless of that today-dated occurrence's state (Open, Done, or Skipped).** The hidden task is not modified: it remains `TaskState.OPEN`, its `toDoDate` and links are unchanged, and it continues to appear in All Tasks (`FR-ALL-1`) and in the editor when opened directly. Only Planning's overdue rendering changes.

- **`FR-PLAN-5.1` Hide is scoped to Planning's overdue bucket only.** The `dated` and `inbox` buckets from `ActionLogic.PlanningGroups` are not affected — a slipped recurring task cannot appear in `dated` (that bucket is `toDoDate ∈ [today, rangeEnd]`) or in `inbox` (`toDoDate == null`), so the exclusion is a pure `overdue`-side rule. All Tasks continues to show every Open task per `FR-ALL-1`; Today continues to show only `toDoDate == today` per `FR-TODAY-1`, and a slipped Open task is not on Today by definition. No other surface is touched.
- **`FR-PLAN-5.2` The rule is same-series only.** Two independent recurring tasks with different `seriesId`s that happen to have overlapping `toDoDate`s do not affect each other. The exclusion is a per-`seriesId` check.
- **`FR-PLAN-5.3` The rule triggers on today-dated existence, not today-dated open-ness.** If today's occurrence is Done or Skipped by the time Planning renders, the slipped older occurrence is *still* hidden — the current cycle has already been addressed and re-surfacing the older instance would ask the user to decide twice about the same intention. If today's occurrence has not been generated yet (a series where the next scheduled date is tomorrow or later), the slipped one **remains visible** — the user still needs to decide what to do with it.
- **`FR-PLAN-5.4` The rule is date-relative and re-evaluated each render.** As `today` advances, the exclusion decision re-evaluates: Monday's slipped Sunday instance was visible on Monday (no today-dated instance existed then); on Tuesday it disappears (Tuesday's instance was generated); if Tuesday's instance itself slips into Wednesday without an intervening user action, on Wednesday the *older* slipped one may re-appear or continue to hide depending on whether Wednesday's instance was generated. The rule is a per-render filter, not a persisted flag on the task.
- **`FR-PLAN-5.5` Multiple older slipped occurrences of the same series are handled as a set.** A pathological case — three consecutive slipped occurrences of a daily series (Sunday, Monday, Tuesday) with a Wednesday-today occurrence — hides *all three* older slipped instances by the same rule (each of them has a same-series today-dated occurrence). The Planning overdue bucket does not become a growing archive of slipped recurrences; the today-dated occurrence is the single point of decision for the current cycle.
- **`FR-PLAN-5.6` One-off (non-recurring) overdue tasks are untouched.** A task with `seriesId == null` never has a "same series next occurrence"; the exclusion filter cannot match. Every one-off overdue task continues to appear in Planning's overdue list per `FR-PLAN-3` / `FR-PLAN-4`.
- **`FR-PLAN-5.7` The overdue count and header copy update accordingly.** The `count = state.overdue.size` line in `PlanningScreen.kt` (roughly `line 141`) uses the filtered `overdue` list, so the "N overdue" copy at the top of the overdue section reflects the visible count. If every slipped occurrence has been hidden by this rule, the entire overdue section (header + card) is not rendered — consistent with the current empty-overdue behaviour.
- **`FR-PLAN-5.8` Slippage-nudge dismissal semantics are unchanged.** `FR-TODAY-5`'s slippage nudge on Today reads from the overdue set to compute its badge; that nudge continues to use whatever the current v2.5.0 rule uses (which reads open Open tasks with `toDoDate < today` from the repository, not through `ActionLogic.planningGroups`). This requirement does not alter the Today nudge. **[DECISION]** below explains why the exclusion is applied at `planningGroups` rather than in the repository query.

> **[DECISION] — Filter at `ActionLogic.planningGroups`, not at the repository.**
> An alternative was to apply the exclusion at the `TaskRepository` level so any surface reading "overdue tasks" would inherit it. But the exclusion is a **Planning-view rendering rule**, not a domain-level state change: the slipped occurrence is still Open, still valid, and other surfaces (All Tasks, the editor, potentially the Today slippage nudge from `FR-TODAY-5`) legitimately want to see it. Locating the filter in `ActionLogic.planningGroups` — the function that already owns the Planning view's grouping logic — keeps the change surgical and the domain object un-mutated. `Task` gains no new field; `TaskRepository` gains no new query.

> **[DECISION] — Today-dated existence triggers the hide, in every state.**
> An alternative rule was "hide the older slipped instance only if today's is Open" — leaving it visible if today's has been Done or Skipped. But that would resurrect the slipped instance the moment the user finishes today's work — the reward for handling today's card would be that Sunday's slipped card *appears* underneath it, which is the opposite of the calm-decision framing (`FR-PLAN-3`). The chosen rule ("today-dated existence is enough") means the user's completion of today's instance closes the current cycle without a new decision cost.

> **[DECISION] — Hide, don't auto-Skip.**
> An alternative was to auto-transition slipped recurring occurrences to `TaskState.SKIPPED` (a legal state per `DM-TASK-1`) once the next occurrence is generated. That would give the hidden instance a durable state and remove it from Open-filtered queries app-wide. But it would also silently change history — a user reviewing All Tasks for their Sunday activity would see the "clean desk" instance auto-Skipped and might rightly ask "when did the app decide that?" The requirement chooses the lighter rendering-only fix; state transitions remain user-authored. If a later increment adds a "auto-close stale slipped recurrences" preference to Settings, it can be built on top of this rendering rule.

**Acceptance criteria**

1. On the emulator, seed a recurring task "clean desk" with `Rule.everyNDays(2)` from Sunday 2026-07-12; generate occurrences through Tuesday 2026-07-14. Leave Sunday's Open. Advance system date to Tuesday. Open Planning: **Sunday's slipped instance does not appear** in the overdue list. **Tuesday's instance appears** in the "Today" `dated` group.
2. Same seed, but on Tuesday's render, mark Tuesday's instance Done and re-open Planning. Sunday's slipped instance **still does not appear** — the current cycle has been closed.
3. Same seed, but skip generation of Tuesday's instance (simulate a series where generation lagged). On Tuesday, Sunday's slipped instance **does appear** in the overdue list — the exclusion condition (a today-dated same-series occurrence) is not met.
4. A one-off Open task (no `seriesId`) with `toDoDate < today` continues to appear in Planning's overdue list unchanged (`FR-PLAN-5.6`).
5. Two independent recurring tasks with overlapping slipped occurrences do not affect each other — each series is evaluated on its own (`FR-PLAN-5.2`).
6. A daily series with three consecutive slipped occurrences (Sun / Mon / Tue) plus a today-dated (Wed) occurrence hides all three older slipped instances from Planning's overdue list (`FR-PLAN-5.5`).
7. All hidden tasks remain visible in All Tasks and are openable in the editor from All Tasks. Their `state`, `toDoDate`, and links are unchanged relative to before render (`FR-PLAN-5.1`).
8. The overdue-section header count matches the visible list length. If all slipped occurrences are hidden by this rule and no one-off overdue exists, the overdue section (header + card) is not rendered (`FR-PLAN-5.7`).
9. Today's slippage nudge (`FR-TODAY-5`) and its dismissal semantics are unchanged. The nudge continues to fire based on the pre-existing slippage-count rule.
10. Recurring-series generation (`FR-REC`) is unchanged — no series-generation code path is touched by this fix. Occurrence ids remain `{seriesId}__{occurrenceDate}` per the deterministic-id rule from v1.1.0.
11. No streak / points / badges / adherence surface appears anywhere as a side effect of the fix (`DM-NOT`).
12. `PlanningViewModel` continues to expose `state.overdue` as a `List<Task>`; no new state field is added. TalkBack announcements on the overdue rows are unchanged.

**Out of scope for v2.6.0**

- **Auto-transitioning slipped recurring occurrences to `Skipped` when the next is generated** — see the second `[DECISION]` above. If a later increment adds an "auto-close stale slipped recurrences" preference, it lives on top of this rendering rule.
- **Extending the exclusion to "any same-series occurrence in the visible planning range, not just today's"** — the reporter's phrasing is specifically "if the next recurrence is today." A broader rule ("hide slipped if any future occurrence exists in the range") is a follow-on request if the tighter rule proves too conservative in practice.
- **Auto-hiding slipped recurring occurrences from All Tasks** — All Tasks is the exhaustive-view surface (`FR-ALL-1`); hiding tasks there would violate that contract.
- **A per-user preference to disable this hiding rule.** The rule is the whole point of the fix; a preference to opt out would recreate the friction that motivated the request.
- **Any change to `ActionLogic.slippedDays` or the "SLIPPED Nd AGO" meta line** — those apply only to overdue tasks that *are* rendered, and the rendering itself is not changed by this fix.

### 2.2 Explicit un-log affordance on every habit log surface (`FR-HAB-9`, refines `FR-HAB-4`, `FR-HAB-5`, `FR-HAB-7`, `FR-HAB-8`)

*Source: `FR-2026-07-13-b`. Refines `FR-HAB-4` (logged two ways), `FR-HAB-5` (collapsed-row scan-first log pill), `FR-HAB-7` (expanded-row three-target layout — log / edit / log-a-date), and `FR-HAB-8` (log-a-date picker from v2.4.0). Realises `DM-HABIT-5` — "logged … via a linked Task marked Done … or edited directly on any date" — in the un-log direction too.*

The reporter's phrasing — "Currently, once a day is logged, it cannot be unlogged" — is accurate for the case that hurts most (quantitative habits: `AmountSheet` only writes `done = true`, no cleared-log path) and effectively true for the frequency case (the toggle-back exists on the today pill and on the picker per `FR-HAB-8.3` but is not discoverable — the label does not change to "un-mark", the picker's second-tap semantics are undocumented).

`FR-HAB-9` **Every habit log surface exposes an explicit un-log path with a distinct label and TalkBack announcement.** For frequency habits, the collapsed-row and expanded-row today pill re-labels to "Un-mark today" when today is already logged. For quantitative habits, the `AmountSheet`, when reopened on an already-logged date, exposes a **"Clear this log"** row that writes an unlog (`logDirect(id, date, done = false, amount = null)`). For both kinds, the "Log a date…" picker's second-tap toggle-back rule from `FR-HAB-8.3` gains an explicit visual/TalkBack signal on already-logged days ("Tap to un-log 2026-07-12"). The un-log write path is a single call — `HabitRepository.logDirect(habitId, date, done = false, amount = null)` — which is already the API in `domain/model/Habit.kt:53`; no new repository method is required.

- **`FR-HAB-9.1` Today pill labels flip on the loggedToday state.** The today pill on the collapsed row (`FR-HAB-5`) and expanded row (`FR-HAB-7`) reads **"Mark today done"** when `loggedToday == false` and **"Un-mark today"** when `loggedToday == true`. The tap behaviour matches: on the "Mark" state, tap logs today (via the existing `vm.logToday(id, done = true)` path — for quantitative habits, still routes through `AmountSheet` per `FR-HAB-4`); on the "Un-mark" state, tap un-logs today. For quantitative habits, tapping "Un-mark today" clears today's log directly — it does **not** re-open `AmountSheet` to ask for an amount, because there is no amount to enter on an un-log. TalkBack reads the current label verbatim ("Mark today done" / "Un-mark today") plus the habit's name.
- **`FR-HAB-9.2` Quantitative `AmountSheet` gains a "Clear this log" row on re-open.** When `AmountSheet` is opened for a quantitative habit on a date that already has a logged entry (any of: the "Mark today done" flow on an already-logged today, the "Log a date…" picker's second tap on an already-logged past day, or the collapsed-row tap for a habit where `loggedToday == true`), the sheet renders a **"Clear this log"** action row alongside the existing amount confirmation button. Tapping it writes `logDirect(id, date, done = false, amount = null)` and dismisses the sheet without saving an amount. The row is visually secondary (text-only button style, `Den.due` colour to signal a destructive-ish action) so it does not compete visually with the primary "Log ___" confirm button. TalkBack reads "Clear this log for {date}".
- **`FR-HAB-9.3` Picker second-tap semantics gain a visible signal on already-logged days.** The `CalendarPicker` used by the "Log a date…" flow (`FR-HAB-8.2`) already renders logged days with a filled-in marker (per `FR-HAB-1`'s calendar-style history rendering). On an already-logged day, tapping the day still triggers the `FR-HAB-8.3` un-log path for frequency habits (unchanged: `logForDate(id, pickedDate, done = false)`) and now, for quantitative habits, opens `AmountSheet` with the "Clear this log" row surfaced (per `FR-HAB-9.2`). The picker announces to TalkBack "Tap to un-log ${date}" on the already-logged days, distinguishing them from unlogged days ("Tap to log ${date}"). The confirmation copy also changes: after un-logging a picker-picked date, the toast / snackbar (if any exists in v2.5.0) or the sheet-close announcement reads "Un-logged for ${date}" (a positive framing — not an error, not a rebuke).
- **`FR-HAB-9.4` The un-log is a single write, and it clears the same fields the log wrote.** `logDirect(id, date, done = false, amount = null)` removes the habit's `history` entry for the given date (or sets it to a not-done marker, per the current repository semantics) and, if the habit is linked to a Goal (`DM-HABIT-5` / `DM-GOAL-3`), rolls back the `DM-ATTR-2` contribution row for that date atomically. There is no partial un-log — you cannot un-log the goal contribution but leave the habit history entry, or vice versa. The `RoomHabitRepository.logDirect` implementation already handles both directions of the toggle (see `data/repo/RoomHabitRepository.kt`); the change here is that the UI now reliably reaches the `done = false` branch on every surface.
- **`FR-HAB-9.5` The recurrence-driven task path is unaffected.** A quantitative habit logged indirectly via a linked recurring task marked Done (`FR-HAB-4`) is not touched by `FR-HAB-9` — un-logging via that path is a task-state operation (mark the task not-Done), which already exists via the task checkbox / editor. `FR-HAB-9` is specifically about the direct-log paths (today pill, picker, amount sheet re-open); it does not add a "un-log from the linked task" affordance.
- **`FR-HAB-9.6` No un-log confirmation dialog.** The un-log is a single tap on any of the three surfaces — no "are you sure?" prompt. `DM-HABIT-5` frames habit logging as low-friction and reversible; a confirmation would violate the friction floor and read as a rebuke. Users who un-log by mistake can re-log by tapping again (the same rule that got them there).
- **`FR-HAB-9.7` No streak-adjacent copy anywhere.** The un-log affordance does not introduce "you broke your streak" copy, "your rhythm is interrupted" copy, or any adherence-flavoured feedback. On an un-log, the surface reads "Un-marked today" / "Un-logged for ${date}" — factual, calm, no judgement. `DM-NOT`, `DEC-2/3/4`.
- **`FR-HAB-9.8` No schema change.** `Habit.history: List<HabitEntry>` and `HabitRepository.logDirect(...)` already exist per `DM-HABIT`. No new fields, no migrations, no new methods.

> **[DECISION] — Re-label the pill, don't split into two pills.**
> An alternative was to render two pills side-by-side ("Mark today" and "Un-mark today"), only one of which is active at a time, so both affordances are always visible. But the pill row on the collapsed and expanded habit cards is already tight against the row's other affordances ("Log a date…", the edit target, the amount indicator on quantitative habits); adding a second pill would either force a wrap or shrink each pill below the `NFR-A11Y-1` 44 dp tap-target. A single re-labelling pill preserves the layout and matches the pattern the codebase already uses on `FR-BACKLOG-3`'s "PULL →" affordance (a single row with content-dependent copy).

> **[DECISION] — Un-log without confirmation.**
> `DM-HABIT-5` frames logging as low-friction and inherently reversible. A confirmation dialog on un-log would signal "this is a big deal," which it isn't — a mis-log is easily corrected by re-logging (one more tap). The chosen shape optimises for the common case of "oh I meant to log yesterday, not today" — one tap to clear today, one tap in the picker to log yesterday, done.

> **[DECISION] — Clear-log row on the AmountSheet, not a separate sheet.**
> An alternative was to route the quantitative un-log through a new "clear log?" sheet. But the AmountSheet is already the natural surface for "review or change this log's amount"; adding a "Clear this log" row keeps the un-log in the same visual context as the edit-amount operation. The row is visually secondary (`Den.due` text-button styling, not a primary `PillButton`) so it does not compete with the confirm button.

**Acceptance criteria**

1. On the emulator, add a frequency habit "walk 30 min". Tap "Mark today done" on the collapsed row — the log lands, the pill re-labels to "Un-mark today", the day's marker appears in the collapsed row's summary (unchanged from v2.5.0). Tap "Un-mark today" — the log clears, the pill re-labels to "Mark today done". Both taps produce a single `HabitRepository.logDirect` call each.
2. Same habit, expanded row: the today pill labels flip identically. Editing an amount is still an isolated tap target (`FR-HAB-7.2`).
3. Add a quantitative habit "practice violin: 40 min". Tap "Mark today done" → `AmountSheet` opens → enter 40 → confirm. Reopen `AmountSheet` for today (either by tapping the today pill or by tapping the amount indicator): the sheet renders a **"Clear this log"** row below/beside the primary confirm button. Tap it — the log clears atomically (habit history entry removed + linked `DM-ATTR-2` contribution row for today rolled back). Reopen the sheet — the "Clear this log" row is no longer present (nothing to clear).
4. Same habit, open "Log a date…" → pick a past date that is already logged → `AmountSheet` opens with the "Clear this log" row. Tap it — the log for that date clears.
5. Same habit, "Log a date…" → pick a past date not yet logged → `AmountSheet` opens without the "Clear this log" row (nothing to clear). Confirm an amount — the log lands.
6. Frequency habit, "Log a date…" → pick an already-logged past date → `logDirect(id, date, done = false)` fires directly (no `AmountSheet` for frequency), the day's marker in the calendar clears, and the picker announces "Un-logged for ${date}".
7. `CalendarPicker` announces to TalkBack "Tap to log ${date}" on unlogged days and "Tap to un-log ${date}" on logged days. Distinct content descriptions per day state.
8. No confirmation dialog appears on any un-log path (`FR-HAB-9.6`).
9. No streak / rhythm-interrupted / adherence-% copy appears on any surface as a result of un-logging (`DM-NOT`).

### 2.3 User-choosable colour palette (`FR-DESIGN-4`, `DM-PREF-1`, `FR-SET-4`, refines `FR-DESIGN-1`)

*Source: `FR-2026-07-13-c`. Refines `FR-DESIGN-1` (Fox Works Den palette translated into a Compose theme — the Den *identity* remains; the request only adds *alternate palettes as a user preference*, with Den as the default). Adds `FR-SET-4` under the Settings area. Introduces one persisted preference `DM-PREF-1`. Interacts with every composable that reads a colour token from `Den`.*

The current `Den` colour object (`android/app/src/main/kotlin/com/thefoxworks/tzafon/ui/theme/Den.kt`) is a static `object` holding the Fox Works Den palette tokens (`bg`, `surface`, `ink`, `muted`, `rust`, `rustDeep`, `amber`, `due`, `green`, `line`, `line2`, `cream`, the v2 state tokens `frozen`/`backlog`/`closed`, and the three theme-accent slots `tHealth`/`tWrite`/`tLearn`). Every composable in the app resolves colours by direct reference — `color = Den.ink`, `background = Den.bg`, `border = Den.rust.a(0.35f)`, etc. The reporter's request is that a user opening Settings can pick from **Den (default)**, **Blue**, **Green**, **Magenta**, **Teal**, and every colour token in the visible UI resolves to the picked palette's value.

`FR-DESIGN-4` **The `Den` colour object is refactored into a `Palette` data class + a `LocalPalette` composition local, so every colour token access resolves through the current palette at render time. Five palettes ship with the app: `denPalette` (default — the current Fox Works Den values, verbatim), `bluePalette`, `greenPalette`, `magentaPalette`, `tealPalette`. The active palette is selected in a new Settings surface (`FR-SET-4`), persisted device-local in `SettingsStore.palette` (`DM-PREF-1`), and read into `LocalPalette` at the root of the composition (`TzafonApp.kt` / `MainActivity.kt`).**

- **`FR-DESIGN-4.1` The refactor is a mechanical rename.** `Den.xxx` accesses become `LocalPalette.current.xxx` (or a shorter `Tz.colors.xxx` helper — implementer's choice). The `Den` `object` is either deleted or repurposed as a thin `object Den { val default: Palette = denPalette }` for tests. Every existing composable that reads a colour continues to compile with the same visual result on the default palette; the visible pixels do not shift on the Den setting.
- **`FR-DESIGN-4.2` The `Palette` data class covers every token currently on `Den`.** All 15 base colour fields (`bg`, `surface`, `surfaceAlt`, `card`, `ink`, `muted`, `faint`, `rust`, `rustDeep`, `amber`, `due`, `green`, `line`, `line2`, `cream`), all 3 v2 state tokens (`frozen`, `backlog`, `closed`), and all 3 theme-accent slots (`tHealth`, `tWrite`, `tLearn`) are on the data class. The `themeAccents: List<Color>` list is a computed property (`listOf(tHealth, tWrite, tLearn)`) that continues to feed `Theme.accentSlot`. **[DECISION]** below explains why the theme-accent slots vary per palette.
- **`FR-DESIGN-4.3` Five palettes ship, curated at design time.** Each palette carries all 21 tokens with values chosen so:
  - **Contrast** on every text-on-surface / text-on-card / ink-on-bg pair meets WCAG AA per `NFR-A11Y-1`.
  - The **rust-equivalent accent** (`rust`) is the palette's primary saturated hue: `blue` → a strong blue, `green` → a forest-adjacent green, `magenta` → a warm magenta, `teal` → a mid-saturation teal. `rustDeep` is a darker/more-saturated shade of the same hue for pressed states.
  - The **background / surface / card family** is a warm-tinted version of that hue for the light-palette rendering (Den's `bg` is warm kraft #F1E5CF; `blue` might use a very pale cool-neutral, `green` a pale sage, `magenta` a pale blush, `teal` a pale mint) — the background is *not* the primary hue at 10% saturation; it's a curated neutral that reads as "the palette's own paper."
  - **`ink`, `muted`, `faint`** are dark-neutral text colours; their specific hue tilts slightly toward the palette's base (a barely-blue ink on the blue palette, for instance) to preserve the "translated Den identity" per `FR-DESIGN-1`.
  - **`due`** is the alert / overdue colour and stays visually distinct from the palette's `rust`-equivalent on non-red palettes — on `magenta`, `due` shifts toward a more orange-red to avoid collision.
  - **`green`** (the completion/positive accent, e.g. the check on Done tasks) stays a clear success-green on every palette; the green palette itself uses a differentiated green (e.g. a lighter/brighter completion green vs. the palette's primary forest hue).
  - The **three theme-accent slots** are re-tuned per palette so the three active-theme visual slots remain distinguishable from each other and from the palette's `rust` — this preserves the `FR-DIR-*` three-slot visual system.
  Exact hex values are set by the implementer with the constraints above; a reference table (in `Den.kt` next to each palette definition) documents the chosen values.
- **`FR-DESIGN-4.4` The palette is read into `LocalPalette` at the composition root.** `MainActivity.kt` (or `TzafonApp.kt`) reads `SettingsStore.palette` as a `StateFlow<String>`, resolves the string to the corresponding `Palette` (unknown / null value defaults to `denPalette`), and provides it via `CompositionLocalProvider(LocalPalette provides currentPalette) { ... }` at the root of the app's composition. Palette changes take effect **immediately** on save — no app restart required — because the composition local re-triggers recomposition of every subscribed composable.
- **`FR-DESIGN-4.5` The Settings picker is `FR-SET-4`, a new palette row.** Under Settings (`ui/settings/SettingsScreen.kt`), a **"Palette"** row is added alongside the existing rows (`FR-SET-1` week start, `FR-SET-2` reminders, `FR-SET-3` sign out, plus v2.4.0 additions). The row's right-hand affordance shows the current palette's name ("Den", "Blue", "Green", "Magenta", "Teal") and its `rust`-equivalent as a small colour swatch. Tapping opens a `PaletteSheet` (`DenSheet` shape per app convention) with the five palettes rendered as vertical rows — each row shows the palette's name, a small preview strip (bg → surface → ink → rust → green sample), and a radio-style selected indicator on the current choice. Tapping a row saves immediately via `SettingsStore.setPalette(name)` and dismisses the sheet.
- **`FR-DESIGN-4.6` The preference is device-local, not synced.** `SettingsStore.palette` follows the same DataStore-Preferences pattern as `weekStart`, `planningPreset`, and `chimeEnabled`. The value is not synced to Firestore (M9b's sync engine covers `users/{uid}/{collection}/{id}` domain entities, not local preferences per the M9b scope). A user signing in on a second device gets `denPalette` by default and can pick their preferred palette on that device independently.
- **`FR-DESIGN-4.7` Non-palette design tokens are unchanged.** Type (fonts), spacing (padding scales), radius (corner-rounding tokens), and shadow / elevation continue to come from `DenType` / the design-system's shape and spacing tokens. Only colour tokens flow through `LocalPalette`. The fox mascot, "DON'T PANIC" voice, and copy are unchanged — this is a palette swap, not a re-brand.
- **`FR-DESIGN-4.8` Dark theme handling is unchanged.** v2.0.0 through v2.5.0 ships a light-only theme (the Den palette is a warm-kraft light theme; there is no dark mode in the current spec). This requirement does not add dark mode. If a later increment adds dark mode, each palette gets a matching dark variant then; for now, all five palettes are light-only and reflect the current light rendering.
- **`FR-DESIGN-4.9` Every composable respects the current palette.** No composable hard-codes a `Color(0xFFXXXXXX)` value at call-time for a palette-participating token. A grep pass over `ui/` for `Color(0x` literals inside `@Composable` functions returns only the `Den.kt` palette definitions themselves and any non-palette use (e.g. a design-required transparency overlay); no ad-hoc palette values remain in feature composables.
- **`FR-DESIGN-4.10` The task-state visual system is preserved per palette.** The v2 state tokens (`frozen`, `backlog`, `closed`) carry meaning — cool slate = suspended, quiet mauve = someday, faded taupe = skipped — and must remain distinguishable from each other and from the palette's primary hue on every palette. The `magenta` palette in particular must not collide `backlog` (quiet mauve) with its primary hue; the `backlog` token shifts on magenta to a cooler, more grey mauve to preserve distinction.

**`DM-PREF-1`** (new — first user-authored device-local preference tracked as a `DM-` code)
**`palette: String`** — one of `"den" | "blue" | "green" | "magenta" | "teal"`. Default `"den"`. Stored in `SettingsStore` under key `"palette"`. Unknown values fall back to `"den"` at read time. No migration required (DataStore-Preferences reads the default on first access).

**`FR-SET-4`** (new — under the Settings functional area)
**Palette row on Settings.** A row labelled "Palette" with the current selection displayed right-aligned. Tapping opens `PaletteSheet` with five options; tapping any option persists it via `SettingsStore.setPalette(name)` and takes effect immediately without app restart. Follows the visual and interaction pattern of the existing `WeekStartRow` / `RemindersRow` in `SettingsScreen`.

> **[DECISION] — Refactor `Den` to a `Palette` data class, don't overlay via M3 `ColorScheme`.**
> An alternative was to keep `Den` and layer palette choice through Material 3's `ColorScheme` (with `MaterialTheme.colorScheme.primary` etc.). But Tzafon's composables read directly from `Den.xxx` for every token, and `M3 ColorScheme` covers a specific set of roles (`primary`, `onPrimary`, `surface`, ...) that don't map cleanly to Den's semantic tokens (`rust`, `amber`, `due`, `frozen`, `backlog`, `closed`, three theme accents, ...). Re-mapping every Den token onto an M3 role would either lose semantic meaning or force a bloated `ColorScheme`. A `Palette` data class + `LocalPalette` composition local is the smaller, more honest refactor: the exact same tokens Den already ships, now parametric.

> **[DECISION] — Per-palette theme-accent tuning, not a single global set.**
> The three theme-accent slots (`tHealth`, `tWrite`, `tLearn`) are used to give each active theme its own visible identity in Directions (`FR-DIR-*`). If they were global across palettes, they might collide with the palette's `rust` on some palettes (e.g. Den's `tWrite` #8C4A63 would clash with `magenta`'s primary hue). Per-palette tuning keeps the three-slot system readable on every palette; the cost — five palettes × three accent tunings — is small and design-time-only.

> **[DECISION] — Immediate re-render, no restart, no confirmation.**
> An "are you sure?" prompt or an "app-restart-required" flow would signal the palette choice is heavy. It isn't — it's aesthetic. `LocalPalette` recomposition takes effect on the next frame, and undoing is one tap on a different palette row. The picker sheet also stays open on tap-to-preview if the implementer chooses a "tap to preview, tap Done to commit" shape — but the base requirement is one-tap-commits, matching the existing `WeekStart` picker's behaviour.

> **[DECISION] — Curated palettes, not a colour-picker.**
> The reporter asks for palettes "based on blue, green, magenta and teal" — five discrete choices, not a free-form colour wheel. A free-form picker would (a) let the user break contrast for their own reading and (b) undermine the "Den identity translated" thesis in `FR-DESIGN-1`. Five hand-tuned palettes is the honest scope; if a later request asks for user-authored palettes, revisit.

> **[DECISION] — Device-local, not synced.**
> Following the existing `SettingsStore` pattern: preferences are per-device, not per-user. A user's aesthetic on their phone need not match their aesthetic on their tablet. If a later increment adds a "sync device preferences" toggle to Settings, palette can join that scope.

### 2.4 Content-direction on the Backlog task list (`FR-DESIGN-3.5`, refines `FR-DESIGN-3` from v2.1.0)
