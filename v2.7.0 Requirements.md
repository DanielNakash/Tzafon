## 1. Scope of v2.7.0

v2.7.0 is a **two-request increment** on top of a shipped v2.6.0. Two source requests are groomed here:

- **`FR-2026-07-15-a` → `FR-HAB-10`.** Let a **Habit** be linked directly to a **Theme**, not only to a Goal — because many habits (a daily push-up count "for better health") have no well-defined goal to serve, but sit naturally under a direction. The important discovery during grooming is that **the data model already anticipated this and the reporting surfaces already consume it** — the request is largely a *close-the-seam* task rather than a new capability. `Habit` already carries `primaryThemeId: String?` and `themeIds: List<String>` (the "full serve set — primary + shared", `DM-HABIT-6`) alongside the optional `goalId` (`domain/model/Habit.kt:18-21`); the Directions hub already attributes a habit to a theme **directly from the habit's own fields**, not via its goal (`ui/directions/DirectionsViewModel.kt:124`). The **gap** is entirely in the editor: `HabitEditorSheet` exposes a *goal* picker but **no theme picker**, and on save it silently **drops `themeIds`** and only carries `primaryThemeId` forward from the pre-existing value (`ui/habits/HabitEditorSheet.kt:342-355`). `FR-HAB-10` (a) adds a theme link picker to the habit editor, mirroring the goal editor's primary + "also serves" picker (`FR-DIR-8.4/8.5`, driven by the pure `GoalLinkLogic` engine), and (b) wires `primaryThemeId` / `themeIds` through the save path so the selection actually persists. No Room schema change is required.

- **`FR-2026-07-15-b` → `FR-AUTH-1`.** Make signing in **required** to use the app. On first launch (and on every launch while signed out), the Welcome view is shown carrying the Google sign-in affordance; a successful sign-in navigates to the Today View; the Settings account card's existing sign-out button returns the user to the Welcome view. The M9b Firebase Auth surface — `AuthRepository` (`domain/model/AuthRepository.kt`), `FirebaseAuthRepository` (`data/auth/FirebaseAuthRepository.kt:30-64`, `authState: Flow<TzafonUser?>`, `signIn(activity)`, `signOut()`), the sign-in button in `SettingsScreen.kt:342-417`, and the Firestore sync manager gated on the same `authState` in `TzafonApp.kt:137-142` — is already in place. `FR-AUTH-1` **is the wiring change that turns the (currently optional, Settings-hosted) sign-in into the app's entry gate**. It removes the `settings.welcomeSeen` DataStore flag as the cold-start gate (`MainActivity.kt:113-119`) and replaces it with an `authState` gate; it replaces the Welcome view's current "Get started" button (`ui/welcome/WelcomeScreen.kt:37-42`) with the same Google sign-in affordance already used in Settings; and it defines the two navigation transitions the current build does not perform (post-sign-in → Today; post-sign-out → Welcome).

The two requests are independent — one is a habit-editor field wiring, the other is a root-nav auth gate — but both are small, tightly scoped, and land in the same increment. `FR-HAB-10` is delivered in M1; `FR-AUTH-1` in M2 (see §Milestones).

All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), the ≤3 active themes cap (`DM-THEME-3`), the compass / chosen-direction thesis, and the Fox Works "Den" identity (`FR-DESIGN-1`). Linking a habit to a theme is a *belonging* relationship (a direction the rhythm serves), not a score — there is no adherence surface, no reward, no badge. It is squarely on-thesis: a theme needs a *why*, not a metric (`DM-THEME-1`), so a habit that "keeps me pointed at *better health*" is a better fit for a theme than for a numeric goal bar.

> **[DECISION] — Requiring sign-in is a deliberate reframing of the "local-first" posture, not a violation of a locked decision.**
> `CLAUDE.md`'s locked decision reads *"Local-first persistence (Room) behind repository interfaces. Firebase (Auth + Firestore sync) is deferred to M9b — keep the repository seam clean so it can be added later."* That decision is about **persistence** (Room stays the authoritative store on device; Firestore is a mirror) and about **sequencing** (do not wire Firebase before M9b). It is **not** a decision that sign-in must remain optional. M9b landed with sign-in *optional* — the Settings copy reads "Yours, on this device · Everything lives here. Sign in to back up and sync across devices." — but that framing was the reasonable default for M9b's *first* landing, not a locked decision. The reporter's request now moves the app to **cloud-backed identity with local-first storage** — Room remains the source of truth on device (so the app stays fully usable offline, `NFR-OFFLINE-1`), but every install now belongs to a signed-in Google identity. `DM-NOT` is untouched (auth introduces no streak/score surface); `DEC-1/2/3/4` are untouched (still native Android, still no gamification). Existing per-device settings (palette, week-start, planning preset, chime, `FR-DESIGN-4.6`) remain device-local. If this reframing is unwanted, overrule this decision and the requirement folds back to "optional sign-in" — but the request is explicit and this doc grooms it as asked.

## 2. Functional requirements

### 2.1 Link a Habit directly to a Theme (`FR-HAB-10`, refines `FR-HAB-6`; reuses `FR-DIR-8`)

*Source: `FR-2026-07-15-a`. Refines `FR-HAB-6` (a habit "may serve one Goal" — this adds the parallel "may serve one or more Themes" that the schema already models via `DM-HABIT-6`). Reuses `FR-DIR-8.4/8.5/8.6` (goal↔theme primary + serves-also picker and the `GoalLinkLogic` selection engine). Realises `DM-HABIT-6` (the habit serve set) and `DM-REL-1` (the "serves: <theme>" display-parent relationship) on the habit side. Feeds `FR-DIR-*` (Directions hub already reads the habit's theme fields) and `FR-JOURNEY-*` (theme-attributed activity over time).*

**Context — what already exists.** `Habit` (`domain/model/Habit.kt`) holds `primaryThemeId: String?`, `themeIds: List<String>` (`DM-HABIT-6` — primary + shared serve set), and `goalId: String?` (may serve one Goal). The Directions hub's `entry(theme)` builder already collects `themeHabits = habits.filter { it.primaryThemeId == theme.id || theme.id in it.themeIds }` and surfaces them in the theme board (and the "N habits held" line). The goal editor already ships a full primary/serves-also theme picker (`FR-DIR-8.4/8.5`) driven by the pure `GoalLinkLogic` (`domain/themes/GoalLinkLogic.kt`) with a `LinkSelection(primaryId, extraServes)` model, a `tapPrimary` promotion rule, a `tapOrphan` "No theme" option, and a serves-also toggle. **What is missing is only the habit-side editor surface and the save wiring.**

`FR-HAB-10` **The Habit editor exposes an optional Theme link — a single primary theme plus optional "also serves" themes — mirroring the goal editor's picker, and the selection is persisted to `Habit.primaryThemeId` / `Habit.themeIds` on save.** Both the goal link and the theme link are independent and optional: a habit may serve a goal, a theme, both, or neither.

- **`FR-HAB-10.1` A "Serves a direction · optional" section is added to `HabitEditorSheet`.** It renders a **primary theme** single-select (radio-style rows over the active themes, plus an explicit **"No direction"** orphan option) and an optional **"Also serves"** multi-select over the remaining active themes — the same two-part shape the goal editor uses (`FR-DIR-8.4`). Copy is direction-framed ("Serves a direction", "Point it at a direction") to match the app's theme/compass vocabulary; the underlying entity is `Theme`.
- **`FR-HAB-10.2` The selection engine is the existing `GoalLinkLogic`, reused (not re-implemented).** The habit editor drives its primary/serves-also state through the same pure engine the goal editor uses: `GoalLinkLogic.fromGoal(primaryThemeId, themeIds)` to seed state, `tapPrimary` / `tapOrphan` / the serves-also toggle for edits, and `LinkSelection.themeIds()` to read the full set back out at save. **[DECISION]** below covers the naming (the engine is habit/goal-agnostic; a rename to a neutral `ThemeLinkLogic` is optional and non-breaking).
- **`FR-HAB-10.3` Only active themes are selectable; a habit already serving an upcoming/archived theme shows it as a read-only annotated chip.** This mirrors `FR-DIR-8.4`'s rule exactly: `activeThemes` (state `ACTIVE`) are the togglable options; if a habit already serves a theme that has since gone `UPCOMING`/`ARCHIVED`, that theme renders as a read-only chip (annotated with its state) rather than a togglable row, and is preserved on save unless the user explicitly drops it. The editor receives both an `activeThemes: List<Theme>` list (selectable) and an `allThemes: List<Theme>` list (to resolve read-only chips), the same two parameters the goal editor takes.
- **`FR-HAB-10.4` The save path persists `primaryThemeId` and `themeIds`.** The current `onSave` constructs a `Habit(...)` that carries `primaryThemeId = initial?.primaryThemeId` and **omits `themeIds` entirely** (`HabitEditorSheet.kt:342-355`) — the bug that makes theme-linking impossible today. `FR-HAB-10` changes the constructed `Habit` to set `primaryThemeId = linkSel.primaryId` and `themeIds = linkSel.themeIds()` from the editor's `LinkSelection`. All other fields (name, kind, target, unit, targetDays, cue, goalId, startedAt, createdAt) are unchanged.
- **`FR-HAB-10.5` When the habit serves a goal and has no theme of its own yet, the goal's primary theme is pre-filled (inherit-but-overridable).** On the create route (or an edit where `primaryThemeId == null` and `themeIds` is empty) for a habit that has a `goalId`, the theme picker **pre-selects the linked goal's `primaryThemeId`** as the habit's primary theme — surfacing the natural default without a second bookkeeping step. This is a **pre-fill, not a binding**: the user may change the primary, add serves-also themes, or choose "No direction". The pre-fill does not re-fire if the user later changes the linked goal, and it does not overwrite a theme the user already set. **[DECISION]** below.
- **`FR-HAB-10.6` The theme section is shown whenever there is something to show.** Following the goal picker's own guard (`if (goals.isNotEmpty() || goalId != null)`), the theme section renders when `activeThemes` is non-empty **or** the habit already carries any theme (`primaryThemeId != null || themeIds.isNotEmpty()`). If the user has created no themes at all and the habit has none, the section is omitted (nothing to link to) — the habit still saves fine with no theme.
- **`FR-HAB-10.7` The goal link and the theme link are fully independent.** Attaching a theme does not require, set, or clear `goalId`; attaching a goal does not require a theme (beyond the `FR-HAB-10.5` pre-fill nudge). A habit may end in any of the four states: theme-only (the reporter's push-ups case), goal-only, both, or neither. The existing goal-link section (`FR-HAB-6`) is unchanged except that it now sits alongside the new direction section.
- **`FR-HAB-10.8` Directions and Journey pick up the link with no further change.** Because `DirectionsViewModel.entry(theme)` already filters habits by `primaryThemeId`/`themeIds` (`ui/directions/DirectionsViewModel.kt:124`), a newly theme-linked habit appears under its theme in the Directions hub and counts toward "N habits held" as soon as it is saved — no Directions-side code change is required. Any Journey attribution that reads the same habit theme fields inherits the link identically.
- **`FR-HAB-10.9` No schema change, no migration.** `primaryThemeId` and `themeIds` already exist on `Habit` and in `RoomHabitRepository` (they are round-tripped by the DAO today; only the editor never wrote a non-inherited value). `FR-HAB-10` adds no fields, no Room migration, no new repository methods.
- **`FR-HAB-10.10` No streak / adherence framing.** The direction link introduces no "you're X% aligned to *better health*" surface, no per-theme adherence bar, no reward for a habit "serving" a theme. The relationship is descriptive belonging only. `DM-NOT`, `DEC-2/3/4`.

> **[DECISION] — Reuse `GoalLinkLogic` as-is; a neutral rename is optional.**
> The primary/serves-also selection engine (`domain/themes/GoalLinkLogic.kt`) is already entity-agnostic — it operates on `(primaryId, extraServes)` string sets and knows nothing about goals specifically (`fromGoal` is just "split a stored primary + list into editor state"). The habit editor can call it verbatim. Renaming it to `ThemeLinkLogic` (with a `fromEntity` alias) would read more honestly now that two editors use it, but that is a cosmetic refactor and **not required** for this requirement; if the implementer renames, keep a deprecated alias so `FR-DIR-8`'s call sites and the existing `GoalLinkLogic` tests stay green.

> **[DECISION] — Inherit the goal's theme as a pre-fill, not a live binding.**
> The reporter asked to "prefer inheriting that goal's theme but still allow a goalless habit to be attached to a theme on its own." The lightest honest reading is a **one-time pre-fill** at edit-open when the habit has a goal but no theme of its own: it removes the double-bookkeeping the reporter worried about, while leaving the user in control. A *live* binding (the habit's theme always tracks the goal's theme) was rejected because (a) it would silently rewrite the habit's direction when a goal is re-pointed, surprising the user, and (b) it would make the habit's own `primaryThemeId` a derived, un-editable value — contradicting the request's "attach a goalless habit to a theme on its own." The chosen shape keeps the two links independent (`FR-HAB-10.7`) with a convenience default, not a constraint.

> **[DECISION] — "Serves a direction," not "Serves a theme," in the copy.**
> The app's user-facing vocabulary for a `Theme` is a *direction* (the compass thesis; Directions is the hub's name). The goal editor uses "theme" in some of its internal labels, but the habit editor's new section adopts the direction-framed copy to stay consistent with the Directions surface the reporter will see the habit appear under. The entity and code remain `Theme`; only the label differs.

> **[DECISION] — Reuse the goal editor's active-only selectability rule.**
> Rather than invent a new selectability policy for habits, `FR-HAB-10.3` adopts `FR-DIR-8.4` verbatim: only `ACTIVE` themes are togglable, upcoming/archived already-served themes render as read-only annotated chips. This keeps the two editors' theme pickers behaviourally identical, so a user who has linked a goal to a theme already understands the habit picker with no relearning, and the ≤3-active-themes framing (`DM-THEME-3`) is respected on the habit side too.

**Acceptance criteria**

1. On the emulator, with at least one `ACTIVE` theme "better health" present, create a new frequency habit "20 push-ups". The editor shows a **"Serves a direction · optional"** section with "better health" as a selectable primary option and a **"No direction"** option. Select "better health" and save. Reopen the habit — the primary direction shows "better health" selected.
2. Open the Directions hub: the "better health" theme board lists "20 push-ups" among its habits, and the theme's summary counts it in "N habits held" once it has a recent log. No Directions-side code change was needed.
3. Create a habit with **no** theme selected (leave "No direction"). It saves successfully with `primaryThemeId == null` and `themeIds` empty, and does not appear under any theme in Directions.
4. With three active themes present, a habit can select one **primary** direction and toggle one or more **"Also serves"** directions; the persisted `themeIds` equals primary + serves-also (deduped), and reopening the editor restores the exact selection. Tapping the current primary promotes the topmost serves-also entry per `GoalLinkLogic.tapPrimary` (identical to the goal editor).
5. A habit that already served a theme which has since gone `UPCOMING`/`ARCHIVED` shows that theme as a **read-only annotated chip** (not a togglable row), and the theme is preserved across an unrelated edit + save (`FR-HAB-10.3`).
6. Pre-fill: create a habit, link it to a goal that serves "better health", and do not touch the direction section. The primary direction is **pre-selected** to "better health" (inherited from the goal). Change it to a different active theme and save — the habit persists the *user's* choice, not the goal's, and re-pointing the goal's theme afterward does not change the habit's direction (`FR-HAB-10.5`, pre-fill-not-binding).
7. A goalless habit can be attached to a theme on its own (criteria 1 already exercises this); a goal-linked habit can additionally serve a *different* theme than its goal — the two links are independent (`FR-HAB-10.7`).
8. If no themes exist at all and the habit has none, the "Serves a direction" section is **omitted** and the habit still saves (`FR-HAB-10.6`).
9. `themeIds` is persisted on save — a habit given a primary + one serves-also, saved, killed-and-relaunched, still shows both (regression guard against the `HabitEditorSheet.kt:342-355` drop bug). `NFR-OFFLINE-1`.
10. TalkBack announces the primary rows as a radio group ("better health, selected" / "No direction") and the serves-also rows as toggles, matching the goal editor's announced semantics. Hit targets meet `NFR-A11Y-1` ≥ 44 dp.
11. No streak / adherence / "% aligned to direction" surface appears anywhere as a result of the link (`DM-NOT`).
12. The existing habit-goal link (`FR-HAB-6`), habit kind/target/cue editing (`FR-HAB-1..8`), and the v2.6.0 un-log affordance (`FR-HAB-9`) continue to work unchanged; the direction section is additive.

**Out of scope for v2.7.0**

- **A live binding that keeps a habit's theme in sync with its goal's theme.** See the second `[DECISION]` — inheritance is a one-time pre-fill, not a constraint. A "keep habit direction synced to its goal" preference is a follow-on if requested.
- **Editing a habit's theme link from the Directions hub** (e.g. drag a habit onto a theme board). The link is edited in the habit editor for now; a hub-side affordance is a separate request.
- **A per-theme "habits serving this direction" management list inside the theme editor.** The theme→habit relationship is currently authored from the habit side only; a symmetric theme-side editor (parallel to `FR-2026-07-12-b`'s goal↔theme two-sided linking) is a follow-on if wanted.
- **Renaming `GoalLinkLogic` → `ThemeLinkLogic`.** Optional and cosmetic (`FR-HAB-10.2` `[DECISION]`); not a requirement of this increment.
- **Any adherence / alignment metric between a habit and its direction.** `DM-NOT` — the link is descriptive belonging only.
- **Changing how the Directions hub or Journey attribute habits to themes.** They already read `primaryThemeId`/`themeIds` correctly (`FR-HAB-10.8`); no change is in scope.

### 2.2 Require sign-in to use the app (`FR-AUTH-1`, refines the M9b Firebase Auth surface)

*Source: `FR-2026-07-15-b`. First user-visible requirement in a new `FR-AUTH-*` area. Builds on the M9b Firebase Auth surface (`domain/model/AuthRepository.kt`, `data/auth/FirebaseAuthRepository.kt`, `TzafonUser(uid, email, displayName)`, the sign-in/sign-out affordances already in `SettingsScreen.kt:342-417`, and the sync gating in `TzafonApp.kt:137-142`). Refines `NFR-SEC-2` (v2.0.0: "Auth stays Google SSO via Firebase Auth (Android SDK); session persists across app restarts until explicit sign-out") from a technology choice into a **usage requirement**: sign-in is not just supported, it is required.*

**Context — what already exists.** M9b implemented the full auth surface:

- `AuthRepository` exposes `authState: Flow<TzafonUser?>` (null = signed out), `currentUid: String?`, `suspend fun signIn(activity: Activity): Result<Unit>`, and `suspend fun signOut()`. Firebase Auth's own listener already persists the session across app restarts (`NFR-SEC-2`).
- `FirebaseAuthRepository` (`data/auth/FirebaseAuthRepository.kt:30-64`) drives Credential Manager + Google ID Provider (no hard-coded client id — sourced from `google-services.json` via `R.string.default_web_client_id`), and its sign-out clears Credential Manager state too so the next sign-in shows the Google account chooser cleanly.
- `SettingsScreen.kt:342-417` (the `AccountCard`) already renders the two states: signed-out shows a **"Sign in with Google"** rust button; signed-in shows `displayName ?: "Signed in"` + email + "synced & backed up" + a **"Sign out"** outline button. Both actions call the repository in a coroutine and the card re-renders off `auth.authState.collectAsStateWithLifecycle()`.
- `TzafonApp.kt:63,137-142` starts / stops the Firestore sync manager as `authState` toggles between non-null and null, so **sync activation is already gated on auth** — no change is needed there.

**What is missing.** The app currently uses `SettingsStore.welcomeSeen: Boolean` (DataStore) as its cold-start gate (`MainActivity.kt:113-119`) — first-time users see Welcome, everyone else lands directly on Today, **regardless of auth state**. The Welcome view's primary button (`ui/welcome/WelcomeScreen.kt:37-42`) reads "Get started" and simply navigates to Today; it does not sign in. And signing in from Settings does not navigate away from Settings; signing out from Settings does not navigate away either. These are the three transitions `FR-AUTH-1` defines.

`FR-AUTH-1` **The app requires a signed-in Google identity to render any surface beyond the Welcome view. Cold start and every navigation-root recomposition consult `AuthRepository.authState`, not `welcomeSeen`; when it is `null`, the Welcome view is the only route; when it is non-null, the app opens on Today. Sign-in on Welcome and sign-out in Settings drive the two transitions.**

- **`FR-AUTH-1.1` `AuthRepository.authState` is the cold-start gate; `welcomeSeen` is retired.** The `MainActivity.kt:113-119` decision — `remember { if (welcomeSeen == true) Tab.TODAY.route else "welcome" }` — is replaced by an `authState`-driven start destination: the Compose root collects `authRepository.authState.collectAsStateWithLifecycle(initial = <loading sentinel>)`, and once the initial value is known, the NavHost's start destination is `"welcome"` iff the collected state is `null`, else `Tab.TODAY.route`. The `SettingsStore.welcomeSeen` field (and its `setWelcomeSeen()` writer, called from `WelcomeScreen.onStart`) is removed from the code path — auth state is now the sole gate. **[DECISION]** below covers the tiny "loading" window between app launch and the first `authState` emission.
- **`FR-AUTH-1.2` The Welcome view carries the Google sign-in affordance.** `WelcomeScreen`'s "Get started" button (`ui/welcome/WelcomeScreen.kt:37-42`) is replaced by a **"Sign in with Google"** button whose visual style matches the Settings account card's signed-out button (rust background, on-primary text) so a user seeing sign-in on Welcome recognises the same affordance in Settings. Pressing it invokes `authRepository.signIn(activity)` off the surrounding coroutine scope. The Welcome view's existing copy (name, tagline, "compass / chosen direction" framing) is preserved — only the CTA changes.
- **`FR-AUTH-1.3` A successful sign-in navigates to Today; a failed sign-in stays on Welcome with a snackbar.** The screen observes `authState` and, on transition from `null` → non-null, calls `nav.navigate(Tab.TODAY.route) { popUpTo("welcome") { inclusive = true } }` — clearing Welcome from the back stack so the Android back gesture from Today does not return to Welcome. If `signIn(activity)` returns `Result.failure` (user cancelled the Google chooser, no network, Credential Manager unavailable, etc.), the button re-enables and a snackbar shows the error message; the user stays on Welcome. **[DECISION]** below covers the "user cancelled vs. actual error" copy.
- **`FR-AUTH-1.4` Sign-out from Settings returns to Welcome and clears the back stack.** The Settings account card's "Sign out" button (`SettingsScreen.kt:378`) currently calls `authRepository.signOut()` and does nothing else. `FR-AUTH-1` adds a nav side-effect: after sign-out completes, close Settings and `nav.navigate("welcome") { popUpTo(nav.graph.startDestinationId) { inclusive = true } }` so the entire main-tab back stack (Today, All Tasks, Backlog, Habits, Directions, Journey, Review, About) is cleared. From Welcome the user may sign back in with the same or a **different** Google account via the same button (`FR-AUTH-1.6`).
- **`FR-AUTH-1.5` The Settings signed-out state (in-place sign-in) is preserved as a secondary path.** Because the account card is still reachable while signed in, a rare edge case is: a user is on Settings, an auth token expiry / server-side revocation flips `authState` from non-null to null *while Settings is open*. The card's existing signed-out rendering (its "Sign in with Google" button) remains — the user is not force-navigated away from Settings mid-interaction; the `authState`-observing root-nav guard (`FR-AUTH-1.1`) instead kicks in on the next composition or when Settings is dismissed. This keeps the auth surface consistent (one component, both states) without a jarring modal-close mid-view. **[DECISION]** below.
- **`FR-AUTH-1.6` The same Google sign-in flow supports account switching.** `FirebaseAuthRepository.signOut()` already clears Credential Manager state (`data/auth/FirebaseAuthRepository.kt:59-64`), so the next `signIn(activity)` presents the Google account chooser rather than silently re-selecting the previous account. The Welcome view's "Sign in with Google" button therefore supports both "same account back in" and "sign in with another account" without a separate CTA. If Credential Manager returns the same account with no chooser (device-managed single-account policies), that is a device behaviour outside the app's control and is not a bug against this requirement.
- **`FR-AUTH-1.7` Local data on first-forced-sign-in belongs to whoever signs in on this install.** A user upgrading from v2.6.0 (or any prior build) may already have local Room data — tasks, habits, goals, themes, reviews — created while signed out. On the first forced sign-in, that data **stays put** in Room (the local store is the source of truth, `NFR-OFFLINE-1`) and the M9b sync engine mirrors it up to the newly-signed-in user's Firestore collections (`users/{uid}/{collection}/{id}`), the same as any locally-authored row today. No confirmation prompt, no "adopt or discard?" dialog — the data adopts the identity of the first account to sign in. **[DECISION]** below covers the account-switch case (sign out → sign in as a *different* account).
- **`FR-AUTH-1.8` Sign-out preserves local data on the device (M9b behaviour, restated for clarity).** Signing out stops the sync manager (`TzafonApp.kt:137-142`) but does **not** wipe Room. The next sign-in — same account or different — re-uses the same Room DB, and the sync engine reconciles it against whichever `uid`'s Firestore is now active. A "delete local data on sign-out" preference is out of scope for v2.7.0 (see below). **[DECISION]** below.
- **`FR-AUTH-1.9` The app is fully usable offline once signed in.** A signed-in user with no network can still read/write every domain surface — Room is authoritative, sync is best-effort — matching `NFR-OFFLINE-1`. The sign-in event itself of course requires network (Google + Firebase Auth); a first-time launch with no network shows Welcome with the button, the sign-in attempt fails with a network snackbar (`FR-AUTH-1.3`), and the user retries when online.
- **`FR-AUTH-1.10` The initial `authState` load must not flash Welcome for already-signed-in users.** Firebase Auth's persisted session is read asynchronously on `FirebaseAuth` init, so a naive implementation would default to `null`, show Welcome for a frame, then flip. The Compose root defers picking a start destination until `authState` has emitted its first non-loading value (either `null` or a `TzafonUser`) — either by (a) rendering a bare Den-themed splash (background colour only, no text) until then, or (b) using `runBlocking` on `FirebaseAuth.currentUser` at Application init to seed the first value synchronously. **[DECISION]** below picks (a) as the implementation.
- **`FR-AUTH-1.11` `FR-DESIGN-4.6` continues to hold — palette and other per-device preferences are not synced.** Signing out and signing back in as a different account does not reset `denPalette`, `weekStart`, `planningPreset`, or `chimeEnabled`; those are DataStore-Preferences values scoped to the install, not the user. This is a restatement, not a change.
- **`FR-AUTH-1.12` No streak / adherence / gamification surface is introduced by requiring sign-in.** `DM-NOT`, `DEC-2/3/4`. Sign-in gates access; it does not score, reward, or badge.

> **[DECISION] — `welcomeSeen` retires; `authState` is the sole gate.**
> Keeping `welcomeSeen` alongside `authState` would let a returning-but-signed-out user skip Welcome, which contradicts `FR-AUTH-1`. It is cleaner to remove the field entirely. Existing DataStore values are ignored (a leftover `true` value causes no harm — the code path that reads it is gone). If a "brand splash on first launch" is later desired it can be re-introduced as a separate route in front of Welcome; this requirement does not need it.
>
> Rationale: fewer gates = fewer failure modes. The M9b sign-in flow's account chooser already serves the "orient the first-time user" role that `welcomeSeen` used to justify.

> **[DECISION] — First-forced-sign-in adopts existing local data into the signing-in account; subsequent account switches do not merge.**
> Two behaviours are possible on the first forced sign-in after an upgrade:
> (a) **Adopt** — the local Room data is treated as belonging to whoever signs in first (`FR-AUTH-1.7`), and the sync engine mirrors it up.
> (b) **Discard/reset** — Room is wiped on the first forced sign-in so the user starts clean.
> This doc picks (a) because pre-existing users have real, unsync'd data they would lose under (b) with no warning; (a) has the desired "your data followed you into the cloud" behaviour and is what the M9b sync engine already does for anything authored while signed out.
> **Subsequent account switches** (signed in as A → sign out → sign in as B on the same install) do **not** attempt to merge A's data into B's Firestore. Room continues to hold whatever it held; the sync engine now writes those rows under B's `uid`. This matches M9b's already-shipped behaviour (`TzafonApp.kt:137-142` swaps `syncManager` scope on `authState` change but does not touch Room). A "wipe local data on sign-out" preference is a follow-on if the account-swap-collision case becomes a real problem in practice (see out of scope). Overrule if a different first-sign-in behaviour is wanted.

> **[DECISION] — A minimal Den-themed splash covers the initial `authState` load.**
> Firebase Auth's persisted-session read is fast (typically < 200 ms) but not synchronous. Two shapes were considered:
> (a) A one-frame "splash": a Den-themed background (`MaterialTheme.colorScheme.background`) with no text or logo, held until `authState` has emitted its first value; then the correct start destination composes.
> (b) `runBlocking { FirebaseAuth.getInstance().currentUser }` at Application init.
> This doc picks (a) — it keeps the Application init non-blocking (Android is picky about ANRs at cold start), avoids Firebase-SDK-blocking-on-main patterns, and gives the theme a beat to settle. If (a) proves visibly janky the implementer may switch to a Den-themed logo splash or fall back to (b); the *user-visible* requirement is only that Welcome must never flash for an already-signed-in user.

> **[DECISION] — Failed sign-in copy distinguishes cancellation from real errors.**
> `FirebaseAuthRepository.signIn(activity)` returns `Result.failure(t)` for both "user cancelled the Google chooser" and "network / provider / config error". The snackbar in `FR-AUTH-1.3` reads:
> - Cancellation (`GetCredentialCancellationException`, `NoCredentialException`): **no snackbar** — the user made a choice, do not scold them; the button re-enables and Welcome is idle.
> - Other errors: snackbar reading **"Couldn't sign in. Check your connection and try again."** with the button re-enabled. The underlying throwable is logged via `Log.w("Tzafon/Auth", …)` for triage but not shown to the user.
> This keeps the failure path humane and matches the Den identity's calm tone.

> **[DECISION] — Auth-state loss mid-Settings does not force-navigate.**
> `FR-AUTH-1.5` says a mid-session `authState` flip from non-null to null (token expiry / server revoke) while Settings is open leaves the user on Settings with the account card in its signed-out state, not a hard nav-jump to Welcome. Rationale: mid-view force-navs are jarring, and the account card is *literally* the surface where re-authenticating makes sense. The root-nav guard picks the user up on the next composition or when Settings is closed, so no surface beyond Welcome ever renders while signed out — the invariant `FR-AUTH-1` requires still holds.

> **[DECISION] — Firestore rules deployment is a deploy-time concern, not a requirement change.**
> `CLAUDE.md` notes an outstanding owner step: **"deploy `android/firestore.rules`"** (production-mode default-deny currently blocks writes). Requiring sign-in does not itself deploy rules; the requirement is satisfied by wiring the auth gate. If the rules are still not deployed at v2.7.0 release, signed-in users can authenticate and write to Room fine but Firestore sync writes fail server-side (already the M9b state). Deploying the rules is called out in the release checklist (`§5`) as a **release-gate** for v2.7.0, but not as a `FR-AUTH-1` sub-requirement — the code change is complete without it.

**Acceptance criteria**

1. Fresh install on the emulator: cold-launch the app. The **Welcome view** is shown with a **"Sign in with Google"** button matching the Settings account card's rust style. There is no "Get started" button anywhere (`FR-AUTH-1.2`).
2. Tap "Sign in with Google" → the Credential Manager Google chooser appears; select an account → the app navigates to the **Today View** with Welcome removed from the back stack (Android back gesture from Today does not return to Welcome). Sync manager starts (`Log.d` observable) (`FR-AUTH-1.3`, `FR-AUTH-1.4`).
3. Kill and relaunch: the app opens **directly on Today** with no flash of Welcome — the persisted Firebase session is honoured (`FR-AUTH-1.10`, `NFR-SEC-2`).
4. From Today, navigate to Settings; tap "Sign out". The app closes Settings and navigates to **Welcome**; the tab back stack is cleared (Android back from Welcome exits the app, not to the previous tab) (`FR-AUTH-1.4`).
5. From Welcome, tap "Sign in with Google" again; the chooser appears and offers **account switching** (the previously-signed-in account is not silently re-selected) (`FR-AUTH-1.6`).
6. Cancel the Google chooser (back/dismiss) → **no snackbar** shown, button re-enables, user stays on Welcome (`FR-AUTH-1.3` `[DECISION]`).
7. Airplane-mode the device, cold-launch: Welcome is shown, tap sign-in → snackbar reads **"Couldn't sign in. Check your connection and try again."**, button re-enables, user stays on Welcome (`FR-AUTH-1.3` `[DECISION]`).
8. Upgrade path: install v2.6.0, create a few tasks / habits / a goal / a theme (signed out), upgrade to v2.7.0. The first cold-launch shows Welcome; sign in with a fresh Google account. The **existing local data is preserved** — the same tasks/habits/goals/themes appear on Today / Habits / Directions after landing (`FR-AUTH-1.7`). The sync manager mirrors them into `users/{uid}/{collection}/{id}` (visible in the Firestore console, subject to rules being deployed).
9. Signed-in, offline (no network, session already persisted): every main surface (Today, All Tasks, Backlog, Habits, Directions, Journey, Settings, About, Review) works — reads and writes both — matching `NFR-OFFLINE-1`. Sync writes queue and drain on reconnect; no UI is gated on network. (`FR-AUTH-1.9`).
10. Account switch: signed in as A, sign out (→ Welcome), sign in as B on the same install. Room data authored under A **stays on the device** and is now mirrored under B's `uid` (`FR-AUTH-1.7` `[DECISION]`). No merge prompt; no data loss.
11. Mid-session revoke: force `authState` to null while Settings is open (e.g. by wiping Firebase session via a debug hook, or simulating in a Compose test). Settings **stays visible** with the account card in its signed-out state; closing Settings navigates to Welcome (`FR-AUTH-1.5`).
12. TalkBack on Welcome announces the sign-in button as **"Sign in with Google, button"**; hit target ≥ 44 dp (`NFR-A11Y-1`). The Settings account card retains its existing TalkBack semantics (v2.6.0 unchanged).
13. Per-device preferences survive an account switch: pick a non-default palette in Settings, sign out, sign in as a different account → the palette on this device is unchanged (`FR-AUTH-1.11`, `FR-DESIGN-4.6`).
14. `DM-NOT` audit clean: no streak, no adherence, no badge, no reward surface introduced by the sign-in gate (`FR-AUTH-1.12`).
15. `SettingsStore.welcomeSeen` is removed from the code path and any leftover DataStore-persisted value is ignored (`FR-AUTH-1.1` `[DECISION]`).
16. All v2.0.0 … v2.6.0 acceptance criteria still pass — no main-surface behaviour regresses. The M9b sync engine's `users/{uid}/…` write path is unchanged.

**Out of scope for v2.7.0**

- **Any auth provider beyond Google SSO.** No email/password, no Apple, no anonymous auth. `NFR-SEC-2` continues to lock the provider.
- **Deleting an account (Firebase `deleteUser`) or erasing a signed-in user's cloud data from within the app.** Sign-out preserves local data (`FR-AUTH-1.8`); a "delete my data" surface is a separate request when needed for policy reasons.
- **A "wipe local data on sign-out" preference.** `FR-AUTH-1.8` explicitly keeps Room across sign-out; adding a wipe toggle is a follow-on if account-swap collisions become a practical problem.
- **A merge / adopt UX for existing local data on first forced sign-in.** `FR-AUTH-1.7` picks the silent-adopt behaviour by decision; a prompt-based flow is a follow-on if warranted.
- **Deploying `android/firestore.rules`.** Called out in `§5` as a release gate; not a `FR-AUTH-1` sub-requirement (`[DECISION]`).
- **A privacy-policy / terms-of-service surface on Welcome or during sign-in.** If required by store policy at release time, add it in a follow-up; not in v2.7.0 scope.
- **Multi-account-on-one-install (fast-switch between two signed-in users).** The model is one account per install at a time. Sign-out → sign-in-as-B is the switch mechanism.
- **Any streak / adherence / points surface introduced through the auth gate.** `DM-NOT`, restated.

## 4. Data model deltas

**None.** This increment adds no fields, no Room migration, and no new repository methods.

- `Habit.primaryThemeId: String?` and `Habit.themeIds: List<String>` already exist (`DM-HABIT-6`, `domain/model/Habit.kt:18-20`) and are already persisted by `RoomHabitRepository`. The only change is that `HabitEditorSheet` now **writes** a user-chosen value into them instead of dropping `themeIds` and inheriting `primaryThemeId` unchanged.
- The habit editor gains two input parameters (`activeThemes: List<Theme>`, `allThemes: List<Theme>`), supplied by `HabitsViewModel` (which today exposes `goals` but not themes — it must also observe `ThemeRepository.observeThemes()` and expose the active/all lists), and `HabitsScreen` passes them into `HabitEditorSheet` alongside the existing `goals`. These are UI-tier wiring changes, not data-model changes.
- The reused `GoalLinkLogic` is pure domain logic with no persistence; using it from a second editor changes no stored shape.
- `FR-AUTH-1` **removes** the `SettingsStore.welcomeSeen: Boolean` DataStore key from the code path (`FR-AUTH-1.1` `[DECISION]`). Existing persisted values are ignored — no migration is needed, no data is destroyed. This is a UI-tier gate change; no domain-model or Room shape is touched. The `TzafonUser(uid, email, displayName)` shape (`domain/model/AuthRepository.kt`) is unchanged.
