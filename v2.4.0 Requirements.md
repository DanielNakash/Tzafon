## 1. Scope of v2.4.0

v2.4.0 is a **design-polish + small-affordance increment** on top of a shipped v2.3.0. Five source requests, no new object types, no schema migrations, no new top-level surfaces (see §4 — Data model deltas below, which is intentionally empty). All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), and the compass / chosen-direction thesis.

The requirements:

- **`FR-ABOUT-2`** refines the About screen introduced by `FR-ABOUT-1` with an explicit type-treatment plan across the three text rows and the Contact Us link, a proportional-to-viewport rule for `FoxLogo` sizing (currently hard-coded at 108 dp), and a vertical-centering layout so the whole screen sits comfortably in the middle of the viewport and fits without scrolling on default text scale in both portrait and landscape. Refines `FR-ABOUT-1.2` (body content order) and `FR-ABOUT-1.6` (layout / no-scroll rule).
- **`FR-NAV-5`** normalises the chrome palette so **every top-level tab and reference view uses the same rust `RustHeader` treatment** — retiring the cream `LayerHeader` currently rendered on Habits / Directions / Journey, which reads today as if those three views belong to a different app. Refines `FR-NAV-1` chrome.
- **`FR-NAV-6`** makes navigation affordances consistent so **no view is a dead-end**: primary and reference views all carry the bottom nav (`DenBottomNav`) and the hamburger (`FR-NAV-3`), while leaf destinations (Settings, About) carry a single "close" (`×`) affordance that returns to whichever view opened them. Refines `FR-NAV-1` (bottom-nav visibility), `FR-NAV-3` (hamburger placement), and `FR-ABOUT-1.1` (About left-slot affordance).
- **`FR-NAV-7`** normalises the screen-title size across `RustHeader` (all views render the title at `DenType.h1`; the `compact = true` opt-in is retired) and restructures Planning's header so the current date sits in the kicker slot and the "WHAT'S ON THE TABLE" line is removed, freeing vertical room for the "Planning" title at full weight without the header growing overall. Refines `FR-PLAN-1` (Planning header layout) and adjusts About / Settings / Backlog / All Tasks title sizing accordingly.
- **`FR-HAB-8`** lets the user log a habit for **a date they choose** (typically yesterday, or an earlier day they forgot) directly from the Habits view — the existing "Mark today done" affordance stays exactly as-is, and a new secondary control opens a date picker that then logs (frequency) or opens the quantity prompt (quantitative) for the picked date. The repository seam (`HabitRepository.logDirect(habitId, date, done, amount)`) already supports arbitrary dates; only the Habits UI changes. Extends `FR-HAB-4` / `DM-HABIT-5` (the "direct log on any date" path is already the contract; only the UI affordance was missing).
- **`FR-PLAN-4`** trims and adds one entry to the overdue-task action-set in Planning: **Keep** `Today` and `Reschedule`, **remove** `Someday` and `Drop`, **add** `Change Status` which opens the existing `StateSheet`. Additionally, the checkbox on an overdue `DecideCard` becomes **tappable** and marks the task Done via the same code path Today / All Tasks use. Refines `FR-PLAN-3`.
- **`FR-AUDIO-1`** plays a **short, gentle chime** when a task moves Open → Done via the checkbox tap. It is **completion feedback**, not gamification (`DM-NOT`) — nothing accumulates, nothing scores, no streak is displayed. It respects the device's silent / DND profile via the notification audio stream, is user-toggleable in Settings, and does not fire on undo, on state-sheet transitions to Done, or during Review / Journey scans.

Nothing here is gamification-adjacent — there is no streak / points / badges / adherence surface anywhere in the refresh (`DM-NOT`, `DEC-2/3/4`). The chime in `FR-AUDIO-1` is single-event completion feedback with no accumulating counter behind it (see the `[DECISION]` callout in §2.7).

## 2. Functional requirements

### 2.1 About screen visual design — type, logo size, centering (`FR-ABOUT-2`, refines `FR-ABOUT-1.2` / `FR-ABOUT-1.6`)

*Source: `FR-2026-07-11-a`. Refines `FR-ABOUT-1.2` / `FR-ABOUT-1.6`; introduces `FR-ABOUT-2.*`.*

`FR-ABOUT-1` shipped an About screen whose body content order, `FoxLogo` presence, and Contact Us affordance are all correct — the design decisions the source request now asks us to make are the ones the v2.3.0 requirement deferred to implementer's discretion: which Den type role each body row uses, how the `FoxLogo` is sized (currently a fixed 108 dp), and whether the entire block should be vertically centered in the viewport. The About screen is an identity surface — it is one of the two places in the app that renders the brand mark at scale (Welcome being the other) — so its typography and proportions matter more per-pixel than they do on the daily-path views.

#### 2.1.1 Type treatment across the About body (`FR-ABOUT-2.1`)

`FR-ABOUT-2.1` **The three body rows use three distinct roles from the Den type stack, chosen so the visual hierarchy reads identity → attribution → build-metadata, top to bottom.** No new font families are introduced; the Den stack (`DenType.serif` = Newsreader, `DenType.body` = Hanken Grotesk, `DenType.mono` = Spline Sans Mono) is exhaustive per `FR-DESIGN-1`.

- **Row 1 — "Produced by The Fox Works" — `DenType.serif`.** This row is the identity headline; it uses the same serif family the app reserves for titles (`DenType.h1` / `h1Compact`), rendered smaller than a screen title but larger than body copy — `22.sp`, `FontWeight.SemiBold`, `Den.ink`, `letterSpacing (-0.3).sp`. Concretely this matches the Material 3 `titleLarge` slot already wired into `Theme.kt` (serif 22.sp SemiBold), so no new `TextStyle` needs to be created — reuse the token.
- **Row 2 — "Implemented by Claude" — `DenType.body`.** Attribution copy; body register, 15.5.sp `FontWeight.Normal`, `Den.ink`. Matches the row 1 rhythm without competing with it visually.
- **Row 3 — "Version X.Y.Z" — `DenType.mono`.** Build metadata; `12.5.sp`, `letterSpacing 0.4.sp`, `Den.muted`. Consistent with `DenType.meta` used in headers for build/date metadata — signals this line is technical, not editorial.

`FR-ABOUT-2.1.1` **Contact Us link — `DenType.body`, `15.sp`, `FontWeight.SemiBold`, `Den.rust`.** Matches the current implementation; kept explicit so it does not drift with the surrounding size changes. Underline is not required (the Den palette + weight are enough to signal it as a link), but the tap target continues to meet `NFR-A11Y-1`'s ≥ 44 dp rule.

`FR-ABOUT-2.1.2` **Row alignment.** All three text rows remain centered horizontally (`textAlign = TextAlign.Center`) as they are today.

#### 2.1.2 `FoxLogo` sizes with the viewport (`FR-ABOUT-2.2`)

`FR-ABOUT-2.2` **`FoxLogo` is no longer hard-coded at 108 dp. It sizes proportionally to the viewport with a bounded ceiling so it is neither timid on a phone in portrait nor overwhelming on a wide/foldable canvas.** The sizing rule the implementer wires into `AboutScreen`:

```
logoSize = clamp(
    min(0.50 × viewportWidth, 0.45 × availableBodyHeight),
    96.dp,
    240.dp,
)
```

Where `viewportWidth` is the About screen's usable width (screen width minus horizontal padding) and `availableBodyHeight` is the vertical room between the bottom of the `RustHeader` and the bottom navigation-bar inset (i.e. the height available to the body `Column`, measured with `BoxWithConstraints` or an equivalent Compose primitive).

Concrete expectations on the three envelope cases:

- **Portrait phone (Pixel 8, ≈ 412 dp × 870 dp).** `0.50 × 412 = 206.dp` binds; height-ceiling does not. The roundel renders around 206 dp — "about half as wide as the screen" per the request — clearly the visual anchor of the screen but comfortably inside the horizontal margin.
- **Landscape phone / small foldable inner (≈ 700 dp × 380 dp).** Height binds: `0.45 × ≈ 230 dp available body = ≈ 104 dp`. The roundel shrinks to ~104 dp so the three text rows above and the Contact Us link below still fit without scrolling.
- **Portrait tablet / large foldable (≈ 900 dp × 1200 dp).** Half-width would be 450 dp; the clamp caps at 240 dp so the logo does not dominate a large canvas.

`FR-ABOUT-2.2.1` **Floor and ceiling are not negotiable.** The 96.dp floor keeps the mark legible on small screens and at very tall text scales; the 240.dp ceiling keeps it identity-sized, not billboard-sized, on wide displays.

`FR-ABOUT-2.2.2` **The `FoxLogo` composable itself is not modified.** Only the `size` parameter passed in from `AboutScreen` changes, using the formula above. The `ring` argument stays `Den.ink.a(0.06f)` as it is today.

#### 2.1.3 Vertical centering + no-scroll on default text scale (`FR-ABOUT-2.3` / `FR-ABOUT-2.4`)

`FR-ABOUT-2.3` **The About body content is vertically centered in the available body area on the default system text scale.** The current layout stacks the three text rows, then the logo, then Contact Us, from the top of the body with `Arrangement.spacedBy(20.dp)`. The new layout wraps that stack in a `Column` whose vertical arrangement is `Arrangement.Center` (or equivalently pads the top and bottom with equal `Spacer(Modifier.weight(1f))` bookends) so the whole block sits in the middle of the available body height rather than hugging the top under the header.

`FR-ABOUT-2.4` **The whole screen fits without vertical scrolling on the default system text scale in both portrait and landscape on a Pixel 8.** With the logo sized per `FR-ABOUT-2.2` and the vertical rhythm from `FR-ABOUT-2.5`, the body never overflows on default text scale. The `verticalScroll` modifier currently applied to the body `Column` is retained as an accessibility fallback — see `FR-ABOUT-2.4.1`.

`FR-ABOUT-2.4.1` **Scroll re-enables only when a large system text scale would otherwise clip content.** Behaviourally the body `Column` becomes scrollable when its natural content height exceeds the available body height (which happens at increased font-scale settings). This preserves `FR-ABOUT-1.6`'s a11y-fallback rule ("if the user increases system font size sufficiently to overflow, the screen becomes vertically scrollable — do not clip content"). Implementer's discretion on the mechanism (`verticalScroll` gated on a measurement, `LazyColumn` with a top/bottom spacer, or an equivalent).

`FR-ABOUT-2.5` **Vertical rhythm inside the centered block.**

- Between the three text rows: `Arrangement.spacedBy(6.dp)` as today — a tight identity block.
- Between the text block and the logo: `28.dp` gap.
- Between the logo and Contact Us: `24.dp` gap.
- Between Contact Us and the "no email app is available" hint (when shown): `10.dp` gap.

These numbers are exact tokens; the current code uses `Arrangement.spacedBy(20.dp)` uniformly, which reads as an unstructured stack. The new rhythm gives the identity block, the mark, and the affordance visibly distinct roles.

> **[DECISION] — Vertical centering is applied even when the content is very short.**
> An alternative was to top-anchor the block for consistency with Settings' scrolling body. But About is a leaf identity screen, not a list, and Settings is a scrolling list that will always begin from the top — the two are not analogous. Centering here is a deliberate identity choice.

> **[DECISION] — `serif` for row 1, not `body` or `mono`.**
> The request asks about "chosen font(s) and how they're used". The three-family Den stack gives us three obvious slots; using `serif` for the identity headline mirrors how the app treats screen titles (`h1` is serif), which visually says "this row *is* the identity". Using body for all three (the current implementation) reads as a leaflet, not a namebrand.

**Acceptance criteria**

1. Opening About shows, top-to-bottom in a **vertically centered** body block: row 1 in Den `serif` at 22.sp SemiBold, row 2 in Den `body` at 15.5.sp Normal, row 3 in Den `mono` at 12.5.sp with 0.4.sp letter-spacing (all centered horizontally); a `FoxLogo` sized per `FR-ABOUT-2.2`; and the "Contact Us" link in Den `body` at 15.sp SemiBold in `Den.rust`.
2. On a Pixel 8 in **portrait** at default system text scale, the `FoxLogo` renders at ≈ 206 dp (≈ 50% of viewport width), and the whole About body (three text rows + logo + Contact Us) is visible without scrolling.
3. On a Pixel 8 in **landscape** at default system text scale, the `FoxLogo` shrinks (height-ceiling binds) so that the whole About body remains visible without scrolling — nothing is clipped.
4. On a large canvas ≥ 900 dp wide (foldable inner / tablet), the `FoxLogo` is capped at 240 dp — it does not scale beyond that ceiling and does not dominate the viewport.
5. At an increased system font-scale (≥ 1.3× or wherever the natural content height exceeds the body area), the body becomes vertically scrollable and no content is clipped (`FR-ABOUT-1.6` fallback preserved).
6. The three rows and the Contact Us link continue to meet WCAG AA ≥ 4.5:1 contrast against the About background in light and dark themes (`NFR-A11Y-1`).
7. `FR-ABOUT-1.4` (version string sourced from `BuildConfig.VERSION_NAME`), `FR-ABOUT-1.5` (mailto intent), `FR-ABOUT-1.7` (`FoxLogo` reuse — no duplication), `FR-ABOUT-1.8` (menu-only entry), `FR-ABOUT-1.9` (read-only; nothing written), and `FR-ABOUT-1.10` (quiet voice on entry / exit) all continue to hold — none of them regresses.
8. No streak / points / badges / adherence surface appears anywhere on the About screen (`DM-NOT`).

**Out of scope for v2.4.0**

- **A dark-mode-specific type-role swap.** The three roles remain the same in both themes — only the colour tokens (`Den.ink` / `Den.muted` / `Den.rust`) change through the theme, which they do already.
- **A per-locale font override on the About screen.** RTL layout applies as it does elsewhere (`FR-2026-07-10-d` from v2.1.0); explicit per-locale font tuning is a separate concern.
- **Animating the `FoxLogo` on entry.** The screen remains quiet on entry / exit per `FR-ABOUT-1.10`.
- **Loosening the 96 / 240 dp clamp on `FoxLogo`.** These are load-bearing; changing them is a future requirement, not a v2.4.0 tuning knob.

### 2.2 Chrome palette consistency across top-level views (`FR-NAV-5`, refines `FR-NAV-1` chrome)

*Source: `FR-2026-07-11-b` (bullet 1). Refines `FR-NAV-1` chrome; deprecates `LayerHeader` on Habits / Directions / Journey.*

Today the seven top-level views split across two header styles:

- **`RustHeader`** (rust background, cream foreground) — Today, Planning, All Tasks, Backlog, Settings, About.
- **`LayerHeader`** (cream / surface background, ink foreground, per-view accent on the compass mark) — Habits, Directions, Journey.

The two styles were introduced in v2.0.0 to signal a "Direction / Reflection layer" separate from the daily-path "Action layer", but in practice — with the app grown to five tabs and the menu-driven reference views — the split reads as visual inconsistency, not as a meaningful layering. The user experience is that "some views look like a different app". Consistency wins.

`FR-NAV-5` **All top-level tab and reference views render their header with `RustHeader`.** Concretely:

- **Habits** (currently `LayerHeader(kicker = "HABITS · RHYTHM", title = "Habits", accent = Den.green, sub = "…", onMenu = …)`) migrates to `RustHeader(kicker = "HABITS · RHYTHM", title = "Habits", onMenu = …)`. The `sub` line ("Aim for the rate, not perfection…") moves out of the header — either into a body intro paragraph (a small `Text` item at the top of the list, in `Den.muted`, matching the existing intro-copy pattern used by Backlog's list) or into `metaLeft` if it fits on one line. Implementer's discretion, subject to `FR-NAV-5.2`.
- **Directions** (currently `LayerHeader(kicker = "DIRECTIONS · YOUR NORTH", title = "Directions", …, sub = "…", onMenu = …)`) migrates identically: `RustHeader` with the same title and kicker, `sub` moves into a body intro paragraph.
- **Journey** (currently `LayerHeader(kicker = "JOURNEY", title = "Journey", accent = Den.rust, …)`) migrates identically.

`FR-NAV-5.1` **`LayerHeader` is deprecated on the seven top-level views.** The composable itself may remain in `components/Headers.kt` for now (some downstream code paths may still reference it), but no top-level tab or reference view calls it after this milestone. Removing the composable outright is out of scope for v2.4.0; deletion happens once no call sites remain.

`FR-NAV-5.2` **The per-view accent (`Den.green` for Habits, `Den.rust` for Directions / Journey) is preserved through body chrome, not the header background.** Where the previous `LayerHeader` compass mark carried the accent colour, the accent now expresses itself in body group headers, chip fills, and progress bars — surfaces that already carry `Den.green` / `Den.rust` tokens today. The header background is uniformly `Den.rust` (`Den.cream` foreground).

`FR-NAV-5.3` **The `RustHeader` `compass = true` slot may be used on Habits / Directions / Journey to preserve the compass motif** (currently rendered by `LayerHeader`'s optional compass). If it is used, the compass tint continues to be `Den.cream` (matching how Today's `RustHeader` handles the motif); it does **not** carry the per-view accent, because a rust background with a green motif would read as decoration, not identity.

`FR-NAV-5.4` **The `kicker` line and the `title` on each migrated view are preserved verbatim** — "HABITS · RHYTHM" · "Habits"; "DIRECTIONS · YOUR NORTH" · "Directions"; "JOURNEY" · "Journey". Only the palette changes.

> **[DECISION] — Deprecate `LayerHeader` rather than repaint it in rust.**
> A minimal alternative was to change `LayerHeader`'s background from cream to rust in place and leave the call sites untouched. Rejected because `LayerHeader` also renders its title in `Den.ink` with a Material 3 `headlineLarge`-sized override (33.sp, half a size smaller than `RustHeader`'s 37.sp) — the two composables' typography stacks differ, and cross-migrating type + palette invites drift. Migrating the call sites to `RustHeader` outright is the cleaner path and also gives us the `FR-NAV-7` title-size normalisation for free.

**Acceptance criteria**

1. Habits, Directions, and Journey render a rust `RustHeader` with cream foreground — visually indistinguishable in palette from Today's header.
2. The kicker + title copy on all three migrated views is preserved verbatim; body-list group headers on those views still render in the per-view accent (green / rust) where they did previously.
3. `LayerHeader` has no call sites on Today, Planning, Habits, Directions, Journey, All Tasks, Backlog, Settings, or About after this milestone.
4. Any body-intro copy that previously lived in the `LayerHeader` `sub` slot (Habits' "Aim for the rate…" line; Directions' body-below-title copy) is preserved somewhere on the screen — either as a body intro paragraph or as a `metaLeft` line in the new `RustHeader`.
5. No streak / points / badges / adherence surface is introduced by the migration (`DM-NOT`).
6. Compass motif contrast on any header that opts into `compass = true` continues to meet `NFR-A11Y-1`.

**Out of scope for v2.4.0**

- **Deleting `LayerHeader` from `components/Headers.kt`.** Migration first; deletion can happen in a later increment once no call sites remain.
- **Introducing a third header style.** The Den palette continues to carry exactly one primary chrome — rust — going forward.

### 2.3 Navigation-affordance consistency — no dead-end views (`FR-NAV-6`, refines `FR-NAV-1` / `FR-NAV-3` / `FR-ABOUT-1.1`)

*Source: `FR-2026-07-11-b` (bullet 2). Refines `FR-NAV-1` (bottom-nav visibility), `FR-NAV-3` (hamburger placement), and `FR-ABOUT-1.1` (About left-slot affordance).*

Today the header-affordance and bottom-nav rules are:

| View | Bottom nav | Header top-right | Header top-left |
| --- | --- | --- | --- |
| Today | shown | hamburger | kicker |
| Planning | shown | hamburger | kicker |
| Habits | shown | hamburger | kicker |
| Directions | shown | hamburger | kicker |
| Journey | shown | hamburger | kicker |
| All Tasks | hidden | hamburger | kicker |
| Backlog | **hidden** | **decorative Moon icon (no menu)** | kicker |
| Settings | hidden | `×` (close) | kicker |
| About | hidden | *(empty)* | back chevron |

Two of these are dead-ends: **Backlog** has no menu button and no bottom nav, so the only way back is the system back gesture — a user who reached Backlog from the menu is effectively locked out of Today until they gesture back or restart. **All Tasks** has a hamburger but no bottom nav, so cross-tab navigation from there requires two taps (menu → tab) instead of one. And leaf destinations (Settings, About) use *different* close affordances (`×` vs. back chevron), which reads as accidental rather than intentional.

`FR-NAV-6` **Every view in the app falls into one of two navigation-chrome classes; the choice is deterministic per view, and no view sits outside the classification.**

- **Class A — daily-path and reference views.** Today, Planning, Habits, Directions, Journey, **All Tasks, Backlog.** All show the `DenBottomNav` at the bottom (`FR-NAV-6.1`) and a hamburger in the header's top-right slot (`FR-NAV-6.2`). Back gesture behaves per platform default.
- **Class B — leaf destinations.** Settings, About. **Both** show a **close (`×`)** in the header's top-right slot, which pops the destination and returns to the underlying view (`FR-NAV-6.3`). Neither shows a bottom nav (they are leaves, not tabs), and neither shows a hamburger (the parent view carries it).

`FR-NAV-6.1` **`DenBottomNav` is rendered on All Tasks and Backlog with no active tab highlighted.** The `active` parameter is passed as `null`-equivalent — the bar renders every tab in its inactive style; no tab shows the rust pill. Tapping any tab navigates to that tab and pops back to the corresponding root destination (the same `goTab` behaviour Today uses). Implementer's discretion on whether to extend `DenBottomNav`'s signature to accept `active: Tab?` or to introduce a sentinel; the visible behaviour is the requirement.

`FR-NAV-6.2` **The hamburger on All Tasks and Backlog uses the same `HeaderMenuButton` composable that Today / Planning / Habits / Directions / Journey already use, in the top-right slot.** On All Tasks it replaces the current explicit `HeaderMenuButton(onClick = …)` wiring (no change to the visible affordance). On Backlog it **replaces the decorative `TzIcons.Moon` currently occupying the `right` slot** — the moon glyph was identity decoration, not a control, and its presence there is why the view reads as a dead-end. Backlog gains `onMenu = { menu = true }` and drops the decorative right slot. The `AppMenuSheet` opened from Backlog's hamburger contains the same four rows (`FR-NAV-4`); the row for "Backlog" is omitted from the sheet when Backlog is the underlying view (implementer's discretion — either omit the row when the current route is Backlog, or leave it and let a re-tap noop, the latter being simpler).

`FR-NAV-6.3` **Settings and About use a `×` (close) affordance in the header's top-right slot** — the same treatment Settings already uses. About's **back chevron in the left slot is removed**; the header's top-left slot on About reverts to the standard kicker line ("TZAFON" in Den mono, matching Settings), and the top-right slot carries the `×`. Tapping `×` pops the destination back to whichever view opened the menu that led to About / Settings. This deletes `FR-ABOUT-1.1`'s "back chevron in the left slot dismisses the About destination" clause and replaces it with a `×` in the right slot; the semantic behaviour (return to the underlying view) is unchanged.

`FR-NAV-6.4` **The `AppMenuSheet` sheet contents (`FR-NAV-1`, refined by `FR-NAV-4`) are unchanged.** The sheet still opens with the same four rows in the same order — All Tasks · Backlog · Settings · About — from any Class-A view's hamburger.

`FR-NAV-6.5` **The five-tab primary structure (`FR-NAV-1`) is preserved.** All Tasks and Backlog remain reference views reached from the menu; they do **not** become bottom-nav tabs. Rendering the bottom nav on those two views is a wayfinding aid, not a promotion — the visible tab set continues to be the same five (Today · Planning · Habits · Directions · Journey).

> **[DECISION] — Bottom nav on All Tasks / Backlog renders with no active tab, not with the "closest" tab highlighted.**
> An alternative was to highlight Today (the default) or the tab the user came from. Rejected: those views are not tabs, and pretending one is highlighted would either mislead the user ("I'm on Today?") or leak backstack state into the header UI. Rendering all five inactive is honest — the bar is a wayfinder, not a status indicator.

> **[DECISION] — Leaf-destination close is `×`, not back chevron.**
> The user's suggestion explicitly names `×`. Consistent with Settings, which has used `×` since M9. About migrates to match.

**Acceptance criteria**

1. From Backlog, tapping any bottom-nav tab navigates to that tab (Today / Planning / Habits / Directions / Journey); the user is never dead-ended on Backlog.
2. From All Tasks, tapping any bottom-nav tab navigates to that tab; the bottom-nav highlight on All Tasks and Backlog shows no active tab.
3. Backlog's header shows a hamburger in the top-right slot; tapping it opens `AppMenuSheet` with the four rows from `FR-NAV-4`. The decorative Moon glyph is no longer present in the header right slot.
4. All Tasks' header continues to show a hamburger in the top-right slot (unchanged behaviour, cleaned wiring via `HeaderMenuButton`).
5. Settings and About both show a `×` (close) affordance in the header's top-right slot; tapping it returns to the underlying view. About no longer shows a back chevron in the left slot; the left slot renders the "TZAFON" kicker consistent with Settings.
6. TalkBack announces the `×` as "Close" on both Settings and About with a distinct `contentDescription`; the hamburger on All Tasks / Backlog announces as "Menu" consistent with the other Class-A views (`NFR-A11Y-1`).
7. No regressions to `AppMenuSheet` contents (four rows: All Tasks · Backlog · Settings · About) or `FR-NAV-1`'s five-tab structure.
8. `DM-NOT` audit clean — no gamification surface introduced.

**Out of scope for v2.4.0**

- **Promoting All Tasks or Backlog to primary tabs.** The five-tab structure is locked.
- **A "close all screens" gesture or a home shortcut in the bottom nav.** The bottom nav's contract remains "tap → go to that tab".
- **Suppressing the `AppMenuSheet` row for the current view.** If the user is on Backlog and taps hamburger → Backlog row, the sheet closes and the user stays on Backlog — acceptable v2.4.0 behaviour; a smarter suppression can come later.

### 2.4 Screen-title size + Planning header restructure (`FR-NAV-7`, refines `FR-PLAN-1`)

### 2.5 Log a habit for a chosen date from the Habits view (`FR-HAB-8`, extends `FR-HAB-4` / `DM-HABIT-5`)

*Source: `FR-2026-07-11-c`. Extends `FR-HAB-4` and `DM-HABIT-5`. Does not modify existing "Mark today done" / collapsed-row log behaviour.*

`DM-HABIT-5` names two logging paths: via a linked task marked Done, or "edited directly on any date". The second path was implemented in v2.0.0 only at repository level (`HabitRepository.logDirect(habitId, date, done, amount)`) and surfaced in the UI as **"Mark today done"** on the expanded card and the log pill on the collapsed row (v2.1.0 `FR-HAB-5`). Both are **today-only**. A user who forgot to mark a habit yesterday, or wants to fill in a gap from earlier in the week, currently has no in-app path — the "any date" half of `DM-HABIT-5` is unreachable from the Habits view.

`FR-HAB-8` **The Habits view exposes a secondary "log a chosen date" affordance that opens a date picker, then applies the direct-log path for the picked date.** The existing "Mark today done" / collapsed-row log affordance is unchanged; the new affordance is additive.

#### 2.5.1 Where the affordance lives (`FR-HAB-8.1`)

`FR-HAB-8.1` **The "log a date" control is presented on the expanded habit card only**, as a second control next to (or immediately below) "Mark today done". It is **not** added to the collapsed row. Rationale: the collapsed row's contract from v2.1.0 `FR-HAB-5.1` is scan-first — one prominent log pill for today, no per-row controls that require picking values. A date picker is not a scan-first affordance; users who want it can expand the card, which is one tap. Keeping the collapsed row untouched preserves the v2.1.0 collapse-by-default win.

The label on the affordance is **"Log a date…"** (the ellipsis matches Den convention for "opens a picker / sheet"). The affordance is a `PillButton`-shaped control matching "Mark today done" visually, but rendered in the `Den.muted` foreground / neutral background pair (not the primary rust) so the primary today-log affordance still reads as the dominant call to action.

`FR-HAB-8.1.1` **Log and edit and log-a-date are three separate tap targets in every state.** `FR-HAB-7.2` already requires log and edit to be isolated hit targets; `FR-HAB-8.1.1` extends that: on the expanded card, "Mark today done", "Log a date…", and the edit affordance are three distinct controls with distinct content descriptions. Tapping any one must not open either of the other two. Hit-target sizes continue to meet `NFR-A11Y-1`.

#### 2.5.2 The picker and the log write (`FR-HAB-8.2`, `FR-HAB-8.3`)

`FR-HAB-8.2` **Tapping "Log a date…" opens a `CalendarPicker` in a `DenSheet` titled "Log which day?".** The picker allows any date on or before today. Future dates are disabled — logging tomorrow's habit is not a use-case `DM-HABIT-5` covers and would allow "pre-completing" a habit, which conflicts with the honest-timeline spirit of `DM-HABIT-3/4`. There is no earliest-date floor beyond what `CalendarPicker` naturally supports.

`FR-HAB-8.2.1` **Picking a date closes the picker and either logs immediately or opens the amount prompt**, depending on `HabitKind`:

- **`frequency` habit** — the picker closes and `HabitRepository.logDirect(habit.id, pickedDate, done = true, amount = null)` runs. No confirmation dialog is shown; the log entry appears immediately in the calendar grid (v2.0.0 `FR-HAB-1`'s calendar-style history).
- **`quantitative` habit** — the picker closes and the existing `AmountSheet` opens (the same sheet the "Mark today done" pill opens on a quantitative habit), but its title reads **"Log Wed, Jul 8 · <habit name>"** (the picked date, not "today") and `HabitRepository.logDirect(habit.id, pickedDate, done = true, amount = <entered>)` runs on confirm. `AmountSheet.suggested` follows the same rule already used for today: the current `logs` entry for the picked date if any, else `habit.target`.

`FR-HAB-8.3` **If a `frequency` log already exists on the picked date, tapping "Log a date…" and picking that same date toggles the log off (deletes the log row via `logDirect(..., done = false, amount = null)`).** This mirrors the existing "tap the log pill twice on the collapsed row / expanded card to un-mark today" behaviour — the affordance semantics are consistent across today-logs and picked-date logs. On a `quantitative` habit, the `AmountSheet`'s existing behaviour applies (entering `0` un-logs; entering a positive amount replaces).

`FR-HAB-8.4` **Attribution: a picked-date log follows the same goal-progress rules as a today-log** — `DM-ATTR-1..3` are unchanged. Specifically, a picked-date frequency-habit tick auto-advances a matching-unit Accumulative goal at most once per date (the dedup is per-date, not global), and `DM-ATTR-3` continues to hold — the habit→goal advance is only automatic when units match. This is already how `HabitRepository.logDirect` composes with the attribution engine on today's date; no behavioural change is needed here.

`FR-HAB-8.5` **The picker announces to TalkBack as "Log which day?" and the confirm interaction announces the picked-date completion (e.g. "Habit logged for Wed, Jul 8") consistent with `NFR-A11Y-1`.** The "Log a date…" pill's content description is "Log a chosen date" (distinct from the today-log pill's "Mark today done" / "Un-mark today").

> **[DECISION] — Expanded card only, not the collapsed row.**
> An alternative was to add the affordance to the collapsed row (as a second sub-pill next to the log pill). Rejected: the collapsed row's contract is scan-first (`FR-HAB-5.1`), and a picker is not a scan-first affordance. Users who miss yesterday will expand the card — that's one tap, and it also lets them see the calendar grid where their picked-date log will appear. The one-tap cost matches the "less-frequent operation gets one more tap" pattern the edit affordance (`FR-HAB-7`) already established.

> **[DECISION] — Future dates are disabled.**
> A permissive alternative was to allow any date. Rejected: pre-logging a habit for tomorrow undermines `DM-HABIT-3/4`'s honest timeline (weeks-to-months, not "pre-book your streak"). If a user wants to log ahead, they can log it on the day. Same-day-in-the-past use cases are all reachable.

**Acceptance criteria**

1. On the **expanded** habit card, a second "Log a date…" pill is visible next to (or immediately below) "Mark today done", in a muted style distinct from the primary rust today-log affordance.
2. On the **collapsed** habit row, the affordance is not shown — the row remains the same one-log-pill scan-first layout from v2.1.0 `FR-HAB-5`.
3. Tapping "Log a date…" opens a `DenSheet` titled "Log which day?" containing a `CalendarPicker` restricted to today and earlier dates; future dates are disabled and cannot be selected.
4. Picking a date on a **frequency** habit closes the sheet and creates a log entry for that date. The calendar-style history on the card updates immediately to show the newly-logged day.
5. Picking a date on a **quantitative** habit closes the calendar sheet and opens the `AmountSheet` with title "Log <date> · <habit name>"; entering an amount and confirming creates the log for the picked date.
6. Picking a date on a **frequency** habit that already has a `done = true` log for that date deletes that log (toggles it off), consistent with the today-log toggle semantics.
7. A picked-date log advances a matching-unit Accumulative goal per `DM-ATTR-1..3` — same rules as a today-log. Non-matching units do not auto-advance a goal.
8. TalkBack announces the affordance as "Log a chosen date" on the pill, and "Log which day?" on the sheet's header.
9. No streak / points / badges / adherence surface is introduced (`DM-NOT`).
10. `FR-HAB-4`, `FR-HAB-5`, `FR-HAB-5.1`, `FR-HAB-7`, `FR-HAB-7.2`, `DM-HABIT-3/4/5`, and `DM-ATTR-1..3` all continue to hold unchanged.

**Out of scope for v2.4.0**

- **A "log a range of dates" bulk affordance.** Backfilling a whole week is a separate design; per-date is enough for the "I forgot yesterday" use-case the request names.
- **Editing a picked-date log via long-press on the calendar grid.** The calendar-history grid stays view-only; edits happen via the affordance.
- **Adding the affordance to the collapsed row.** See `FR-HAB-8.1` `[DECISION]`.
- **Backdated logs contributing to a Focus / Review "reflect" surface as if made in real time.** Review reads history as-of the review date; a backdated log is a normal log with an earlier `date` field, no special ledger.

### 2.6 Overdue action-set + tappable checkbox in Planning (`FR-PLAN-4`, refines `FR-PLAN-3`)

*Source: `FR-2026-07-11-d`. Refines `FR-PLAN-3` (overdue is presented as "decide what to do with these").*

`FR-PLAN-3` presents overdue tasks as a calm decision panel — four `PillButton`s under each overdue row (`Today` / `Reschedule` / `Someday` / `Drop`) and a display-only `TaskCheckbox` next to the title. Two things about this shape have proved friction-y in practice:

- **The checkbox is not tappable.** Users expect the standard "tap the box → mark it done" affordance that Today, Planning's non-overdue rows, All Tasks, and Backlog all offer. Because overdue rows behave differently, tapping the box currently opens the task editor (via the `pressable(onOpen)` on the whole row) — an *interrupt* on the natural "just tick it off" gesture.
- **The `Someday` and `Drop` buttons are two of four fingers on a small row, and both are corner-case actions that duplicate what the `StateSheet` (`Change Status`) already offers.** `Someday` is `→ Backlog`; `Drop` is `→ Closed`. Both are reachable via the existing state sheet; presenting them as first-class chips on every overdue row weights them more than their use-frequency merits, and — critically — nudges the user to *close-or-park* overdue work rather than *do or defer* it, which is the opposite of what `FR-PLAN-3`'s calm-decision framing is meant to elicit.

`FR-PLAN-4` **Overdue `DecideCard`s in Planning replace `Someday` / `Drop` with a single `Change Status` action that opens the existing `StateSheet`, keep `Today` and `Reschedule`, and make the checkbox a first-class tap target that marks the task Done.**

#### 2.6.1 The revised action row (`FR-PLAN-4.1`, `FR-PLAN-4.2`)

`FR-PLAN-4.1` **The overdue row exposes exactly three `PillButton`s, in this order and copy:** `Today` · `Reschedule` · `Change Status`.

- **`Today`** — unchanged. Calls `vm.doToday(task.id)` (the existing "set To Do Date = today" path).
- **`Reschedule`** — unchanged. Opens the existing `CalendarPicker` sheet ("Move it to") which then calls `vm.rescheduleTo(task.id, pickedDate)`.
- **`Change Status`** — new. Opens the existing `StateSheet` composable for that task (`current = task.state`, `isRecurring = task.seriesId != null`), routing its `onPick` into `vm.toState(task.id, targetState)`. This gives the user access to every legal state transition — Done, Closed, Frozen, Backlog (the previous `Someday`), Open — through the app's single, calm state UI, rather than two hand-picked shortcuts.

`FR-PLAN-4.2` **`Someday` and `Drop` are removed from the overdue action-row entirely.** They are not moved to an overflow menu — the `Change Status` sheet is where they live, along with all other transitions. The `onSomeday` / `onDrop` / `somedayGuardTask` wiring inside `PlanningScreen` becomes dead code; when the guard for a recurring→Backlog transition applies, it is now surfaced from inside the `StateSheet`'s existing `RecurringCannotBacklog` guard pane (which the `StateSheet` already renders on-demand — `initialGuard` is only needed if we bypass the list). Because `Change Status` opens the state list first, we drop `initialGuard = StateMachine.Guard.RecurringCannotBacklog` — the guard fires naturally if the user picks Backlog on a recurring task, which is the same behaviour every other `StateSheet` entry point gets.

#### 2.6.2 The checkbox becomes a tap target (`FR-PLAN-4.3`)

`FR-PLAN-4.3` **The `TaskCheckbox` inside each overdue `DecideCard` becomes tappable and marks the task Done.** Tapping the checkbox triggers `requestToggle(task)` — the same helper Planning already uses on non-overdue rows, which correctly routes to the `AmountSheet` for a quantitative-habit-linked task (`DM-HABIT-5` / `DM-GOAL-3`) or `vm.toggleDone(task.id)` for everything else. This matches the checkbox behaviour on Today, on Planning's non-overdue dated groups, and on All Tasks.

`FR-PLAN-4.3.1` **Tapping the title / row body still opens the editor.** The `pressable(onOpen)` on the whole row is preserved so users who want the editor still get it. The checkbox becomes an *isolated* hit target ahead of the row's press area, using the same pattern `TaskRow` already uses on non-overdue rows (the checkbox has its own `pressable(onToggle)` that consumes the tap before the row's `pressable(onOpen)` sees it).

`FR-PLAN-4.3.2` **Marking an overdue task Done via the checkbox does not first prompt the user to re-date it.** The task remains at its overdue `toDoDate` (which is now in the past); Done from a past To Do Date is a legal, expected state transition (`DM-TASK-1`) — the historical To Do Date is preserved so the Journey / Review can show *when* the task was originally planned versus *when* it was completed. The `Done`-transition's side-effects (linked-habit tick per `DM-HABIT-5` — logged on `task.toDoDate ?: today` per `HabitMath` — and goal contribution per `DM-ATTR`) fire exactly as they do for a same-day Done.

`FR-PLAN-4.4` **`FR-PLAN-3`'s calm-framing voice is preserved.** The "DECIDE →" kicker, the "SLIPPED Nd AGO" meta, and the `Den.due` accent all remain. The action row's three-button layout continues to read as a decision panel; the checkbox is not a fourth button visually — it stays the standard checkbox chrome, not a chip.

> **[DECISION] — `Change Status` opens `StateSheet`, not a compact inline menu.**
> An alternative was to add a small overflow menu (`⋮`) that offered every state transition inline. Rejected: `StateSheet` is the app's single, calm state-transition surface (`DM-TASK-1..3`), including all guard copy (freeze-a-series confirm, recurring-can't-backlog). Duplicating that copy inline would risk drift; reusing the sheet is one line of code and stays consistent with All Tasks / editor's own state-change routes.

> **[DECISION] — The task keeps its original overdue To Do Date on Done.**
> An alternative was to bump `toDoDate` to today when the user checks off an overdue task ("done today, so date it today"). Rejected: it silently rewrites history. The Journey / Review reads `toDoDate` as the *planned* date, and `Task.completedAt` (already stored) as the *actual*; the two-value shape is the honest record. `Today` is available as a distinct action for the case where the user wants to reflect "I'm actually doing this today".

**Acceptance criteria**

1. On each overdue row in Planning, exactly three `PillButton`s are rendered in this order: `Today`, `Reschedule`, `Change Status`. `Someday` and `Drop` are no longer present.
2. Tapping `Today` calls `vm.doToday(task.id)` — behaviour unchanged from v2.3.0.
3. Tapping `Reschedule` opens the existing `CalendarPicker` sheet; picking a date calls `vm.rescheduleTo(task.id, pickedDate)` — behaviour unchanged.
4. Tapping `Change Status` opens the `StateSheet` for the task with `current = task.state`, `isRecurring = (task.seriesId != null)`; picking any state routes to `vm.toState(task.id, target)`. All existing guards (recurring-can't-backlog, freeze-terminates-series) fire from inside the sheet unchanged.
5. Tapping the checkbox on an overdue row marks the task Done via the same helper (`requestToggle`) used on Planning's non-overdue rows: quantitative-habit tasks route to `AmountSheet`; everything else calls `vm.toggleDone(task.id)`.
6. Tapping the checkbox does **not** open the task editor. Tapping the row title / body area still does.
7. Marking an overdue task Done via the checkbox does not rewrite `task.toDoDate`; the task's original planned date is preserved.
8. The overdue group's calm framing — "DECIDE →" kicker, `Den.due` accent, "SLIPPED Nd AGO" per-row meta — is unchanged.
9. TalkBack announces the checkbox on an overdue row with a "Mark done" content description (matching the checkbox on non-overdue rows); the three action pills announce their own labels.
10. No streak / points / badges / adherence surface is introduced by the change (`DM-NOT`).

**Out of scope for v2.4.0**

- **A "Done for all overdue" batch button.** The whole point of `FR-PLAN-3`'s decide panel is per-task judgement; a batch is a different UX and would need its own justification.
- **Rewriting `toDoDate` to today on overdue-Done.** See `[DECISION]` above.
- **Presenting the `StateSheet` inline (bottom-sheet peek) versus the current full-height sheet.** Sheet chrome is out of scope; the requirement is that the sheet is what opens.
- **Adding a `Change Status` action to non-overdue rows.** Non-overdue rows already reach state-change via the editor; the overdue row's needs are the specific concern here.

### 2.7 Positive completion chime on Done (`FR-AUDIO-1`, new area, refines `FR-TODAY-1` / `FR-ALL-2` / `FR-PLAN-3` completion-tap behaviour)

*Source: `FR-2026-07-11-e`. Introduces the `FR-AUDIO-*` area (previously empty). Refines the checkbox-tap side-effects on Today, Planning, All Tasks — audio is added; visible behaviour is unchanged.*

`DM-NOT` and `DEC-2/3/4` lock out streaks, points, badges, and adherence percentages — the accumulating, comparative surfaces that turn "did the thing" into "scored the thing". A **single, one-off completion chime** on Done is not that shape: it is *tap feedback* on a specific action (Open → Done via the checkbox), analogous to the platform-standard soft "check" sound that macOS uses on Reminders complete and iOS uses on some system taps. It carries no counter, does not compound over time, and does not compare the user to any target. It is `PRIN-2`-compatible (calm voice, positive framing) and does not introduce any of the anti-patterns `DM-NOT` names.

`FR-AUDIO-1` **When a task moves Open → Done via a checkbox tap (Today, Planning, All Tasks — including the overdue-row checkbox from `FR-PLAN-4`), the app plays a short, gentle positive chime.**

#### 2.7.1 What plays, and when (`FR-AUDIO-1.1`, `FR-AUDIO-1.2`)

`FR-AUDIO-1.1` **The chime is a short (≤ 500 ms), soft, positive tone-cluster** shipped as a single audio asset in `app/src/main/res/raw/chime_done.<ext>` (implementer's choice of `.ogg` / `.m4a` — pick the smallest asset that renders cleanly across API 26+). Voice: a two-note ascending pair or a single soft mallet-struck tone. It must not be a "success!" fanfare and must not include any voice or lyric.

Concrete acoustic profile:
- **Duration:** ≤ 500 ms, no reverb tail past that ceiling.
- **Peak:** normalized around −6 dBFS so the chime is audible over ambient without being sharp.
- **Timbre:** soft mallet, marimba, or bell-with-fast-decay — nothing brassy, nothing synth-arcade.
- **Onset:** ≤ 15 ms attack; no click.

Implementer's discretion on the exact sample; the acoustic profile above is the constraint.

`FR-AUDIO-1.2` **The chime fires on exactly one transition: `Open → Done` via a checkbox tap on Today / Planning / All Tasks.** It does **not** fire on:

- **Undo** (Done → Open via the same checkbox) — the reverse tap is silent.
- **State-sheet transitions** that happen to land on Done (`vm.toState(id, DONE)`) — those are contemplative decisions, not the daily "tick it off" gesture; adding a chime there would make the state sheet feel congratulatory.
- **Batch completions** (if / when they exist).
- **Habit logs** — `FR-HAB-4` / `DM-HABIT-5` direct logs and `FR-HAB-8` picked-date logs do **not** chime. Habits are already framed as "rhythm, not score" (`DM-HABIT-3`); adding a chime per log would push them toward the streak feel `DEC-2` locks out.
- **Review / Focus / Journey** scans and edits.
- **Sync-driven Done writes** (if a Done was applied on another device and syncs in) — the chime is tied to a *user gesture on this device*, not to the observed state change.

`FR-AUDIO-1.3` **The chime uses `AudioAttributes.USAGE_ASSISTANCE_SONIFICATION` (or `USAGE_NOTIFICATION_EVENT` if `USAGE_ASSISTANCE_SONIFICATION` proves unreliable on some OEMs) with `CONTENT_TYPE_SONIFICATION`.** Playing on the notification/sonification stream ensures the chime respects the device's Do Not Disturb, ringer mute, and Bluetooth-routing behaviour. It must not play on the `USAGE_MEDIA` stream — the chime is not media.

`FR-AUDIO-1.4` **Playback uses `SoundPool` or an equivalent low-latency player.** `MediaPlayer` is acceptable if latency in practice stays under ~150 ms from checkbox tap to onset, but `SoundPool` is preferred because it pre-loads the asset and avoids the "tap → 400 ms silence → chime" perception on cold play. Whichever primitive is chosen, it must not leak: the player is initialised once (Application scope or a small `ChimePlayer` service) and released on process teardown.

#### 2.7.2 The Settings toggle (`FR-AUDIO-1.5`, `FR-AUDIO-1.6`, `FR-AUDIO-1.7`)

`FR-AUDIO-1.5` **A Settings toggle "Completion chime" defaults to `ON` and lets the user turn the chime off.** Location: inside the existing Settings screen (`FR-SET`), in a new row or a small "Sounds" section. Persisted via `SettingsStore` (new key `chime_enabled: Boolean`, default `true`). When `false`, `FR-AUDIO-1.2` is a no-op — no chime, no side effect.

`FR-AUDIO-1.6` **The toggle's copy is calm and value-neutral.** Label: "Completion chime". Subtitle: "Plays a short sound when you check off a task." No "boost your focus" / "celebrate wins" framing — that language is gamification-adjacent (`PRIN-2`).

`FR-AUDIO-1.7` **The device's own sound profile is authoritative.** If the phone is on silent, or Do Not Disturb suppresses notification sonification, the chime is inaudible regardless of the Settings toggle. Because `USAGE_ASSISTANCE_SONIFICATION` / `USAGE_NOTIFICATION_EVENT` routes through the notification stream, this is automatic — the app does not need to check ring mode itself. The Settings toggle is a *user preference*, not a mute switch layered on top.

#### 2.7.3 Accessibility and no-regression (`FR-AUDIO-1.8`, `FR-AUDIO-1.9`)

`FR-AUDIO-1.8` **The chime is additive, not a replacement.** All existing visible feedback on Done — checkbox fill, row strike-through, Journey entry write — continues to fire regardless of chime state. A user with the chime off (or on a silenced device) sees exactly the same visual completion feedback as v2.3.0. A user relying on visual feedback loses nothing.

`FR-AUDIO-1.9` **Playback does not block, throttle, or debounce the state write.** The checkbox tap continues to call `requestToggle(task)` / `vm.toggleDone(task.id)` synchronously; the chime fires from the same tap handler as a fire-and-forget side effect. If audio initialisation fails silently (missing asset, hardware error), the state write must not be affected — the chime is best-effort.

> **[DECISION] — Chime on the checkbox tap, not on any Done transition.**
> An alternative was to fire on every Open → Done regardless of entry path (state sheet, editor save, etc.). Rejected because the "tap-feedback" framing that keeps this clear of `DM-NOT` depends on the chime being tightly bound to the *tap gesture that just happened*. Firing on state-sheet Done or on an editor-save Done would decouple the sound from the tap and drift toward "the app celebrates your progress" — which is exactly what `DEC-2/3` prohibits.

> **[DECISION] — Default `ON`, single toggle, no volume slider.**
> Two alternatives: (a) default `OFF` with the toggle in a "sounds" subsection and (b) an in-app volume slider. (a) was rejected because the request phrasing ("make a nice positive short chime sound") clearly wants the sound present out of the box; a user who dislikes it has one toggle. (b) was rejected because the device's own volume rocker + silent-mode already give the user granular control on the notification stream — an in-app slider duplicates system settings for no perceived gain.

> **[DECISION] — No chime on habit logs.**
> `FR-HAB-4` / `FR-HAB-8` deliberately do not chime. Adding a chime per habit log would frame habits as accumulating "wins", edging toward the streak feel `DEC-2` locks out. Habit logging stays visually confirmatory (the log pill state changes, the calendar grid updates) — that's the honest feedback shape.

**Acceptance criteria**

1. Tapping the checkbox on a Today / Planning (dated group or overdue) / All Tasks row that transitions the task Open → Done plays the chime asset from `res/raw/chime_done.*` once, ≤ ~200 ms after the tap.
2. Tapping the checkbox again to un-mark (Done → Open) does not play the chime.
3. Marking a task Done via the `StateSheet` (from `Change Status` in Planning's overdue row `FR-PLAN-4`, or from All Tasks / editor) does not play the chime.
4. Marking a habit log — via "Mark today done" (`FR-HAB-4` / `FR-HAB-5`), via the amount sheet, or via the new "Log a date…" affordance (`FR-HAB-8`) — does not play the chime.
5. When the Settings toggle "Completion chime" is off, no Open → Done tap plays audio; when on, taps play audio (subject to device ringer / DND).
6. When the device is silenced (ringer off or DND blocking notification sonification), no chime is audible even with the toggle on — playback routes through the notification stream so the OS handles this automatically.
7. The chime audio asset itself is a soft, positive, ≤ 500 ms tone; no voice, no fanfare, no reverb tail past the ceiling; peaks at ~ −6 dBFS.
8. The state write on Done is unaffected by chime playback — a chime-init failure does not cause the checkbox tap to no-op.
9. No streak / points / badges / adherence surface is introduced by the chime; nothing accumulates in the UI as a consequence of the chime firing (`DM-NOT`).
10. `AudioAttributes.usage` is `USAGE_ASSISTANCE_SONIFICATION` or `USAGE_NOTIFICATION_EVENT`; it is not `USAGE_MEDIA`.

**Out of scope for v2.4.0**

- **Multiple chime variants / sound-pack picker.** One built-in chime is enough; a picker introduces surface without evidence of demand.
- **Haptic feedback on Done.** Haptics are a separate, complementary channel; adding them here would double the design surface and needs its own request.
- **Habit-log chime.** See `[DECISION]` above.
- **A "celebration burst" animation.** No visual celebration; the chime is audio-only, and the existing checkbox fill / strike-through is the visual.
- **Firing the chime from the state sheet or editor-save Done.** See `[DECISION]` above.
- **Volume slider inside the app.** The system stream and the on/off toggle are the two knobs.
