## 1. Scope of v2.10.0

v2.10.0 is a **focused bug-fix / consistency increment** on top of a shipped v2.9.0. Two source requests are groomed here — an RTL alignment miss on the *read* half of the Goal-step fix that v2.9.0 introduced, and a two-part fix on the `AT_TIME` cue path (save-gate label rule + reminder-delivery reliability). Neither introduces a schema change, a new user surface, or a new preference; each closes a small gap between what the spec already says and what the app currently shows.

- **`FR-2026-07-23-a` → `FR-DESIGN-3.7`.** v2.9.0 shipped `FR-DESIGN-3.6` to lay out the Goal-step row `LayoutDirection.Rtl` when the step's label is RTL. The **editor** row (`GoalEditorSheet`) got this right by construction because its label `Text` already carries `Modifier.weight(1f)` and the surrounding step-list `Column` is populated one row per line — the wrapper flips the row, the weighted `Text` fills, and the checkbox lands at the trailing (right) edge. The **read-view** row (`GoalCard`, `ui/goals/GoalCard.kt:161-186`) is a shrink-to-content `Row` inside an LTR outer `Column`, and the label `Text` has no `weight` or `fillMaxWidth`; providing `LayoutDirection.Rtl` inside a row that never fills the width simply reorders its two shrunk children from right-to-left starting at the row's *own left edge*, which is exactly the visual the reporter still sees — checkbox on the left, Hebrew glyphs to its right, huddled at the left margin. `FR-DESIGN-3.7` extends `FR-DESIGN-3.6`'s row to fill the width and gives the label a `weight(1f)` so the RTL flip actually moves the checkbox to the right and anchors the label to the reading margin, matching how the editor already renders.
- **`FR-2026-07-23-b` → `FR-CUE-2` + `FR-NOTIF-4`.** The reporter's request has two parts, both on the `AT_TIME` cue path:
  - **`FR-CUE-2` — the label may be empty on `AT_TIME`.** `FR-CUE-1.5` gates the "Set the cue" button on `label.isNotBlank() && (type != CueType.AT_TIME || isValidHhMm(time))`. On a time-driven cue the *time* is what fires the reminder — the label is descriptive prose. The reporter's point is that requiring a non-blank label on `AT_TIME` is over-strict: a user who just wants "remind me at 08:30" should not have to invent a label. `FR-CUE-2` relaxes the `AT_TIME` half of the gate to `isValidHhMm(time)` only; `AFTER_ROUTINE` and `AT_PLACE` continue to require a non-blank label (they have no other field to identify the cue by). The `NotifyLogic.cueLine` composer (`domain/notify/NotifyLogic.kt:38-46`) already renders a label-less cue as the time string alone (`label.isEmpty() → time ?: ""`), so the notification body degrades cleanly to `"08:30"` when no label is supplied — no downstream change required.
  - **`FR-NOTIF-4` — `AT_TIME` reminders fire at the set time, not "some time later".** `FR-NOTIF-2` promised `AlarmManager` for exact-time cues, and `NotifyScheduler.schedule` (`notify/NotifyScheduler.kt:57-62`) attempts `setExactAndAllowWhileIdle` — but only *if* `alarms.canScheduleExactAlarms()` returns true. On Android 12+ (API 31+), the `SCHEDULE_EXACT_ALARM` permission the manifest declares (`AndroidManifest.xml:6`) is a *special access* grant that a fresh install on API 33+ does **not** receive automatically; the user must approve it in Settings → Apps → Tzafon → Alarms & reminders. Because the app never surfaces this state (or offers a one-tap route into that Settings page), a typical install silently falls back to `setAndAllowWhileIdle`, which Android may defer by minutes to hours — the "fires at an unrelated time" symptom the reporter observes. `FR-NOTIF-4` adds a Settings-side affordance to detect the missing exact-alarm access, explain what it costs the user, and hand them the standard `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` intent to grant it. Delivery on grant is unchanged (still the `setExactAndAllowWhileIdle` path already coded); the fix is closing the perception gap and shepherding the user through the OS-mandated grant.

Neither is gamification-adjacent: a shrink-to-content layout fix on an existing row, a two-token relaxation on a save-gate expression, and an operating-system-permission affordance. `DM-NOT` and `DEC-2/3/4` continue to hold. All other locked decisions from v2.0.0 — the five-tab primary structure (`FR-NAV-1`), the compass / chosen-direction thesis, local-first-with-clean-seam persistence, the Fox Works "Den" identity, the state-machine and recurrence model, and `PRIN-9` "never engagement-bait" — are untouched. Note in particular that `FR-NOTIF-4` does **not** change *what* is delivered (`NotifyLogic.remindersFor(...)` is unchanged) — only *how reliably* the OS delivers it on time.

## 3. Functional requirements

### 3.1 Goal-card step rows visibly RTL — the row fills, the label weights (`FR-DESIGN-3.7`, refines `FR-DESIGN-3.6`)

*Source: `FR-2026-07-23-a`. Refines `FR-DESIGN-3.6` (v2.9.0 — Goal-step row respects content-direction on RTL labels). Scope is the `GoalCard` step row (`ui/goals/GoalCard.kt`); the `GoalEditorSheet` step row is already correct (its label `Text` carries `Modifier.weight(1f)`, so the v2.9.0 wrapper works as intended there) and stays as-is.*

`FR-DESIGN-3.6` wraps the Goal-card step row in `CompositionLocalProvider(LocalLayoutDirection provides LayoutDirection.Rtl)` when the step's label starts with a strong RTL character, and expects the RTL layout direction to place the checkbox on the trailing (right) edge and let the label extend leftward from it. The wrapper does exactly what it says — the inner `Row`'s child order flips right-to-left — but the `Row` in `GoalCard` has neither `fillMaxWidth()` nor a weighted child, so it collapses to the width of `checkbox (14.dp) + 5.dp gap + text(intrinsic)` and clings to the *outer* Column's start edge, which is still LTR because the wrapper is *inside* the Column, not around it. The visible result is what the reporter reports: checkbox on the left, Hebrew glyphs to its right, both huddled at the left margin — exactly what the fix was supposed to eliminate.

`FR-DESIGN-3.7` **completes `FR-DESIGN-3.6` on the Goal-card step row: the wrapped `Row` fills the card's width, and the step-label `Text` carries `Modifier.weight(1f)` so it consumes the remaining space; with those two additions the ambient `LayoutDirection.Rtl` inside the wrapper actually moves the checkbox to the right and anchors the RTL glyphs to the right reading margin.**

- **`FR-DESIGN-3.7.1` The step `Row` fills the width.** In `ui/goals/GoalCard.kt` (roughly `lines 162-166`), add `.fillMaxWidth()` to the `Row`'s `Modifier` chain (currently only `Modifier.pressable { onToggleStep(i) }`). The row now spans the enclosing `Column`'s inner width; under `LayoutDirection.Rtl` the row's *own* start-to-end axis runs right-to-left across that full width, so its first-placed child (the checkbox) lands at the right edge and its second child (the label) fills leftward from there.
- **`FR-DESIGN-3.7.2` The label `Text` takes a `weight(1f)`.** Add `Modifier.weight(1f)` to the step-label `Text` (currently no `Modifier`; roughly `lines 176-183`), mirroring `GoalEditorSheet.kt:181`. The weighted label now consumes the row's remaining horizontal space, so its own `TextDirection.Content` alignment (from the existing `.contentDir()` on the `TextStyle`) lands the RTL glyphs at the right edge of that space — under the wrapper's `LayoutDirection.Rtl`, "right" is the layout's *start*, so the glyphs anchor to the reading margin exactly where the reader's eye enters.
- **`FR-DESIGN-3.7.3` The pressable target stays the whole row.** `Modifier.pressable { onToggleStep(i) }` on the outer `Row` is preserved; adding `fillMaxWidth()` makes the touch target larger (the row now spans the card width, so tapping anywhere on the row toggles the step) — a modest, welcome side effect that matches the pattern the editor row already has (its `Row` on line 163-167 has no `fillMaxWidth`, but the weighted label absorbs the slack; there the `pressable` is *inside* on the checkbox, so this note only applies to the read-view row).
- **`FR-DESIGN-3.7.4` The LTR case is unchanged in appearance.** For a step whose label starts with an LTR character, the row is not wrapped in an RTL provider (`FR-DESIGN-3.6.2` — the wrapper's condition is `s.label.isRtl()`, unchanged). The added `fillMaxWidth()` + `weight(1f)` on an LTR row makes the row span the card width and the label extend from the checkbox to the card's right edge — visually identical to today (the label was left-anchored either way; the extra whitespace was on the right in both cases). No LTR regression.
- **`FR-DESIGN-3.7.5` The chrome around the steps stays LTR.** `FR-DESIGN-3.6.5`'s "only the step rows are wrapped — the surrounding Goal card / editor keep their ambient (LTR) layout" continues to hold. The card's title `Text` at `GoalCard.kt:104-109` (which uses `.contentDir()` for glyph shaping, not row-flipping), the type tag, the "N of M steps" row, the endowed bar, the percentage, and the ENGINE chips row are all outside the wrapper and stay LTR — the goal-title's Hebrew glyphs continue to shape correctly via `TextDirection.Content` on the `TextStyle`, which is orthogonal to the row-level layout direction.
- **`FR-DESIGN-3.7.6` No `String.isRtl()` change.** The first-strong-character detection helper introduced in `FR-DESIGN-3.6.1` (in `ui/theme/BiDi.kt` per the M3 build note, or wherever it landed) is reused verbatim — the bug being fixed here is *inside* the wrapper, not in its condition.
- **`FR-DESIGN-3.7.7` The strike-through on done steps reads with the label.** The `TextDecoration.LineThrough` applied on `done` steps (`GoalCard.kt:181`) is a *text-style* property that decorates whatever glyph runs the layout produces — under the RTL wrapper the line reads right-to-left through the Hebrew glyphs, matching how strikethrough works in native RTL text on any Android app. No additional decoration change.
- **`FR-DESIGN-3.7.8` `GoalEditorSheet` is out of scope.** The editor's step `Row` at `ui/goals/GoalEditorSheet.kt:164-188` already renders RTL correctly because the label `Text` carries `Modifier.weight(1f)` on line 181; the v2.9.0 `FR-DESIGN-3.6` wrapper works there as intended. This refinement touches only the read-view row.
- **`FR-DESIGN-3.7.9` No `DM-NOT` surface.** RTL alignment is purely visual; no score, adherence, or badge is introduced or altered (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — `fillMaxWidth()` + `weight(1f)`, not per-child alignment tweaks.**
> The alternative — computing `Alignment.End` on the checkbox conditionally and per-side paddings on the label — would work but re-invents what `Row(fillMaxWidth) + Text(weight(1f))` already expresses declaratively. Matching the editor row's shape (`GoalEditorSheet.kt:164-188`) keeps the two composables symmetric and makes future BiDi refinements a one-line change in both places. This is the same reasoning `FR-DESIGN-3.6`'s DECISION gave for using `LocalLayoutDirection` in the first place — keep the row's declarative shape, let the framework do the rest.

> **[DECISION] — Widen the pressable target implicitly, don't wrap it in a separate `fillMaxWidth` box.**
> A defensible alternative was to leave the inner `Row` shrunk and instead put a `Row(fillMaxWidth().pressable(...))` around it. That works but adds a nested `Row` for no visible benefit; the direct `.fillMaxWidth()` on the existing row is one modifier and inherits the existing pressable, giving the same enlarged touch target (`FR-DESIGN-3.7.3`) with less scaffolding.

### 3.2 `AT_TIME` cue may be saved with an empty label (`FR-CUE-2`, refines `FR-CUE-1.5`)

*Source: `FR-2026-07-23-b` (first bullet). Refines `FR-CUE-1.5` (v2.9.0 — "Set the cue" button gates on `label.isNotBlank() && (type != CueType.AT_TIME || isValidHhMm(time))`). Scope is the AT_TIME variant of the shared `CueSheet` (`ui/components/CaptureSheets.kt`) used by both the Task editor (`DM-TASK-4`) and the Habit editor (`DM-HABIT-1`). `AFTER_ROUTINE` and `AT_PLACE` continue to require a non-blank label.*

`FR-CUE-1.5` shipped a save-gate that always required a non-blank label. That was fine for `AFTER_ROUTINE` and `AT_PLACE` — those triggers *are* the label ("after the first coffee", "at the studio") — but over-strict for `AT_TIME`, where the *time* is the load-bearing field. The reporter wants to be able to save a plain "remind me at 08:30" cue without inventing a synthetic label. `NotifyLogic.cueLine` already handles this shape gracefully — `label.isEmpty() → time ?: ""` (`domain/notify/NotifyLogic.kt:41-46`), producing a notification body of just `"08:30"` — so the reminder degrades cleanly.

`FR-CUE-2` **on the AT_TIME variant of the shared CueSheet, the "Set the cue" button gates on a valid `HH:mm` time alone; the label may be empty. AFTER_ROUTINE and AT_PLACE continue to require a non-blank label.**

- **`FR-CUE-2.1` The save-gate expression becomes trigger-aware in both directions.** The current expression at `CaptureSheets.kt:169-170`
  ```kotlin
  val canSave = label.isNotBlank() &&
      (type != CueType.AT_TIME || isValidHhMm(time))
  ```
  becomes
  ```kotlin
  val canSave = when (type) {
      CueType.AT_TIME -> isValidHhMm(time)
      CueType.AFTER_ROUTINE, CueType.AT_PLACE -> label.isNotBlank()
  }
  ```
  (or an equivalent one-liner using an `if` on `type`). The rewrite makes the per-trigger contract explicit — one branch per `CueType` — which is the shape `FR-CUE-1.5` should have grown into once the label rule diverged by trigger.
- **`FR-CUE-2.2` The write path already handles an empty label.** `onSave(Cue(type, label.trim(), time.trim().takeIf { it.isNotBlank() }))` at `CaptureSheets.kt:176` writes `label = ""` when the field is blank; `Cue(type, label = "", time = "08:30")` is a valid domain value (`domain/model/Task.kt` — `Cue.label: String`, not nullable, so `""` is the intended empty sentinel). No `Cue` shape change.
- **`FR-CUE-2.3` The rendered cue on the editor row degrades cleanly.** Task and habit editors render a saved cue via the same `NotifyLogic.cueLine` composer (or its editor-side equivalent) — `label.isEmpty() && time != null → time`, so a label-less `AT_TIME` cue shows as `"08:30"`. Callers rendering `Cue.label` directly (`ui/editor/TaskEditorScreen.kt`, `ui/habits/HabitEditorSheet.kt`) already tolerate an empty string (they render nothing where the label would go, and continue to render the time next to the clock glyph); no editor-side change required.
- **`FR-CUE-2.4` The AT_TIME label placeholder copy is unchanged.** `CaptureSheets.kt:104` still shows "Right after lunch" as the placeholder on AT_TIME — the placeholder is a *hint*, not a mandate; the user reading the placeholder now understands it as optional context they may add. **[DECISION]** below.
- **`FR-CUE-2.5` Switching triggers still re-evaluates the gate.** If the user picks `AT_TIME`, enters `08:30` but leaves the label blank (save enables), then switches to `AFTER_ROUTINE`, the save button *disables* until a non-blank label is entered (the new branch of `FR-CUE-2.1`). Switching back to `AT_TIME` re-enables save on the `08:30` alone. The `remember` state for `label`/`time` continues to persist across chip taps as today (`FR-CUE-1.6`).
- **`FR-CUE-2.6` Applies uniformly to both editors.** `CueSheet` is instantiated by `TaskEditorScreen` (`ui/editor/TaskEditorScreen.kt:222`) and `HabitEditorSheet` (`ui/habits/HabitEditorSheet.kt:123`); the fix is on the shared composable, so both editors inherit it in one change. (`FR-CUE-1.9`, carried.)
- **`FR-CUE-2.7` No visible-error state added.** Consistent with `FR-CUE-1.8`, the disabled state on the save button remains the whole affordance — there is no red hint on an empty label under `AT_TIME` because the empty label is now *valid*; there is no red hint on a missing time either, matching the calm voice (`FR-DESIGN-1`).
- **`FR-CUE-2.8` `NotifyLogic` and `NotifyScheduler` are unchanged.** The reminder pipeline (`domain/notify/NotifyLogic.remindersFor`, `notify/NotifyScheduler.schedule`) already tolerates an empty label on any cue — `cueLine` composes the visible line, and neither the schedule key (`"task-${t.id}-$date"` / `"habit-${h.id}-$date"`) nor the alarm's exact-time computation reads the label. `FR-CUE-2` requires no notify-side change.
- **`FR-CUE-2.9` No `DM-NOT` surface.** A label-less cue changes no score / streak / adherence / badge display (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Keep the placeholder copy on the label field under `AT_TIME`.**
> An alternative was to swap the placeholder to something like "Optional context" when the trigger is `AT_TIME`, to hint that it's now optional. Rejected because (a) the placeholder is short and the user is only in this sheet briefly, (b) the disabled/enabled state on the save button already communicates what is required (the button enables with an empty label as soon as the time is valid — the user *learns* it's optional by using it), and (c) an on-the-fly placeholder swap on chip taps would jitter the sheet's visual rhythm for negligible gain. The v2.9.0 placeholder is preserved.

> **[DECISION] — Symmetric branches, not a mutating boolean.**
> The `when(type)` rewrite (`FR-CUE-2.1`) reads more clearly than `(type == AT_TIME && isValidHhMm(time)) || (type != AT_TIME && label.isNotBlank())`. It also makes the per-trigger contract discoverable in one glance for anyone reading the sheet later — which is likely the same person adding the next `CueType`.

**Acceptance criteria**

1. Open the Task editor for a new task, tap the cue slot to open `CueSheet`, tap the **AT A TIME** chip. Leave the label field blank, enter `08:30` in the time field: the "Set the cue" button is **enabled** (`FR-CUE-2.1`). Tap it: cue is saved with `label = ""`, `time = "08:30"`.
2. Same sheet, blank label, enter an invalid time (`8:3`, `24:00`, empty): button **disabled**. Enter `08:30`: button enables (`FR-CUE-1.4` unchanged, gate is now time-only on AT_TIME).
3. Same sheet, enter a label ("morning routine") and `08:30`: button enabled (`FR-CUE-2.1`, non-empty label is *allowed* on `AT_TIME`, just no longer required). Tap: cue saves with `label = "morning routine"`, `time = "08:30"`.
4. Same sheet, blank label + `08:30`, then switch to **AFTER A ROUTINE**: button **disables** (label is required for `AFTER_ROUTINE`; `FR-CUE-2.5`). Type "coffee": button enables. Switch back to AT A TIME: label field still shows "coffee" and `time` still shows `08:30`; button enabled.
5. Same sheet, blank label + `08:30`, then switch to **AT A PLACE**: button **disables** (label is required for `AT_PLACE`). Type "studio": button enables (`FR-CUE-2.1`).
6. Repeat (1)–(5) starting from `HabitEditorSheet` (open the habit editor's cue row). Behaviour is identical (`FR-CUE-2.6`).
7. Save a label-less `AT_TIME` cue on a task with `toDoDate = today`; open the task in the editor — the cue row reads `08:30` (via `NotifyLogic.cueLine`'s empty-label branch; `FR-CUE-2.3`). Confirm the reminder is scheduled (see also §3.3 acceptance for delivery timing).
8. `DM-NOT` audit clean — no score/streak/badge surface added (`FR-CUE-2.9`).

**Out of scope for v2.10.0**

- **Relaxing the label requirement on `AFTER_ROUTINE` or `AT_PLACE`.** These triggers have no other identifying field; a blank label there would leave the user with an unnameable cue. Requirement is scoped to `AT_TIME` only (`FR-CUE-2.1`).
- **Auto-suggesting a label from context** (task title, habit name). Not requested; a save-gate change is the minimum fix.
- **Changing the placeholder copy on the label field.** Rejected by DECISION.
- **Storing `label = null` instead of `""`.** `Cue.label: String` (non-nullable) is preserved (`FR-CUE-2.2`); the empty string is the sentinel for "no descriptive prose". No migration.

### 3.3 `AT_TIME` reminders fire at the set time — exact-alarm access surfaced (`FR-NOTIF-4`, refines `FR-NOTIF-2`)

*Source: `FR-2026-07-23-b` (second bullet). Refines `FR-NOTIF-2` (v2.0.0 — "Delivery is via native Android notifications — `AlarmManager` for exact-time cues, `WorkManager` for periodic checks"). Scope is the exact-alarm special-access gate that `NotifyScheduler.schedule(...)` (`notify/NotifyScheduler.kt:57-62`) already checks silently, plus a Settings-view affordance so the user can grant it. No change to `NotifyLogic.remindersFor(...)`, `TopUpWorker`, `BootReceiver`, `Notify.postReminder`, or the `AlarmManager` intent shape.*

`FR-NOTIF-2` promised **exact** alarms for time-driven cues, and `NotifyScheduler.schedule` attempts exactly that:

```kotlin
if (alarms.canScheduleExactAlarms()) {
    alarms.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, atMs, pi)
} else {
    alarms.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, atMs, pi)
}
```

The manifest declares `<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" />` (`AndroidManifest.xml:6`), which on Android 12 (API 31) was granted by default. On Android 13+ (API 33+, and Tzafon's `targetSdk = 36`), `SCHEDULE_EXACT_ALARM` is a **user-toggled special access** — a fresh install must have the user visit *Settings → Apps → Tzafon → Alarms & reminders* to enable it, and there is no runtime-permission dialog for it (the standard `POST_NOTIFICATIONS` launcher does not cover it). Because Tzafon never surfaces this state or offers a route to that settings screen, a typical install on modern Android silently falls through to `setAndAllowWhileIdle` — an *inexact* alarm the OS is free to defer by minutes to hours, especially under Doze / battery-saver. The user's observation ("the notification is triggered, but at what seems to be either unrelated or erroneous time") matches this deferral pattern precisely: the reminder does eventually post, but at whatever moment the OS chose to batch it, not at the cue's `HH:mm`.

`FR-NOTIF-4` **on Android 12+ (API 31+), the app detects when exact-alarm special-access is not granted, explains why it matters, and offers a one-tap route to the standard `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` OS settings page. Once granted, the reminder path already delivers exact alarms per `FR-NOTIF-2`; no scheduling-code change beyond this affordance.**

- **`FR-NOTIF-4.1` A "Precise cue timing" row appears in Settings under the existing "Reminders" section.** Directly under the existing `Cue-based reminders` DenSwitch (`ui/settings/SettingsScreen.kt:161-198`), add a second row: title "Precise cue timing", supporting line "Lets `Right after lunch · 08:30` fire *at* 08:30 — not whenever Android next wakes." (or an equivalent calm-voice phrasing consistent with `FR-DESIGN-1` and `PRIN-9`). The row shows a trailing chip / affordance whose state reflects `alarms.canScheduleExactAlarms()` — "Granted" (`Tz.colors.green` dot) when true; "Set up" (a `PillButton` in `Tz.colors.rust`) when false.
- **`FR-NOTIF-4.2` The `Set up` affordance launches the standard OS intent.** Tapping `Set up` fires an `Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM).apply { data = Uri.parse("package:${context.packageName}") }` (matching the Android 12+ contract) with `Intent.FLAG_ACTIVITY_NEW_TASK`. Wrap the call in a try/catch — devices that don't support the intent (rare, but possible on some OEM ROMs) surface the platform's generic app-details screen as a fallback. The row's state re-reads `canScheduleExactAlarms()` on the Settings screen's `onResume` / `LifecycleEventEffect(Lifecycle.Event.ON_RESUME)` so the chip flips to "Granted" as soon as the user returns from the OS page.
- **`FR-NOTIF-4.3` The row is hidden on pre-Android 12 devices.** The exact-alarm special access does not exist below API 31; `canScheduleExactAlarms()` is API 31+. Wrap the row in `if (Build.VERSION.SDK_INT >= 31) { … }` so it does not appear on the small minority of older devices where the app already uses exact alarms without a grant.
- **`FR-NOTIF-4.4` The row is only actionable when `Cue-based reminders` is on.** If the DenSwitch above is off (`remindersOn == false`), the precise-timing row is either hidden or shown disabled (a subdued visual with `Set up` un-tappable and a supporting line "Turn on cue-based reminders first"). Precise timing without reminders enabled would be a no-op. Choice between hidden and disabled is a small design call — hidden keeps the section compact; disabled makes the eventual capability discoverable. **[DECISION]** below prefers **hidden**.
- **`FR-NOTIF-4.5` On first grant, the app immediately re-runs the top-up.** After the user returns from the OS grant flow and the row detects `canScheduleExactAlarms() == true`, the Settings screen calls `TopUpWorker.runNow(applicationContext)`. Every `AlarmManager` alarm previously set with `setAndAllowWhileIdle` is refreshed via `setExactAndAllowWhileIdle` on this pass because `PendingIntent.FLAG_UPDATE_CURRENT` reuses the pending intent (`NotifyScheduler.kt:55`) and `setExact…` supersedes the earlier inexact registration. This closes the gap where a cue saved *before* the grant would otherwise fire inexactly until the next 24-hour periodic top-up.
- **`FR-NOTIF-4.6` No fallback change on the inexact path.** When exact-alarm access is *not* granted (a user who chooses not to enable it), `NotifyScheduler.schedule` continues to fall back to `setAndAllowWhileIdle` — the reminders will fire, just not precisely. This preserves the "reminders work at all without any extra grant" property the app has today; `FR-NOTIF-4` only adds a *path* to precision, it does not gate reminders behind it.
- **`FR-NOTIF-4.7` No new permission.** The manifest already declares `SCHEDULE_EXACT_ALARM` (`AndroidManifest.xml:6`); nothing changes there. **[DECISION]** below rejects introducing `USE_EXACT_ALARM`.
- **`FR-NOTIF-4.8` No change to `NotifyLogic.remindersFor(...)`.** The set of reminders and their `HH:mm` times is unchanged — a task's AT_TIME cue still fires only on `t.toDoDate == today || t.dueDate == today` (`FR-NOTIF-1`); a habit's cue still fires daily unless today's log exists (`FR-NOTIF-1`); the `afterMinutes` intraday filter still drops times already past on the current top-up pass. `FR-NOTIF-4` is a delivery-precision fix, not a reminder-set change.
- **`FR-NOTIF-4.9` No change to the notification body.** `Notify.postReminder(...)` continues to render `title = t.title`, `body = NotifyLogic.cueLine(cue)`. The body degrades cleanly for a label-less `AT_TIME` cue (see `FR-CUE-2.3`) — the notification then reads title="task title", body="08:30".
- **`FR-NOTIF-4.10` The Settings-view row copy avoids engagement-bait.** "Precise cue timing" states what the toggle does; the supporting line uses the user's own cue as its example ("Lets `Right after lunch · 08:30` fire *at* 08:30 — not whenever Android next wakes"). No emoji, no exclamation marks, no adherence framing (`PRIN-9`, `DM-NOT`, `FR-DESIGN-1`).
- **`FR-NOTIF-4.11` No `DM-NOT` surface.** An OS-permission affordance is a plumbing detail; no score / streak / adherence / badge (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Hide the row when `Cue-based reminders` is off; don't disable-and-explain.**
> Both options were considered. **Hide** keeps the Reminders section compact when it has no work to do, matches the Den voice's preference for absence over noise, and reveals the row exactly at the moment it becomes useful (immediately after the DenSwitch flips on). **Disable-and-explain** would advertise a capability the user hasn't opted into yet, which nudges toward "here's another thing to grant" — the opposite of the calm we want (`FR-DESIGN-1`, `PRIN-9`). If future feedback suggests the row is undiscoverable, a small "About cue reminders" caption under the DenSwitch can point at it; not needed for v2.10.0.

> **[DECISION] — Use `SCHEDULE_EXACT_ALARM` + user grant, not `USE_EXACT_ALARM`.**
> `USE_EXACT_ALARM` (API 33+) grants exact-alarm access at install time without a user prompt, but Google Play's policy restricts it to apps whose *primary function* is alarms, timers, or calendars. Tzafon is a task manager whose cue reminders are *one* feature among many (state machine, recurrence, habits, goals, themes, review, journey); declaring `USE_EXACT_ALARM` risks a Play policy strike or app rejection at publication. `SCHEDULE_EXACT_ALARM` + a user-facing affordance is the standards-compliant path for our category — the extra tap on first setup is a small cost the user pays once, in exchange for reliable timing.

> **[DECISION] — Immediate top-up after grant, no scheduled deferral.**
> Waiting for the next 24-hour periodic pass to refresh alarms after the user grants exact access would recreate the same "reminders fired at unrelated time" symptom for cues saved between grant and next top-up. Calling `TopUpWorker.runNow(applicationContext)` on the Settings screen once `canScheduleExactAlarms() == true` is a single line that closes the gap (`FR-NOTIF-4.5`).

> **[DECISION] — No banner on Today about the grant state.**
> An alternative was to surface a one-time nudge on Today ("cue reminders would fire precisely if you allow it — set up in Settings"). Rejected because Today's nudges (`FR-TODAY-4/5/6/8`) are for the user's own state, not for the OS's; adding an "app-plumbing" nudge to Today would dilute the calm surface Tzafon is careful about. The Settings-view row is where the toggle lives and where the user will find it when they wonder why their reminders feel imprecise.

**Acceptance criteria**

1. On a fresh install on Android 13+, open Settings. The "Reminders" section shows the existing `Cue-based reminders` DenSwitch. Turn it on and grant the `POST_NOTIFICATIONS` permission (unchanged). A second row appears under it: "Precise cue timing" — with the `Set up` affordance visible (`FR-NOTIF-4.1`, `FR-NOTIF-4.3`, `FR-NOTIF-4.4`).
2. Tap `Set up`: the OS's *Alarms & reminders* page for Tzafon opens (`FR-NOTIF-4.2`). Toggle it on and press back — the Settings row's affordance flips to "Granted" (`FR-NOTIF-4.2`, on-resume re-check).
3. Save an AT_TIME cue on a task planned for today at a time a few minutes in the future (e.g. current time + 3 min). The reminder posts within the minute of the cue's `HH:mm` (`FR-NOTIF-4.5`, `setExactAndAllowWhileIdle` path). Repeat without the grant: the reminder still fires, but may be deferred by the OS (behaviour today; `FR-NOTIF-4.6`).
4. On a device where the user *revokes* exact-alarm access after granting it (Settings → Apps → Tzafon → Alarms & reminders → off), returning to Tzafon's Settings shows the affordance back to `Set up` (state re-read on resume). Existing alarms fall back to the inexact path on their next scheduling pass (`FR-NOTIF-4.6`).
5. On a device pre-Android 12 (API < 31, unlikely at Tzafon's `minSdk = 26`), the "Precise cue timing" row does not appear; the existing exact-alarm path continues to work as it did in v2.0.0 (`FR-NOTIF-4.3`).
6. Turning `Cue-based reminders` off hides the "Precise cue timing" row (`FR-NOTIF-4.4`). Turning it back on brings it back with its current grant state.
7. Save a label-less AT_TIME cue (per `FR-CUE-2`) on a task planned for today; the notification body reads `08:30` (the time alone; `FR-NOTIF-4.9`, `FR-CUE-2.3`).
8. `DM-NOT` audit clean — no score/streak/badge surface added (`FR-NOTIF-4.11`).
9. TalkBack announces the row as a togglable settings item with a clear supporting line (`NFR-A11Y-1`). The `Set up` affordance has role `Button` and an appropriate `contentDescription`.
10. The `combine(...).debounce(2000)` observer in `TzafonApp.onCreate` (`TzafonApp.kt:160-169`) continues to trigger a `TopUpWorker.runNow(...)` on cue/task/habit edits (unchanged behaviour); after `FR-NOTIF-4.5`'s immediate top-up on grant, the debounced observer keeps the alarms fresh on subsequent edits.

**Out of scope for v2.10.0**

- **Declaring `USE_EXACT_ALARM`.** Rejected by DECISION on Play-policy grounds.
- **A Today-surface banner nudging the user to grant exact-alarm access.** Rejected by DECISION.
- **Enabling `AT_TIME` reminders for tasks whose `toDoDate` / `dueDate` is *not* today.** Preserves `FR-NOTIF-1`'s scope; a task's cue still fires only on the day the task is planned or due.
- **Rescheduling today's *already-past* cue to tomorrow proactively.** The `afterMinutes` filter (`NotifyLogic.remindersFor`, line 72) continues to skip a cue whose time already elapsed; tomorrow's alarm lands on the next daily top-up as today. Changing this into a "tomorrow-first" behaviour is a separate request not filed here.
- **A calendar/geofence-based cue source.** Deferred per `FR-NOTIF-3`.
- **A separate ringtone or channel for cue reminders.** The single `cues` channel with `IMPORTANCE_DEFAULT` (`Notify.kt:26-33`) is unchanged.
- **UI to test-fire a reminder from Settings.** A "Send me one now" tester button would ease diagnosis, but the standard Android grant flow is enough for v2.10.0.
