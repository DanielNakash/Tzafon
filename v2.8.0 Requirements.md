## 1. Scope of v2.8.0

v2.8.0 is a **single-request increment** on top of a shipped v2.7.0. One source request is groomed here:

- **`FR-2026-07-18-a` → `DM-EXPORT-1`, `FR-DATA-1`, `FR-DATA-2`.** Give the user a **data export** they can read and keep, and an **import** that restores it after a data-loss event. The two goals the reporter names — *(1)* "take my data and do whatever they want with it" and *(2)* "import it back … a backup" — set the master constraint: the export is not a *view* of the data, it is a **lossless, round-trippable serialization** of it. That single insight drives the whole shape: a human-readable, non-proprietary, non-encrypted format (**pretty-printed UTF-8 JSON**, `DM-EXPORT-1`) that nonetheless **preserves every field and every relationship** so an import reconstructs the app's state exactly. `FR-DATA-1` is the export half (serialize → write a `.json` file the user picks a location for, from **Settings**); `FR-DATA-2` is the import half (read a picked `.json` file → validate → apply, with a **conflict prompt** when the app is not empty). App preferences are **out of scope** (the reporter's remark A); privacy of the written file is the **user's responsibility** (the reporter's explicit posture), so the file is plaintext by design with a one-line caution at export time.

The feature is delivered in two milestones — **M1 export** (`FR-DATA-1`) then **M2 import** (`FR-DATA-2`) — because import depends on the format M1 establishes. Both are text/serialization + Settings-UI work; neither touches the Room schema, the recurrence engine, or the domain model.

All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), the compass / chosen-direction thesis, local-first-with-clean-seam persistence, and the Fox Works "Den" identity (`FR-DESIGN-1`). Export/import introduce no score, no reward, and no adherence surface — they move the user's own data in and out, nothing more.

> **[DECISION] — Export the *domain* objects as JSON, not the flat Room entity rows, and not the Firestore codec's maps.**
> There are three serializations already in the codebase that a naive reading might reuse: the Room `*Entity` rows (`data/db/Entities.kt`), and `FirestoreCodec.toMap/fromMap` (`data/sync/FirestoreCodec.kt`) which turns those rows into Firestore document maps for the M9b sync path. **Both are rejected as the export payload** because the Room rows encode lists and structured fields as *opaque tokens* — `goalIds`/`themeIds` as CSV strings, `Goal.steps` joined with control characters `␞`/`␟` (`Entities.kt:308-319`), the whole recurrence `Rule` flattened into ~20 sibling columns — which directly violates the reporter's "readily readable" requirement. The **domain** objects (`Task`, `Series`, `Habit`, `HabitLog`, `Goal`, `Theme`, `Review`, `Contribution`) are the *lossless-yet-readable* form: `goalIds` is a real JSON array, `steps` is an array of `{label, done}` objects, the recurrence `Rule`/`dueRule` are nested objects, `cue` is a nested object, enums serialize by name, and every date is already an ISO `yyyy-MM-dd` string (`DM` conventions, v2.0.0). Because `toEntity()`/`toDomain()` are total inverses, the domain model loses nothing the entity holds — so domain-object JSON is **both** readable **and** lossless. Gson is already a dependency (it backs `FirestoreCodec`), so no new library is needed. Overrule only if a caller specifically needs the entity-shaped file; the reporter's two goals both point at the readable domain form.

## 2. Data model

### 2.1 The export document (`DM-EXPORT-1`)

*Source: `FR-2026-07-18-a`. New `DM-EXPORT-*` area. Defines the on-disk backup file only — no Room schema, no domain-model, and no repository shape changes (Room is untouched in v2.8.0; see §4).*

`DM-EXPORT-1` **The export is a single UTF-8, pretty-printed JSON document with a manifest header and one array per data collection, serialized from the domain objects.** The document is self-describing, deterministically ordered, and carries everything an import needs to reconstruct the app's state.

- **`DM-EXPORT-1.1` Envelope shape.** The top-level JSON object has exactly two parts: a **`manifest`** object and a **`collections`** object.

  ```json
  {
    "manifest": {
      "format": "tzafon.export",
      "formatVersion": 1,
      "appVersion": "2.8.0",
      "appVersionCode": 280,
      "exportedAt": 1752790000000,
      "exportedAtIso": "2026-07-18T00:26:40+03:00",
      "counts": {
        "tasks": 42, "series": 3, "habits": 5, "habitLogs": 120,
        "goals": 6, "themes": 4, "reviews": 9, "contributions": 11
      }
    },
    "collections": {
      "tasks": [ /* Task objects */ ],
      "series": [ /* Series objects */ ],
      "habits": [ /* Habit objects */ ],
      "habitLogs": [ /* HabitLog objects */ ],
      "goals": [ /* Goal objects */ ],
      "themes": [ /* Theme objects */ ],
      "reviews": [ /* Review objects */ ],
      "contributions": [ /* Contribution objects */ ]
    }
  }
  ```

- **`DM-EXPORT-1.2` The eight collections are the complete content set.** Exactly the eight domain collections backed by the eight Room tables (`Entities.kt`): `tasks` (`Task` — includes both standalone tasks **and** materialized series occurrences whose id is `{seriesId}__{occurrenceDate}`), `series` (`Series`, carrying the nested recurrence `Rule` and optional `dueRule`), `habits` (`Habit`), `habitLogs` (`HabitLog`), `goals` (`Goal`, carrying the `steps: [{label, done}]` array), `themes` (`Theme`), `reviews` (`Review`, carrying its `snapshot` string), and `contributions` (`Contribution`). No collection is partial: a full export contains every row of every collection.
- **`DM-EXPORT-1.3` The manifest carries version, provenance, and counts — and no identity.** `format` is the constant discriminator `"tzafon.export"`; `formatVersion` is an integer starting at **1** (bumped only when the document shape changes incompatibly, `FR-DATA-2.6`); `appVersion`/`appVersionCode` record the producing build (`BuildConfig`); `exportedAt`/`exportedAtIso` timestamp the export; `counts` gives the per-collection row count so an import can verify completeness (`FR-DATA-2.4`). The manifest deliberately **excludes the Firebase `uid`, email, display name, and any auth token** — the file is content, not identity; on import the data adopts whoever is signed in (`FR-DATA-2.9`, mirroring `FR-AUTH-1.7`).
- **`DM-EXPORT-1.4` Dates stay ISO strings; timestamps stay integers.** Every `yyyy-MM-dd` field already is (and remains) an ISO string; epoch-millis fields (`createdAt`, `stateChangedAt`, `completedAt`, `startedAt`, `lastActivityAt`, `archivedAt`, …) serialize as JSON integers (Long), not doubles — the same number-bridge concern `FirestoreCodec` already handles (`FirestoreCodec.kt:39-43`). No date is reformatted, localized, or offset — a round-trip is byte-stable on the date fields.
- **`DM-EXPORT-1.5` Enums serialize by name.** `TaskState`, `HabitKind`, `LogSource`, `GoalType`, `GoalState`, `ThemeState`, `ArchivedOutcome`, `ReviewKind`, `ReviewStatus`, `ContributionVia`, and the recurrence `Pattern`/`IntervalUnit`/`MonthMode`/`DueMode` all serialize as their Kotlin `name` (e.g. `"OPEN"`, `"QUANTITATIVE"`), matching the string form already stored in Room and used by `FirestoreCodec`. An unknown enum name on import is a validation error (`FR-DATA-2.5`).
- **`DM-EXPORT-1.6` Deterministic serialization.** The document is **pretty-printed** (2-space indent, `GsonBuilder().setPrettyPrinting()`) for readability, and **deterministically ordered** so two exports of unchanged data are identical: collections are emitted in the fixed order of `DM-EXPORT-1.1`, and rows **within** each collection are sorted by a stable key — `createdAt` then `id` for the id-keyed collections, `(habitId, date)` for `habitLogs`, `periodStart` for `reviews`. Determinism makes the file diffable (a user can `git`-track their backups) and makes the round-trip test (`NFR-TEST-1`) an exact-equality check.
- **`DM-EXPORT-1.7` Referential integrity is preserved by construction.** All soft references between collections are plain string ids (there are no DB-level foreign keys — `Entities.kt` columns are nullable strings / CSV): `Task.seriesId|themeId|habitId|goalIds`, `Series.themeId|habitId|goalIds`, `Habit.primaryThemeId|themeIds|goalId`, `HabitLog.habitId|sourceTaskId`, `Goal.primaryThemeId|themeIds`, `Theme.renewedToThemeId` (self-reference), `Contribution.taskId|goalId`, and the deterministic occurrence id `{seriesId}__{occurrenceDate}`. Because a full export includes **every** collection and preserves **every** id verbatim (`DM-EXPORT-1.2`), all references still resolve after an import — the relationships survive without needing FK metadata in the file.
- **`DM-EXPORT-1.8` Forward/backward tolerance is a property of the reader, not the file.** The file records its `formatVersion`; the *reader* (`FR-DATA-2.6`) decides what it accepts. Unknown fields on read are ignored by Gson and missing fields fall to domain defaults (the tolerance `FirestoreCodec.kt:14-16` already relies on) — so a v2.8.0 app reads a future v2.9.0 export's *known* fields, and a future app reads a v2.8.0 export by filling defaults for fields added later. This is what makes the file a durable **backup** rather than a snapshot that rots against a newer app.

## 3. Functional requirements

### 3.1 Export the user's data to a file (`FR-DATA-1`, new `FR-DATA-*` area; lives in `FR-SET-*`)

*Source: `FR-2026-07-18-a` (goal 1: "take my data and do whatever they want with it"). New functional area. Hosted in the Settings view (`FR-SET-*`, the reporter's remark C). Produces a `DM-EXPORT-1` document. Preserves `NFR-OFFLINE-1` (fully local, no network), `DM-NOT`.*

`FR-DATA-1` **A "Export data" action in Settings serializes the entire content set to a `DM-EXPORT-1` JSON document and writes it to a user-chosen location via the Android Storage Access Framework.** The result is a single readable `.json` file the user owns.

- **`FR-DATA-1.1` Entry point in Settings.** A **"Your data"** section is added to `SettingsScreen`, containing an **"Export data"** row (and the `FR-DATA-2` "Import data" row). It sits below the existing account card and above/below the palette + preference rows, styled with the Den section conventions the screen already uses. Tapping "Export data" begins the export flow.
- **`FR-DATA-1.2` The serializer reads every collection through the repository seam.** Export collects the full content set by reading each repository's list surface — `TaskRepository.observeTasks()` / `observeSeries()`, `HabitRepository` habits + logs, `GoalRepository`, `ThemeRepository`, `ReviewRepository`, and the contributions surface — taking a **single snapshot** (`Flow.first()`) of each, off the main thread (a `Dispatchers.IO` coroutine). Nothing goes through storage directly (`TaskRepository.kt:8` "nothing above this interface may touch storage directly"). The snapshot is assembled into the `DM-EXPORT-1` envelope and serialized with a pretty-printing Gson (`DM-EXPORT-1.6`).
- **`FR-DATA-1.3` The file is written via SAF `ACTION_CREATE_DOCUMENT`.** Export launches `ActivityResultContracts.CreateDocument("application/json")` with a **suggested filename** `tzafon-backup-<yyyy-MM-dd>.json` (e.g. `tzafon-backup-2026-07-18.json`). The user picks the destination (Drive, Downloads, Documents, a share target, …); the app writes the UTF-8 bytes to the returned `content://` URI through a `ContentResolver` output stream. The app **never** writes to raw external storage — scoped-storage-clean, no storage permission required.
- **`FR-DATA-1.4` A plaintext caution is shown before/at export.** Because the file is unencrypted by design and privacy of the written file is the user's responsibility, the "Export data" row (or a one-line note in the confirming step) reads a calm, Den-toned caution: **"Your backup is a plain, unencrypted file. Store it somewhere you trust."** No blocking dialog is required — a persistent helper line under the row satisfies this; the caution must be visible before the file is written. **[DECISION]** below.
- **`FR-DATA-1.5` Success and failure are reported.** On a successful write, a snackbar confirms **"Data exported"** (optionally with the row count, e.g. "Exported 200 items"). If the user cancels the SAF chooser, nothing happens and no error is shown (a choice, not a fault — matching `FR-AUTH-1.3`'s cancellation tone). If the write fails (IO error, revoked URI), a snackbar reads **"Couldn't export. Try again."** and the underlying throwable is logged via `Log.w("Tzafon/Data", …)`.
- **`FR-DATA-1.6` Export is read-only with respect to app state.** Producing the file mutates nothing — no row is touched, no `stateChangedAt` bumped, no occurrence generated. Re-exporting immediately produces a byte-identical file (`DM-EXPORT-1.6` determinism), which is a cheap correctness check.
- **`FR-DATA-1.7` Fully offline.** Export needs no network — it is local serialization + a local file write (`NFR-OFFLINE-1`). It works signed-in or (should the auth gate ever be relaxed) signed-out; it does not consult Firestore. The exported data is exactly what Room holds locally, the authoritative store.
- **`FR-DATA-1.8` No `DM-NOT` surface.** Export introduces no streak/points/badge/adherence surface; it reports at most a factual item count. `DM-NOT`, `DEC-2/3/4`.

> **[DECISION] — A persistent caution line, not a blocking "are you sure?" dialog.**
> The reporter made privacy the user's responsibility, so the app's job is to *inform*, not to *gate*. A modal "your file will be unencrypted — continue?" on every export would be nagging friction for a routine backup. `FR-DATA-1.4` instead surfaces the caution as an always-visible helper line under the "Export data" row, so the user sees it without a dialog interrupting them. If a stronger confirmation is wanted (e.g. for store-policy reasons), it can be added as a one-time dialog later; the requirement is only that the caution is visible before the write.

**Acceptance criteria**

1. On the emulator, populate the app with a representative spread (a few tasks including a recurring series with materialized occurrences, a quantitative habit with logs, a goal with steps, an active + an archived theme, a completed review, a contribution). Open **Settings → Your data → Export data**. The SAF "create document" chooser appears with a suggested name `tzafon-backup-2026-07-18.json`.
2. Save to Downloads; a snackbar confirms **"Data exported"**. Open the file (pull via `adb`, view as text): it is **pretty-printed UTF-8 JSON** with a `manifest` (format `"tzafon.export"`, `formatVersion` 1, `appVersion` "2.8.0", `counts` matching the populated data) and a `collections` object with all eight arrays (`DM-EXPORT-1.1/1.2/1.3`).
3. The file is **readable and non-proprietary**: `goalIds`/`themeIds` are JSON arrays (not CSV), `Goal.steps` is an array of `{label, done}` objects (not `␞`/`␟`-joined), each `Series` carries a nested `rule` object, `cue` is a nested object, enums read as names, dates read as ISO strings (`DM-EXPORT-1.4/1.5`, DECISION on domain-object export).
4. A materialized series occurrence appears in `tasks` with its `{seriesId}__{occurrenceDate}` id, and its `seriesId` matches an entry in `series` — the relationship is intact in the file (`DM-EXPORT-1.7`).
5. Export twice without changing data → the two files are **byte-identical** (`DM-EXPORT-1.6`, `FR-DATA-1.6`).
6. Cancel the SAF chooser → nothing is written, no error snackbar (`FR-DATA-1.5`).
7. Airplane-mode the device and export → it still succeeds (fully local, `FR-DATA-1.7`, `NFR-OFFLINE-1`).
8. The "Export data" row shows the plaintext caution line before any file is written (`FR-DATA-1.4`).
9. TalkBack announces the "Export data" row as a button ≥ 44 dp; the caution line is announced as its supporting text (`NFR-A11Y-1`). RTL lays the row out mirrored (`FR-DESIGN-3.5`).
10. `DM-NOT` audit clean — no streak/adherence/badge introduced (`FR-DATA-1.8`).

**Out of scope for v2.8.0**

- **Exporting app preferences** (palette, week-start, planning preset, chime). The reporter excluded these (remark A); they are per-device install settings, not user content (`FR-DESIGN-4.6`).
- **Encryption / password-protection of the file.** Plaintext by design (`FR-DATA-1.4`); the user owns file privacy. An optional encrypted export is a follow-on if ever requested.
- **Partial / filtered export** (e.g. "only my goals", a date range). v2.8.0 exports the full content set; scoped export is a separate request.
- **A non-JSON format** (CSV, PDF, iCal). JSON is the readable-and-relational choice; other formats are follow-ons.
- **Automatic / scheduled / cloud backups.** Export is a manual, user-initiated action. (Firestore sync already mirrors data for signed-in users; `FR-DATA-1` is the *portable file* the reporter asked for, orthogonal to sync.)

### 3.2 Import the user's data from a file (`FR-DATA-2`, new `FR-DATA-*` area; lives in `FR-SET-*`)

*Source: `FR-2026-07-18-a` (goal 2: "import it back … a backup"). Consumes a `DM-EXPORT-1` document. Hosted in Settings (remark C). Preserves `NFR-OFFLINE-1`, `DM-NOT`; reuses the recurrence engine's idempotent occurrence generation (the oracle) so restored series reconcile cleanly.*

`FR-DATA-2` **An "Import data" action in Settings reads a user-chosen `DM-EXPORT-1` JSON file, validates it, and applies it to the local store in a single atomic transaction. When the app already contains data, the user is first asked how to resolve conflicts — "Backup wins" or "Current wins."** A restore of a file exported by `FR-DATA-1` reconstructs the app's state exactly.

- **`FR-DATA-2.1` Entry point in Settings.** An **"Import data"** row sits alongside "Export data" in the "Your data" section (`FR-DATA-1.1`). Tapping it launches the import flow.
- **`FR-DATA-2.2` The file is read via SAF `ACTION_OPEN_DOCUMENT`.** Import launches `ActivityResultContracts.OpenDocument(arrayOf("application/json"))`; the user picks a file; the app reads its UTF-8 bytes from the `content://` URI through the `ContentResolver`. No storage permission is required.
- **`FR-DATA-2.3` Parse + shape validation happen before anything is written.** The bytes are parsed as JSON and checked: valid JSON; a `manifest` with `format == "tzafon.export"`; a supported `formatVersion` (`FR-DATA-2.6`); and a `collections` object. A file that fails any of these is **rejected wholesale** with a clear snackbar (e.g. **"That doesn't look like a Tzafon backup."** / **"This backup is from a newer version of Tzafon."**) and **no change is made** to the store.
- **`FR-DATA-2.4` Completeness check against the manifest counts.** After parsing, each collection's actual array length is compared to `manifest.counts`. A mismatch (truncated / tampered file) surfaces a warning; **[DECISION]** below fixes whether the mismatch blocks or merely warns. Row objects that fail to deserialize into their domain type (unknown enum name, wrong types) abort the import before any write (`FR-DATA-2.5`).
- **`FR-DATA-2.5` Deserialization is strict enough to fail safe.** Each array element is deserialized to its domain type (`Task`, `Series`, …). Unknown JSON keys are ignored (forward-compat, `DM-EXPORT-1.8`); missing keys fall to domain defaults (backward-compat); but a value that cannot map (an enum name the build doesn't know, a string where a number is required) aborts the whole import with a snackbar and **no partial write** (`FR-DATA-2.7`).
- **`FR-DATA-2.6` `formatVersion` gates acceptance and drives migration.** The app declares the highest `formatVersion` it understands (**1** in v2.8.0). A file with `formatVersion` **≤** the app's is accepted (an older version is upgraded through an ordered migration chain — none needed at v1, but the seam exists for v2.8.0+n). A file with `formatVersion` **>** the app's is **rejected** with "backup is from a newer version" (`FR-DATA-2.3`) rather than risking a lossy partial read. This is the property that makes a backup taken today restorable against a future build.
- **`FR-DATA-2.7` The apply step is a single atomic transaction — all-or-nothing.** Once validation passes, all writes happen inside one Room transaction (a repository-level `importAll(...)` seam, or `withTransaction { … }`). If any write throws, the transaction rolls back and the store is left **exactly** as it was before the import; a snackbar reports the failure. A half-restored database is never observable (`NFR-OFFLINE-1` correctness).
- **`FR-DATA-2.8` Conflict resolution is a single up-front choice, offered only when the app is non-empty.** If the current store has **zero** rows across all collections (a fresh install / post-data-loss restore), the import applies directly with no prompt — the common restore case is frictionless. If the store is **non-empty**, before applying, a dialog asks how to treat rows whose primary key already exists, offering exactly two options (the reporter's remark B):
  - **"Backup wins"** — the backup row **overwrites** the existing row (`INSERT … ON CONFLICT REPLACE` / upsert) for every collection.
  - **"Current wins"** — the backup row is **skipped** where a row with the same primary key already exists; only backup rows with a **new** primary key are inserted.

  The chosen policy applies uniformly to the whole import (one decision, not per-row). Primary keys per collection are: `id` for tasks/series/habits/goals/themes/reviews/contributions, and the composite `(habitId, date)` for `habitLogs` (`Entities.kt:129`). A **Cancel** on the dialog aborts the import with no change.
- **`FR-DATA-2.9` Imported data adopts the current identity; no `uid` is read from the file.** The file carries no identity (`DM-EXPORT-1.3`). Imported rows are written to the local Room store as-is; if the user is signed in, the M9b sync engine mirrors them under the current `users/{uid}/…` on its next pass — exactly as it treats any locally-authored row (`FR-AUTH-1.7`). Importing a file that was exported from account A while signed in as account B simply makes that data B's now; there is no cross-account rejection.
- **`FR-DATA-2.10` Restored series reconcile idempotently.** Because occurrence ids are the deterministic `{seriesId}__{occurrenceDate}` (carried from v1.1.0) and `Series.generatedThrough` is preserved by the import, the recurrence engine does **not** re-materialize occurrences that the file already restored — re-generation is idempotent against the deterministic id (the oracle's `services/series.js` contract). No duplicate occurrences appear after an import (verified against the recurrence parity suite).
- **`FR-DATA-2.11` Import is idempotent under re-application.** Importing the **same** file twice is safe: under "Current wins" the second import is a no-op (every key already exists → all skipped); under "Backup wins" the second import overwrites rows with identical values (no net change). Deterministic ids make this hold across all collections.
- **`FR-DATA-2.12` The result is summarized.** After a successful apply, a snackbar (or a small result line) reports what happened — e.g. **"Imported 200 items"** for a clean restore, or **"Imported 40, replaced 12"** / **"Imported 40, skipped 12"** to reflect the conflict policy. The summary is factual, not gamified (`DM-NOT`).
- **`FR-DATA-2.13` Fully offline.** Import is local file read + local transactional write; no network (`NFR-OFFLINE-1`). Any resulting Firestore mirror write is best-effort and drains on reconnect (`FR-AUTH-1.9`).
- **`FR-DATA-2.14` No `DM-NOT` surface.** Import introduces no streak/adherence/badge; at most a factual count. `DM-NOT`, `DEC-2/3/4`.

> **[DECISION] — Two conflict options exactly, applied globally; the empty-store restore skips the prompt.**
> The reporter specified exactly two options — "Backup wins" (overwrite) and "Current wins" (skip) — so `FR-DATA-2.8` implements those and no third ("keep both / duplicate with a new id"), which would fork identities and break the deterministic-id contract. The policy is a **single global choice** for the whole import rather than per-collection or per-row, because a per-row prompt across potentially hundreds of rows is unusable and the reporter framed it as one decision. The prompt is **suppressed when the store is empty**, because the flagship use case — restoring after data loss onto a fresh install — has no conflicts to resolve, and forcing a "Backup wins vs Current wins" choice there is a meaningless question. Overrule if the prompt should always appear.

> **[DECISION] — A count mismatch warns but does not hard-block; a deserialization failure hard-blocks.**
> `FR-DATA-2.4`'s `manifest.counts` check is an integrity signal. Two failure classes are treated differently: (a) a **count mismatch** (manifest says 42 tasks, array has 41) indicates possible truncation/tampering — the import surfaces a warning and asks the user to confirm proceeding, but does not itself corrupt anything since the apply is still atomic; (b) a **deserialization failure** (a row that cannot become a valid domain object) hard-aborts before any write, because applying it would either throw mid-transaction (rolled back anyway) or silently drop data. This keeps a slightly-stale-but-parseable file usable while refusing a structurally broken one. Overrule to make the count mismatch a hard block if stricter behavior is wanted.

> **[DECISION] — "Current wins" may leave soft references pointing at not-imported rows; this is tolerated.**
> Under "Current wins" with a non-empty store, a *new* backly-imported task could reference a series that was skipped (because a same-id series already existed) — or, more generally, a backup row could reference an id that the policy chose not to import. Because Tzafon's cross-collection references are **plain strings with no FK enforcement** (`Entities.kt`) and every reader already tolerates a dangling reference (a missing theme just isn't shown; occurrence generation is id-driven), the import does **not** attempt to enforce graph consistency or rewrite references. Enforcing it would require either overriding the user's "Current wins" choice for referenced rows or rejecting the import — both worse than the app's existing, already-tolerant behavior. The clean restore path (empty store, or "Backup wins" over a superset) has no dangling references by construction (`DM-EXPORT-1.7`). Overrule only if a referential-repair pass is later wanted.

**Acceptance criteria**

1. **Clean restore (the backup case).** On a fresh install (empty store), Settings → Your data → **Import data**; pick a `tzafon-backup-*.json` produced by `FR-DATA-1`. **No conflict prompt appears** (store was empty). A snackbar reports "Imported N items". Every surface — Today, All Tasks, Backlog, Habits, Directions, Journey, Review — shows exactly what the source install had, including the recurring series' occurrences, the quantitative habit's logs, the goal's steps, the archived theme, and the contribution (`FR-DATA-2.8`, round-trip fidelity).
2. **Round-trip equality.** Export from install A → wipe → import into a fresh install B → export from B. The two export files are **byte-identical** (`DM-EXPORT-1.6`), proving losslessness across every field of all eight collections.
3. **Conflict prompt appears only when non-empty.** With data already present, tapping Import and picking a file shows a dialog offering exactly **"Backup wins"** and **"Current wins"** (plus Cancel) (`FR-DATA-2.8`, remark B).
4. **Backup wins.** Choose "Backup wins": rows whose id exists in both are **overwritten** by the backup's values; rows only in the backup are inserted; rows only in the current store remain. A task edited locally after the backup reverts to the backup's version (`FR-DATA-2.8`).
5. **Current wins.** Choose "Current wins": rows whose id already exists are **left untouched**; only backup rows with a new id are inserted. The locally-edited task keeps its local version (`FR-DATA-2.8`).
6. **Atomicity.** Simulate a mid-apply failure (e.g. an injected error on one collection in a test) → the store is unchanged from before the import; a failure snackbar shows; no partial rows are present (`FR-DATA-2.7`).
7. **Bad file rejected.** Import a non-JSON file, a JSON file without the `manifest`, and a file with `format != "tzafon.export"` → each is rejected with a clear message and **no change** to the store (`FR-DATA-2.3`).
8. **Newer-version file rejected.** Import a file whose `manifest.formatVersion` is `2` → rejected with "This backup is from a newer version of Tzafon"; no change (`FR-DATA-2.6`).
9. **Count mismatch warns.** Hand-edit an exported file to delete one task row (leaving `counts.tasks` unchanged) → import surfaces the count-mismatch warning and asks to confirm; confirming still applies atomically (`FR-DATA-2.4` DECISION).
10. **Series reconcile, no duplicates.** After importing a file containing a series with materialized occurrences, the recurrence engine does not create duplicate occurrences (deterministic ids); the parity suite stays green (`FR-DATA-2.10`).
11. **Idempotent re-import.** Import the same file twice under "Current wins" → the second import reports 0 new / all skipped and changes nothing; under "Backup wins" → the second import changes nothing net (`FR-DATA-2.11`).
12. **Identity adoption.** Export while signed in as A; on a fresh install signed in as B, import → the data appears and, with rules deployed, mirrors under B's `users/{uid}/…` (`FR-DATA-2.9`, `FR-AUTH-1.7`).
13. **Offline.** Import works in airplane mode (`FR-DATA-2.13`, `NFR-OFFLINE-1`).
14. TalkBack announces the Import row and both conflict-dialog options as buttons ≥ 44 dp; the dialog is RTL-mirrored (`NFR-A11Y-1`, `FR-DESIGN-3.5`). `DM-NOT` audit clean (`FR-DATA-2.14`).

**Out of scope for v2.8.0**

- **A merge / diff UI** (per-row "keep mine / keep theirs", three-way merge). The reporter specified a single global two-option choice (`FR-DATA-2.8`).
- **A "keep both / duplicate with new id" conflict option.** Rejected in `FR-DATA-2.8` DECISION — it breaks deterministic identity.
- **Referential-repair on import** (fixing dangling soft-references under "Current wins"). Tolerated, not repaired (`FR-DATA-2.8` third DECISION).
- **Importing app preferences.** Out of scope with the export side (remark A).
- **Importing a partial file / selective import** ("only bring in my goals"). Whole-document import only in v2.8.0.
- **Importing from another app's format.** Only Tzafon's own `DM-EXPORT-1` document is accepted.
- **A `formatVersion` migration chain.** The seam exists (`FR-DATA-2.6`) but no migration is authored at v1; the first real migration lands when a future increment changes the document shape.

## 4. Data model deltas (Room)

**None.** This increment adds no Room fields, no migration, and no change to the domain model or the existing repository read surfaces.

- The export/import operate on the **existing** domain objects and read them through the **existing** repository `observe*()`/list surfaces (`FR-DATA-1.2`). The only repository-tier addition is an **import apply seam** — a transactional `importAll(snapshot, policy)` (or a small `DataTransferRepository` that composes the existing repos inside one `withTransaction`) — which writes through existing DAO upsert/insert methods; it introduces no new table, column, or entity shape (`FR-DATA-2.7`).
- `DM-EXPORT-1` defines an **on-disk file** shape, not a stored app shape — Room, the `*Entity` rows, and `FirestoreCodec` are all untouched.
- Gson is already on the classpath (it backs `FirestoreCodec`, `data/sync/FirestoreCodec.kt:3-4`); export/import add a pretty-printing `Gson` instance but no new dependency.

## 5. Non-functional requirements

No new NFRs. The one functional area **strengthens conformance** with existing NFRs:

- **`NFR-OFFLINE-1`** — export and import are fully local (SAF file IO + local serialization/transaction); neither needs network (`FR-DATA-1.7`, `FR-DATA-2.13`). The feature also *improves* resilience: it gives the user a durable, off-device copy that survives an app/data-loss event, which is the reporter's goal 2.
- **`NFR-SEC-2`** — the export carries **no** auth identity or token (`DM-EXPORT-1.3`); importing does not authenticate or change the signed-in account (`FR-DATA-2.9`). The plaintext file's privacy is the user's responsibility, surfaced by the `FR-DATA-1.4` caution.
- **`NFR-A11Y-1`** — the Settings "Your data" rows and the conflict dialog meet ≥ 44 dp hit targets and carry TalkBack labels (`FR-DATA-1.9`, `FR-DATA-2.14`).
- **`FR-DESIGN-3.5`** — the rows and dialog honor RTL.
- **`NFR-TEST-1`** — the testable core is pure and does not need the emulator: (a) a **round-trip property test** — build a domain snapshot spanning all eight collections (a series with occurrences, a quantitative habit with back-logged logs, a goal with steps, an archived theme, a review with a snapshot, contributions), serialize → deserialize → assert deep equality, and assert re-serialization is byte-identical (`DM-EXPORT-1.6`); (b) **conflict-policy tests** — "Backup wins" overwrites and "Current wins" skips on a seeded store; (c) **validation tests** — bad JSON, missing/foreign `format`, `formatVersion > supported`, unknown enum name each reject with no write; (d) an **atomicity test** — an injected mid-apply failure rolls back; (e) an **idempotency test** — double import under each policy; (f) the recurrence **parity suite** confirms restored series produce no duplicate occurrences (`FR-DATA-2.10`). A thin Compose/instrumented test covers the SAF wiring and the empty-vs-non-empty prompt branch.

All other `NFR-*` from v2.0.0 … v2.7.0 continue to apply unchanged.

5. No `DM-NOT` surface (streaks / points / badges / adherence %) appears anywhere as a side effect (`FR-DATA-1.8`, `FR-DATA-2.14`).
6. Domain tests are green: the round-trip, conflict-policy, validation, atomicity, and idempotency suites (`NFR-TEST-1`), plus the recurrence parity suite unchanged.
