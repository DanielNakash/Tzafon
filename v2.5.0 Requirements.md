## 1. Scope of v2.5.0

v2.5.0 is a **small, focused increment** on top of a shipped v2.4.0. Three source requests, no new object types, no schema migrations, no new top-level surfaces (see §4 — Data model deltas below, which is intentionally empty). All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), the ≤3 active themes cap (`DM-THEME-3`), and the compass / chosen-direction thesis.

The three requirements:

- **`FR-NAV-8`** fixes a regression introduced by `FR-NAV-6.1` in v2.4.0. When `DenBottomNav` began rendering on All Tasks and Backlog as a wayfinder (a correct outcome of `FR-NAV-6`), the floating "add" `Fab` on those two views was not re-anchored to clear it — All Tasks and Backlog still position the `Fab` with `.navigationBarsPadding().padding(end = 20.dp, bottom = 24.dp)`, which only clears the system gesture bar, not the app's bottom nav. The result: on a Pixel 8 in portrait the `Fab` sits **behind** the rust `DenBottomNav` pill row, partially obscured and with a reduced tap target. Today never had this problem because its `Fab` uses `.padding(end = 20.dp, bottom = 104.dp)` — a hard bottom offset that clears both the bottom nav and the system inset. `FR-NAV-8` normalises the `Fab` clearance rule across every Class-A view carrying a `DenBottomNav` so the add affordance is fully visible and comfortably tappable, and pins the rule so the same regression cannot re-appear the next time a new Class-A view gains a `Fab`. Refines `FR-NAV-6.1` (bottom-nav on All Tasks / Backlog) and holds the friction-floor contract from `FR-CAPTURE-1` (quick-add must be a low-effort, thumb-reachable target).
- **`FR-DIR-8`** finally exposes the multi-theme goal relation that `DM-GOAL-6` promised in v2.0.0. Today the goal↔theme link is single-picker on create (via `FR-DIR-7`'s hub-level route) and effectively invisible on edit: a goal edited from anywhere never lets the user change its `primaryThemeId`, and the extra `themeIds` list (a goal serving multiple themes) has no editor surface at all. Symmetrically, an existing goal cannot be linked to a theme from the theme's side — the expanded theme body only offers "Add a goal to this theme" (create-new), not "connect an existing goal". `FR-DIR-8` closes both gaps with a **bidirectional connect surface**: (a) from the goal editor's theme picker (now exposed in edit mode too), with primary + serves-also multi-select, and (b) from the expanded theme body, with a "Connect an existing goal" affordance that lists goals not already primary-owned here. The relation is stored only on the goal side (`primaryThemeId` + `themeIds`), matching `DM-GOAL-6` verbatim; the theme model gains no goal-list field. Refines `FR-DIR-3`, `FR-DIR-4`, `FR-DIR-5`, and `FR-DIR-7`; realises `DM-GOAL-6` in the UI.
- **`FR-BACKLOG-5`** fixes the default-state mismatch when a task is created **from** the Backlog view. Today, the floating quick-add on Backlog calls `saveDraft(TaskDraft(title = …))` with `TaskDraft`'s default `state = TaskState.OPEN`, so a task typed into Backlog silently lands in Today's Open pool instead of the someday pool — leaving the Backlog view empty even after the user just added something to it. The expand-to-full-form route from the Backlog quick-add sheet inherits the same default. `FR-BACKLOG-5` makes the Backlog view a **state-scoped surface**: every task created from Backlog (quick-add and full-form) starts in `TaskState.BACKLOG`, with `toDoDate = null`, so the user's mental model ("what I put here stays here until I pull it") matches the observed behaviour. Refines `FR-BACKLOG-1` (someday/maybe pool) and holds `FR-BACKLOG-4` (only non-recurring tasks in Backlog) — the requirement carries an inline safeguard for the full-form add path so recurrence-with-Backlog cannot be saved.

None of the three is gamification-adjacent — one is a layout offset on an existing affordance, one is a pure linking surface between two existing entities, and one is a default-state fix on an existing create path (`DM-NOT`, `DEC-2/3/4`).

## 2. Functional requirements

### 2.1 Add-button clearance over the bottom nav (`FR-NAV-8`, refines `FR-NAV-6.1` and holds `FR-CAPTURE-1`)

*Source: `FR-2026-07-12-a`. Refines `FR-NAV-6.1`; holds `FR-CAPTURE-1`; introduces `FR-NAV-8.*`.*

The Today view's floating "add" `Fab` (`ui/today/TodayScreen.kt`) is positioned with `Modifier.align(Alignment.BottomEnd).padding(end = 20.dp, bottom = 104.dp)` — a bottom offset large enough that the `Fab`'s bounding box sits **above** the `DenBottomNav` row (nominally ~72 dp tall including the outer padding the nav bar carries), with visible breathing room and the system gesture inset absorbed by the nav bar itself. All Tasks (`ui/alltasks/AllTasksScreen.kt`) and Backlog (`ui/backlog/BacklogScreen.kt`) currently position their `Fab` with `Modifier.align(Alignment.BottomEnd).navigationBarsPadding().padding(end = 20.dp, bottom = 24.dp)` — that offset was correct in v2.3.0 when neither view rendered a `DenBottomNav`, but is wrong in v2.4.0 where both views do render it (per `FR-NAV-6.1`). The two `Fab`s are now partially hidden by the pill row.

`FR-NAV-8` **The floating add `Fab` on every Class-A view that renders `DenBottomNav` is positioned so its bounding box clears the bottom nav and the system gesture inset in full, with the same visible bottom offset the Today view uses today.** Concretely:

- **`FR-NAV-8.1` The clearance rule is the Today pattern.** The `Fab` on All Tasks and Backlog is anchored with `Modifier.align(Alignment.BottomEnd).padding(end = 20.dp, bottom = 104.dp)` — matching Today verbatim. `navigationBarsPadding()` is **not** applied on top of this offset; the 104 dp bottom offset already accounts for both the nav bar (~72 dp) and the system inset that `DenBottomNav` itself absorbs. Applying `navigationBarsPadding()` in addition would double-count the gesture inset and push the `Fab` too far up on devices with three-button navigation.
- **`FR-NAV-8.2` The Today view is unchanged.** Its current offset is the reference; no code moves on `TodayScreen.kt`. This requirement pins the existing placement as the shared contract so a future edit does not silently drop it.
- **`FR-NAV-8.3` The pattern generalises.** Any future Class-A view (per `FR-NAV-6`) that ships a floating add `Fab` uses the same anchor. If a shared `FabScaffold` composable emerges from this fix, all three call sites (Today, All Tasks, Backlog) use it; if not, the three call sites carry identical modifier chains (the same-line diff is the sanity check).
- **`FR-NAV-8.4` The `Fab` composable itself is not modified.** Only the enclosing `Box` modifier on `AllTasksScreen.kt` and `BacklogScreen.kt` changes. `Fab.onClick` wiring, size, tint, and elevation stay exactly as they are today.
- **`FR-NAV-8.5` Screens without a `DenBottomNav` are out of scope.** Settings and About are Class-B leaves per `FR-NAV-6` — they have no `Fab` and no bottom nav, and this requirement does not touch them. Planning, Habits, Directions, and Journey either do not carry a floating add `Fab` at all (their add-flow lives inside the view body or through the hamburger menu) or, where they do (`PlanningScreen`'s undated inbox helper), the placement already clears the nav bar and is not touched by this fix.

> **[DECISION] — Mirror Today, don't introduce a new offset token.**
> An alternative was to define a `FabBottomOffset` design token and use it on all three call sites. But the three offsets are already identical in intent, the current codebase has no other `Fab` placement token, and introducing one to fix a three-line regression would be over-engineering. The intent is captured in `FR-NAV-8.1` and the three call sites diff cleanly against each other — that is enough. If a fourth or fifth Class-A view gains a `Fab` in a later increment, the token can be extracted then.

> **[DECISION] — Don't stack `navigationBarsPadding()` on top of the 104 dp offset.**
> Today does not apply `navigationBarsPadding()` at all, and its `Fab` sits at a visually correct height on the Pixel 8 in both gesture-nav and three-button-nav configurations. `DenBottomNav` itself renders a `windowInsetsPadding(WindowInsets.navigationBars)` (or an equivalent inset absorption) as part of its rust background — so the 104 dp above it is measured from the top of the nav bar, which already sits above the gesture inset. Adding `navigationBarsPadding()` to the `Fab` `Box` would inset it a second time and produce a visible gap on three-button-nav devices.

**Acceptance criteria**

1. On a Pixel 8 in portrait at default text scale, opening **All Tasks** shows the floating add `Fab` fully visible above the `DenBottomNav` pill row with the same visible bottom gap the Today view has (measured pixel-parity on a screenshot at the same emulator resolution).
2. On a Pixel 8 in portrait at default text scale, opening **Backlog** shows the floating add `Fab` fully visible above the `DenBottomNav` pill row with the same visible bottom gap the Today view has.
3. Tapping the visible `Fab` on All Tasks opens the same quick-add sheet it opens today (`FR-CAPTURE-1`); tapping the visible `Fab` on Backlog opens the same quick-add sheet it opens today. Neither wiring changes.
4. The Today view's `Fab` position is unchanged: a screenshot diff against the last-shipped v2.4.0 build shows zero pixel movement on `TodayScreen`.
5. On a Pixel 8 emulated with **three-button navigation** (Settings → System → Gestures → Navigation mode: 3-button), the `Fab` on All Tasks and Backlog still clears the bottom nav without a visible extra gap between the bottom nav and the system nav bar — i.e. `navigationBarsPadding()` has not been left in the modifier chain alongside the 104 dp offset.
6. On a Pixel 8 in landscape at default text scale, the `Fab` on All Tasks and Backlog remains fully visible above the bottom nav — the landscape envelope does not clip it and does not introduce a scroll bar under the `Fab`.
7. The `Fab` tap target on All Tasks and Backlog continues to meet `NFR-A11Y-1`'s ≥ 44 dp touch-target rule with no reduction against v2.4.0 measurements.
8. No streak / points / badges / adherence surface appears anywhere as a side effect of the fix (`DM-NOT`).

**Out of scope for v2.5.0**

- **A shared `FabScaffold` composable.** Deliberately deferred (see `[DECISION]` above); the three call sites carry identical modifier chains and that is enough.
- **A design token for the 104 dp bottom offset.** Same rationale — introducing a token to fix a three-line regression is over-engineering.
- **Any change to the `Fab` size, tint, elevation, or icon.** The composable is unchanged; only the enclosing `Box` modifier moves.
- **Any change to non-`Fab` add affordances** (in-body add-row helpers, hamburger-menu shortcuts, editor-open flows). Only the floating `Fab` on Class-A views with a `DenBottomNav` is in scope.

### 2.2 Theme ↔ goal linking — bidirectional connect surface (`FR-DIR-8`, refines `FR-DIR-3`, `FR-DIR-4`, `FR-DIR-5`, `FR-DIR-7`)

*Source: `FR-2026-07-12-b`. Refines `FR-DIR-3` (nested goal cards under themes), `FR-DIR-4` (goal cards show "serves: <Theme> (+N)"), `FR-DIR-5` (shared goals appear once, under primary, with a shared-goals cluster), and `FR-DIR-7` (hub-level goal-create theme picker). Realises `DM-GOAL-6` — "A Goal may serve any number of Themes" — in the UI.*

`DM-GOAL-6` and the data model already say a goal serves any number of themes: `Goal.primaryThemeId` is the display parent (the theme the goal renders under in Directions per `FR-DIR-5`), and `Goal.themeIds` is the full serve set. The v2.2.0 `FR-DIR-7` hub-level "Add a goal" route wired a single-select theme picker for `primaryThemeId` on **create**. Two gaps remain:

1. **Edit** on an existing goal never exposes any theme picker — a goal's `primaryThemeId` is fixed at create time unless the user deletes and recreates it, and `themeIds` cannot be edited at all. This is a silent regression against `DM-GOAL-6`.
2. **The theme side** of the relation has no connect affordance. The expanded theme body offers "Add a goal to this theme" (create-new only). A user with an existing orphan goal — or a goal already primary-owned by theme A that they want to *also* serve theme B — has no route to make that link from theme B's side.

`FR-DIR-8` **Both the goal's edit surface and the expanded theme body expose an explicit "connect an existing" affordance, and the goal editor's theme picker exposes the full multi-theme surface (primary + serves-also) in both create and edit modes.** The link is stored only on the goal (`primaryThemeId` + `themeIds`); the theme model gains no goal-list field.

- **`FR-DIR-8.1` Connect-from-theme affordance.** In the expanded body of an active theme (`FR-DIR-3`), a **"Connect an existing goal"** row sits alongside the existing "Add a goal to this theme" create-new row. Its label is distinct from the create row so a user does not confuse "connect" (link an existing goal) with "add" (create a new goal). Tapping it opens a picker sheet.
- **`FR-DIR-8.2` Connect-a-goal picker.** The sheet lists every existing goal that is not already **primary-owned by this theme** (goals already primary-owned here are already visible in the nested body; goals already shared here appear with a "connected" state and disable re-selection). Each row shows the goal's `title`, its current primary theme (or "no theme" for orphans), and its `type` (Steps · An amount · Directional). Sort: orphans first, then goals primary-owned by other active themes, alphabetical within each group. `completed` and `frozen` goals are excluded (`GoalState`); only `ongoing` goals are connectable.
- **`FR-DIR-8.3` Orphan primary prompt.** When the picked goal has `primaryThemeId == null` (i.e. it lives in the orphan-Goals section per `FR-DIR-1`), the picker asks **"Make this theme the primary?" [Yes, make it primary / Just serve it]** exactly once. "Yes, make it primary" writes `primaryThemeId = <thisTheme>` and adds the theme to `themeIds` — the goal now appears in the theme's nested body (`FR-DIR-3`) and disappears from the orphan section. "Just serve it" adds the theme to `themeIds` only — the goal stays in the orphan section, and its card gains a "also serves: +1" note per `FR-DIR-4`. When the picked goal already has a `primaryThemeId ≠ null` (i.e. it's primary-owned elsewhere), no prompt is raised — the picker silently adds this theme to `themeIds`, and the goal now appears in this theme's shared-goals cluster per `FR-DIR-5`.
- **`FR-DIR-8.4` Goal editor exposes the full multi-theme surface, in every mode.** `GoalEditorSheet` (both hub-level create per `FR-DIR-7` and edit on an existing goal) presents a **primary theme** selector — a single-select including a "No theme (orphan)" option — and a **serves also** multi-select underneath. Saving writes `primaryThemeId` (or null for orphan) and `themeIds` (the union of primary + serves-also, deduplicated). The picker lists all `active` themes at time of open; `upcoming` and `archived` themes are excluded (see `[DECISION]` below).
- **`FR-DIR-8.5` Nested "Add a goal to this theme" route prefills primary, hides serves-also by default.** The expanded-theme "Add a goal to this theme" affordance (`FR-DIR-3`) — the create-new route, distinct from the connect-existing route of `FR-DIR-8.1` — continues to open `GoalEditorSheet` with the theme prefilled as `primaryThemeId`. The serves-also multi-select is present but collapsed by default in this route (a fresh goal opened from a theme's create affordance is one-tap to save; a user who wants to serve additional themes can expand the section). In both hub-level create and edit, the serves-also section is visible by default.
- **`FR-DIR-8.6` Disconnect from goal editor.** In the goal editor's serves-also multi-select, tapping an already-selected theme deselects it (removes from `themeIds`). Deselecting the currently-selected **primary** in the primary selector while at least one serves-also theme remains **silently promotes** the topmost remaining served theme to primary (deterministic promotion by original serves-also selection order — first added, first promoted; no prompt). Deselecting all themes writes `primaryThemeId = null` and moves the goal to the orphan section on save. The "No theme (orphan)" option in the primary selector is the explicit route to orphan a goal.
- **`FR-DIR-8.7` Disconnect from theme side.** In the expanded theme body's **shared-goals cluster** (`FR-DIR-5`'s "+ shared goals (n)"), each shared reference exposes a small "unlink from this theme" affordance (a chip-level ✕, a long-press menu, or an equivalent — implementer's choice within `NFR-A11Y-1`). Activating it removes this theme from that goal's `themeIds`. If the removed theme was the goal's primary (an edge case: the goal happens to be primary-owned here but is also displayed in the shared cluster of a *different* theme it serves; the affordance lives on the shared side, so from *this* theme's shared cluster the affordance never removes *this* theme's primaryhood — it only removes shared serves), the `FR-DIR-8.6` promotion rule applies. **Primary-owned goals nested under a theme do not expose the unlink affordance from the theme side** — that would leave the goal without a home; the operation is only meaningful from the goal editor's primary selector.
- **`FR-DIR-8.8` Save is quiet — no gamification voice.** No "you connected a goal to a theme!" copy, no "your compass is broader," no adherence-% side effects. On save from either surface, Directions re-renders with the new nesting: the goal shows in its new primary theme's nested body, and any secondary themes it serves show it in their shared-goals cluster (`FR-DIR-5`). (`DM-NOT`, `DEC-2/3/4`.)
- **`FR-DIR-8.9` Sequence of connect-then-open-editor is safe.** Connecting a goal from the theme side does not open the goal editor as a side effect. The link is written and the sheet closes; the user can subsequently tap the goal card / shared reference to open the editor if they want to fine-tune. Conversely, editing a goal's themes from the goal editor does not open any theme editor.
- **`FR-DIR-8.10` No schema change.** `Goal.primaryThemeId: String?` and `Goal.themeIds: List<String>` already exist per `DM-GOAL-6`. `Theme` gains no goal-list field. `GoalRepository.upsert(goal)` remains the only write path. Firestore sync inherits automatically.

> **[DECISION] — Bidirectional connect surface, but goal-owned relation.**
> The theme has no `goalIds` list. Storing the relation only on the goal side matches `DM-GOAL-6` verbatim and keeps a single source of truth — both the theme editor's "connect an existing goal" affordance and the goal editor's theme picker write the same fields (`primaryThemeId`, `themeIds`) on the same goal row. An alternative (a `Theme.goalIds` list, kept in sync with `Goal.themeIds`) would double the write surface and require reconciliation on every edit, for no display benefit — Directions already renders the shared cluster (`FR-DIR-5`) from the goal side.

> **[DECISION] — Silent primary promotion on primary deselect.**
> The alternative — an "which theme is primary now?" prompt on every primary-deselect — is a modal wall on a light operation. Deterministic promotion (first remaining served theme by original selection order) preserves at least one home for the goal without asking; the user can still open the picker and reassign primary at any time. The one explicit case that *does* prompt is orphan-goal connection from the theme side (`FR-DIR-8.3`), because orphans are a first-class state and the user's intent — primary or shared — is genuinely ambiguous there.

> **[DECISION] — Active-only theme list in both pickers.**
> Both the theme-side connect-goal picker (`FR-DIR-8.2`) and the goal editor's theme picker (`FR-DIR-8.4`) list only `active` themes. Linking to an `upcoming` theme has no visible home in Directions until the theme activates; linking to an `archived` theme reads as "adding a goal to a finished bearing" and violates `FR-DIR-4`'s emphasis on live progress against the compass. Users who want to link to an upcoming theme wait for auto-activation (`FR-DIR-6`) or promote the upcoming theme manually. Users editing a goal that already serves an `upcoming` or `archived` theme (from before the theme's state changed) see the theme in the serves-also list as a **read-only chip** with its state annotated ("upcoming" / "archived") — the link is preserved but not re-editable from this picker until the theme returns to `active` (or a subsequent increment adds an explicit "manage historical links" surface, out of scope here).

> **[DECISION] — Orphan connection prompt is a one-liner, not a wizard.**
> The primary-or-shared prompt on connecting an orphan goal (`FR-DIR-8.3`) is a single row of two labelled buttons in the same picker sheet — not a new full-screen surface, not a follow-up sheet. The whole connect flow stays one tap → one prompt (for orphans only) → back to Directions. Two-tap for shared goals already primary-owned elsewhere; three-tap for orphans.

**Acceptance criteria**

1. In the expanded body of an active theme, a **"Connect an existing goal"** row is visible alongside the existing "Add a goal to this theme" create-new row. The two rows are visually distinguishable (label + icon) so the user does not confuse connect with create.
2. Tapping "Connect an existing goal" opens a picker sheet listing every `ongoing` goal that is not already primary-owned by this theme. Each row shows the goal's `title`, its current primary theme (or "orphan"), and its `type`. Goals already shared here are visible but disabled with a "connected" annotation. Orphans render first; goals primary-owned by other active themes follow. `completed` and `frozen` goals are excluded.
3. Selecting a non-orphan goal from the picker adds this theme to the goal's `themeIds` immediately, closes the sheet, and re-renders Directions with the goal appearing in this theme's shared-goals cluster per `FR-DIR-5`.
4. Selecting an orphan goal from the picker raises exactly one prompt: **"Make this theme the primary? [Yes, make it primary / Just serve it]"**. Choosing "Yes" writes `primaryThemeId = <thisTheme>` and adds the theme to `themeIds`; the goal appears in the theme's nested body and disappears from the orphan section. Choosing "Just serve it" adds the theme to `themeIds` only; the goal remains in the orphan section and its card gains an "also serves: +1" annotation.
5. Opening `GoalEditorSheet` on an existing (edit) goal shows the theme picker with a **primary** single-selector (including a "No theme (orphan)" option) and a **serves also** multi-select underneath, both pre-populated from the goal's current `primaryThemeId` and `themeIds`. Saving persists both fields as picked. This works for goals opened from any surface — Directions nested body, orphan section, shared cluster, hub-level Goal card tap.
6. Opening `GoalEditorSheet` from the hub-level "Add a goal" route (`FR-DIR-7`) shows the same primary + serves-also picker as in edit mode, with serves-also visible by default. Opening `GoalEditorSheet` from the nested "Add a goal to this theme" route prefills the theme as primary and shows serves-also collapsed by default, expandable in-place.
7. Deselecting the current primary in the primary selector while at least one serves-also theme remains promotes the topmost remaining served theme to primary silently (no prompt); deselecting all themes writes `primaryThemeId = null` on save, and Directions renders the goal in the orphan section.
8. From the expanded theme body's shared-goals cluster, each shared-goal reference exposes an "unlink from this theme" affordance. Activating it removes this theme from that goal's `themeIds` and re-renders Directions with the goal no longer in this theme's shared cluster. Primary-owned goals in the theme's nested body do not expose the unlink affordance from the theme side.
9. The theme picker in both the theme-side connect route and the goal editor lists only `active` themes; `upcoming` and `archived` themes do not appear. A goal that already serves an `upcoming` or `archived` theme (from before the theme's state changed) shows that theme in serves-also as a read-only chip annotated with its state — the link is preserved and not silently dropped.
10. No streak / points / badges / adherence surface appears anywhere in the flow (create-time, edit-time, connect-time, disconnect-time, on save). The `DM-NOT` audit trail continues to hold.
11. TalkBack announces "Connect an existing goal" (theme-side), "Primary theme" and "Also serves" (goal-editor picker labels), and "Unlink from this theme" (shared-cluster affordance) with distinct content descriptions. Hit targets meet `NFR-A11Y-1` sizing (≥ 44 dp).
12. Directions renders correctly after every link/unlink combination — a goal serving three active themes appears once (nested under primary) and shows a "+ shared goals (2)" cluster reference under each of the other two active themes per `FR-DIR-5`.

**Out of scope for v2.5.0**

- **A parallel "connect an existing habit" affordance on the theme side.** Habits already carry `primaryThemeId` / `themeIds` per `DM-HABIT-6`, so the same pattern generalises — but the request is specifically about goals, and shipping habit-side connect alongside would triple the surface area and risk a regression on the tightly-owned Habits view. Habit-side connect is a straight follow-on request once `FR-DIR-8` lands.
- **A `Theme.goalIds` list.** Deliberately not added — see `[DECISION]` above.
- **Reordering themes within a goal's `themeIds` list.** The order is set at pick time and used only for the deterministic-promotion rule (`FR-DIR-8.6`); a UI to reorder is not requested and not implemented.
- **Editing links to `upcoming` or `archived` themes** beyond preserving the read-only chip. A dedicated "manage historical links" surface can be added later if the read-only annotation proves confusing in practice.
- **Bulk connect / disconnect operations** ("connect three goals at once", "unlink all shared goals"). Not requested.
- **A cross-goal "themes I serve" summary view.** Directions renders "also serves: +N" per goal card per `FR-DIR-4`; a dedicated summary is a Journey-tier question, not a Directions one.
- **Any change to the create flow of `Theme`** (`ThemeEditorSheet`). The theme editor never gets a goal-list field — themes are direction-first, and coupling create-a-theme with pick-your-goals here would confuse the mandatory-`why` moment (`DM-THEME-1`).
- **Changing the display rule of `FR-DIR-5`** (a shared goal appearing once under primary, referenced in the shared cluster elsewhere). The rendering is unchanged; only the *paths to create the shared link* are added.

### 2.3 Backlog-view add defaults to Backlog state (`FR-BACKLOG-5`, refines `FR-BACKLOG-1` and holds `FR-BACKLOG-4`)

*Source: `FR-2026-07-12-c`. Refines `FR-BACKLOG-1` (someday/maybe pool). Holds `FR-BACKLOG-4` (only non-recurring tasks can enter Backlog). Interacts with `FR-CAPTURE-1` / `FR-CAPTURE-2` (the shared quick-capture surface) and `DM-TASK-1` (the five-state machine).*

The Backlog view is defined by `FR-BACKLOG-1` as the someday/maybe pool: a task is *in* Backlog when `state == TaskState.BACKLOG`. But the current create paths from the Backlog view do not honour this. The floating quick-add `Fab` on `BacklogScreen` (`ui/backlog/BacklogScreen.kt`) opens the shared quick-capture sheet and, on save, routes to `BacklogViewModel.quickAdd(title)`, which writes a `TaskDraft(id = null, title = title)` — the `TaskDraft` data class defaults `state = TaskState.OPEN` (see `domain/model/Task.kt`), so the new task lands in `Open`, gets a `toDoDate = today` from the repository's save path, and immediately shows up in **Today**, not in the Backlog view the user just added it from. The user's expected mental model — "the box says Backlog; things I add here go into Backlog" — is silently violated.

The same is true of the expand-to-full-form route: the quick-add sheet's `onExpand(title)` hands the title to the full task editor, which builds a fresh `TaskDraft` with `state = TaskState.OPEN` by default. A user who taps "expand" to give the task more detail ends up with an Open task in Today just as surely as one who confirms the quick-add row.

`FR-BACKLOG-5` **A new task created from the Backlog view — via the quick-add sheet or via the expand-to-full-form editor route — defaults to `state = TaskState.BACKLOG` with `toDoDate = null`, and lands in Backlog on save unless the user explicitly changes the state or adds a `toDoDate`.** Applies to the two create entry points on the Backlog view only; the Today, Planning, All Tasks, and hamburger-menu-anywhere entry points are unchanged.

- **`FR-BACKLOG-5.1` Quick-add from Backlog writes `BACKLOG` state directly.** `BacklogViewModel.quickAdd(title)` builds its `TaskDraft` with `state = TaskState.BACKLOG` and `toDoDate = null`. The repository's `saveDraft` path already honours the draft's declared state — no other change to `saveDraft` semantics is required. The saved task appears in the Backlog view on return (subject to the Backlog visibility filter, `state == TaskState.BACKLOG`) and does **not** appear in Today's `Open` pool.
- **`FR-BACKLOG-5.2` Expand-to-full-form from Backlog opens the editor pre-set to Backlog.** The full task editor opened via the Backlog quick-add sheet's expand route receives a `TaskDraft(id = null, title = <typed>, state = TaskState.BACKLOG, toDoDate = null)` as its initial value. The state selector in the editor shows `Backlog` selected; the user can change it before save (e.g. to `Open` with a `toDoDate`) and the change is honoured, but the default aligns with the view they came from. The other create entry points into the editor (from Today, Planning, All Tasks, hamburger-menu shortcuts) continue to open with `state = TaskState.OPEN` as today.
- **`FR-BACKLOG-5.3` Recurrence-in-Backlog is not saveable.** `FR-BACKLOG-4` states only non-recurring tasks can enter Backlog. In the editor's Backlog-defaulted state (from `FR-BACKLOG-5.2`), if the user adds recurrence to the draft, the state selector's `Backlog` option becomes disabled with a short one-line hint ("Backlog is for non-recurring tasks — a recurring series can't be 'someday'"), and the state is auto-switched to `Open` (with a `toDoDate = today`) at the moment recurrence is added. This mirrors the pattern in the reverse direction — the existing "Recurring → Backlog is not allowed (offer Frozen)" transition from `FR-BACKLOG-2` — so the two paths converge on the same guardrail.
- **`FR-BACKLOG-5.4` Alignment links stay dormant on create.** A new task entering Backlog carries any theme / habit / goal links the user set at create time as **dormant** per `FR-BACKLOG-1` — no habit completion, no goal progress, no `DM-ATTR` contribution rows written until the task is pulled to Open. The editor's link fields are still editable while the task is in Backlog state (a user might set up their alignment before pulling), but no ledger writes occur until the pull transition.
- **`FR-BACKLOG-5.5` Other-view add paths are unchanged.** Adds from Today (`FR-TODAY-*`), Planning (`FR-PLAN-*`), All Tasks (`FR-ALL-*`), and the shared hamburger-menu / capture routes continue to default to `state = TaskState.OPEN` with `toDoDate = today` (or the view's contextual default) — as they do today. Only the two Backlog-originated create paths change. A task added from Today never lands in Backlog by default; a task added from Backlog never lands in Today's Open pool by default. Symmetry restored.

> **[DECISION] — the view is the intent.**
> An alternative was to add a "where to?" chooser on Backlog's `Fab` ("Add to Backlog / Add to Today") so the current default is preserved for users who use Backlog's `Fab` as a general-purpose add. But `FR-BACKLOG` positions Backlog as an explicit state-scoped pool ("someday/maybe"), not a general inbox — a user opening the Backlog view is already in the "someday mode" mental frame, and forcing a chooser at the friction floor violates `FR-CAPTURE-1`. The chooser is over-engineering; the view is the intent. Users who want to add a Today task from Backlog can navigate to Today via the bottom nav (one tap) and use its `Fab` instead.

> **[DECISION] — auto-switch on recurrence, don't hard-block.**
> `FR-BACKLOG-5.3`'s auto-switch (Backlog → Open when recurrence is added in the editor) is friendlier than a save-time error dialog. Recurrence and Backlog are model-incompatible per `FR-BACKLOG-4`; a user who deliberately adds recurrence has clearly moved out of "someday" intent and into "recurring routine" intent. Silently promoting the state to Open (with the visible one-line hint) matches the pattern `FR-BACKLOG-2` uses in the reverse direction — the app takes the user's most recent explicit signal (adding recurrence) as authoritative and updates the state to match, rather than surfacing a modal error.

**Acceptance criteria**

1. On the Backlog view, tapping the floating `Fab` opens the quick-add sheet; typing a title and confirming saves a new task with `state == TaskState.BACKLOG` and `toDoDate == null`. The task appears in the Backlog view on return; it does **not** appear in Today's `Open` list, in Planning's overdue/upcoming lists, or in the Today overload count.
2. On the Backlog view, tapping the floating `Fab`, typing a title, and choosing "expand" opens the full task editor. The editor's state selector reads `Backlog`; the `toDoDate` field is empty; the title is the typed text. Saving without further change persists the task in `TaskState.BACKLOG`.
3. In the expand-to-full-form editor from Backlog, changing the state selector from `Backlog` to `Open` (with a `toDoDate` picked) saves the task in `TaskState.OPEN` with the picked `toDoDate`. The change is honoured — the Backlog default is a starting point, not a hard rail.
4. In the expand-to-full-form editor from Backlog, adding recurrence to the draft auto-switches the state to `Open` with `toDoDate = today` and disables the `Backlog` state option with the one-line hint. Saving persists a recurring `Open` task (`FR-REC` unchanged). Removing the recurrence does **not** auto-switch back to `Backlog` — once the user has moved into the recurring branch, the state stays where they moved it (they can flip back manually).
5. Adding a task from **Today**'s quick-add `Fab` continues to default to `state = TaskState.OPEN` with `toDoDate = today` — unchanged from v2.4.0. Adding from **Planning**, **All Tasks**, and hamburger-menu shortcuts likewise unchanged. Only the two Backlog-view create paths change behaviour.
6. A task created from Backlog with a theme / habit / goal link at create time enters Backlog with those links stored but **dormant** per `FR-BACKLOG-1` — no `DM-ATTR` contribution rows are written, no habit `history` entry is created, no goal `currentQty` advances. On the subsequent pull-to-Open (`FR-BACKLOG-3`) the links reactivate going forward.
7. No streak / points / badges / adherence surface appears anywhere in the flow (`DM-NOT`).
8. TalkBack announcements on the state selector in the editor read "State: Backlog" (or the current in-app equivalent) when opened from the Backlog `Fab`. Hit targets on the `Fab` and the state selector remain within `NFR-A11Y-1`.

**Out of scope for v2.5.0**

- **A "where to?" chooser on the Backlog `Fab`** — see `[DECISION]` above.
- **Changing the default state on any other view's add path.** Only the two Backlog-originated create paths change.
- **A per-user preference** ("default add-to-Backlog to Open") — the view *is* the intent per `[DECISION]`; a preference for the opposite default would recreate the current bug behind a setting.
- **Retroactively re-stating tasks previously mis-created via Backlog's `Fab`** in earlier versions. Existing tasks are not migrated; only the create path changes going forward. Users can manually move stray Open tasks to Backlog via the state-change flow in the editor.
- **Any change to the pull-out-of-Backlog transitions** (`FR-BACKLOG-3`). The "pull when inspired" flow is unchanged.
- **Any change to the Backlog visibility filter in All Tasks** (`FR-ALL-3`'s Backlog toggle). Unchanged.
