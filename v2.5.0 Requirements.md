## 1. Scope of v2.5.0

v2.5.0 is a **single-fix hotfix increment** on top of a shipped v2.4.0. One source request, one regression to close, no new object types, no schema migrations, no new top-level surfaces (see §4 — Data model deltas below, which is intentionally empty). All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %), the five-tab primary structure (`FR-NAV-1`), and the compass / chosen-direction thesis.

The requirement:

- **`FR-NAV-8`** fixes a regression introduced by `FR-NAV-6.1` in v2.4.0. When `DenBottomNav` began rendering on All Tasks and Backlog as a wayfinder (a correct outcome of `FR-NAV-6`), the floating "add" `Fab` on those two views was not re-anchored to clear it — All Tasks and Backlog still position the `Fab` with `.navigationBarsPadding().padding(end = 20.dp, bottom = 24.dp)`, which only clears the system gesture bar, not the app's bottom nav. The result: on a Pixel 8 in portrait the `Fab` sits **behind** the rust `DenBottomNav` pill row, partially obscured and with a reduced tap target. Today never had this problem because its `Fab` uses `.padding(end = 20.dp, bottom = 104.dp)` — a hard bottom offset that clears both the bottom nav and the system inset. `FR-NAV-8` normalises the `Fab` clearance rule across every Class-A view carrying a `DenBottomNav` so the add affordance is fully visible and comfortably tappable, and pins the rule so the same regression cannot re-appear the next time a new Class-A view gains a `Fab`. Refines `FR-NAV-6.1` (bottom-nav on All Tasks / Backlog) and holds the friction-floor contract from `FR-CAPTURE-1` (quick-add must be a low-effort, thumb-reachable target).

Nothing here is gamification-adjacent — the fix is a layout offset on an existing affordance (`DM-NOT`, `DEC-2/3/4`).

## 2. Functional requirements

### 2.1 Add-button clearance over the bottom nav (`FR-NAV-8`, refines `FR-NAV-6.1` and holds `FR-CAPTURE-1`)

*Source: `FR-2026-07-12-a`. Refines `FR-NAV-6.1`; holds `FR-CAPTURE-1`; introduces `FR-NAV-8.*`.*

The Today view's floating "add" `Fab` (`ui/today/TodayScreen.kt`) is positioned with `Modifier.align(Alignment.BottomEnd).padding(end = 20.dp, bottom = 104.dp)` — a bottom offset large enough that the `Fab`'s bounding box sits **above** the `DenBottomNav` row (nominally ~72 dp tall including the outer padding the nav bar carries), with visible breathing room and the system gesture inset absorbed by the nav bar itself. All Tasks (`ui/alltasks/AllTasksScreen.kt`) and Backlog (`ui/backlog/BacklogScreen.kt`) currently position their `Fab` with `Modifier.align(Alignment.BottomEnd).navigationBarsPadding().padding(end = 20.dp, bottom = 24.dp)` — that offset was correct in v2.3.0 when neither view rendered a `DenBottomNav`, but is wrong in v2.4.0 where both views do render it (per `FR-NAV-6.1`). The two `Fab`s are now partially hidden by the pill row.

`FR-NAV-8` **The floating add `Fab` on every Class-A view that renders `DenBottomNav` is positioned so its bounding box clears the bottom nav and the system gesture inset in full, with the same visible bottom offset the Today view uses today.** Concretely:

- **`FR-NAV-8.1` The clearance rule is the Today pattern.** The `Fab` on All Tasks and Backlog is anchored with `Modifier.align(Alignment.BottomEnd).padding(end = 20.dp, bottom = 104.dp)` — matching Today verbatim. `navigationBarsPadding()` is **not** applied on top of this offset; the 104 dp bottom offset already accounts for both the nav bar (~72 dp) and the system inset that `DenBottomNav` itself absorbs. Applying `navigationBarsPadding()` in addition would double-count the gesture inset and push the `Fab` too far up on devices with three-button navigation.
- **`FR-NAV-8.2` The Today view is unchanged.** Its current offset is the reference; no code moves on `TodayScreen.kt`. This requirement pins the existing placement as the shared contract so a future edit does not silently drop it.
- **`FR-NAV-8.3` The pattern generalises.** Any future Class-A view (per `FR-NAV-6`) that ships a floating add `Fab` uses the same anchor. If a shared `FabScaffold` composable emerges from this fix, all three call sites (Today, All Tasks, Backlog) use it; if not, the three call sites carry identical modifier chains (the same-line diff is the sanity check).
- **`FR-NAV-8.4` The `Fab` composable itself is not modified.** Only the enclosing `Box` modifier on `AllTasksScreen.kt` and `BacklogScreen.kt` changes. `Fab.onClick` wiring, size, tint, and elevation stay exactly as they are today.
- **`FR-NAV-8.5` Screens without a `DenBottomNav` are out of scope.** Settings and About are Class-B leaves per `FR-NAV-6` — they have no `Fab` and no bottom nav, and this requirement does not touch them. Planning, Habits, Directions, and Journey either do not carry a floating add `Fab` at all (their add-flow lives inside the view body or through the hamburger menu) or, where they do (`PlanningScreen`'s undated inbox helper), the placement already clears the nav bar and is not touched by this fix.

> **[DECISION] — Mirror Today, don't introduce a new offset token.**
> An alternative was to define a `FabBottomOffset` design token and use it on all three call sites. But the three offsets are already identical in intent, the current codebase has no other `Fab` placement token, and introducing one to fix a three-line regression would be over-engineering. The intent is captured in `FR-NAV-8.1` and the three call sites diff cleanly against each other — that is enough. If a fourth or fifth Class-A view gains a `Fab` in a later increment, the token can be extracted then.

> **[DECISION] — Don't stack `navigationBarsPadding()` on top of the 104 dp offset.**
> Today does not apply `navigationBarsPadding()` at all, and its `Fab` sits at a visually correct height on the Pixel 8 in both gesture-nav and three-button-nav configurations. `DenBottomNav` itself renders a `windowInsetsPadding(WindowInsets.navigationBars)` (or an equivalent inset absorption) as part of its rust background — so the 104 dp above it is measured from the top of the nav bar, which already sits above the gesture inset. Adding `navigationBarsPadding()` to the `Fab` `Box` would inset it a second time and produce a visible gap on three-button-nav devices.

**Acceptance criteria**

1. On a Pixel 8 in portrait at default text scale, opening **All Tasks** shows the floating add `Fab` fully visible above the `DenBottomNav` pill row with the same visible bottom gap the Today view has (measured pixel-parity on a screenshot at the same emulator resolution).
2. On a Pixel 8 in portrait at default text scale, opening **Backlog** shows the floating add `Fab` fully visible above the `DenBottomNav` pill row with the same visible bottom gap the Today view has.
3. Tapping the visible `Fab` on All Tasks opens the same quick-add sheet it opens today (`FR-CAPTURE-1`); tapping the visible `Fab` on Backlog opens the same quick-add sheet it opens today. Neither wiring changes.
4. The Today view's `Fab` position is unchanged: a screenshot diff against the last-shipped v2.4.0 build shows zero pixel movement on `TodayScreen`.
5. On a Pixel 8 emulated with **three-button navigation** (Settings → System → Gestures → Navigation mode: 3-button), the `Fab` on All Tasks and Backlog still clears the bottom nav without a visible extra gap between the bottom nav and the system nav bar — i.e. `navigationBarsPadding()` has not been left in the modifier chain alongside the 104 dp offset.
6. On a Pixel 8 in landscape at default text scale, the `Fab` on All Tasks and Backlog remains fully visible above the bottom nav — the landscape envelope does not clip it and does not introduce a scroll bar under the `Fab`.
7. The `Fab` tap target on All Tasks and Backlog continues to meet `NFR-A11Y-1`'s ≥ 44 dp touch-target rule with no reduction against v2.4.0 measurements.
8. No streak / points / badges / adherence surface appears anywhere as a side effect of the fix (`DM-NOT`).

**Out of scope for v2.5.0**

- **A shared `FabScaffold` composable.** Deliberately deferred (see `[DECISION]` above); the three call sites carry identical modifier chains and that is enough.
- **A design token for the 104 dp bottom offset.** Same rationale — introducing a token to fix a three-line regression is over-engineering.
- **Any change to the `Fab` size, tint, elevation, or icon.** The composable is unchanged; only the enclosing `Box` modifier moves.
- **Any change to non-`Fab` add affordances** (in-body add-row helpers, hamburger-menu shortcuts, editor-open flows). Only the floating `Fab` on Class-A views with a `DenBottomNav` is in scope.

## 5. Acceptance criteria for "v2.5.0 is done"

v2.5.0 is complete when:

1. `FR-NAV-8` passes its per-section acceptance criteria on the emulator.
2. All v2.0.0 / v2.1.0 / v2.2.0 / v2.3.0 / v2.4.0 acceptance criteria still pass — nothing regresses. In particular:
   - `FR-NAV-6.1` continues to hold — the `DenBottomNav` still renders on All Tasks and Backlog, and the underlying wayfinding contract from v2.4.0 is preserved.
   - `FR-CAPTURE-1`'s friction floor continues to hold — quick-add on Today, All Tasks, and Backlog is reachable in one tap from a fully-visible `Fab`.
   - `FR-NAV-1`'s five-tab primary structure holds — All Tasks and Backlog remain reference views, not tabs.
   - `DM-NOT` (no gamification anywhere) holds across the fix.
3. Automated tests cover:
   - a Compose UI test asserting the `Fab` on **All Tasks** is not occluded by `DenBottomNav` — either by asserting the `Fab`'s bounding box has a strictly positive vertical gap above the `DenBottomNav`'s top edge, or by asserting the `Fab` modifier chain contains `padding(bottom = 104.dp)` (or the extracted shared token) and does **not** stack `navigationBarsPadding()` on top.
   - a Compose UI test asserting the same for **Backlog**.
   - a Compose UI test (or snapshot comparison) asserting the `Fab` position on **Today** is unchanged relative to v2.4.0 — `bottom = 104.dp`, `end = 20.dp`, no `navigationBarsPadding()`.
   - a Compose UI test asserting tapping the `Fab` on All Tasks opens the quick-add sheet with `title = ""`; and the same for Backlog (behavioural regression guard).
4. Debug build installs and launches; no logcat `FATAL` / `AndroidRuntime` lines introduced. Screenshots of All Tasks, Backlog, and Today (portrait + landscape, gesture nav + three-button nav) show the `Fab` fully visible above the bottom nav on every screen.

### M1 — Add-button clearance over the bottom nav (`FR-NAV-8`)

- **Scope:**
  1. In `ui/alltasks/AllTasksScreen.kt`, change the `Fab` anchor `Box` modifier from `Modifier.align(Alignment.BottomEnd).navigationBarsPadding().padding(end = 20.dp, bottom = 24.dp)` to `Modifier.align(Alignment.BottomEnd).padding(end = 20.dp, bottom = 104.dp)` — mirroring the Today pattern per `FR-NAV-8.1`.
  2. In `ui/backlog/BacklogScreen.kt`, make the identical change to the `Fab` anchor `Box`.
  3. Do **not** modify `TodayScreen.kt`'s `Fab` anchor (`FR-NAV-8.2`).
  4. Do **not** modify the `Fab` composable itself, its `onClick` wiring, its size, its tint, or its elevation (`FR-NAV-8.4`).
  5. Do **not** introduce a shared `FabScaffold` composable or a design token for the 104 dp offset (see `[DECISION]` in §2.1).

- **Verify:**

- **Done when:** M1 tests pass; §5 acceptance criteria for `FR-NAV-8` all pass; commit references `FR-NAV-8`, `FR-NAV-6.1`, `FR-CAPTURE-1`, and cross-references source request `FR-2026-07-12-a`.
