## 1. Scope of v2.2.0

v2.2.0 is a **discoverability & ergonomics increment** on top of a shipped v2.1.0. Three small requests, no new object types, no new views, no schema migrations (see §4 — Data model deltas below, which is intentionally empty). All locked decisions from v2.0.0 continue to hold — in particular the whole of `DM-NOT` (no streaks / points / badges / adherence %) and the ≤3 active themes cap.

The three requirements:

- **`FR-HAB-7`** restores a first-class **edit habit** affordance so users can revise a habit's fields without deleting and recreating it. `FR-HAB-2` already reserved "create / edit / delete" as Habits-view responsibilities, but v2.1.0's `FR-HAB-5` collapsed habit cards by default and pushed edit behind an expand step, degrading discoverability.
- **`FR-DIR-7`** puts **add-a-goal** on the Directions hub as a first-class, hub-level affordance alongside add-a-theme. Today, goal creation is reachable only from inside an *expanded* theme or via the orphan-goals section (visible only when at least one orphan goal already exists) — so a user with three collapsed themes has no visible route to create a goal at all. This surfaces the affordance without displacing the theme-create route.
- **`FR-NAV-3`** swaps the header **menu affordance** from the Fox Works roundel to a conventional hamburger icon. The roundel reads as a brand mark, not a menu control, so users don't discover that the reference views (All Tasks · Backlog · Settings) live behind it.

Each is a UI-surface change against existing entities, repositories, and sheets. Together they close three discoverability gaps observed in real use of v2.1.0.

## 2. Functional requirements

### 2.1 Edit habit — full-detail edit surface (`FR-HAB-7`)

*Source: `FR-2026-07-10-e`. Refines `FR-HAB-2` and `FR-HAB-5`.*

`FR-HAB-7` **The Habits view exposes a discoverable "edit habit" affordance that opens a habit in the same editor surface used to create one, with every field the user chose at create time available for editing.** The editable set is exactly the create form's set: `name` (`DM-HABIT-1`), `cue` (`DM-CUE`), the **target** (rate for `frequency`, quantity + `unit` for `quantitative`), the **days-per-week / in-period** target, the served **theme** (`primaryThemeId`) and served **goal** (`DM-HABIT-6`). `history` remains manipulated only via logging (`DM-HABIT-5`) — the editor exposes no "reset history" control (destructive history removal stays behind `DM-HABIT-7` delete, which the editor already surfaces per `FR-HAB-2`).

`FR-HAB-7.1` **Affordance reachable in both collapsed and expanded states.** `FR-HAB-5` collapsed habit cards by default; the edit route must not sit only inside the expanded body, or reaching edit silently costs an extra expand tap and the change made in v2.1.0 quietly regresses the create-edit-delete parity `FR-HAB-2` guarantees. From the **collapsed row**, an explicit tap target (icon or equivalent) opens the editor. From the **expanded card**, the same route is available — either the existing body-press route or an explicit control, at the implementer's discretion, provided the log control and the edit control never collide (see `FR-HAB-7.2`).

`FR-HAB-7.2` **Log and edit are separate tap targets in every state.** The log-activity control (`DM-HABIT-5`, `FR-HAB-4`) never opens the editor, and the edit control never logs. This holds on both the collapsed row (where the log pill is already an isolated hit target per v2.1.0's `FR-HAB-5.1`) and inside the expanded card. Hit-target sizes remain within `NFR-A11Y-1`'s touch-target guidance.

`FR-HAB-7.3` **Editor UI is create-parity.** The same composable that renders the create-habit form renders the edit form, populated with the habit's current values. The destructive **delete** affordance already present in the editor (`FR-HAB-2`, `DM-HABIT-7`) is preserved. Saving writes back through the habit repository; cancelling closes without a write.

`FR-HAB-7.4` **`kind` is fixed once the habit has any logged history.** Switching a habit from `frequency` to `quantitative` (or vice versa) reinterprets every past log — a frequency tick has no `amount`, and a quantitative entry has no meaningful "did it happen" boolean if the numeric target has been dropped. Rather than silently retype history or invent a retroactive migration, the editor **disables the `kind` field when `history` is non-empty** and shows a short one-line hint ("Kind is fixed once you've logged this habit — delete and recreate if you need to switch"). When history is empty — including immediately after creation — `kind` remains editable.

`FR-HAB-7.5` **Non-`kind` changes take effect prospectively; past logs are preserved verbatim.** Changing `target`, `targetDays`, `unit`, `cue`, `name`, `primaryThemeId`, or `goalId` does not rewrite any prior `history` entries. The in-period rate simply recomputes against the new target (`DM-HABIT-3`), and the calendar-style history renders the recorded amounts as-is under the new label. The recompute must not introduce an adherence-percentage or streak surface (`DM-NOT`, `DEC-2/4`).

`FR-HAB-7.6` **Cue proximity in the edit form.** The `cue` field retains the same "front-and-centre" prominence in the edit form as in the create form (`FR-HAB-1` — *a habit card without its cue is just a tracker*). Editing must not be an opportunity to demote the cue below other detail.

`FR-HAB-7.7` **Save is quiet — no gamification voice.** Save closes the sheet and the Habits view reflects the new details. There is no "you're breaking a rhythm," "keep going," streak-continuation, or adherence copy on save. (`DM-NOT`, `DEC-2/4`, `FR-HAB-3`.)

`FR-HAB-7.8` **Linked-task safety.** Editing `name`, `cue`, `target`, `targetDays`, `unit`, `primaryThemeId`, or `goalId` does **not** re-link, regenerate, or otherwise modify any Task that references the habit (`DM-HABIT-6`). The task↔habit link is by `habitId`, and cards that display the habit's name read it at display time — so renaming is a pure display update. `DM-HABIT-8`'s "apply to all occurrences (incl. past) or new occurrences only" prompt is scoped to linking / unlinking and continues to apply only there; a plain field edit under `FR-HAB-7` does not raise that prompt.

> **[DECISION] — fix `kind` after first log, don't destroy history.**
> Two alternatives to `FR-HAB-7.4` were considered: (a) allow `kind` change and drop all prior history, and (b) allow `kind` change and store both projections in `history`. (a) is a hidden destructive edit approaching `DM-HABIT-7`'s severity, hiding under an ordinary "Save" button; (b) triples the data-model complexity for a case the user can already solve by deleting and recreating. Fixing `kind` after first log keeps the editor honest — every visible field is safe to change, and the one field that isn't tells you why.

**Acceptance criteria**

1. From the Habits view, an obvious "edit habit" tap target exists on both **collapsed** and **expanded** habit cards; activating it opens the same editor sheet used to create a habit, populated with the habit's current `name`, `cue`, `kind`, `target`, `targetDays`, `unit` (if quantitative), `primaryThemeId`, and `goalId`.
2. Editing `name`, `cue`, `target`, `targetDays`, `unit`, `primaryThemeId`, or `goalId` and saving persists the change through the habit repository; on return to the Habits view the card renders the new values and the `history` list is unchanged.
3. When the habit has empty `history`, the `kind` field is editable; when `history` is non-empty, the `kind` field is disabled and a short one-line hint explains why. The editor's destructive **delete** affordance (`FR-HAB-2`, `DM-HABIT-7`) is present and unchanged.
4. The log control (from either collapsed or expanded state) never opens the editor; the edit control never logs. Both hit targets meet `NFR-A11Y-1` touch-target guidance.
5. No streak / adherence-% / points / badge surface appears anywhere in the edit flow, including on save (`DM-NOT`, `DEC-2/4` unchanged).
6. Editing a habit that has linked Tasks (including linked *recurring* Tasks per `DM-HABIT-8`) does not modify, regenerate, or re-prompt for those Tasks; the tasks continue to reference the same `habitId` and render the updated `name` at display time.
7. TalkBack announces the edit affordance with a distinct content description in both collapsed and expanded states, and the collapsed row's log affordance keeps its existing announcement (`NFR-A11Y-1`, `FR-HAB-5` acceptance-criterion 6).

**Out of scope for v2.2.0**

- **Bulk edit of multiple habits at once.** Not requested and inconsistent with the "one path at a time" friction-floor philosophy (`FR-CAPTURE`).
- **In-editor history correction / reset.** History is manipulated via logging (`DM-HABIT-5`) and full destruction remains behind `DM-HABIT-7` (delete). A softer mid-life "reset history" control would open a second destructive path with less friction than delete.
- **Editing `kind` after first log.** See `FR-HAB-7.4` and the [DECISION] callout above; the delete-and-recreate escape hatch already exists.
- **Retro-editing linked Tasks when the habit changes.** Explicitly not part of this edit path per `FR-HAB-7.8`; `DM-HABIT-8`'s prompt remains scoped to link/unlink.
- **Editing the habit from surfaces other than the Habits view** (e.g. from a linked task's editor). Consistent with `FR-HAB-2`, edit lives on the Habits view.

### 2.2 Add a goal from Directions — first-class hub-level create (`FR-DIR-7`)

*Source: `FR-2026-07-10-f`. Refines `FR-DIR-4`; interacts with `FR-DIR-6` (theme create/cap).*

Today the Directions hub exposes exactly one primary create action — the floating "Theme" button (`FR-DIR-6`). Goal creation is nested one level deeper: either inside an *expanded* theme (`FR-DIR-3`'s "Add a goal to this theme" affordance) or in the orphan-Goals section (`FR-DIR-1`) — and the orphan section only renders when at least one orphan goal already exists. A user with three collapsed themes and no orphan goals therefore has **no visible route from Directions to create a goal**, even though `DM-GOAL` is a first-class direction-layer object at the same tier as Theme.

`FR-DIR-7` **The Directions view exposes a first-class "add a goal" affordance at the hub level, alongside the existing "add a theme" affordance.** The affordance is visible on entry to Directions (`scope = active`) *without* the user having to expand a theme, and *without* requiring an orphan goal to already exist. It coexists with — does not replace — the two existing nested routes.

`FR-DIR-7.1` **Two primary creates share the same entry point.** The single hub-level primary action (today: "Theme" FAB) becomes a two-option create: **Add a goal** and **Add a theme**. The exact affordance style is left to the implementer within these constraints:

- Both options must be discoverable in ≤ 1 tap from Directions.
- The Theme create route (`FR-DIR-6`) must continue to open the same `ThemeEditorSheet` with the same behaviour (including the ≤3 active cap flow, `capBlocked`, and archive prompts).
- The two options are visually distinguishable (labels or icons) so a user does not tap "Theme" when they meant "Goal".
- The affordance respects `NFR-A11Y-1` touch-target sizing and contrast.

> **[DECISION] — expanded FAB with two labelled actions.**
> Two viable Material 3 patterns fit: (a) replace the single "Theme" FAB with a "+" FAB that, when tapped, opens a small chooser sheet ("Add a goal" / "Add a theme") that then routes to the appropriate editor; (b) an expanded FAB / speed-dial with two labelled buttons. Both are acceptable under `FR-DIR-7.1`. The implementer picks the one that reads best against the Den aesthetic — the goal is a single discoverable hub-level action with two clear labelled destinations. **Do not** silently repurpose the existing FAB to open only Goal (would regress `FR-DIR-6`), and **do not** stack two independent FABs (visually dominant, competes with the compass rose).

`FR-DIR-7.2` **Create form is `GoalEditorSheet` at create-parity.** The hub-level create opens the same `GoalEditorSheet` composable used by the nested "Add a goal to this theme" affordance. The form exposes every field required at creation per `DM-GOAL-1`:

- `title` (required)
- optional `description`
- `type` ∈ { **Stepped**, **Accumulative**, **Generic** }
- type parameters: for **Stepped**, the steps list (with `DM-GOAL-2`'s endowed *"Defined this goal ✓"* first step auto-added, unchanged); for **Accumulative**, `target` quantity + `unit` + `current` (endowed starting progress, unchanged)
- optional `deadline`
- optional one-line `commitment` (the lightweight commitment-device field from `DM-GOAL-1`)
- `primaryThemeId` — **nullable**, so a hub-level create can produce an orphan goal (`FR-DIR-1`'s orphan section)
- additional served themes (`themeIds`) — a goal may serve any number of themes per `DM-GOAL-6`

`FR-DIR-7.3` **Theme picker included in the create form.** Because the hub-level route is not scoped to a single theme (unlike the nested "Add a goal to this theme" route, which prefills the theme), the form presents a **theme picker** — including a "no theme (orphan)" option — that writes `primaryThemeId`. The picker lists all `active` themes at time of open. `upcoming` and `archived` themes are excluded (a fresh goal serving a not-yet-started or ended direction has no place to render).

`FR-DIR-7.4` **Endowed progress on create is unchanged (`DM-GOAL-2`).** Never an empty bar: Stepped goals still get the *"Defined this goal ✓"* first step already checked; Accumulative goals still record honest starting progress on `current`. The hub-level route inherits this from `GoalEditorSheet` — it is not re-implemented.

`FR-DIR-7.5` **Anti-overwhelm on create is unchanged (`DM-GOAL-5`).** The dismissible soft warning past 5 active goals continues to appear on save; it remains a nudge, never a hard block. Hub-level create does not bypass, escalate, or duplicate the warning.

`FR-DIR-7.6` **Nested routes remain.** The "Add a goal to this theme" affordance inside an expanded theme continues to exist under `FR-DIR-3/4` and continues to prefill the theme picker. The orphan-section "Add a goal" affordance (visible when the orphan section exists) also remains. `FR-DIR-7` is *additive* — it does not remove either nested route.

`FR-DIR-7.7` **Primary-action confirmation contrast.** The create-goal confirm button must satisfy `FR-HAB-6.2`'s scoped audit — readable primary-action contrast in both light and dark themes, no reversed white-on-bright regression.

`FR-DIR-7.8` **Save is quiet.** On save, the sheet closes and the Directions view reflects the new goal in the correct section (orphan if `primaryThemeId == null`, nested under the primary theme otherwise). No streak / points / badges / adherence copy appears (`DM-NOT`, `DEC-2/3/4`).

`FR-DIR-7.9` **Completion path is unchanged.** `DM-GOAL-4`'s "Where would you like to go from here?" post-completion prompt continues to apply — it is a property of goal completion, not of goal creation, and hub-level create does not touch it.

**Acceptance criteria**

1. From the Directions view (`scope = active`), the hub-level primary create surface exposes **two clearly labelled options**: "Add a goal" and "Add a theme". Both are reachable in ≤ 1 tap from the Directions hub without expanding any theme.
2. Selecting "Add a theme" opens the existing `ThemeEditorSheet` with unchanged behaviour (including `FR-DIR-6`'s cap and `capBlocked` flow).
3. Selecting "Add a goal" opens `GoalEditorSheet` with every field required by `DM-GOAL-1` — `title`, optional `description`, `type` (Stepped / Accumulative / Generic), type parameters, optional `deadline`, optional `commitment`, and a **theme picker** listing active themes plus a "no theme (orphan)" option that writes `primaryThemeId`.
4. Saving a goal with `primaryThemeId == null` renders it in the orphan-Goals section on return; saving with a chosen theme renders it nested under that theme's expanded body.
5. Endowed progress (`DM-GOAL-2`) applies unchanged from the hub-level route: a new Stepped goal shows the auto-added *"Defined this goal ✓"* step checked; an Accumulative goal shows the honest starting-progress bar.
6. The anti-overwhelm soft warning past 5 active goals (`DM-GOAL-5`) appears on save via the hub-level route on the same threshold and remains dismissible; it never hard-blocks.
7. The nested "Add a goal to this theme" affordance inside an expanded theme, and the orphan-section "Add a goal" affordance, both continue to work and continue to prefill correctly.
8. No streak / points / badges / adherence surface appears in the create flow or on save (`DM-NOT`, `DEC-2/3/4`). Confirm-button contrast on create-goal meets WCAG AA ≥ 4.5:1 in light and dark themes (`FR-HAB-6.2`, `NFR-A11Y-1`).
9. TalkBack announces the hub-level create options with distinct content descriptions ("Add a goal", "Add a theme"); hit targets meet `NFR-A11Y-1` sizing.

**Out of scope for v2.2.0**

- **Adding goals from views other than Directions** (e.g. a Today shortcut). `FR-CAPTURE` handles cross-view quick capture for Tasks; the direction layer stays scoped to the Directions hub, consistent with `FR-HAB-2`'s "habits create/edit lives on Habits".
- **A separate "Goals" top-level view** in the bottom nav. `FR-NAV-1` fixes the primary nav at five entries; Goals live inside Directions as `FR-DIR-1` requires.
- **Reworking `GoalEditorSheet` beyond wiring the hub-level entry point.** Any missing field surfaced by `DM-GOAL-1` in the current editor is fixed inside the editor, not by adding a parallel form.
- **Bulk goal import / templates.** Not requested.

### 2.3 Header menu affordance — hamburger, not roundel (`FR-NAV-3`)

*Source: `FR-2026-07-10-g`. Refines `FR-NAV-1` (menu affordance for reference views).*

`FR-NAV-1` states that "All Tasks and Backlog are reachable via search/menu". Today, the "menu" trigger is the **Fox Works roundel** (`FoxLogo`) mounted in the right slot of the `RustHeader` on Today, Planning, and All Tasks. Tapping it opens `AppMenuSheet` ("Around the den") which lists All Tasks · Backlog · Settings. The roundel reads as a brand mark, not as a control — users don't discover that it's tappable, and the reference views quietly become unreachable.

`FR-NAV-3` **The header menu affordance on views that mount `AppMenuSheet` is a conventional "hamburger" icon (three horizontal bars), not the Fox Works roundel.** Applies to every screen that currently uses `FoxLogo` in the header's right slot as a menu trigger — Today (`FR-TODAY`), Planning (`FR-PLAN`), and All Tasks (`FR-ALL`).

`FR-NAV-3.1` **Consistent Den styling.** The hamburger uses the same Den tokens (`TzIcons` family, `Den.rust` / `Den.cream` / `Den.ink` per the surrounding header chrome) so it visually belongs to the header — matching stroke weight and contrast with the other header icons (compass, chevrons, plus). It sits in the same right slot the roundel currently occupies, with equivalent hit-target size (≥ 44dp per `NFR-A11Y-1`).

`FR-NAV-3.2` **Content description.** The tap target announces "Menu" (or an equivalent short imperative — implementer's choice within `NFR-A11Y-1`) via `contentDescription`. The prior "The Fox Works" description does not survive the change, because the affordance no longer identifies the brand.

`FR-NAV-3.3` **`AppMenuSheet` contents and voice are unchanged.** The sheet still opens as "Around the den" and contains the same rows (All Tasks · Backlog · Settings) in the same order, with the same icons and subtitles. This requirement swaps the *trigger*, not the sheet.

`FR-NAV-3.4` **The Fox Works brand mark stays elsewhere in the app.** The `FoxLogo` composable is not deleted. Onboarding / Welcome surfaces (`WelcomeScreen`), Settings, and any other non-menu use of the roundel for identity continue to render it. This is a narrow *menu-affordance* swap; the mascot is preserved wherever it functions as identity rather than as a control.

`FR-NAV-3.5` **Contrast.** The hamburger against the `RustHeader` background meets **WCAG AA ≥ 4.5:1** in both light and dark themes (`NFR-A11Y-1`). The stroke weight is heavy enough to remain legible at the default header scale on a Pixel 8 emulator.

> **[DECISION] — swap the affordance, keep the sheet and the mascot.**
> Two alternatives were considered: (a) replace the roundel *and* migrate `AppMenuSheet` to a Material 3 modal navigation drawer, (b) leave the roundel and only add supporting affordance elsewhere. (a) is a larger change than the request describes and would compete with the bottom-nav's five-tab primary structure (`FR-NAV-1`); (b) doesn't solve the discoverability problem the user reported. Swapping the icon while keeping the bottom-sheet menu and the mascot's non-menu uses is the minimum coherent change.

**Acceptance criteria**

1. On Today, Planning, and All Tasks, the header's right slot shows a hamburger icon (three horizontal bars) styled in the Den palette, not the Fox Works roundel.
2. Tapping the hamburger opens the same `AppMenuSheet` ("Around the den") with the same rows (All Tasks · Backlog · Settings, in that order) and same subtitles / icons.
3. TalkBack announces the header menu control as "Menu" (or an implementer-chosen equivalent per `NFR-A11Y-1`).
4. The `FoxLogo` composable still exists and is still rendered wherever it was used for identity (Welcome / onboarding, and any other non-menu surface).
5. The hamburger's contrast against the header background meets WCAG AA ≥ 4.5:1 in both light and dark themes. Hit-target ≥ 44dp per `NFR-A11Y-1`.
6. No behavioural change to the sheet itself — no new rows added, no rows removed, no reordering.

**Out of scope for v2.2.0**

- **Migrating the menu to a Material 3 modal navigation drawer.** The `AppMenuSheet` bottom-sheet pattern is unchanged; only the trigger is swapped.
- **Adding new entries to the menu** (e.g. a shortcut to Directions from within the menu). Directions is already in the primary bottom nav (`FR-NAV-1`); the menu is for reference views specifically.
- **Removing the Fox Works roundel from the app.** Explicitly preserved in non-menu locations per `FR-NAV-3.4`.
- **Adding a menu affordance to Directions / Habits / Journey.** Those views don't currently mount `AppMenuSheet` — extending the menu to them is a separate discoverability question and not part of this request.

## 3. Non-functional requirements

No new NFRs in v2.2.0. The three functional requirements **strengthen conformance** with existing `NFR-A11Y-1`:

- `FR-HAB-7` — adding a discoverable edit affordance on the collapsed habit row requires an explicit content description distinct from the log and expand affordances already announced under `FR-HAB-5`.
- `FR-DIR-7` — the hub-level create surface exposes two distinct labelled options ("Add a goal", "Add a theme"), each with its own content description; confirm-button contrast on create-goal continues to satisfy `FR-HAB-6.2`'s scoped audit.
- `FR-NAV-3` — the hamburger replaces a decorative brand mark with a functional icon; content description ("Menu") and contrast (WCAG AA ≥ 4.5:1) must both improve on the roundel it replaces.

All other `NFR-*` from v2.0.0 and v2.1.0 continue to apply unchanged.

## 5. Acceptance criteria for "v2.2.0 is done"

v2.2.0 is complete when:

1. `FR-HAB-7`, `FR-DIR-7`, and `FR-NAV-3` each pass their own acceptance criteria in §2 on the emulator.
2. All v2.0.0 and v2.1.0 acceptance criteria still pass — nothing regressed, in particular:
   - `DM-NOT` (no gamification anywhere), including on save from the habit-edit flow and the hub-level goal-create flow;
   - `FR-HAB-5`'s collapse-by-default, log-from-collapsed behaviour, and no-persisted-expand rule (edit must not accidentally persist expand state or move logging back into the expanded body);
   - `DM-HABIT-7` delete confirmation remains the only path that removes habit history;
   - `DM-HABIT-8` link/unlink prompt behaviour is unchanged by a plain field edit;
   - `FR-DIR-6`'s theme create + ≤3 active cap + `capBlocked` flow is unchanged by the introduction of the hub-level goal-create option;
   - `DM-GOAL-2` endowed progress and `DM-GOAL-5` anti-overwhelm nudge apply unchanged from the hub-level goal-create route;
   - `AppMenuSheet` contents, order, and voice are unchanged; the `FoxLogo` composable still renders wherever it functions as identity rather than as a menu trigger.
3. Automated tests cover:
   - opening the habit editor from the collapsed row and from the expanded card, and asserting field pre-population;
   - persisting a non-`kind` habit field change (name, cue, target, targetDays, unit, primaryThemeId, goalId) and re-reading the habit;
   - the disabled-`kind` habit behaviour when history is non-empty, and the editable-`kind` behaviour when history is empty;
   - a Compose UI test that the log control on both collapsed and expanded habit states does not open the editor;
   - a Compose UI test that Directions exposes both "Add a goal" and "Add a theme" as discoverable hub-level primary actions without expanding a theme;
   - saving a hub-level goal with no theme lands it in the orphan section; saving with a chosen theme lands it nested under that theme;
   - a Compose UI test that the header's right slot on Today, Planning, and All Tasks renders a hamburger with `contentDescription = "Menu"` (or agreed equivalent) and opens `AppMenuSheet` on tap.
4. Debug build installs and launches; no logcat `FATAL` / `AndroidRuntime` lines introduced. Confirm-button contrast on create-goal and hamburger contrast against the header background both meet **WCAG AA ≥ 4.5:1** in light and dark themes (`NFR-A11Y-1`, `FR-HAB-6.2`).

## 6. Milestones

Ordered plan for the builder. Each milestone ends with a green test suite, a headless install-and-screenshot verification, and a git commit citing the milestone + requirement codes.

### M1 — Edit habit (`FR-HAB-7`, refines `FR-HAB-2` and `FR-HAB-5`)

- **Scope:** add a discoverable edit affordance to the Habits view's habit card on both the collapsed row and the expanded body, routing to the existing `HabitEditorSheet` (which already supports edit mode via `initial: Habit?`). Keep the log control isolated on both states. In `HabitEditorSheet`, disable the `kind` selector when the habit has non-empty history and show a one-line hint; keep it editable at create time and when history is empty. Preserve the existing delete affordance and its destructive confirmation (`DM-HABIT-7`). No new tokens, no schema change.
- **Why first:** highest-value ergonomics fix — a functional regression that shipped in v2.1.0's collapse change; landing it first restores create-edit-delete parity guaranteed by `FR-HAB-2`.
- **Verify:** Compose UI tests for (a) opening the editor from the collapsed row, (b) opening it from the expanded card, (c) log control on both states never opens the editor, (d) saving a non-`kind` field change persists and re-renders, (e) `kind` field is disabled when history is non-empty and editable when it isn't.
