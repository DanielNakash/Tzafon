## 1. Scope of v2.12.0

v2.12.0 is a **capture-and-retrieval increment** on top of a shipped v2.11.0. Two source requests are groomed here; neither is a bug report — both are the user asking a surface they already live in to do a little more of the work.

- **`FR-2026-07-31-a` → `FR-PLAN-6`.** All Tasks has had live title/description search since `FR-ALL-2` (v2.0.0): a search row in the header's `bottomContent`, an `ActionLogic.matchesQuery` filter in the view model, and a "Nothing matches — try fewer words." empty state (`ui/alltasks/AllTasksScreen.kt:170-208`, `ui/alltasks/AllTasksViewModel.kt:110/137`). Planning has no equivalent — its header `bottomContent` carries only the `FR-PLAN-2` range presets (`ui/planning/PlanningScreen.kt:98-129`), so a user who wants to find "the dentist thing" somewhere in an overdue pile plus a 30-day range has to leave Planning for All Tasks and lose their triage context. `FR-PLAN-6` adds the same search affordance to Planning, filtering all three of its buckets (overdue decide-cards, dated groups, Inbox) through the *same* `ActionLogic.matchesQuery` predicate, so the two views can never drift in what "matches" means.
- **`FR-2026-07-31-b` → `FR-CAPTURE-3` + `FR-PLAN-7`.** The shared one-line quick-add (`ui/capture/QuickAddSheet.kt`, `FR-CAPTURE-1`) takes a title and nothing else — a cue means expanding into the full editor, which is exactly the friction `FR-CAPTURE-1`'s "friction floor" exists to avoid. The user wants to type `Call the bank 08:30` and get a task titled *Call the bank* carrying an `AT_TIME` cue at `08:30`. `FR-CAPTURE-3` specifies that parse: a trailing `HH:MM` token (validated by the same `HH_MM_REGEX` the `CueSheet` save-gate uses, `ui/components/CaptureSheets.kt:48-49`) is lifted off the title into `Cue(AT_TIME, label = "", time = "08:30")` — precisely the label-less shape `FR-CUE-2` made saveable and `FR-CUE-3` made visible on the row — with a quiet inline preview in the sheet and a one-tap opt-out so the parse is never silent magic. `FR-PLAN-7` adds the second half of the user's request: on Planning, a quick-add whose title carried a parsed time also gets `toDoDate = today`, because `NotifyLogic.remindersFor` only ever schedules a task reminder when `toDoDate == date || dueDate == date` (`domain/notify/NotifyLogic.kt:58-70`) — an undated task with an `08:30` cue is a cue that never fires.

Neither request is gamification-adjacent. A search field, a string parse, and a date default. `DM-NOT` and `DEC-2/3/4` continue to hold. All other locked decisions from v2.0.0 — the five-tab primary structure (`FR-NAV-1`), the compass / chosen-direction thesis, local-first-with-clean-seam persistence, the Fox Works "Den" identity, the state-machine and recurrence model, and `PRIN-9` "never engagement-bait" — are untouched.

## 3. Functional requirements

### 3.1 Planning carries the same live search as All Tasks (`FR-PLAN-6`)

*Source: `FR-2026-07-31-a`. Adds `FR-ALL-2`'s search affordance to the Planning view. Scope: `ui/planning/PlanningScreen.kt` (the header `bottomContent` and the three list sections) and `ui/planning/PlanningViewModel.kt` (a `query` flow into the existing `combine`). The shared predicate `ActionLogic.matchesQuery` (`domain/action/ActionLogic.kt:135-140`) is reused verbatim — no new matching logic.*

All Tasks' search is three moving parts, and Planning gets all three in the same shape:

- a search `Row` inside the `RustHeader`'s `bottomContent` — a `TzIcons.Search` glyph, a `BasicTextField` on a `Color.White.a(0.16f)` rounded field, and an `X` clear affordance that appears once the field is non-empty (`AllTasksScreen.kt:173-208`);
- a `MutableStateFlow<String>` in the view model folded into the state `combine`, filtering with `ActionLogic.matchesQuery` (`AllTasksViewModel.kt:60/77/110`);
- a "Nothing matches — try fewer words." line when a live query yields an empty list (`AllTasksScreen.kt:295-305`).

`FR-PLAN-6` **Planning gains a live title/description search in its header, filtering all three Planning buckets — overdue decide-cards (`FR-PLAN-3`), the dated groups within the range (`FR-PLAN-1`), and the Inbox — through `ActionLogic.matchesQuery`. Matching semantics, placeholder copy, clear affordance and the no-results line are identical to All Tasks (`FR-ALL-2`), so a user's mental model of "search" is one model, not two.**

- **`FR-PLAN-6.1` The search row sits above the range presets.** In `ui/planning/PlanningScreen.kt:98-129`, the `RustHeader`'s `bottomContent` becomes a `Column`: the search `Row` first, then the existing horizontally-scrollable `RangePreset` chip `Row` with its current `Modifier.padding(top = 11.dp)` rhythm — mirroring All Tasks, where search sits above the `SHOW:` toggle row (`AllTasksScreen.kt:171-225`). The range chips themselves are unchanged in content, styling, and behaviour (`FR-PLAN-2`).
- **`FR-PLAN-6.2` The field is visually identical to All Tasks'.** Same `RoundedCornerShape(11.dp)`, same `Color.White.a(0.16f)` fill, same `horizontal = 12.dp, vertical = 10.dp` padding, same `TzIcons.Search(16.dp, Color.White.a(0.8f))` leading glyph, same `DenType.body` 14 sp white text, same `Tz.colors.cream` cursor, same `singleLine = true`, same placeholder **"Search title or description…"** at `Color.White.a(0.72f)`, and the same `TzIcons.X(13.dp, …)` clear button that appears only when the field is non-empty. No new colour is introduced; everything resolves through `Tz` / `DenType` (`FR-DESIGN-4`).
- **`FR-PLAN-6.3` The view model filters, not the screen.** `PlanningViewModel` gains `private val query = MutableStateFlow("")` and `fun setQuery(q: String)`, folded into the existing `combine(...)` that already merges tasks, preset, custom end, habits and goals. The `build(...)` function applies `ActionLogic.matchesQuery(task, q)` to the task list **before** `ActionLogic.planningGroups(...)` groups it, so grouping, sorting and the `FR-PLAN-5` slipped-recurring exclusion all operate on the filtered set with no duplicated bucket logic. `PlanningUiState` gains `val query: String = ""` alongside the existing fields, matching `AllTasksUiState.query`.
- **`FR-PLAN-6.4` Search filters what Planning would show anyway — it does not widen the range.** A live query narrows the overdue / dated / Inbox buckets Planning already computes for the chosen range (`FR-PLAN-2`); it does **not** reach past `rangeEnd`, does not reveal Done / Closed / Frozen / Backlog tasks (Planning shows only `TaskState.OPEN`, per `ActionLogic.planningGroups`), and does not un-hide a task excluded by `FR-PLAN-5`. All Tasks remains the exhaustive index (`FR-ALL-1`). See the **[DECISION]** below, and the no-results copy in `FR-PLAN-6.6` which points the user there.
- **`FR-PLAN-6.5` Group headers with no surviving match disappear.** Because filtering happens before grouping, a dated group whose every task was filtered out produces no `GroupHeader` at all, and the `Overdue` header + decide-card container render only when at least one overdue task matches. No empty headers, no zero counts — the counts on the headers are the *matching* counts.
- **`FR-PLAN-6.6` A distinct no-results line replaces the empty state while searching.** Planning's existing empty state ("The table is clear" / "Captured things land here to be given a day.", `PlanningScreen.kt:215-234`) fires when all three buckets are empty. While a query is live, that copy is **suppressed** — an empty result is not an empty table — and is replaced by the All Tasks no-results line, extended with a pointer to the exhaustive index: **"Nothing in range matches — All Tasks searches everything."** Same `DenType.body` 13.5 sp, `Tz.colors.muted`, centred, `padding(top = 40.dp)` treatment as `AllTasksScreen.kt:295-305`.
- **`FR-PLAN-6.7` The query is transient view state.** The text survives configuration change via `rememberSaveable` (as on All Tasks, `AllTasksScreen.kt:112`) but is **not** persisted to DataStore and not synced — leaving Planning and returning starts from an empty field. The range preset keeps its existing DataStore persistence (`settings.planningPreset`); search does not join it.
- **`FR-PLAN-6.8` The range chips stay live while searching.** Changing the range with a query active re-filters within the new range (the two are independent inputs to the same `combine`). Changing the range still drives the generation horizon (`FR-REC-3`) exactly as today — search never touches `applyHorizon`.
- **`FR-PLAN-6.9` Every row action still works on a filtered row.** Tapping a matching row opens the editor; the checkbox toggles Done (chiming per `FR-AUDIO-1`); a matching overdue `DecideCard` keeps its full action set (`FR-PLAN-4` — today / reschedule / change status). The filter is a display predicate, never a capability gate.
- **`FR-PLAN-6.10` RTL search behaves as on All Tasks.** The query matches on the underlying string regardless of visual direction (`FR-DESIGN-3.3`): a Hebrew query matches a Hebrew title. The input's `TextStyle` carries the same content-direction resolution used elsewhere for user-authored text (`FR-DESIGN-3`), so a Hebrew query renders RTL inside the field while the surrounding chrome stays LTR.
- **`FR-PLAN-6.11` No `DM-NOT` surface.** A search field surfaces no score / streak / adherence / badge, and the result count is a plain header count, not a metric (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Planning's search is range-bounded; All Tasks stays the exhaustive index.**
> Two readings of "a search option as in the All Tasks View" were possible: (a) search everything from Planning, effectively making Planning a second All Tasks; or (b) search *within* Planning's own contents — overdue + the chosen range + Inbox. Choice (b), because `FR-ALL-1` defines All Tasks as *the* exhaustive-view surface and `FR-PLAN-1/2` define Planning as a bounded triage table; a Planning search that silently returned tasks dated four months out would contradict the range control the user just set two chips above the field. The cost — a user searching in Planning for something outside the range finds nothing — is paid off by `FR-PLAN-6.6`'s no-results copy, which names All Tasks explicitly. A user who wants everything is one hamburger tap away.

> **[DECISION] — Reuse `ActionLogic.matchesQuery` verbatim; no per-view matching rules.**
> A richer Planning-specific matcher was considered (match on habit name, goal title, or cue label as well). Rejected for this increment: `FR-ALL-2` defines search as title/description, and two surfaces with two different definitions of "matches" is precisely the drift `FR-CUE-3.1` was written to prevent on the display side. If richer matching is wanted, it belongs in `ActionLogic.matchesQuery` where both views inherit it at once — a separate request.

**Acceptance criteria**

1. Open Planning. A search field sits in the header directly above the range-preset chips, visually identical to All Tasks' (`FR-PLAN-6.1`, `FR-PLAN-6.2`), with the placeholder "Search title or description…".
2. With an overdue task titled "Dentist", a task dated tomorrow titled "Dentist forms", and an undated Inbox task titled "Call plumber": type `dent`. The Overdue card shows only "Dentist", the tomorrow group shows only "Dentist forms", and the Inbox group disappears entirely (`FR-PLAN-6.3`, `FR-PLAN-6.5`).
3. Type `plumb`: only the Inbox group renders, with its single match; the Overdue header and all dated groups are gone (`FR-PLAN-6.5`).
4. Type `zzzz`: no groups render, and the line "Nothing in range matches — All Tasks searches everything." appears; the "The table is clear" empty state does **not** appear (`FR-PLAN-6.6`).
5. Tap the `X` clear affordance: the field empties and the full unfiltered table returns, including the Overdue card and the Inbox (`FR-PLAN-6.2`).
6. Search matches on description as well as title — a task titled "Errand" with description "collect the dentist forms" matches `dentist` (`FR-PLAN-6.3`, via `ActionLogic.matchesQuery`).
7. Search is case-insensitive: `DENTIST`, `dentist` and `Dentist` return the same set (`ActionLogic.matchesQuery`, unchanged).
8. With a query live, switch the range preset from 7 days to 30 days: results re-filter within the wider range without clearing the query; a task dated 20 days out that matches now appears (`FR-PLAN-6.8`).
9. With a query live, a task dated 20 days out under a 7-day range does **not** appear (`FR-PLAN-6.4`) — the same task is findable in All Tasks' search.
10. A slipped recurring occurrence hidden by `FR-PLAN-5` stays hidden when its title is typed into the search field (`FR-PLAN-6.4`).
11. Done / Closed / Frozen / Backlog tasks never appear in Planning search results, with or without a query (`FR-PLAN-6.4`).
12. Tap a matching row → the editor opens for that task. Tap a matching row's checkbox → it completes and chimes per `FR-AUDIO-1`. A matching overdue card still offers today / reschedule / change status (`FR-PLAN-6.9`).
13. Rotate the device with a query live: the text survives (`rememberSaveable`); navigate away to Habits and back: the field is empty (`FR-PLAN-6.7`).
14. Type a Hebrew query: it renders RTL inside the field, matches the Hebrew title, and the surrounding header chrome is unmoved (`FR-PLAN-6.10`).
15. `DM-NOT` audit clean (`FR-PLAN-6.11`).

**Out of scope for v2.12.0**

- **Search on Today, Habits, Directions or Journey.** The request names Planning; Today is a single day's short list and Habits/Directions are not task indexes.
- **Searching outside the range from Planning.** See DECISION; All Tasks covers it.
- **Matching on habit name, goal title, cue label, or commitment text.** See DECISION — a shared-predicate change, if wanted, is its own request.
- **Search history, recent queries, or suggestions.** Nothing is stored (`FR-PLAN-6.7`); a recents list would be state the user never asked to keep.
- **A results count badge or "N of M" readout.** Group header counts already say how much matched (`FR-PLAN-6.5`).
- **Fuzzy / typo-tolerant matching.** `matchesQuery` is a substring test; keeping it identical across both views is the point.

### 3.2 Quick-add reads a trailing `HH:MM` as an `AT_TIME` cue (`FR-CAPTURE-3`, refines `FR-CAPTURE-1`)

*Source: `FR-2026-07-31-b` (first sentence). Scope: the shared one-line quick-add `ui/capture/QuickAddSheet.kt` and the three view-model draft builders behind it (`TodayViewModel.quickAddDraft`, `PlanningViewModel.quickAdd`, `BacklogViewModel.quickAddDraft`), plus the expand-to-editor route. The parse itself is pure domain logic and lives where it can be unit-tested without Compose.*

`FR-CAPTURE-1` set the friction floor: "title + Enter → saved". Everything else — dates, cue, alignment, recurrence — is behind EXPAND. That floor is right, but it means the single most common piece of structure a person adds in the same breath as the title ("…at half eight") costs a full editor round-trip. The user's request is to let the title carry that one piece of structure inline, in the one unambiguous shape a clock has: `HH:MM`.

The receiving shape already exists and is already well-behaved: `FR-CUE-2` (v2.10.0) made `Cue(AT_TIME, label = "", time = "08:30")` a valid saveable cue, and `FR-CUE-3` (v2.11.0) made it *visible* — `Cue.display()` renders a label-less time cue as `08:30` on every task row and editor slot. A quick-add parse therefore writes a shape the rest of the app already renders, reminds on, syncs and exports correctly.

`FR-CAPTURE-3` **in the shared quick-add sheet, a valid `HH:MM` token at the very end of the typed title is lifted off the title and saved as `Cue(type = AT_TIME, label = "", time = "<HH:mm>")` on the new task. The sheet shows a quiet inline preview of the parse before saving, and a single tap on that preview cancels it, keeping the title literal.**

- **`FR-CAPTURE-3.1` The parse is pure, shared, and unit-tested.** A single function — e.g. `QuickAddParse.parse(raw: String): Parsed` in `domain/action/` (or `domain/capture/`), returning `Parsed(title: String, time: String?)` — is the only place the rule lives. All three quick-add call sites and the expand path call it; no call site re-implements the regex. It takes no Android dependency so it is testable under `testDebugUnitTest` (`NFR-TEST-1`).
- **`FR-CAPTURE-3.2` The token rule.** After trimming trailing whitespace, the raw title matches the parse when it ends with **whitespace followed by a valid 24-hour `HH:MM`**, i.e. `^(?<title>.*\S)\s+(?<time>([01]\d|2[0-3]):[0-5]\d)$`. The time half is exactly `HH_MM_REGEX` from `ui/components/CaptureSheets.kt:48` — zero-padded, colon required, `00:00`..`23:59` — so what quick-add accepts and what the `CueSheet` save-gate accepts can never diverge. `Parsed.title` is the capture group trimmed; `Parsed.time` is the matched token.
  - **[DECISION]** below covers the non-zero-padded (`8:30`) case.
- **`FR-CAPTURE-3.3` No token, no change.** When the title does not end in a valid token, `parse` returns `Parsed(title = raw.trim(), time = null)` and every downstream path behaves exactly as it does today (`FR-CAPTURE-1`, `FR-CAPTURE-2`, `FR-TODAY-7`, `FR-BACKLOG-5.1`). This is the overwhelmingly common case and must be byte-identical to today's behaviour.
- **`FR-CAPTURE-3.4` A time-only title does not parse.** If stripping the token would leave a blank title (the user typed just `08:30`), the parse does **not** fire: the title stays `08:30` and no cue is set. A task must have a title (`canSave = draft.title.isNotBlank()`, `TaskEditorScreen.kt:113`), and inventing one would be the app putting words in the user's mouth.
- **`FR-CAPTURE-3.5` The preview is visible, and one tap opts out.** While the field's current text parses, the sheet renders a quiet line under the input — mono caption, `Tz.colors.muted`, e.g. **`CUE · 08:30 — TAP TO KEEP AS TEXT`** — showing the time that will be set. Tapping it disables the parse for this capture: the caption switches to the opted-out state (e.g. `08:30 KEPT IN TITLE — TAP TO SET AS CUE`) and the task saves with the literal typed title and no cue. Editing the field re-evaluates from the parsing state. The affordance meets the `NFR-A11Y-1` ≥ 44 dp target and carries a content description naming both the time and the action.
  - This is what keeps "Watch the 9:45 train" honest: the user sees, before pressing save, that `9:45` is about to become a cue, and dismisses it with one tap.
- **`FR-CAPTURE-3.6` EXPAND carries the parse into the editor.** Tapping EXPAND on a parsing title opens the full editor with the **stripped** title and the cue **pre-filled** as `Cue(AT_TIME, "", "<HH:mm>")` — the user sees the same outcome the inline save would have produced, and can adjust it in the cue slot. This requires one new optional nav argument on the editor route (`editor?…&presetCue={presetCue}`, an `HH:mm` string) which `MainActivity` folds into the new-task `TaskDraft` alongside the existing `presetToday` / `presetBacklog` handling (`MainActivity.kt:429-482`). If the parse was opted out per `FR-CAPTURE-3.5`, EXPAND passes the literal title and no `presetCue`.
- **`FR-CAPTURE-3.7` The cue is written through the existing draft seam.** Each quick-add draft builder gains the parsed cue: `TodayViewModel.quickAddDraft(title, today)` and `BacklogViewModel.quickAddDraft(title)` take the parsed title and an optional `time`, and `PlanningViewModel.quickAdd` does the same (see `FR-PLAN-7` for its date rule). No new repository method — `TaskDraft.cue` already exists and `saveDraft` already persists it.
- **`FR-CAPTURE-3.8` Backlog parses the cue but keeps its state contract.** A Backlog quick-add with a trailing time saves `state = BACKLOG`, `toDoDate = null` (`FR-BACKLOG-5.1`, unchanged) **and** the parsed cue. The cue will not remind while the task is in Backlog — `NotifyLogic.remindersFor` skips any task whose state is not `OPEN` — but the time the user typed is preserved, so pulling the task out of Backlog later restores a task that already knows when it wants to happen. See **[DECISION]**.
- **`FR-CAPTURE-3.9` Today keeps its date default and gains the cue.** Today's quick-add already sets `toDoDate = today` (`FR-TODAY-7`); adding the cue makes the reminder fire the same day with no further user action. No change to `FR-TODAY-7`'s date rule.
- **`FR-CAPTURE-3.10` The parse never fabricates a label.** The saved cue's `label` is the empty string — not the time, not the stripped title. `Cue.display()` (`FR-CUE-3`) then renders the row chip as `08:30`, and `NotifyLogic.cueLine` composes the same string for the notification body. A user who wants descriptive prose on the cue adds it in the cue sheet.
- **`FR-CAPTURE-3.11` The parse is on the logical string, and RTL titles work.** Matching runs against the code-point sequence, which is the order the user typed; `.contentDir()` affects rendering only (`FR-DESIGN-3`). A Hebrew title typed as `לצלצל לבנק 08:30` parses to title `לצלצל לבנק` + time `08:30`, even though the time renders at the visual left. Bidirectional control characters are not stripped; if the trimmed string does not end in the token the parse simply does not fire (`FR-CAPTURE-3.3`).
- **`FR-CAPTURE-3.12` Recurrence, alignment and description are untouched.** Quick-add still creates a single non-recurring, unaligned task (`FR-CAPTURE-1`); the only field the parse adds is `cue`.
- **`FR-CAPTURE-3.13` No `DM-NOT` surface.** A cue parsed off a title is descriptive scheduling, not evaluation (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Require the zero-padded `HH:MM`; do not accept `8:30`, `8.30`, `830`, `8pm` or `at 8:30`.**
> The request names "text in the form HH:MM", and the app already has exactly one definition of a valid time string — `HH_MM_REGEX` (`FR-CUE-1.4`) — used by the cue save-gate. Reusing it verbatim means a token the user can type into quick-add is a token the cue sheet would accept, with no second grammar to learn or maintain. Accepting looser shapes (`8:30`, `8.30`, `20h`) raises the false-positive rate on ordinary titles ("Pay invoice 8.30" is a sum of money, "Read pages 8-30" is a range) and the cost of each false positive is a mangled title. If a looser grammar is wanted later, it is one change inside `QuickAddParse` and every call site inherits it.

> **[DECISION] — The parse is visible and reversible, not silent.**
> An alternative was to parse silently and let the user fix a bad guess afterwards in the editor. Rejected on `FR-DESIGN-1` (calm voice) grounds: an input that quietly rewrites what the user typed is the opposite of calm, and the failure mode ("Watch the 9:45 train" → a task called "Watch the") is annoying enough to sour the feature. The inline preview (`FR-CAPTURE-3.5`) makes the parse legible before commit and its one-tap opt-out makes it free to decline. This is a caption and a tap target, not a confirmation dialog — the friction floor (`FR-CAPTURE-1`) is preserved for everyone who ignores it.

> **[DECISION] — Backlog stores the parsed cue rather than suppressing the parse.**
> Two options on the Backlog surface: suppress parsing entirely (Backlog is undated and its cue cannot fire), or parse and store. Chose store, because the alternative means the same keystrokes do different things on different surfaces for a reason the user cannot see, and because a stored cue is lossless — when the task is pulled out of Backlog into a date, the cue is already there. The Backlog *state* and *undated* contract (`FR-BACKLOG-5.1`) is untouched: no date is inferred there, and `FR-PLAN-7` is explicitly Planning-only.

**Acceptance criteria**

1. On Today, open quick-add and type `Call the bank 08:30`. The preview caption reads `CUE · 08:30 — TAP TO KEEP AS TEXT`. Press ↵ SAVE. The new task's title is `Call the bank`, its `toDoDate` is today (`FR-TODAY-7`), and its row chip reads `08:30` (`Cue.display()`, `FR-CUE-3.2`). Open it in the editor: the cue slot's primary line reads `08:30` and its type is `AT_TIME`. (`FR-CAPTURE-3.2`, `FR-CAPTURE-3.7`, `FR-CAPTURE-3.9`, `FR-CAPTURE-3.10`)
2. Same task: a reminder is scheduled for today at 08:30 (`FR-NOTIF-1`, `FR-NOTIF-4`); its notification body reads `08:30`, matching the row chip exactly (`FR-CUE-3`, acceptance 9).
3. Type `Call the bank` (no token) and save: title is `Call the bank`, `cue` is null, and every other default is exactly as today (`FR-CAPTURE-3.3`). No preview caption appears.
4. Type `Call the bank 8:30` (not zero-padded): no preview caption, no parse; the saved title is the literal `Call the bank 8:30` (`FR-CAPTURE-3.2`, DECISION on the grammar).

**Out of scope for v2.12.0**

- **Natural-language dates in the title** (`tomorrow`, `mon`, `next week`, `3/9`). The request is about a *time*; date parsing is a far larger grammar with far worse failure modes, and the date pickers already exist one tap away.
- **Parsing a cue *label* out of the title** (`Call the bank after coffee`). Only the mechanical `HH:MM` shape is specified.
- **Parsing in the full editor's title field.** The editor has a dedicated cue slot two rows below the title (`FR-EDITOR-1`); a parse there would fight an explicit control.
- **Parsing in the habit editor's name field.** Habits set their cue in their own cue row (`FR-CUE-2.6`).
- **A duration or range (`08:30-09:00`).** Tzafon has no duration field (`DM-TASK-*`); the trailing token is a point in time.
- **12-hour input (`8:30pm`) or locale-aware time entry.** `Cue.time` is stored `HH:mm` (`FR-CUE-1.4`); display localisation remains out of scope as it was in v2.11.0.
- **Applying the parse to the Directions theme quick-add** (`DirectionsViewModel.quickAddTask`) — it has no quick-add sheet wired to it today; if one lands, it inherits `QuickAddParse` for free.

### 3.3 A Planning quick-add carrying a parsed time is dated today (`FR-PLAN-7`, refines `FR-CAPTURE-2` on the Planning surface only)

*Source: `FR-2026-07-31-b` (second sentence). Scope: `PlanningViewModel.quickAdd` and the Planning expand path in `MainActivity.kt:336`. This is the single exception to `FR-CAPTURE-2`'s undated default on Planning, and it fires only when `FR-CAPTURE-3`'s parse produced a time.*

`FR-CAPTURE-2` defaults every new task to undated, and `FR-TODAY-7` (v2.1.0) carved out exactly one exception — Today's quick-add — with a note that "Planning's own quick-add (once/if added) would similarly infer no date, matching Planning's Inbox emphasis". Planning's quick-add did land, and it does exactly that: `PlanningViewModel.quickAdd` writes `TaskDraft(id = null, title = title)`, undated, into the Inbox.

The user's second sentence asks for a narrow exception on top of that, and the reminder pipeline explains why it is the right one: `NotifyLogic.remindersFor` schedules a task reminder only when `t.toDoDate == date || t.dueDate == date` (`domain/notify/NotifyLogic.kt:58-70`). A Planning quick-add of `Call the bank 08:30` under today's rules produces an undated Inbox task carrying an `08:30` cue that can never fire — the user typed a time and got silence. Typing a clock time *is* the expression of intent that `FR-TODAY-7`'s DECISION says a bare Planning capture lacks.

`FR-PLAN-7` **when a quick-add invoked from the Planning view produces a parsed time (`FR-CAPTURE-3`), the new task is written with `toDoDate = today` in addition to the cue. A Planning quick-add with no parsed time remains undated and lands in the Inbox, exactly as today.**

- **`FR-PLAN-7.1` The date rule is conditional on the parse, not on the view alone.** `PlanningViewModel.quickAdd` sets `toDoDate = today` **only** when `QuickAddParse` returned a non-null time. `Parsed.time == null` → `toDoDate = null` → Inbox, unchanged (`FR-CAPTURE-2`, and the v2.1.0 DECISION stands for the bare case).
- **`FR-PLAN-7.2` Today is the app's `Dates.todayIso()`.** The same `today` the view model already holds (`PlanningViewModel.today`), so a task captured at 23:58 with an `08:30` cue is dated *that* day — and its cue time, being already past, simply schedules nothing further that day (`NotifyLogic.remindersFor`'s `afterMinutes` guard drops times already past). See **[DECISION]**.
- **`FR-PLAN-7.3` The task appears immediately in the right places.** With `toDoDate = today` it joins Today's list (`FR-TODAY-1`) and Planning's own `today` dated group rather than the Inbox — visible on the same screen the user just typed into, one group down.
- **`FR-PLAN-7.4` The expand path from Planning follows the same rule.** `MainActivity.kt:336` currently opens the editor from Planning with `openEditor(title = title)` — no date preset. When the typed title parsed, the expand call becomes `openEditor(title = <stripped>, presetToday = true, presetCue = <HH:mm>)`, so the editor opens pre-set to today with the cue filled and the user can clear either before saving. When it did not parse (or the user opted out), the expand call is unchanged.
- **`FR-PLAN-7.5` The exception is Planning-only.** Today already dates to today (`FR-TODAY-7`); Backlog stays undated and in Backlog state (`FR-CAPTURE-3.8`, `FR-BACKLOG-5.1`); All Tasks' add opens the editor directly (`MainActivity.kt:381`) and is unaffected. No other surface infers a date from a time.
- **`FR-PLAN-7.6` No existing task is ever re-dated.** `DM-TASK-8` (no automatic date changes on existing tasks) is untouched — this rule applies only to the initial write of a *new* task from the Planning quick-add.
- **`FR-PLAN-7.7` The task is `OPEN`.** No state change: Planning quick-adds are `TaskState.OPEN` as today.
- **`FR-PLAN-7.8` No `DM-NOT` surface.** A date default surfaces no score / streak / adherence (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — "Today", not "the next occurrence of that time".**
> A time typed late in the evening (`23:58` capture, `08:30` cue) could arguably mean tomorrow morning. Rejected: the user's request says "will also set the To Do Date to today", and a rule that sometimes means today and sometimes tomorrow is a rule the user has to model in their head at the friction floor. Today is predictable, matches the literal request, and is one tap to change in the editor. The already-past cue simply doesn't ring — `NotifyLogic` drops it — and the task is still sitting in Today where the user put it.

> **[DECISION] — The date follows the *parse*, not the view.**
> The narrow alternative reading is "Planning quick-adds should just date to today, full stop" — but that would overturn the v2.1.0 DECISION that deliberately keeps Planning's capture feeding the Inbox, which is the whole point of Planning's "needs a date" group. Keeping the exception conditional on a typed time preserves the Inbox for bare captures and gives the time-carrying capture the date it needs to function.

**Acceptance criteria**

1. On Planning, quick-add `Call the bank 08:30`. The new task is titled `Call the bank`, is dated today, carries the `08:30` cue, and appears in Planning's **today** group — not in the Inbox (`FR-PLAN-7.1`, `FR-PLAN-7.3`).
2. The same task appears on the Today view immediately (`FR-TODAY-1`), and a reminder is scheduled for 08:30 today if that time has not already passed (`FR-NOTIF-1`).
3. On Planning, quick-add `Call the bank` (no time). The task is **undated** and lands in the Inbox — "needs a date" — exactly as before v2.12.0 (`FR-PLAN-7.1`, `FR-CAPTURE-2`).
4. On Planning, type `Call the bank 08:30`, tap the preview caption to opt out (`FR-CAPTURE-3.5`), then save: the title is literal and the task is **undated** in the Inbox — the opt-out cancels both the cue and the date (`FR-PLAN-7.1`).
5. On Planning, type `Call the bank 08:30` and tap **EXPAND**: the editor opens with the title `Call the bank`, `To Do Date` pre-set to today, and the cue slot showing `08:30`. Clearing the date there and saving produces an undated task with the cue intact (`FR-PLAN-7.4`, `DM-TASK-8`).
6. On Backlog, quick-add `Order boots 19:00`: the task is `BACKLOG` and **undated** — `FR-PLAN-7` does not apply (`FR-PLAN-7.5`).
7. On Today, quick-add `Call the bank 08:30`: dated today (already `FR-TODAY-7`), cue `08:30`. No double-application, no behaviour change beyond the cue (`FR-CAPTURE-3.9`).
8. Editing an existing undated task's title to end in `08:30` in the full editor does **not** date it or create a cue — the parse is a quick-add rule only (`FR-PLAN-7.6`, `FR-CAPTURE-3` out-of-scope list).
9. Unit tests pin the draft-level outcomes for all three surfaces with and without a parsed time (`NFR-TEST-1`), in the shape `CaptureDefaultsTest` already uses.
10. `DM-NOT` audit clean (`FR-PLAN-7.8`).

**Out of scope for v2.12.0**

- **Dating a bare Planning quick-add to today.** See DECISION — the Inbox default stands for titles with no time.
- **Rolling the date to tomorrow when the typed time has already passed.** See DECISION.
- **Setting `dueDate` from a parsed time.** The cue is a trigger, not a deadline (`DM-TASK-*`).
- **Applying the same conditional-date rule to Backlog or All Tasks.** Explicitly Planning-only (`FR-PLAN-7.5`).
