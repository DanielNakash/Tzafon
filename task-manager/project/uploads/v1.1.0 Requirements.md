## Overview

Version 1.1.0 extends the task data model with three new properties — Description, To Do Date, and Due Date — adds full recurrence support for both dates, and introduces the All Tasks View as the primary interface for browsing tasks.

---

## 1. Task: Description

**What it is:** An optional free-form text field that supplements the task title with additional detail.

**Requirements:**
- Description is optional. A task without a description is fully valid.
- The user may add, edit, or remove a description at any time.
- When a task is displayed in detail, the description is shown below the title.
- Description is not shown in list/row views where only the title is displayed.

**[DECISION]** No character length limit is defined for this version.

---

## 2. Task: To Do Date

**What it is:** The date on which a task is intended to be worked on. It is the primary sorting and filtering key for date-based views.

**Requirements:**
- A task may have a To Do Date, or may have none. Having no To Do Date is valid; the task is treated as undated.
- The To Do Date is set and changed only by the user. The system never modifies it automatically.
- The To Do Date is used as the sort key in the All Tasks View (§4).

---

## 3. Task: Due Date

**What it is:** The date by which a task must be completed. Unlike the To Do Date, it is not a scheduling date — it is a deadline.

**Requirements:**
- Due Date is optional. It is empty by default.
- The user may set, change, or clear the Due Date at any time. The system never modifies it automatically.

### Due Date Indicators

The app shall display indicators related to the Due Date as follows:

| Scenario | Indicator |
|---|---|
| To Do Date = Due Date | A persistent indicator is shown on the task whenever it is displayed, communicating that its scheduled date is also its deadline. |
| To Do Date ≠ Due Date, and today = Due Date | On the due date, a note is shown on the task (in any view where it appears) indicating it is due today. |
| Due Date is empty | No indicator is shown. |

### Due Date on Recurring Tasks

For a recurring task, the Due Date operates in one of two modes, chosen at setup time:

**Mode 1 — Singular Due Date**
A single fixed deadline for the entire recurring series. This date also serves as the recurrence end date — no new occurrences are generated after it. The standalone "recurrence end date" setting (§5) is unavailable when a Singular Due Date is set, since both represent the same concept.

Use case: a task that recurs toward a single time-bounded goal (e.g., weekly preparation tasks leading up to a project deadline).

**Mode 2 — Recurring Due Date**
The Due Date recurs on its own independent recurrence rule. All pattern options available for the To Do Date (§5) are also available for the Due Date, configured entirely independently. Each occurrence carries its own To Do Date and its own Due Date, derived from their respective rules. The two are not required to align or maintain any fixed offset.

Use case: a task with a recurring deadline (e.g., "make a weekly post" — To Do Date recurs every Monday, Due Date recurs every Friday of the same week).

**[DECISION]** When Mode 2 is active, the To Do Date and Due Date recurrence rules may each independently define their own end date.

## 4. All Tasks View

**What it is:** The primary view for browsing all tasks. Intended as the default landing view of the app.

**Requirements:**
- All tasks are displayed in this view.
- Tasks are sorted by To Do Date, oldest to newest.
- Tasks with no To Do Date are shown as a separate group at the bottom of the list, after all dated tasks.
- Done tasks are hidden by default.
- A toggle allows the user to show or hide Done tasks.

**[DECISION]** The full structure specification defines that Done, Closed, and Frozen tasks are all hidden by default. Since Closed and Frozen states are not introduced in this version, the toggle currently controls Done task visibility only. When those states are added in a future version, they will fall under the same hidden-by-default rule and the toggle will cover them automatically.

**[OUT OF SCOPE for this version]** Filters and custom sort options.

---

## 5. Recurrence

**What it is:** The ability to configure a task to repeat automatically according to a rule, generating independent occurrences on a schedule.

### 5.1 Supported Patterns

Three recurrence patterns are supported:

1. **Interval-based:** Repeat every X days, weeks, or months.
   - *Examples:* every 3 days; every 2 months.

2. **Weekday-based:** Repeat on specific days of the week, every X weeks.
   - *Examples:* every Monday and Thursday, every week; every Tuesday, every 2 weeks.

3. **Day-of-month-based:** Repeat on a specific date or weekday position within the month, every X months.
   - *Examples:* the first Sunday of every month; the 25th of every 2 months.

### 5.2 Per-Occurrence Operations

The following operations shall be available on individual occurrences of a recurring task:

| Operation | Behaviour |
|---|---|
| **Reschedule one** | Change the To Do Date of a single occurrence. No other instances are affected. |
| **Edit forward** | Change the recurrence rule from a chosen occurrence onward. Modifies the existing series in-place — the series is not split. |
| **Delete one** | Delete a single occurrence. No other instances are affected. |
| **Delete all** | Delete all occurrences of the task at once. |
| **End date** | Define a date after which no new occurrences are generated. Not available when a Singular Due Date is set (§3) — in that mode, the Due Date already serves as the end date. |

### 5.3 Series Behaviour

- The next occurrence date is always calculated from the recurrence rule, independently of prior occurrences. An unfinished or closed prior occurrence does **not** delay or block the next one.
- If a recurring task is set to **Frozen**, the user shall be shown a confirmation prompt. Upon confirmation, the recurrence series is terminated — no new occurrences will be generated. The frozen task instance itself is retained.
- When a Frozen recurring task is **thawed** to Open or Done, the recurrence is restored and the next occurrence is generated in Open state per the rule. See *Task & Habit Structure Requirements.md* §3 for the full thaw behaviour spec.

## Out of Scope for v1.1.0

The following items are deferred to future versions. Where already specified, *Task & Habit Structure Requirements.md* is the reference for their eventual implementation:

- Task states beyond Open and Done (Closed, Frozen — including thaw behaviour)
- Linked Habit property
- Today View, Triage View, and Habits View
- Search, filters, and custom sort options
