## 1. Scope of v2.9.0

v2.9.0 is a **focused bug-fix / consistency increment** on top of a shipped v2.8.0. Three source requests are groomed here — a Today-view arithmetic inconsistency, two Cue-editor input bugs, and an RTL alignment miss on Goal steps. None introduces a schema change, a new user surface, or a new preference; each closes a small gap between what the spec already says and what the app currently shows.

- **`FR-2026-07-19-a` → `FR-TODAY-8`.** In v2.6.0 (`FR-PLAN-5`) Planning's overdue list learned to **hide** a slipped recurring occurrence once the same series has an occurrence dated today — the older one is stale noise, the current cycle already sits on the desk. That refinement was deliberately scoped to Planning only; `FR-PLAN-5.8` explicitly left the Today slippage banner (`FR-TODAY-4`) using its pre-existing count. The reporter has now noticed the resulting split-brain: "N tasks slipped past — review in Planning" reports (say) 3, the user taps through, and Planning shows 1, because 2 of the 3 are recurring occurrences whose next instance is today and have therefore been filtered out. The count that sends the user to Planning must match what Planning will actually render. `FR-TODAY-8` re-uses the exact `FR-PLAN-5` predicate in the Today slippage count so the two surfaces agree by construction.
- **`FR-2026-07-19-b` → `FR-CUE-1`.** The shared `CueSheet` (`ui/components/CaptureSheets.kt`) — used by both the Task editor (`DM-TASK-4`) and the Habit editor (`DM-HABIT-1`) — has two input-side bugs on the `AT_TIME` variant: (a) the HH:mm text field is configured with `KeyboardType.Number`, so the numeric IME on most Android devices does not offer the colon, leaving the user unsure how (or whether) to enter a proper `HH:mm` value; and (b) the sheet's primary "Set the cue" button gates on `label.isNotBlank()` only, so on `AT_TIME` the user can save with an empty or malformed time — the cue that is *supposed* to fire a reminder gets saved without the one field that a time-driven reminder needs (`DM-CUE-3`, `FR-NOTIF-1`). `FR-CUE-1` fixes both: the time input accepts a colon (correct IME + accepted characters), and on `AT_TIME` the save button requires a valid `HH:mm` in addition to a non-blank label.
- **`FR-2026-07-19-c` → `FR-DESIGN-3.6`.** `FR-DESIGN-3` (v2.1.0) established the rule: user-authored text renders in the direction of its first strong character (`textDirection = TextDirection.Content`). `FR-DESIGN-3.5` (v2.6.0) applied that rule to the Backlog row's title, which was still hard-LTR. The Goal card's step rows (`ui/goals/GoalCard.kt:151-176`) already pass `.contentDir()` on the step-label `Text`, so the *glyphs* render right-to-left when the label is Hebrew — but the row's checkbox+text layout stays LTR (checkbox on the left, label rightward), so a Hebrew step reads with its checkbox on the wrong side and its glyphs pushed away from the natural reading margin. `FR-DESIGN-3.6` extends the content-direction rule to the *row* — when the step's label is RTL, the row is laid out RTL so the checkbox sits on the trailing (right-hand) side, matching the direction the reader's eye enters the line. The same fix applies to the corresponding editor row in `GoalEditorSheet` for symmetry.

None of the three is gamification-adjacent: one is a filter-alignment fix on an existing count, one is a two-line input-field fix on a shared editor, and one is a per-row layout-direction fix. `DM-NOT` and `DEC-2/3/4` continue to hold across all three. All other locked decisions from v2.0.0 — the five-tab primary structure (`FR-NAV-1`), the compass / chosen-direction thesis, local-first-with-clean-seam persistence, the Fox Works "Den" identity, and the state-machine / recurrence model — are untouched.

## 3. Functional requirements

### 3.1 Today's slippage count adopts Planning's same-series hide rule (`FR-TODAY-8`, refines `FR-TODAY-4`; reuses the `FR-PLAN-5` predicate)

*Source: `FR-2026-07-19-a`. Refines `FR-TODAY-4` (the calm, closeable slippage banner on Today). Reuses `FR-PLAN-5`'s series-aware filter verbatim; the `FR-PLAN-5.8` note that "this requirement does not alter the Today nudge" is superseded by this refinement. Holds `FR-TODAY-5` (overload warning, unrelated), `FR-TODAY-2/3/6`, and all Planning rendering rules.*

`FR-TODAY-4` renders a closeable banner on Today when `ActionLogic.slippedCount(tasks, today) > 0`, worded "N tasks slipped past — tidy them up in Planning." `slippedCount` today (`ActionLogic.kt:41-42`) is:

```kotlin
fun slippedCount(tasks: List<Task>, today: String): Int =
    tasks.count { it.state == TaskState.OPEN && (it.toDoDate ?: today) < today }
```

`ActionLogic.planningGroups(...)` — the function that renders the overdue bucket the banner points at — additionally strips slipped recurring occurrences whose series has a today-dated occurrence (`FR-PLAN-5`, computed via `seriesDueToday`). The banner's count therefore over-reports: a recurring "clean desk" that slipped on Sunday counts here even though Planning will hide it on Tuesday when Tuesday's instance exists. Tapping the banner ("review in Planning") lands on a Planning list smaller than the count promised — the calm nudge becomes a small credibility bug.

`FR-TODAY-8` **the Today slippage count is computed with the same predicate `ActionLogic.planningGroups` uses to populate its overdue bucket, so a slipped recurring occurrence hidden from Planning is also excluded from the banner's count.** The banner otherwise behaves unchanged: it still shows only when the resulting count is `> 0`, still respects the daily dismissal (`slipDismissed`), and still links to Planning.

- **`FR-TODAY-8.1` The rule is the `FR-PLAN-5` predicate, verbatim.** For every task with `state == OPEN` and `(toDoDate ?: today) < today`, exclude those whose `seriesId != null` **and** whose series has any task with `toDoDate == today` (regardless of that today-dated task's state — Open, Done, or Skipped — matching `FR-PLAN-5.3`). One-off overdue tasks (`seriesId == null`) are unaffected and continue to count (`FR-PLAN-5.6`).
- **`FR-TODAY-8.2` The computation is co-located with the existing count.** The simplest realization is to extend `ActionLogic.slippedCount(tasks, today)` in place: build the same `seriesDueToday` set `planningGroups` builds (`tasks.filter { it.seriesId != null && it.toDoDate == today }.map { it.seriesId }.toSet()`), then filter the counted set with the same `filterNot` clause. A shared private helper on `ActionLogic` (e.g. `slippedOverdue(tasks, today): List<Task>`) called by both `slippedCount` and `planningGroups` is acceptable and preferred if it does not force a second pass over the list.
- **`FR-TODAY-8.3` The two surfaces agree by construction.** After this refinement, "N tasks slipped past — tidy them up in Planning" and the Planning overdue-section's own count (`state.overdue.size`, `FR-PLAN-5.7`) evaluate to the same integer on the same task set. This equality is a property the code enforces because the two use the same predicate — not a coincidence to be verified per-render.
- **`FR-TODAY-8.4` The banner's visibility rule tracks the corrected count.** When the corrected count is zero (every slipped task is hidden by the rule and no one-off overdue exists), the banner is not rendered — matching Planning's own "no overdue section when overdue is empty" behaviour (`FR-PLAN-5.7`). When the corrected count is `> 0`, the banner appears unless the user dismissed it today (`slipDismissed == today`), unchanged from v2.0.0.
- **`FR-TODAY-8.5` The banner's copy pluralization uses the corrected count.** The existing `if (count == 1) "task" else "tasks"` conditional (`ui/today/TodayScreen.kt:163`) uses whatever integer `state.slippedCount` now holds. No new copy strings.
- **`FR-TODAY-8.6` Overload and slippage remain independent.** `FR-TODAY-5`'s overload warning fires on `openTodayCount` (open tasks with `toDoDate == today`) and is unchanged. The two nudges never nag simultaneously (v2.0.0 rule) — this refinement does not change that.
- **`FR-TODAY-8.7` No `DM-NOT` surface.** The banner remains a plain count with a link to Planning; no score, streak, badge, or adherence framing appears (`DM-NOT`, `DEC-2/3/4`).

> **[DECISION] — Fix at `ActionLogic`, not at the repository or the ViewModel.**
> The `slippedCount`/`planningGroups` pair are already the domain-side owners of the "what belongs in Planning's overdue?" question; keeping both branches in `ActionLogic` makes the equality of `FR-TODAY-8.3` a local, testable property of one file. Lifting the exclusion into `TaskRepository` was rejected in `FR-PLAN-5` for the same reason it is rejected here: the hidden task is still Open and still legitimately shown in All Tasks and the editor. Extracting a `slippedOverdue(tasks, today)` helper (`FR-TODAY-8.2`) is the cleanest expression; a duplicated inline filter is acceptable if the helper does not fit naturally.

**Acceptance criteria**

1. Seed a recurring task "clean desk" (daily); generate occurrences through today. Leave two prior occurrences Open (Sunday, Monday); today's exists as Open. On Today: the slippage banner is **not shown** (both prior instances are hidden by `FR-PLAN-5` / `FR-TODAY-8`), so the corrected count is 0 (`FR-TODAY-8.4`).
2. Same seed, and add one Open one-off task with `toDoDate = yesterday`. On Today: the banner reads **"1 task slipped past — tidy them up in Planning"** (singular). Tapping it lands on Planning; the overdue section shows exactly one card. The banner count equals Planning's overdue count (`FR-TODAY-8.3/8.5`).
3. Same seed, and replace the one-off with three one-off tasks dated 3 / 5 / 7 days ago. On Today: banner reads **"3 tasks slipped past — tidy them up in Planning"** (plural). Planning's overdue shows exactly three cards.
4. Turn off the "hide today's instance exists" condition by removing today's "clean desk" occurrence. On Today: the two prior Sunday/Monday instances now count — banner reads **"2 tasks slipped past …"** and Planning shows both (`FR-PLAN-5.3` — no today-dated instance, exclusion does not apply).
5. Dismiss the banner (existing behaviour): re-open Today the same day → banner stays hidden (`slipDismissed`); advance the system date one day → banner returns with the freshly-computed corrected count (unchanged from v2.0.0).
6. Unit test on `ActionLogic`: for a fixture with both series-hidden and one-off overdue tasks, `slippedCount(...) == planningGroups(...).overdue.size` (`FR-TODAY-8.3`, direct property test).
7. TalkBack announces the banner unchanged; RTL layout unchanged (`NFR-A11Y-1`, `FR-DESIGN-3`).
8. `DM-NOT` audit clean — no streak/adherence/badge surface (`FR-TODAY-8.7`).

**Out of scope for v2.9.0**

- **Changing the banner's copy or its dismissal semantics.** `FR-TODAY-4`'s "closeable, links to Planning, one dismissal per day" behaviour is preserved.
- **Extending the same-series hide rule to any other surface** (All Tasks, the editor). `FR-PLAN-5.1` and this refinement keep the hide scoped to Planning + the Today banner that points at it. All Tasks continues to show every Open task.
- **Auto-transitioning hidden slipped occurrences** (auto-Skip / auto-Close). Explicitly rejected in `FR-PLAN-5` and re-rejected here — state changes remain user-authored.

### 3.2 CueSheet AT_TIME field bugs — colon input and save gating (`FR-CUE-1`, new `FR-CUE-*` area; refines `DM-CUE-2`)

*Source: `FR-2026-07-19-b`. New functional area covering the shared `CueSheet` editor used by both the Task editor (`DM-TASK-4`) and the Habit editor (`DM-HABIT-1`). Refines the AT_TIME variant of `DM-CUE-2` (Cue shape: `trigger` + label; the time slot exists to drive `DM-CUE-3`/`FR-NOTIF-1` reminders). The bug scope is exactly the `CueSheet` shown when the user is editing a cue whose trigger is `AT_TIME`.*

`CueSheet` (`android/app/src/main/kotlin/com/thefoxworks/tzafon/ui/components/CaptureSheets.kt`, roughly `lines 47-167`) exposes three trigger chips — `AFTER_ROUTINE`, `AT_TIME`, `AT_PLACE` — and always shows a single-line label field. When the trigger is `AT_TIME` a second row appears with an HH:mm text field (`lines 110-149`) and a "REMINDS AT THIS TIME" annotation. Two bugs sit in this row today:

1. **The time field's IME hides the colon.** The `BasicTextField` at `line 129` sets `KeyboardType.Number`. On most Android IMEs (Gboard, SwiftKey) the numeric keypad this keyboard type requests does not surface a `:` key, so the user cannot type a valid `HH:mm` — the field silently rejects the only separator the format needs. `onValueChange` accepts any characters the IME sends (`if (it.length <= 5) time = it`), so the *field* is not the gate; the *IME* is.
2. **Save doesn't require a time.** The "Set the cue" button (`line 152-159`) is enabled on `label.isNotBlank()` alone, so on `AT_TIME` the user can save a cue with `time` empty or with a malformed string. The saved Cue then has `cueTime == null` (or a non-parseable value), and `FR-NOTIF-1`'s at-time reminder path has nothing to schedule — the cue that was *supposed* to fire at a time silently doesn't.

`FR-CUE-1` **on the AT_TIME variant of the shared CueSheet, the time field accepts a colon by using the standard `Time` keyboard type, and the save button requires a valid `HH:mm` time in addition to a non-blank label.**

- **`FR-CUE-1.1` The time field's `KeyboardType` becomes `KeyboardType.Number` → `KeyboardType.Time`** (`androidx.compose.ui.text.input.KeyboardType.Time`). This IME variant surfaces digit keys **and** the colon, and is the correct semantic type for an HH:mm input. Users who prefer a hardware keyboard remain unaffected — a colon was always physically typeable; the change unblocks the IME users.
- **`FR-CUE-1.2` The `onValueChange` filter accepts digits, colon, and enforces `length ≤ 5`.** The current `it.length <= 5` guard is preserved; a character filter is added so the field cannot accumulate letters or symbols even if the IME misbehaves (accept only `it.all { it.isDigit() || it == ':' }`). This is a belt on top of `FR-CUE-1.1`'s braces — the parser (`FR-CUE-1.4`) is the ultimate arbiter.
- **`FR-CUE-1.3` Placeholder and font remain the mono `"08:30"` placeholder shown today** (`CaptureSheets.kt:132-137`). No new copy; the placeholder already communicates the expected format.
- **`FR-CUE-1.4` A canonical HH:mm parser gates save.** Add a pure `isValidHhMm(String): Boolean` helper (co-located in `CaptureSheets.kt` or a small `domain/action/CueLogic.kt` if a natural home exists) that accepts strings matching `^([01]\d|2[0-3]):[0-5]\d$` — i.e. `00:00` through `23:59`, requiring exactly one colon and zero-padded fields. Empty is invalid. Trailing/leading whitespace is trimmed before parsing (matching the existing `.trim()` in `onSave`).
- **`FR-CUE-1.5` The save button's enabled expression becomes trigger-aware.** `SheetPrimaryButton(enabled = …)` computes to `label.isNotBlank()` for `AFTER_ROUTINE` and `AT_PLACE`, and to `label.isNotBlank() && isValidHhMm(time)` for `AT_TIME`. Switching the trigger chip re-evaluates the expression live (the sheet's `remember` state already recomposes on chip taps).
- **`FR-CUE-1.6` Switching *away from* AT_TIME does not require a valid time.** If the user picks `AT_TIME`, types something in the time field, then switches to `AFTER_ROUTINE`, the save button re-enables on the label alone — the time field is no longer shown so its value is irrelevant. The `time` state is preserved (so switching back reveals what was typed) but does not gate save. This matches the existing `time.trim().takeIf { it.isNotBlank() }` write on `onSave` (`line 157`), which already writes `null` when the field is empty.
- **`FR-CUE-1.7` The saved `Cue.time` is exactly the entered `HH:mm` string.** Storage stays a plain `TEXT?` column on both the `tasks` and `habits` tables (unchanged from v2.0.0 — see `Entities.kt`). No format normalization beyond the parser's zero-padded shape is done at write time; downstream readers (`FR-NOTIF-1`, `NotifyLogic`) continue to consume the raw string.
- **`FR-CUE-1.8` No visible error state is added when the time is invalid.** The disabled save button is the whole affordance — matching the sheet's calm voice (`FR-DESIGN-1`) and avoiding a red-error escalation on what is a routine mistake. The placeholder `08:30` communicates the target format; the button re-enables the moment a valid string is present. **[DECISION]** below.
- **`FR-CUE-1.9` Applies uniformly to both editors.** `CueSheet` is instantiated by `TaskEditorScreen` (`ui/editor/TaskEditorScreen.kt:222`) and `HabitEditorSheet` (`ui/habits/HabitEditorSheet.kt:123`); the fix is on the shared composable, so both editors inherit it in one change.

> **[DECISION] — Disabled save button, no in-field error text.**
> An alternative was to show a subdued red hint under the time row ("Use HH:mm, e.g. 08:30") whenever the parser rejects. Rejected because (a) the placeholder already carries the format shape, (b) the visible disabled state on the primary button already tells the user *something* is missing, and (c) a persistent red hint on a routine mistake tilts the "DON'T PANIC" voice toward scolding. If a stronger cue is wanted later, a one-line supporting text under the row (in `Tz.colors.muted`, not error) is the milder next step.

> **[DECISION] — Use `KeyboardType.Time`, not a `TimePickerDialog`.**
> A `TimePickerDialog` would guarantee validity by construction, but replacing the current inline text row with a modal picker is a UX shift the reporter did not ask for; the reporter's phrasing ("the text box for the time doesn't allow typing a colon") assumes the text field stays. `KeyboardType.Time` is the minimum change that lets the existing field work correctly. A later increment can add a picker chip alongside the text field if useful; this requirement does not preclude it.

**Acceptance criteria**

1. Open the Task editor for a new task, tap "When will you do this?" to open `CueSheet`, tap the **AT A TIME** chip. Focus the time field: the IME shows a **keypad that includes a colon key** (`KeyboardType.Time`, `FR-CUE-1.1`). Type `08:30`: the field accepts all three characters and displays `08:30`.
2. Same sheet, leave time blank and type a label ("morning"). The "Set the cue" button is **disabled** (`FR-CUE-1.5`, `FR-CUE-1.4`). Type an invalid time (`8:3`, `8:30`, `24:00`, `12:60`, `08`): button stays disabled. Enter `08:30`: button enables. Tap it: cue is saved with `time = "08:30"`.
3. Open the same sheet, pick `AT_TIME`, type `08:30`, then switch back to `AFTER_ROUTINE`. The save button enables on the label alone (`FR-CUE-1.6`). Switch back to `AT_TIME`: the previously typed `08:30` is still there and save re-enables.
4. Repeat (1)–(3) starting from `HabitEditorSheet` (open the habit editor's cue row). Behaviour is identical (`FR-CUE-1.9`).
5. Attempt to type a non-digit / non-colon character (`a`, `-`, `.`) via a hardware keyboard: the field silently rejects it (`FR-CUE-1.2`).
6. Save an `AT_TIME` cue with `time = "08:30"` on a Task; open the notify path (`FR-NOTIF-1`): the reminder schedules correctly for 08:30 today/next occurrence (unchanged from v2.0.0 — verifies that the saved shape is what downstream expects, `FR-CUE-1.7`).
7. TalkBack announces the time field as an editable text with the placeholder `08:30`; announces the save button's disabled state (`NFR-A11Y-1`). RTL — the sheet's mirrored layout continues to place the time field / annotation in the expected trailing order (`FR-DESIGN-3`).
8. Unit test: `isValidHhMm("00:00") == true`, `isValidHhMm("23:59") == true`, `isValidHhMm("08:30") == true`, `isValidHhMm("8:30") == false`, `isValidHhMm("24:00") == false`, `isValidHhMm("12:60") == false`, `isValidHhMm("") == false`, `isValidHhMm("0830") == false`, `isValidHhMm(" 08:30 ") == true` (after trim) (`FR-CUE-1.4`).
9. `DM-NOT` audit clean — no score/badge/streak surface added.

**Out of scope for v2.9.0**

- **A native `TimePickerDialog` or wheel picker.** Not requested; explicitly deferred by DECISION.
- **12-hour AM/PM entry.** `FR-CUE-1.4` accepts 24-hour HH:mm only, matching what `NotifyLogic` and the existing placeholder assume. Adding a 12-hour toggle is a separate request.
- **Time-zone selection on the cue.** Cues fire in the device's local time (v2.0.0 `FR-NOTIF-1` model); no timezone field is added.
- **Validation surface on `AFTER_ROUTINE` / `AT_PLACE`.** These triggers have no structured time and continue to gate on `label.isNotBlank()` only (`FR-CUE-1.5`).
- **Storing the time in a normalized `LocalTime` column.** Storage remains `TEXT?` (`Entities.kt`); no migration.

### 3.3 Goal step rows respect content-direction on RTL labels (`FR-DESIGN-3.6`, refines `FR-DESIGN-3`; mirrors the `FR-DESIGN-3.5` pattern)

*Source: `FR-2026-07-19-c`. Refines `FR-DESIGN-3` (v2.1.0 — user-authored text renders in the direction of its first strong character). Mirrors `FR-DESIGN-3.5` from v2.6.0, which applied the same content-direction rule to the Backlog row's title. Two composables in scope: `GoalCard` (the read-view step row) and `GoalEditorSheet` (the editable step row).*

`FR-DESIGN-3` decreed that user-authored strings render in the direction of their first strong character — implemented as the `TextStyle.contentDir()` extension (`ui/theme/Type.kt:19`), which sets `textDirection = TextDirection.Content`. That extension is already applied to the goal-step label `Text` in `GoalCard.kt:172` and `GoalEditorSheet.kt:189`, so the *glyphs* of a Hebrew step render right-to-left — the letters shape correctly. But the *row* containing the checkbox + label is a `Row` composed under the ambient (LTR) `LocalLayoutDirection`, so the checkbox sits on the row's *start* edge (visually left) and the label extends *rightward* from it. For an RTL label this leaves the checkbox on the wrong side of the reader's eye — the natural entry point in RTL is the right edge, and the label's text is pushed toward the LTR margin instead of anchoring to the reading margin.

`FR-DESIGN-3.6` **when the step's label is RTL by the content-direction rule, the step row is laid out RTL** — checkbox on the trailing (right) side, label anchored to the right reading margin, with the whole row's horizontal arrangement mirrored. When the label is LTR (or the label is empty), the row lays out LTR as today.

- **`FR-DESIGN-3.6.1` The direction decision is per-step, driven by the label's first strong character.** Reuse the same first-strong-character detection the `TextDirection.Content` semantics implicitly use: a shared helper (e.g. `String.isRtl(): Boolean` on a small `ui/theme/BiDi.kt`) walks the label until it finds a strong RTL character (`Character.DIRECTIONALITY_RIGHT_TO_LEFT`, `…_RIGHT_TO_LEFT_ARABIC`, `…_RIGHT_TO_LEFT_EMBEDDING`, `…_RIGHT_TO_LEFT_OVERRIDE`, `…_RIGHT_TO_LEFT_ISOLATE`) or a strong LTR one; the first strong character decides. Empty labels resolve LTR (they fall back to the ambient direction, which the whole app uses `LTR` for; irrelevant for a checked step and safe for an empty new step in the editor).
- **`FR-DESIGN-3.6.2` The row wraps in a `CompositionLocalProvider(LocalLayoutDirection provides <dir>)`.** When the label is RTL, provide `LayoutDirection.Rtl`; otherwise leave the ambient direction untouched (an explicit LTR override is unnecessary and would break Arabic on an app with an RTL system locale — this app runs LTR by default per `FR-DESIGN-3`, but the guard keeps the fix locale-safe). The wrapped `Row` inherits the direction, so its start/end resolve correctly.
- **`FR-DESIGN-3.6.3` `GoalCard` step rows (`ui/goals/GoalCard.kt`, roughly `lines 152-176`).** The `Row` around checkbox + label wraps in the provider from `FR-DESIGN-3.6.2`. The existing `horizontalArrangement = Arrangement.spacedBy(5.dp)` and `verticalAlignment = Alignment.CenterVertically` stay; the spacing now applies in the mirrored direction. `.pressable { onToggleStep(i) }` on the outer Row is unchanged — a tap anywhere on the row still toggles.
- **`FR-DESIGN-3.6.4` `GoalEditorSheet` step rows (`ui/goals/GoalEditorSheet.kt`, roughly `lines 154-190`).** The editor row (checkbox + editable label + optional remove-button) wraps in the same provider so the label anchors to the reading margin and the remove-button is placed at the leading edge under RTL. The `BasicTextField`'s existing `.contentDir()` on its `textStyle` continues to shape the entered glyphs correctly; the wrapper handles the row-level layout that the text-style extension cannot reach.

- **`FR-DESIGN-3.6.8` No `DM-NOT` surface.** RTL alignment is purely visual; no score, adherence, or badge is introduced or altered.

> **[DECISION] — Wrap the row in a `LocalLayoutDirection` provider; don't chase `LayoutDirection` per child.**
> The alternative — flipping specific child modifiers (`Alignment.End` on the checkbox, `Modifier.weight(1f)` on the label, per-side padding) — is fragile and drifts from the rest of the Compose codebase's convention. `LocalLayoutDirection` is exactly the composition local the framework provides for this case; providing it around the row is one line, keeps the row's declarative shape intact, and applies uniformly to `horizontalArrangement` and every start-/end-resolving modifier below.

> **[DECISION] — Only two composables in scope for v2.9.0.**
> A wider RTL audit (Habits chips, Directions hub rows, Review lists, …) is deferred. The reporter's request is explicit about the *goal's steps*, and the `FR-DESIGN-3.5` precedent set the pattern of targeted, one-composable-at-a-time RTL fixes. Extending to other user-authored rows can be groomed as separate requests when observed. This DECISION also declines a "make every row content-direction-aware globally" refactor.
